### 可行方案（最终采用）
- 脚本 `loop_lsq.py`：关键帧子图 ICP 检测回环（loops.npz 存盘可复用，`REUSE_LOOPS=1` 跳过 6 min ICP）→ **只解位置、不碰旋转**，**增量形式**（未知量 = 对里程计的修正 dx）：
  - 里程计：`dx_{i+1} − dx_i = 0`（w_o=1，保持形状）
  - 回环：`dx_b − dx_a = E_ab`（w_l=100）
  - 极小 Tikhonov 去规范零空间，`dx_0=0` 后处理归一
  - **直接稀疏求解**（`A.T@A` + `scipy.sparse.linalg.spsolve`），不用迭代解 —— 一次成功。

## 架构反思：为什么"事后 RTK 配准 + 事后回环"这条路注定失败（2026-09-12 18:10，boss 提问）
- **结论：不是回退，是架构纠错。**「用 RTK」有两种完全不同的用法：
  - **旧（已做）= 事后配准**：`geo_trajectory.py` L65–82 就是全部——全局最小二乘拟合 **1 个 scale + 1 个 R + 1 个平移（4 自由度）**，`enu_est = scale*(local_xy-loc_mean)@R.T + enu_mean`。**6522 个点被压成 4 个参数**。只决定"整张地图摆在地球哪里"，完全改不了地图形状。
  - **新（提议）= 建图时约束**：每帧 RTK 位置 + 每帧双天线航向 = **约 1.96 万个绝对观测**，进位姿图与 KISS 相对约束联合求解 → 轨迹逐帧弯曲。
  - 比喻：旧 = 建好整栋楼再整体挪一下摆正；新 = 每块砖按图纸砌。
- **失败 5 条（按重要性）**：
  1. **架构性**：KISS-ICP 是**纯里程计、无回环检测**，误差从第一帧单调累积；2544 m 累积 24.7 m 闭合差（0.97%），在植被主导非结构化校园属正常水平。不是参数问题。
  2. **后处理能力 < 误差量级**：4 自由度要吸收 25 m 非刚性形变 → 做不到，只能把误差平均摊开，**这就是 U 型残差（两端 11 m / 中段 1.5 m）的来源**。数学上无出路。
  3. **回环约束少且不独立**：51 条回环基线全在 1760–3870 帧（同一次重访）→ **≈1 条独立观测**，中段零覆盖。
  4. **回环本身不可信**：无一条内点 RMSE < 0.15 m；最优组（fitness 0.97）仍差 1.1 m。
  5. **砍旋转的代价**：只解位置（因面内 yaw 仅 0.23°、那 3° 是可疑俯仰/横滚）→ 修正上限 2.52 m，**比待修误差小一个数量级**。

## 探测③（更正「新发现①」的结论）：去斜的量级是真的，但对地图精度的贡献很小

新脚本 `probe_scan_time.py` / `probe_deskew.py`（本地与远端 `/root/gpufree-data/slam_comp/`）。

时间模型（已实测确认，推翻早前 `decode_bag.py` 注释里的单位猜测）：

- `header.stamp == timebase == 帧基准时刻`（**ns**），`offset_time` 也是 **ns**，每帧跨度 **97.1–100.1 ms**。
- bag 记录时刻 = 基准时刻 **+101.5~103.2 ms**（即记录发生在帧结束）。所以点时刻 = `header.stamp + offset_time`。
- **坑**：Livox CustomMsg 头部在 `rsvd[3]` 之后还有 **4 字节 `data_type`**，`decode_bag.py` 读对了（`off += 1+3; narr=u32; off+=4`），少读这 4 字节会让 x 恒为 0.0、`offset_time` 变成 2^20 的倍数——我第一版探针就踩了这个，所有数字作废。

去斜实测（每帧逐点位移的均值）：

|---|---|---|---|

- **平行于航向的面（侧墙、路面）**：5 帧里 4 帧**去斜前后完全不变**（0.2→0.2 / 0.5→0.5 / 0.3→0.3 / 0.3→0.6 cm）。这类面在沿轨剪切下是**数学不变**的。

  实测 r≤50 满足 99.48%、−4≤z≤2 满足 97.51%、**同时满足 97.24%** → 兜底只占 2.76%，**不是 terrain 虚高的主因**。
  且 `mask len == N`，主路径根本没走兜底分支。terrain 54.74% 是模型自己预测的。
- **调色板**：`SK_COLORS` 数组其实是「**Cityscapes 的色值按 SemanticKITTI 的类别顺序排列**」
  （数组[8]=[128,64,128]=CS road 而 SK 8 也=road，依次类推都自洽）。
  所以配色**语义上自洽、不会标错类**，只是不是 SK 标准配色。

### 附带发现：颜色链路有损（次要，但可白捡）

提交 PCD 反推的类别分布 ≠ 模型原始输出：vegetation 29.9%→38.55%（+8.6pp）、
sidewalk 18.8%→8.22%（**−10.6pp**）、fence 5.7%→1.97%。原因：`semantic_label_ml.py` 用
`voxel_down_sample`（0.15 m）会**对颜色求平均**，之后 `colors_to_labels()` 从混色反推最近调色板项。
→ 修法：下采样时对**标签做多数投票**，不要对颜色求平均。可完全绕开。

## SFPNet 换模型实验：结论是"没救"，但原因不是模型（2026-09-12 晚）

### 一句话结论
**SFPNet-SK 权重实测与 Cylinder3D 打平，换模型治不了 ground 内部细分的病。
真正的原因是这批数据 + SemanticKITTI 标签体系本身只支撑到这一层。**

### 打通的技术链路（全部有实测记录）

1. **ckpt 加载 100% 通过。** 根因是 spconv 的权重布局**取决于 algo 与编译期宏**：
   `spconv/pytorch/conv.py` ~line 128
   ```python
   if self.algo == ConvAlgo.Native and not ALL_WEIGHT_IS_KRSC:
       weight_shape = [*kernel_size, in_channels, out_channels]   # RSCK
   else:
       weight_shape = [out_channels, *kernel_size, in_channels]   # KRSC
   ```
   algo 按核体积 kv 自动选，阈值 32：k=1(kv=1)/k=3(kv=27) 走 MaskImplicitGemm→KRSC；
   k=5(kv=125)/k=7(kv=343) 掉到 Native→RSCK。**SFPNet 的 focal 调制核长恰好是 3/5/7，
   所以一个 checkpoint 里同时存在两种布局**——这就是"同一模块 focal_layers.0 是
   (32,3,3,3,32)、focal_layers.1 却是 (5,5,5,32,32)"的真正原因。
   我们的 wheel `ALL_WEIGHT_IS_KRSC=True`，只需把 RSCK 张量 permute(4,0,1,2,3)。
   脚本：`sfpnet_ckpt.py::load_aligned()`（按模型期望形状自动找轴，通用）。
   结果：OK=388 / layout-repaired=18 / unfixable=0 / strict=True 通过。
   **18 个里还包括 stride=2 的 `unet.conv` 降采样核 (2,2,2,64,32)**。

2. **SK 权重配置**（仓库只发了 S.MID 的 demo config，SK 的是自己推的）：
   `input_c=4, m=32, classes=19, block_reps=2, layers=[32,64,128,256,256],
   focal_* = [[3,1,1,1]]*5, unet_layers=[1,2,3,4,5]`，写进 `sfpnet_sk.yaml`。
   注意 `load_cfg_from_cfg_file()` 只吃 `.yaml`，不认 json。

3. **推理每帧 93 ms（T4）**，端到端无损（输出点数 == 输入点数）。

4. 两个编译型依赖用 shim 顶掉：`torch_scatter`（只要 scatter_mean）、
   `timm.models.layers.DropPath`。

### 对拍结果（152 帧，跨全程 stride 43，两模型跑**同一批帧**）

| 判据 | Cylinder3D | SFPNet-SK |
|---|---|---|
| 车轮下最低 25% 点 → road | 5.37% | 6.88% |
| 全图 road | 5.06% | 5.32% |
| 车轮下 → 任一 ground 类 | 81.8% | **89.1%** |
| road vs sidewalk 高度中位差 | 0.114 vs 0.099 m | -0.003 vs 0.083 m |
| 全图 vegetation | 26.76% | 20.20% |
| 全图 building | 9.01% | 3.65% |

**读法**：两个架构完全不同（柱面划分 vs 稀疏焦点调制）、归纳偏置完全不同，
落在同一个分布上。地面类判断都对（82–89%），但 ground 内部 road/sidewalk/terrain
的三级切分基本是随机的（中位高度差只有 1–8 cm）。**这是"数据只能支撑到这个程度"
的强证据，不是模型的问题。**

### 我自己上一轮的判据立错了（必须记住）
"车轮正下方 road 占比应 >80%"是我上一轮拍脑袋定的。**SemanticKITTI 的 `road`
特指车道**，我们这个场景是园区铺装地，模型把它叫 terrain/sidewalk 未必是错。
正确的判据应该是分两层：① 是不是地面类（是，89%）② ground 内部切分是否与几何一致（否）。

### 顺手修的环境坑

### RViz 踩坑（最费时，写下来别再踩）
1. **PointCloud2 的 Decay Time 没有"替换"语义**。`0` = 永久累积（重复点越堆越多），

2. 修法：**每帧重发整张累积地图**（`PUB_EVERY=1`）+ `Decay Time: 0.35`
   （必须 > 发布间隔 0.24 s，否则大部分时间屏幕空白）。改完从"一点地图都没有"
   变成连续铺开。
3. **`/map`（终态全图）死活渲染不出来**：同一份数据走 `/map_live` 通道正常，
   只有 `/map` 不显示，原因未查明，已放弃调试。已在 README §4 如实写明，
   并说明影响仅限末帧。
4. **rviz.log 干净不代表没事** —— 那次屏幕上什么都没有，日志里一行告警都没有。

`build_cmp.py`：152 帧（scan_idx 35..6514，覆盖全程 **99%**）+ **同一组融合位姿**，

两版跑的是同一批帧，所以任何颜色差异都只是模型本身的观点，没有混杂因素。

### 踩到的坑（重要，别再踩）
`read_pcd_binary` 里 `COUNT 1` 被我写成子数组维度 `('x','<f4',(1,))`，
于是 `np.stack` 出来是 **(N,3,1)** 而不是 (N,3)，
`(3,3) @ (1,3,N)` **静默广播**成垃圾坐标 —— 不报错，只是数字全错。
- 症状：位姿轨迹完全正常（z 只有 6.8 m 跨度），但变换后点云 z 飞到 286 m
- 判据：正确建图必须落在薄 z 层内。交付的 `semantic_map.pcd` 实测 z ∈ [-6.9, +9.8]（**交付物是好的**）
- 修法：`COUNT==1` 时不加子数组维度；并在脚本里加 z 跨度断言（>60 m 直接 abort）

### 无真值几何审计（新方法，可复用）
没有人工标注就算不出 mIoU。改用一个**不可能靠类别倾斜作弊**的判据：
1. 每 1 m 格内 z 的低 5% 分位 = 该处"局部地面"
2. 伪真值：dz<0.5 m ⇒ 表面；dz>2.0 m ⇒ 空中结构
3. 算 surface/elevated 的 recall 与 precision，取 F1 均值

| 指标 | Cylinder3D | SFPNet |
|---|---|---|
| surface recall | 71.5% | **78.9%** |
| surface precision | 84.0% | 83.0% |
| elevated recall | **94.2%** | 88.4% |
| elevated precision | 30.1% | **36.3%** |
| F1 surface | .772 | **.809** |
| F1 elevated | .456 | **.515** |
| **F1 均值（头条）** | **61.4%** | **66.2%** |
| 几何不可能桶（全部点） | 24.4% | **19.3%** |
| 把真·平坦点标成垂直类 | 20.6% | **11.6%** |

**最有力的是分歧点仲裁**：两版做出相反结构判断的点共 98,531 个，
其中 71,420 个可由几何裁决 —— **Cylinder3D 对 16.8%，SFPNet 对 83.2%（差 66.4 pp）。**
