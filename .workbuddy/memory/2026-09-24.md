## 诊断：T4 连不上（SSH 与 Jupyter 同时不通）

### 结论
**不是密码问题，不是本地网络问题，是地址/实例层面的不可达。**
`183.239.162.232:30032` 在当前时刻：**所有端口 TCP TIMEOUT + ICMP 100% 丢包**。

### 证据（逐条排除）
| 检查 | 结果 | 排除了什么 |
|---|---|---|
| 密码比对（sha256[:12]） | 老板给的与 `ssh_env.sh` 里**逐字符相同**（len 16） | **不是凭据问题**。密码错会看到"认证失败"，不会是超时 |
| TCP 探测 30032 / 22 / 8888 / 8000 / 8080 | **全部 TIMEOUT**（WinError 10060） | 一个服务都没有 → 不是"Jupyter 挂了但 SSH 还好" |
| ICMP ping | 100% loss | 主机层面无应答 |
| 本地网络 | `pypi.org:443`、`openloong.obs…:443` 均 OPEN | **不是本机网络问题** |
| 叠加网地址（前次远端日志里的 `SSH_CONNECTION` = `100.70.121.192 → 100.102.176.121:22`） | 22/30032/8888 也全 TIMEOUT；本机**没装 Tailscale** | 绕不开，也走不了这条路 |

### 一个值得记住的区别：TIMEOUT ≠ REFUSED
- **REFUSED**（WinError 10061）= 主机活着，只是那个端口没人监听 → 服务没起。
- **TIMEOUT**（WinError 10060）= 完全没人应答 → 实例停机、或 NAT 映射/地址已换、或被丢包。

历史记录里前几次宕机是 **REFUSED**，这次是 **TIMEOUT**，**故障形态不一样**。
按量 GPU 实例**每次关机开机常常重新分配 SSH 端口**，所以最可能的解释是：
老板手上的地址是旧的（Jupyter 与 SSH 走同一个入口，所以两者一起失效）。

### 新增工具（可复用）
- `vendor/sim_scripts/t4_retarget.sh`：**把控制台那行 ssh 命令粘进来，一条命令改址 + 立刻验证**。
  支持 `"ssh -p 30032 root@1.2.3.4"` 与 `<host> <port>` 两种写法；自动备份 `ssh_env.sh`；
  **保留密码与 `SSH_TIMEOUT`**；打印 TIMEOUT/REFUSED/成功 对应的结论。已实测往返改回后文件逐字节相同。
- `vendor/sim_scripts/t4_jupyter_check.sh`：**在机器上跑**，诊断"SSH 通了但 Jupyter 打不开"的四个真凶——
  进程是否活着、监听在哪个端口、**是否只绑了 `127.0.0.1`（最常见的坑）**、token/URL 在哪；
  只读，不改配置。
- `.workbuddy/tmp/probe_ports.py`：TCP 探测并**把 errno 翻译成人话**（OPEN / REFUSED / TIMEOUT）。

### 自己踩的坑（写脚本时）
`t4_retarget.sh` 第一版把一句给用户看的提示（`(password left unchanged)`）写在了**重定向块内部**，
结果**这句话被写进了 `ssh_env.sh`**，同时 `SSH_TIMEOUT=2400` 被丢掉。
**教训：`{ ... } > file` 里只能放真正要写进文件的行；所有面向用户的 echo 必须在重定向之外。**
已修复，并用"往返后逐字节相同"做了回归验证。配置已从备份恢复、5 个变量齐全。

### 需要老板做的事
去控制台确认：① 实例状态是**运行中**；② **重新复制当前的 ssh 登录命令 / Jupyter 地址**。
拿到新地址后：`bash vendor/sim_scripts/t4_retarget.sh "<粘贴那行>"` 即可一键接管并验证。

## 更正（同日，09:57 复测）：上面"地址是旧的"这个结论**是错的**

老板把控制台那行重新发了一次，**地址和密码与之前逐字符相同**，于是又做了一轮更深的探测。
结论反转：**机器是好的，是我们这条网络到不了它。**

### 决定性证据：第三方节点 + 对照组

```
本机 TCP    30032 / 22 / 8443  全部 TIMEOUT；ICMP 100% 丢包
平台主站    gpufree.cn = 106.13.50.6 : 443 和 80 都 OPEN   -> 排除"整个平台挂了"
本机出网    portquiz.net:30032 OPEN                        -> 排除"校园网封高位端口"
第三方节点  CONTROL 1.1.1.1:30032  -> 0 OK / 6 FAIL
            CONTROL 8.8.8.8:30032  -> 0 OK / 6 FAIL
            TARGET 183.239.162.232:30032 -> 6 OK / 0 FAIL（0.07-0.30 s）
```

**对照组把工具本身验了**：确定没人监听的地址全部失败 ⇒ 探测可信 ⇒ 目标那 6/6 是真连通。
⇒ **容器在跑、sshd 在听**，只是从我们这里（`CERNET 58.194.168.205` → 山东联通 → 山东移动）
一个 SYN-ACK 都回不来。tracert 能走到移动骨干 `183.233.80.94` 就断，像是**回程被黑洞**。

### 另一个关键发现：Jupyter 和 SSH 本来就是同一个入口

`pc1.jupytergateway.gpufree.cn` 解析出来的 **A 记录 = 183.239.162.232**，正是 SSH 那台。
所以"jupyter 一直连不上"和"ssh 连不上"从来不是两个问题 —— **DNS 是新的**
（223.5.5.5 / 119.29.29.29 / 8.8.8.8 / 114.114.114.114 四家一致，TTL 600），
也不是记录过期，**就是同一个不可达**。
