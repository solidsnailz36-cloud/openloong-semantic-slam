**固态蜗牛队** · 复赛作品（完整可复现版本）

## 1. 它现在能做什么

一条在线循环，**一次运行**产出全部交付物：

```
 ingest → deskew → odometry → detect → fuse → traversable → worldmap → 驱动 → render
  (explore | goto)
        │                                    │                      │
    运行视频                            建图 pcd               逐帧性能表
                                   + 类别表 + 目标关联实例      frames.csv / summary.json
```

| 能力 | 状态 | 证据 |
|---|---|---|
| **在线建图** | ✅ | 仿真 108,215 点 / 真实 **253,775 点**，带 label + rgb |
| **三分类通行地图** | ✅ | 可通行 / 障碍 / **未知**，三种颜色，面板与 pcd 同源 |
| **语义标注** | ✅ | 45 个 id：2 个几何类（零训练）+ 23 类室内物体（COCO 投影）|
| **目标关联（实例化）** | ✅ | `ObjectRegistry` 跨帧维持 id；真实侧 20 个实例（person 12 / fire extinguisher 5 / clock 1 / chair 1 / tv 1）|
| **自主探索** | ✅ | frontier + sweep + island，10 个目标段平均效率 94–96% |
| **语义导航（`--goto`）** | ✅ | "先探索直到该类上地图，再交棒 A\* 导航"；测试 5/5 |
| **卡住自救** | ✅ | 三档油门 + 画弧 + backoff；见 §3 |
| **TF 输出** | ✅ | `tf.csv`（人能读）+ `tf/`（标准 ROS 2 bag，`ros2 bag play` 可放）|
| **终审打包** | ✅ | `package_submission.py` 逐条核对，**任一 FAIL 就非零退出** |

**交付包实测**：`md5 408d97bce998f5b571ee975f04c98f78`，37,059,063 B，**0 FAIL / 0 WARN**。

## 2. 怎么运行

### 2.1 环境

```bash
pip install -r requirements.txt
```

| 档 | 内容 | 说明 |
|---|---|---|
| 核心 | `numpy` `opencv-python` `onnxruntime` `PyYAML` | 两源都必须 |
| 里程计 | `kiss-icp` | 全项目只有 `r2slam/odometry.py` 一处构造它 |
| 数据源 A | `rospy` `message_filters` `sensor_msgs` | 随 ROS 1 Noetic 提供，不走 pip |
| 数据源 B | `rosbags` | 纯 python 读 ROS 2 bag，**不需要装 ROS 2** |

⚠️ **交付环境的硬约束**：出厂只有 `numpy + cv2 + onnxruntime`。诊断脚本一律不许
`import scipy`；**运行时不带 PyTorch**（torch 只在**离线**用来产出 `.onnx`，不进管线）。
容器基线是 py3.8.10 / **onnxruntime 1.16.3（只到 opset 19）** ⇒ **导出一律 `--opset 19`**。

### 2.2 一条命令跑完两源（复现交付物的那条链）

```bash
bash vendor/sim_scripts/run_final.sh sim     # 仿真：起 Gazebo → 在线跑 → 编码视频
bash vendor/sim_scripts/run_final.sh real    # 真实：本机 .venv 跑 bag → 编码视频
```

### 2.3 直接跑主程序

```bash
# ---- 仿真：两阶段。阶段一驱动 + 落帧，阶段二用同一批帧复算（检测/渲染/编码）----
# 为什么要分两阶段：Gazebo 软渲染 + RViz 会把 8 核 cgroup 配额吃满，
# 所有墙钟数字被放大数倍（实测同一份代码：阶段一 trav_fit 19.9 ms → 阶段二 104 ms）。
python3 tools/online_pipeline.py --config config/sim_house.yaml --duration 400 \
    --explore --no-detect --no-render --dump /tmp/cap --dump-grids /tmp/grids \
    --out /tmp/out_sim
kill_sim.sh
python3 tools/online_pipeline.py --config config/sim_house.yaml --npz /tmp/cap \
    --panel-h 540 --encode --out /tmp/out_sim

# ---- 真实 ROS 2 bag（路径由环境变量指定，避免同一份配置在不同机器上分叉）----
R2SLAM_BAG_PATH=/path/to/three1 python3 tools/online_pipeline.py \
    --config config/real_r2.yaml --out out/online_real --speed 1.4 --encode

# ---- 决赛行为：先探索，直到目标类别上地图，再交棒导航 ----
python3 tools/online_pipeline.py --config config/sim_house.yaml \
    --explore --goto '沙发' --duration 300 --out /tmp/goto
```

## 3. 算法栈

| 环节 | 算法 | 实现位置 | 训练？ |
|---|---|---|---|
| **去斜** | 匀速模型运动补偿 `p_ref = T_motion(dt) @ p` | `deskew.py` | 无 |
| **里程计** | **KISS-ICP**（体素降采样 + 点到面 ICP） | `odometry.py`（唯一构造处） | 无 |
| **航向** | 上一条**指令**的角速度死推（轮式里程计语义） | `heading.py` | 无 |
| **2D 检测** | ONNX 推理 + **自研 NMS** + 轴序免疫解码 | `detect.py` | 用现成权重，**未微调** |
| **2D 分割（可选）** | YOLO26n-seg @320，只画相机面板 | `seg.py` | 用现成权重 |
| **框 → 3D** | 框内点 **30 分位深度** + 反投影回框的硬判据 | `fusion.py` | 无 |
| **可通行** | 地面 **RANSAC** + 高度带 + **闭运算** + 障碍膨胀 | `traversable.py` | **零训练** |
| **障碍层** | 多帧**投票** + 地面比例否决 + 开运算 | `worldmap.py` | 无 |
| **探索** | frontier 簇 + **sweep**（没靠近过的可达地面）+ A\* 连通分量可达性 | `explore.py` | 无 |
| **导航** | 实例关联 + 指令解析 + **A\*** + 三档油门/画弧 | `nav.py` | 无 |
| **渲染** | 只用 cv2（两个平台都有），跑在 worker 线程 | `viz.py` | 无 |

**"一套代码两个数据源"是这个栈的第一条设计不变量**：

- `r2slam/config.py` 与 `r2slam/sources/` 是全项目**唯一**允许出现 `if sim / if real` 的地方，
  而且分支不写在代码里，写在 `config/*.yaml` 里（相机模型、分辨率、外参、点云字段名、是否去斜、线程数、voxel、量程）。
- 其余模块只认 `Frame`，不认数据源。**任何下游模块里出现 `if sim`，就是设计失败。**

| 差异项 | `sim_house.yaml` | `real_corridor.yaml` |
|---|---|---|
| 中间件 | ROS 1 live | ROS 2 bag（sqlite 重放） |
| LiDAR | VLP-16，5,600 点/帧 @5 Hz | 48×1024，49,152 点/帧 @10 Hz |
| 点云字段 | `x y z intensity ring time` | `x y z intensity confidence offset_time` |
| 去斜 | 不需要（`time` 全 0） | **必须**（`offset_time` 0–0.094 s） |
| 相机 | 320×180 针孔，D 全 0，HFOV 114.6° | 1600×1296 鱼眼等距 `r = A11·θ` |
| 扫描器随车体转？ | **不转**（见下） | 转 |

### ★ 官方仿真器的一个缺陷：LiDAR 不随车体旋转

`vehicleSimulator.cpp` 在移动 LiDAR 模型前**重新赋值四元数、把 yaw 写死为 0**：

```cpp
geoQuat = tf::createQuaternionMsgFromRollPitchYaw(terrainRoll, terrainPitch, 0);
lidarState.pose.orientation = geoQuat;    // ← yaw 没了
```

LiDAR 被搬到车体位置，但**朝向恒为世界对齐**。实测我们的 yaw 全程在 ±1.6° 内，
真值 yaw 扫过 359°，指令累计转过 6656° —— **KISS-ICP 报"没转"是对的**。

两个后果都要处理：① **航向从扫描里不可观测** ⇒ 任何按航向控制的策略永远转不完
（实测 586 s 只到过 15 个 1 m 网格）；`heading.py` 用指令死推，**误差 p50 1.85°**。
② **相机—LiDAR 外参只在 yaw≈0 成立** ⇒ 正确变换是 `p_cam = Rz(-yaw) @ Tcl @ p_lidar`。

⚠️ "反投影回原框"那种自检**抓不到第 2 条**：它是一次往返，同一个错误变换首尾相消
（实测 98.9% 通过，yaw 90–180° 区间 100% 通过）。**自检只能抓"前后不一致"，抓不到"整体错了一个角度"。**

### 探索策略的五条硬规则（都是量出来的）

1. **可达性是"连通"，不是"直线"。** 老版本用直线射线判断 ⇒ **只有门口正对时才可能选中门后的前沿**，
   门在侧面时门后整片区域永远被否掉，机器人在原地转。现在用"机器人所在的可走连通域"，
   直线不通就用 A\* 规划一条再跟随 —— **探索与导航只差"目标从哪来"**。
2. **地面掩码必须先闭运算再谈"塞不塞得下机器人"。** LiDAR 对地面采样稀疏：按 0.22 m 腐蚀
   ⇒ 103.1 m²；先 5×5 闭运算 ⇒ 135.5 m²。**差 32 m² 全是测量假象**。但闭运算不能穿过已知障碍
   （1 格厚的墙会被填掉），正解是 `free = close(free) & ~dilate(obstacle, 3×3)`。
3. **航向差不是停车的理由 —— 该画弧。** "先转到位再走"实测让机器人 **56% 的帧在原地转**
   （`|w| > 0.1` 占 96%，在 2.7×3.6 m 的盒子里走了 25.97 m 却只挪 1.74 m）。
4. **大视场传感器上 frontier 不够用，要问"我去过哪"。** 40 m 世界对齐扫描器一个视点就看完屋子，
   所有前沿都在身边一两米，而机器人**真能走到**的 100.4 m² 里 **94 m² 从没靠近过**。
   ⇒ `sweep` 优先去"从没靠近过的可达地面"（用 `wmap.traj` 标记访问过的位置），frontier 降级为兜底。
5. **每个"什么都没发生"的判据，都要说清它盯的是哪个量。** 这套策略在这上面栽了三次：
   停条件盯"过了多少帧"（可原地转一帧也不产生信息）→ 改成"到过目标却没学到东西"；
   可达性盯"直线"（可机器人不能飞）→ 改成连通分量；停滞判定盯"看到的地面"（可走过新地方不长这个量）
   → 改成"没走过的地面"。

## 4. 借鉴了哪些项目的什么内容

### 4.1 实际使用（按环节）

| 项目 | 我们用了它的**什么** | 用在哪 |
|---|---|---|
| **[KISS-ICP](https://github.com/PRBonn/kiss-icp)** | 配准内核（体素降采样 + 点到面 ICP）与其配置对象 | `r2slam/odometry.py` —— **全项目唯一构造处**，测量工具与管线共用，防参数漂移 |
| **[YOLO-World](https://github.com/AILab-CVC/YOLO-World) / YOLOv8-World v2** | 开放词汇检测器的**权重与 baked-vocabulary 机制**：把 51 条 prompt 编码进权重后导出 ONNX | `vendor/detector/yoloworld_alias_320.onnx`（当前默认）。导出走 ultralytics，**离线一次** |
| **CLIP `ViT-B-32` / MobileCLIP** | 构建 baked vocabulary 时的**文本塔**（把 prompt 编码成 embedding） | 仅**离线**构建模型时用；运行时不需要 |
| **[YOLOE](https://github.com/THU-MIG/yoloe)** | 视觉提示 / 免提示开放词汇的**实验**（`11l-seg` 视觉提示 10/10 命中机器人） | 未上默认 —— 能力通过但**撞预算**（detect 62 → **284 ms**） |
| **[onnxruntime](https://github.com/microsoft/onnxruntime)** | 推理后端；默认模型与分割头都走它 | `detect.py`（与 cv2 双后端）/ `seg.py` |
| **[OpenCV](https://github.com/opencv/opencv)** | 图像解码/letterbox、形态学闭运算与膨胀、栅格渲染、可视化 | 全栈 |
| **[rosbags](https://gitlab.com/ternaris/rosbags)** | 读真实 ROS 2 bag（sqlite）+ **写** TF bag | `sources/bag_ros2.py` / `tf_out.py` |
| **Gazebo Classic + ROS 1 Noetic** | 官方仿真环境与话题 | `sources/sim_ros1.py` |
| **[imageio-ffmpeg](https://github.com/imageio/imageio-ffmpeg)** | 取 ffmpeg 做视频编码 | `package_submission.py` / `online_pipeline.py` |

### 4.3 评估过、但**没用**的（附判死依据）

| 方案 | 结论 | 依据 |
|---|---|---|
| **FastInst-AA** | 不试 | ResNet50 骨干、**不在 ONNX 直通路径上**；我们整帧预算约 200 ms 且要与 odom/map 分 |
| **UniPercepNet-S** | 不试 | COCO mask AP 38.0，**RTX A5000 上 43 ms/帧** —— "一张强 GPU 上的单帧耗时就已经等于我们整个 detect 预算" |
| OVO / OV-MAP / Hydra / ConceptGraphs | 判死 | 依赖 SAM2 + open_clip / CropFormer+detectron2 / GTSAM+voxblox / **LLaVA-7B + GPT-4**，都上不了边缘 |
| LEGO-SLAM / opcseg / Mask3D 等 3D 网络 | 判死 | MinkowskiEngine CUDA 算子**导不出 ONNX** |
| MobileSAM | 登记未落地 | 整链 615M→9.66M、456→12 ms，但 **CPU 上 ~3 s ⇒ 只能关键帧跑**，且无文本、非开放词汇 |
| INT8 静态量化（YOLO-World） | 判死 | CPU 上第一轮零检出；修好后只 **1.35–1.42×**；51 类上 **丢 31% 框** |
| YOLOE **文本**提示 | 判死 | 15 条措辞 + 单类隔离全部**零响应**（`max` ≤ 0.011），阳性对照 `person` 0.816 |
| 点云层判别器（18 维几何特征分"真假障碍"） | 判死 | 在线留一 **AUC 0.638 < 0.65**（事前判死线）；高度 `h_med` AUC **0.495**（抛硬币）|
| 自研纯几何实例聚类 | 推翻 | **63.4% 的簇只落在墙上**，精度 35.9% |
| `score = V/(1+d)` 排序形式 | 自创且**错** | 11 个系统（含 NBV）**没有一个用除法** |

> ★ 一句话：**两个最贵的候选（FastInst-AA / UniPercepNet-S）是靠"先看它自己报的数字"否掉的**，
> 不需要花一天装 MMCV。**先算预算，再谈方案。**

> ⚠️ **三条边界必须一起说**：① 厂商里程计**不是真值**（室内无 GNSS，它是另一套 SLAM 的实现），
> 这是**量级核对**，不能写成"定位误差"。② 1 秒与 5 秒 RPE 差 3.5 倍。③ ATE 的 p50 与 p90 差 1.7 倍
> ⇒ 有少数段被打偏，与"漂移"那条老结论一致。

### 5.3 实时性（在线栈本体，已扣除渲染）

| 环境 | 帧 | odom | detect | trav_fit | map | **在线栈合计** | 预算 |
|---|---|---|---|---|---|---|---|
| 仿真 5,600 点 @5 Hz | 141 | 14.4 | 31.9 | 19.5 | 3.2 ms | **≈69 ms** | 200 ms |
| 真实 49,152 点 @10 Hz | 1,336 | 10.1 | 32.0 | 24.9 | 15.6 ms | **≈95 ms** | **100 ms** |

- 把 `render` 搬出关键路径后，它在路径上只剩 **1.35 ms**（原来是 60.46 ms 量级）。
- 分割头全路径 **23.96 ms**，约为它所伴随的检测器（66.42 ms）的三分之一 ——
  **想上分割，卡的不是算力，是解码与投影的工程量**。
- ⚠️ **真实侧 95/100 ms 没有余量**；这是 Xeon + 8 核 cgroup 额度的数字，**换个平台就崩**。

### 5.4 探索能力（同场景对照，可复算）

| | 关掉 `sweep` | 打开 `sweep` |
|---|---|---|
| 在规划路径上的帧 | **0** | **456** |
| 可通行 | 138.5 m² | **165.9 m²（+19.8%）** |
| 轨迹 | 24.6 m | 36.3 m |

**目标段平均效率**（净位移 ÷ 起始距目标）：西向长段实测 **94.7–96.1%**。

## 6. 自主感知算法

### 6.1 三分类：可通行 / 障碍 / **未知**

这是**赛题评分里明确点名**的一项（"显式区分可通行、障碍或未知"），也是这套栈最扎实的部分：

| 层 | 判据 |
|---|---|
| **几何类 0/1** | 地面 RANSAC + 高度带 → `background` / `traversable`，**零训练、零标注** |
| **障碍层** | 多帧**投票**（`MIN_VOTES=2`）+ 高度带 `[0.35, 2.00] m` + 地面比例否决 + 开运算 |
| **未知类** | `seen & ~ground & ~obstacle` —— 有回波但没被判定为可走或障碍 |

关键约束：**一个格子不能既铺地板又立墙**（`OBSTACLE_GROUND_RATIO=1.0` 允许地板证据否决同格障碍）。
`add()` 的末句固定为 `ground = ground_ever & ~obstacle`。

### 6.2 语义：2D 检测 → 标定投影 → 3D

- 检测器**没有被训练或微调过**。保留哪些 COCO 类别不是"能检出什么"（那是全部 80 类），
  而是两条**物理约束**：**LiDAR 看得见**（太小没有回波 ⇒ 只会变成误报）与**人能用一句话指出来**。
- 每个类还有两个门限（`min_points` 支撑点数、`min_box_frac` 框高占画面比例），**都是物理量而不是调参**。
- **人与物体走同一条几何**：框内点 30 分位深度 + **反投影回框内的硬判据**。
- 开放词汇（可自定词表）这条路已走通到"**能导出 ONNX、代价 284 ms**"——
  它是**能力储备，不是当前的分数**。

### 6.3 障碍层为什么不"聪明"一点

试过给障碍层加一个点云层判别器（用高度/点数/邻域 18 维特征区分"真障碍"与"贴着墙的假障碍"），
**判死**：在线留一 AUC **0.638 < 0.65**（事前写死的线），高度中位数 AUC **0.495**（抛硬币）。
⇒ **门内假障碍与真家具，在点云层上就是同一种东西**，光靠几何特征分不开。**不堆特征了。**

### 6.4 ★ 反直觉的一条：报"车卡住了"之前，必须把两列并排打出来

`frames.csv` 里**同时**有估计列（`pose_x/y`，策略实际据以决策的）和**真值列**（`truth_x/y`）。

一次实测：脚本报"车在 (−9.75, 6.59) 停了 **24 s**"。但同一个 22.3 s 窗口里：

| | 里程计 | 真值 |
|---|---|---|
| 累计路径 | 0.708 m | **5.545 m** |
| 净位移 | **0.032 m** | **5.308 m** |

`err_xy` 从 0.11 单调爬到 **5.74 m**，**真值车已经穿过墙开到房外**。
逐帧对齐后，坍缩**精确发生在车体前缘越过墙内表面那一帧**（`registered/points` 0.846 → **0.717**）。

根因在源码里读出来的，不是猜的：`registered` 是 `len(reg_in)`，即**裁过 `[min_range, max_range] = [0.3, 40]` 的
在距点数**，**不是配准成功数**（名字极易读成后者）。**倒车顶墙 ⇒ 贴墙回波落进 0.3 m 被裁
⇒ KISS-ICP 在行进方向退化 ⇒ 位姿冻结 ⇒ 策略"永远没进展"⇒ 从旧位姿/旧地图重选点 ⇒ 正反馈到墙钟耗尽。**

📏 **由此得到一条可筛查的尺子**：`min(registered/points)`。40 个归档跑**零重叠** ——
洼到 0.53 / 0.59 的两个必然冻结，≥0.896 的 33 个必然不冻结 ⇒ **真实发生率 2/40 = 5%**。

⇒ **"卡住"和"探得少"是症状量，不是故障量**。报它们必须同时报 `max err_xy` 与 `min(registered/points)`，
否则会把"传感器退化"记成"规划失败"，然后去改一个没坏的地方。

## 7. 创新性：工程贡献 vs 算法创新

### 7.1 先说诚实的部分

> 本项目自己的复评里写着（`docs/评审小灶_评分标准全面复评_20261010.md`）：
> **"整栈 = KISS-ICP + 几何地面 + COCO/YOLO-World 检测 + 自己写的建图/探索策略"** ——
> **算法层面没有原创。如果问"你的方法新在哪"，目前答案是"没有"。**

这不是自谦，是**边缘算力预算下的工程选择**：整帧约 200 ms 要与 odom/map/explore 分，
任何"更先进"的 3D 网络都先在这一关被否掉（§4.3）。**用成熟组件 + 把工程约束量清楚，是这个场景里的正确解。**

### 7.2 但工程层面有六条**可复现**的贡献

| # | 贡献 | 实测证据 |
|---|---|---|
| 1 | **"一套代码、两个数据源"落到架构不变量**：`config.py + sources/` 是唯一允许知道仿真/真实的地方，下游出现 `if sim` 即视为设计失败 | 5.6k 点 @5 Hz 与 49k 点 @10 Hz 走**同一条循环**；两源阈值**没有为任何一源单独调过** |
| 2 | **`sweep`：优先去"从没靠近过的可达地面"** —— 对标文档判定**无对应方案** | 关掉：`0` 帧在规划路径上、138.5 m²；打开：`456` 帧、**165.9 m²（+19.8%）** |
| 3 | **发现并处理官方仿真器 LiDAR 不随车体旋转**（源码级定位到 `vehicleSimulator.cpp`） | 指令死推航向 **p50 1.85°**；修好前 586 s 只到过 15 个 1 m 网格 |
| 4 | **三分类地图（含"未知"类）做成默认** | 正好命中评分里"显式区分可通行/障碍/未知"、"仅地面分割计部分"那一项 |
| 5 | **发现"贴墙 ⇒ 里程计坍缩"这条正反馈链**，并给出零重叠筛查尺子 | 40 跑零重叠；发生率 **2/40 = 5%**；见 §6.4 |
| 6 | **一批量出来、反直觉的硬规则** | 闭运算再腐蚀（+32 m² 全是假象）；目标要指向块的**深处**（指向最近格会变成每 0.6 m 换目标的蠕行）；块按**离起点**距离排序（按离当前位置会在走廊里来回横跳，实测 214 帧只挪 0.61 m）；**起点可以 snap、终点不行**（一次事故：终点被 snap 到脚下 0.24 m，导航绕了 674 s、走 158.65 m 只前进 5.78 m）|

### 7.3 方法论上的三条（比上面更耐用）

1. **先算预算，再谈方案。** 两个最贵的候选是靠"先看它自己报的数字"否掉的，省了一天装环境。
2. **不要在饱和的机器上做优化决策。** 照一个 150 ms 的读数把地面 RANSAC 向量化，
   空闲机上**零提速**还把平面挪了 1.2 cm ⇒ 已回退。那 150 ms 是机器争抢。
3. **配额受限的容器里，任何库按 `nproc` 自开的线程池都要显式限制。**
   同一个机制栽了**三次**（KISS-ICP 的 TBB / onnxruntime 的 intra-op / **OpenCV 的全局池**），
   而且它**拖慢的是进程里完全无关的单线程代码**（地面拟合 20 → 138 ms）。

## 9. 已知边界与不确定项

我们不藏不确定项 —— 这是一个**采集数据用的仓库**，不是营销页：

1. **真实侧没有真值。** 一切"误差"都是与厂商里程计的量级核对（§5.2）。
   评判口径下"你的精度是多少"这个问题，**目前只能给内部三条判据 + 一个比例**。
2. **"探索能力"的上限由仿真器的传感器配置决定。** 这份仿真的 LiDAR 是**世界对齐**的
   ⇒ **转圈不产生任何新信息**，而 40 m 量程一个视点就能看完屋子 ⇒ "探索"在这里天然退化为
   "微动填地板掩码的洞"。所以我们只敢说"**把可达的洞都填掉了**"，**不敢说"学会了找没去过的房间"**。
3. **实时性无余量**（真实 95/100 ms），且嵌入式平台未测。
4. `calib.yaml` 里 `FishPoly` 的 `k2..k7` **闭式形式未确定**，用纯等距 `r = A11·θ` 已能对齐走廊透视结构。
5. 人物的评价口径（检测框还是分割掩码）未定；本栈给框 + 三维位置 + 高度区间，两种口径都能换算。
6. **KISS-ICP 内部为什么在退化点云上返回零运动，我没有逐帧点云可证**（归档跑没有帧转储）。
   §6.4 那条链的**可观测部分**（接触帧 / `registered` 崩 / 位姿冻结 / `err_xy` 单增）全在数据里；
   **内部那一步是推断**，明确标注。
