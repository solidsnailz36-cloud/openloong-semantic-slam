1. **`t_cc` 把整张形态学账单算进了自己**：`reach_cells` 里计时的起点写在了 `free_space()` **之前**，

**教训（与 §69.8 同族）**：`t_cc` 那个 bug 的形状是"两个 stage 声称同一段墙钟"；

## 3. 慢在哪里

### 3.1 一次评估（`reach_cells`）的组成

一次评估 = 一张 600×600 `free_space()` + 一次整图 `connectedComponents` + `bincount/argmax/lab==seed`。

| stage | LIVE ms/次 | replay ms/次 | 微基准 p50 ms | 说明 |
|---|---|---|---|---|
| `t_close` | 0.489 (17.9%) | 0.491 (17.9%) | 0.268 | `MORPH_CLOSE` 椭圆 5×5 |
| `t_copy` | 0.435 (15.9%) | 0.434 (15.8%) | 0.013 | `ground.copy()` |
| `t_cc` | 0.597 (21.9%) | 0.611 (22.2%) | **0.932** | `connectedComponents(4)` 600² |
| `t_solid` | 0.215 (7.9%) | 0.192 (7.0%) | 0.095 | `dilate(obstacle)` 3×3 |
| `t_radius` | 0.207 (7.6%) | 0.195 (7.1%) | 0.254 | `dilate(~free)` 5×5 ← **代码里没有 `erode`，这就是那一步** |
| `t_and` + `t_and2` | 0.158 (5.8%) | 0.133 (4.9%) | 0.081 | 两次 `&` |
| `t_seed` | 0.179 (6.5%) | 0.286 (10.4%) | 0.410 | `bincount+argmax+(lab==seed)` |
| **(残差)** | **0.451 (16.5%)** | 0.405 (14.7%) | — | **缓存键 `ground.sum()+seen.sum()` + `.astype(uint8)` + Python 开销** |
| **合计** | **2.732** | **2.747** | **3.501** | |

**微基准（宿主、空闲、60 次重复、§70 那张最终地图）**给出最干净的一刀：

```
一份 free_space()（cache miss） = 2.160 ms
   ├─ 我打了标记的形态学 6 步    = 0.711 ms  (33%)
   │    close 0.268 | radius 0.254 | solid 0.095 | and2 0.042 | and 0.039 | copy 0.013
   └─ 没打标记的其余部分          = 1.449 ms  (67%)
        cache key ground.sum()+seen.sum() = 0.550   ← 单独测的
        ground.astype(uint8)              = 0.146
        其余 Python / 临时数组
一次完整评估 = free_space 2.160 + connectedComponents 0.932 + seed 0.410 = 3.501 ms
```

⇒ **"600×600 形态学 vs `connectedComponents`"的答案不是二选一：两者各占约 1/3 与 1/4，
而最大的单项其实是缓存键——它 100% 白付**（保险丝每次评估前手动把 `_cache_key = None`，
键算完必然 miss）。

### 3.2 每帧固定成本（与候选数无关）

| stage | LIVE ms/帧 | replay ms/帧 | 说明 |
|---|---|---|---|
| `t_cand` | 0.991 | 0.974 | `obstacle & ~_topo_prev` 两次全图布尔 + `np.argwhere` |
| `t_decide` | 0.291 | 0.101 | 阈值循环 + 日志 + 重算 `ground` |
| `t_mutate_base` | 0.139 | 0.087 | 把候选全部拿掉、重算 `ground` |
| `t_prev` | 0.031 | 0.026 | `obstacle.copy()` |
| **合计** | **1.45** | **1.19** | 可接受 |

⇒ **固定部分没问题。问题全部在 `候选数 × 2.73 ms`。**

顺带两个**不是瓶颈但会随规模变坏**的点：
* `t_cand` = 1.0 ms/帧，其中 `np.argwhere` 与两次全图布尔运算是纯浪费——`_topo_prev` 完全可以存成
  "上一帧 obstacle 的格集合"而不是整张 360 000 的布尔图。
* `_topo_fuse` 里 `c not in set(cands)` 写在列表推导的条件里，**`set(cands)` 每次迭代都重建**
  （Python 逐项求值条件表达式）⇒ 对被暂缓格数是 O(n²)。现在 n≤52 无所谓，但它在每帧路径上。

### 3.3 ★★ 真正的放大器：候选数，而候选数几乎全是"冻结的暂缓集合"

**LIVE：**

| 量 | p50 | p90 | p99 | max |
|---|---|---|---|---|
| `n_cand`（每次评估的候选数） | **48** | 49 | 88 | 548 |
| 其中 `n_defer_prev`（上一帧就在暂缓里的） | **48** | 48 | 52 | 52 |

```
纯新晋升 5 134 次   重测 43 169 次   ⇒ 89.4% 的评估是"重测"
```

**暂缓集合会冻结。** 逐帧看 `n_defer`（帧末暂缓格数）：

```
frame    1   2   3 ... 39  101  151  201  251  274  301  401  601  901 1139
n_cand   0 548  42 ... 19    2   13    3   57   53   51   48   48   48   48
n_defer  0   0   0 ...  0    0    0    0   49   52   51   48   48   48   48
```

从 **frame 242/243 起冻结在 48 格，一直到 frame 1139（898 帧）**。
全程只有 52 个格被重测过，其中 4 个在 frame 312 被正常放行，**48 个永不放行**。

成本归属：

```
保险丝总墙钟        136.7 s
  ├─ 重测这 48 格   118.1 s  (86%)
  └─ 新晋升          18.6 s  (14%)
```

而 `n_defer_prev p50 = n_cand p50 = 48` 意味着**稳态下没有任何新晋升**：保险丝在稳态的
100% 工作是对一个冻结集合做重复记账，**131 ms/帧**。

**REPLAY 是另一种 regime**：1044 帧有暂缓、但只有 **5 个格**粘住；重测只占 16%（1513/9270）。
⇒ 这解释了 §70（ON p50 42 ms）与本轮 live（p50 147 ms）的差别：**不是代码变了，是暂缓集合大了 10 倍。**

### 3.4 附带发现：那 48 格是一整块**真值空地**

冻结集合的世界坐标（odom 帧 == sim 帧，两者在 frame 1 逐位相等，偏移 (0.000, 0.000)）：

```
cell(341..346, 303..319)  →  world x 4.15..4.65 , y 0.35..1.95
```

即 **0.6 m × 1.7 m 一整块**，`truth(真值栅格) 占用 = 48/48 为 0`，离最近真值障碍 **0.51 m**。
逐格看：`(345,303)`…`(346,319)` 全部 `truth=free`，每格被重测 892–898 帧。

⇒ 保险丝**做对了**（这确实是幽灵障碍、确实该扣着），代价是**每帧 131 ms 去反复确认它**。
这不是 §69 那个"两格门口幽灵"，是同一机制在实时地图上的另一种表现：**一整块**。

## 7. ★ 最小改动：判据一字不改，把哪一步换成什么

### 7.1 硬事实（决定"能不能变便宜"的那条）

对候选格 `c`，把它加进 `obstacle` 之后，`walk = free_space()` 与 base 的差异
**被 `c` 的 Chebyshev ±4 邻域（9×9 = 81 格）完全包住**。逐步推：

| 步骤 | 影响半径 |
|---|---|
| `obstacle` 变（第 c 格） | ±0 |
| `ground = ground_ever & ~obstacle` | ±0 |
| `closed = CLOSE(ground, 5×5)` | **±2**（5×5 结构元） |
| `solid = dilate(obstacle, 3×3)` | ±1 |
| `free1 = closed & ~solid` | ±2 |
| `bad = dilate(~free1, 5×5)` | **±4** |
| `free2 = free1 & (bad == 0)` | **±4** |

⇒ **360 000 格里，只有 81 格可能变化。** 这不是近似，是上界。

### 7.2 三层改动，按收益排序

**(a) 不要每帧重测没变过的暂缓格。** —— 直接砍掉 86%（118.1 s / 136.7 s）
暂缓格的 Δ 只可能在"base 地图在它附近变了"时才变。触发条件可以是：
① 该格 ±R 窗口内本帧有新的 `ground`/`votes` 变化（每格一个 dirty 帧号，O(1) 判断）；
② 或每 N 帧兜底重测一次。
⚠️ **这会改变"暂缓多久才被放行"的时延 ⇒ 它是行为改动，不是免费午餐**，必须 A/B
（判死条件见 §7.4）。但它**不改判据**：Δ 还是同一个式子、同一个 base，只是不再每帧算。
*只做这一条，稳态就从 131 ms/帧 掉到 ~1.5 ms/帧。*

**(b) 把"一次评估"从全图缩到 9×9 窗口。** —— 砍掉新晋升那一支（18.6 s）与启动尖峰（2.5 s）
利用 §7.1：每帧做**一次**全图评估拿到 base 的 `walk` 与 `lab`；对每个候选，只在 9×9 窗口里
重算 `walk`（crop 之后 `cv2` 是微秒级），再判"窗口内属于机器人分量的格是否还连成一块并接到边界"。
- **能证明 Δ = 0 的候选 ⇒ 直接采纳**（这是绝大多数）。
- **证明不了的 ⇒ 回落到一次完整 `reach_cells`**。
⇒ **构造上精确**（完整评估仍是仲裁者），省下来的比例 = 1 − 回落率，**回落率必须实测**。
- 更彻底的做法：`Δ(c) > 0` ⟺ 删掉 `c`（加上它的 ≤8 格 halo）会把机器人所在 base 分量切开
  ⟺ `c` 是该分量的**割点**。割点每帧算一次、候选查表即可，判据同样不变。
  ⚠️ numpy 里跑割点算法（Tarjan 本质串行）是否能在 1–2 ms 内做完 2 万格的连通块，
  **未验证** —— 这是 (b) 的"更好但没实测"的分支，先按窗口+回落做。

**(c) 删掉白付的缓存键。** —— 0.550 ms/候选，占单候选成本 **16%**，且**行为完全不变**
（保险丝本来就每次都 miss）。给 `free_space` 一个显式"不走缓存"的路径，或把键换成便宜的
变更计数器。**这一条是三者里唯一"零行为风险"的，可以先做。**

**(d) 顺手（不是瓶颈）**：`t_cand` 1.0 ms/帧的整图布尔 + `argwhere` 换成集合差分；
`set(cands)` 从列表推导里拿出来。

### 7.3 预期（**是预期，不是结论**）

| | 现在 | (a)+(b)+(c) 后（估） |
|---|---|---|
| 稳态帧 | 130 ms | ~4 ms（1 次全图 2.7 + 48 次查表 + 固定 1.5） |
| 启动帧 f2 | 2505 ms | ~50–100 ms |
| fuse / `ms_map` | 87.5% (p50) | ~5% |
| `ms_map` p50 | 147 ms | ~20 ms |

⚠️ **验收只能在闭环上做**：§70 已经证明 replay 里 320 ms/帧也无所谓，**replay 过 Gate ≠ 闭环过预算。**

### 7.4 判死条件（预先写下）

1. 回落率 > 20% ⇒ (b) 的窗口判据没用，改走割点路线或放弃；
2. (a) 使"某格被暂缓超过 X 帧仍不放行"的最坏时延显著变长（对照当前：48 格 898 帧未放行）⇒ (a) 变相封禁，撤回；
3. (c) 之后 `prod_on` 决策 md5 变化 ⇒ 缓存键不是纯浪费，撤回；
4. 闭环重跑里程 < 对照臂 80%、或 `plan_failures` 未回到 ~20 ⇒ 不是成本问题，回 §70 的 fallback 线；
5. 出现新的单帧 >50 m² 塌陷 / 真障碍被误拦 ⇒ 无条件撤回。

### 9.1 落地①：(c) 删掉白付的缓存键 —— **零行为风险，已证**

## 13. ★★★ 归因查清：**是我的成本上界有缺陷，不是 B3 本身**（2026-10-09）

> 一条 ON 臂 + `--b3-prof`（`out/_b3_diag.sh`，`sim_span = 300.0 s`，1270 帧）。
> 注意这条**本身偏坏**（里程 41.9 m，ON 中位 82.4），所以下面是**结构性事实**，不是分布。

### 13.1 主假设成立：**积压不排空**

```

f201 -300   med    0
```

### 13.2 ★★ 而且"扣住"在地图里的语义是**错的**：它变成"可通行"

这是闭环才暴露的问题。代码里：

```python
# worldmap.py: 每次改 obstacle 之后
np.logical_and(self.ground_ever, ~self.obstacle, out=self.ground)   # ← ground 是 obstacle 的纯函数

# nav.py:479 free_space()
free = wmap.ground.copy()        # ← 规划器读的是 ground
```

**⇒ 被扣住的格 `obstacle=False` ⇒ 直接变成 `ground` ⇒ 被规划器当成"可以开过去的地板"。**

但安全层不是这么看的：

```python
def blocked(self):   # worldmap.py:893  —— 只看前方通不通
    return self.obstacle | self.obstacle_now
```

`obstacle_now` 是**当帧原始回波**，在过滤之前写好。被扣住的格**若当帧还有回波，就仍在 `blocked()` 里**。

**⇒ 规划器说"能走"，安全门说"别撞" —— 这正是 `wedge` ×4.7 / `blocked` ×3.1 的来源。**

**⚠️ 对 B3 本身是不公平的**：机制**自己**的暂缓格是"晋升它会砍掉一块连通域的门口幽灵格"，
把它们当可通行**正是这个机制的目的**。问题出在**上界扣住的是任意格**（候选表里排在后面的那些），
把 2000 多个**任意格**当可通行地板，就成了灾难。

### 13.4 ★★ 所以结论要分成两句，不能混

1. **作为"可交付的配置"：FAIL，撤回。** 事前判据两条同时不过，这是定论，
   **不需要等归因**。`OBSTACLE_TOPO_FUSE_M2` 默认保持 `0.0`。
2. **作为"B3 机制有没有用"：这一轮没有干净地测到。**
   ON 臂是 `fuse 1.0 + retest 20 + max-eval 32` 三个开关捆在一起，
   而其中 `max-eval` 有一个**语义缺陷**（§13.2），它一个人就能产出这两个 FAIL。
   **⇒ 把 FAIL 说成"B3 不行"是过度的；把它们说成"B3 没测出来"也是过度的。
   准确说法：这一轮的 ON 臂测的是"带缺陷的成本上界"，不是 B3。**

**⚠️⚠️ 但有一个必须先说的反证，它让上面这条诊断不能单独成立。**

**§70 那次 `K=1.0` 闭环 FAIL 是在「没有上界」的情况下发生的** —— `max-eval` 这个开关当时还不存在。
那次的账是 `ms_map` max 2254 ms、**里程 20.44 m vs 对照 123.98 m**（对照现在知道是单跑，
但 20.44 也在 OFF 分布的下界 **59.4** 之下很多）。也就是说：

**已经有过一次观察：fuse 开着、没有上界 ⇒ 里程照样塌。**

⇒ 所以"上界是元凶"目前只是**一个能同时解释两个 FAIL 的假设**，不是结论。
**§13.1/13.2 是事实**（积压不排空、被扣住的格成了"可通行"），
**但"这就是里程掉 36% 的原因"是推论。** 有可能两个机制都在起作用，
也有可能是 fuse 自己（K=1.0 把门口幽灵格当可通行，可能让机器人反复冲进死角）。

**⇒ 这正是 §13.5 的消融 B 要回答的，而且它现在只有一个未知数。**

**⭐ 教训（已进技能）**：
* **一个臂只改一件事。** 判据 FAIL 不贵，"FAIL 却说不清归因"才贵 —— 本轮为此多花了一条诊断跑。
* **"扣住 / 顺延 / 降级"这类省成本的手法，必须写清被扣住的格在**下游每一个消费者**眼里是什么。**
  这里 `deferred ⇒ obstacle=False ⇒ ground ⇒ free_space`（规划器认为可通行）
  而 `blocked()` 仍认为不可通行 —— **一个语义，两个消费者，两个答案。**
  自检："这个暂缓集合，会被哪些量读走？每个量读到的语义一致吗？"
