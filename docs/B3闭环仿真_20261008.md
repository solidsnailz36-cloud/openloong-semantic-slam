**不要让它直接“优化 B3”。**

## 第二阶段才设计加速

我会优先考虑一个原则：

> **不要对 600×600 地图的每一个候选都完整重算一次连通域。**

现在相当于：

```
一帧 19 个候选
×
每个候选一次完整 600×600 topology computation
```

这是典型的**算法复杂度方向不对**。

更合理的结构应该是：

```
正常地图
   ↓
先判断候选是不是“可能影响当前拓扑”
   ↓
绝大多数候选直接跳过
   ↓
只有靠近：
    robot→frontier
    robot→room
    窄通道
    当前可达区域边界
的候选
   ↓
才做 topology fuse
```

也就是说：

**B3 不应该成为“每个候选都跑一次全地图可达性分析”。**

它应该是一个**便宜的门卫**，只有怀疑“这个格子可能把一个大区域切断”时，才启动昂贵检查。

## 2. 直接根因：成本，不是地图

`frames.csv` 的逐阶段耗时（同一 build，p50/p90/max，ms）：

| stage                           | B3 ON                      | B3 OFF                    | 变化                                  |
| ------------------------------- | -------------------------- | ------------------------- | ----------------------------------- |
| **`ms_map`**（`wmap.add`，保险丝在这里） | **42.1 / 147.4 / 2254.4**  | **15.6 / 20.7 / 28.3**    | p50 **2.7×**、p90 **7×**、max **80×** |
| `ms_explore`                    | 26.6 / 213.7 / 290.0       | 37.4 / 67.1 / 255.9       | p90 **3.2×**                        |
| `ms_detect`                     | 95.5 / 109.0 / 472.1       | 96.4 / 107.8 / 221.6      | 基本相同                                |
| **`ms_total`**                  | **270.4 / 489.2 / 2606.8** | **252.7 / 287.6 / 459.9** | p90 **1.7×**、max **5.7×**           |

仿真以 **5 Hz** 发布（实测 LiDAR 间隔 0.199–0.201 s）⇒ **每帧预算 200 ms**。

- `ms_total` p90 = **489 ms** ⇒ 至少 10% 的帧**超预算 2.4 倍**；
- `ms_map` **max = 2254 ms** ⇒ 存在**单帧 2.25 秒**的地图阶段；这期间机器人仍按上一帧指令在跑  
  （2.25 s × 0.55 m/s ≈ **1.2 m 的盲开**）；
- 结果：**4.35 fps（对照 5.00）**，且这些抖动正是"目标算在过期位姿上"的来源。

下游读数与之自洽：`plan()` 几乎全失败（**562 vs 17**）、`arrivals` 只有 1（对照 21）、  
`sweep_targets`/`island_probes` 全 0（对照 10/12）—— **两个唯一能把机器人送进房间的机制从未触发**。

> **费用为什么这么大**：保险丝对**每一个候选**都要算一次"试装后的可达"，而每次可达 =  
> `PathPlanner.free_space`（600×600 上的 5×5 close + 3×3 dilate + 5×5 erode）+ `connectedComponents`。  
> 本次闭环平均 **19.1 个候选/帧**（6748 / 353），而 §69 的 replay 只有 6.2 个/帧（9270 / 1489）。  
> 早期建图那一波尤其贵，而这一跑只有 353 帧，建图期占了大头。

**⚠️ 这条链条里"成本 ⇒ 决策退化"是推断（有 562/17 与 1/21 的对照支持），不是直接观测到的因果。**  
但"`ms_map` p90 从 20 涨到 147、max 2254 ms"是直接测量。

## 5. 结论与下一步

**结论**：B3 的**机制**没错（replay 与本次闭环都没有出现"门被封死"或 `reach` 塌陷）；  
错的是**代价** —— 它把每帧地图时间从 16 ms 抬到 42 ms（p90 147 ms，max 2.25 s），  
打崩了 5 Hz 的控制回路，于是 `plan()` 562 次失败、只到达目标 1 次、20.4 m 就不动了。

**下一步（按优先级，不改 K、不改默认值）**：

1. **量清单帧成本**：把保险丝的耗时按"候选数 × 每次可达"拆出来（`ms_map` 里单列），  
   确认 max 2254 ms 那一帧有多少候选；
2. **削成本**（任选，先量再改）：
   - **只对"新晋升且票数低"的格做试装**（门口幽灵是 `votes=2`，真墙是几十上百）；
   - 每次可达**复用**同一帧的 `free_space` 中间量，或用一个**低分辨率**可达（0.2 m 格）做**筛选**，  
     只在候选落进"可疑区"时才用全分辨率复核；
   - 限制每帧最多审 N 个候选，其余推到下一帧（把突发摊平）；
3. **然后重跑同一条 A/B**（同一 build、`--obstacle-topo-fuse 0/1`），  
   验收口径：里程 ≥ 对照的 80%、`plan_failures` 回到 ~20 量级、进入房间数 ≥ 对照。

**⚠️ 这条最值得记的教训**：**replay 没有墙钟预算**。  
§69 在 replay 上 PASS，是因为那里 320 ms/帧也无所谓；  
同一个机制在 5 Hz 闭环里就因为 42 ms/帧而把系统拖垮。  
**任何"每帧多算几遍可达/规划"的机制，必须在闭环上量 `ms_*`，不能只在 replay 上过 Gate。**
