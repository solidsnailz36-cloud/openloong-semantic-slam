## 1. 仿真侧"人没标"：把**框的分辨率下限**当成了"物体有多高"

### 1.1 证据：框高在 ~32 px 处触底

把真值真人的位置按当帧位姿投到图像，读检测器自己的框（`out/_box_measure.py`）：

| 距离 | 框高 | 由 `深度 × 框高 ÷ 焦距` 反推的身高 |
|---|---|---|
| 2.42 m | 74 px | **1.74 m** ✓（这条对了） |
| 3.96 m | 50 px | 1.93 m |
| 5.93 m | 34 px | 1.96 m |
| 8.20 m | 33 px | 2.56 m |
| 9.93 m | 32 px | **3.09 m** |

框高**不再随距离缩小**（32 px ≈ 检测器 letterbox 输入下两个 32-px stride），
于是 `隐含高度 = 深度 × 框高 ÷ 焦距` **随距离线性增长**，而物体并没有变大。

### 1.2 代价（同一次 1229 帧跑的逐框统计）

真正**覆盖真人**的框 258 个，去向：

| 结果 | 框数 | 其中覆盖真人 |
|---|---|---|
| 接受 | 849 | 229 |
| `reject_wide` | 397 | **1** |
| `reject_short` | 225 | 14 |
| `reject_cluster_too_small` | 167 | 11 |
| `reject_all_floor` | 83 | 0 |
| `reject_tall` | 21 | 0 |
| `reject_no_points` | 20 | 3 |

而**改动前**：接受 567 里只有 112 覆盖真人；`框高上限`杀 50、`框高÷实测高`比门限杀 68。
⇒ 真人只在 35% 的帧里被标出来，真正覆盖真人的框只有 43% 活下来。

### 1.3 修法：两条充分条件取 `or`，不要取 `and`

```
pass_width = width_lat <= 0.55                  # 量出来的，任何距离都成立
pass_box   = (box_h_px >= 48) and (0 < 框推高 <= 2.40)   # 框够大才有资格发言
if not (pass_width or pass_box): 拒绝            # 只有"框不能发言"且"截面不对"才拒
```

- `width_lat`＝**选中簇在相机系里、垂直于视线的横向跨度**（`xc[:,0]` 的极差；`xc` 是算深度时已有的那个变换）。
  中位值：仿真市民 **0.29 m** / 仿真墙面碎块 **0.80 m** / 真实真人 **0.46 m**。
- `48 px` = 实测触底值 32 的 1.5 倍；`2.40 m` = `LABEL_MAX_HEIGHT[person]`（同一个物理窗口）。
- **为什么不能用 `and`**：两条判据各自只在部分条件下成立，`and` 会在**不适用的那条**上把真样本判死。
  `and` 版本会让真实侧 **79%（342/431）的真人框被误杀**；`or` 版本真实侧 **431/431 全保留**。
- ⚠️ **第一版把宽度写成了 LiDAR 系的 `max(x_span, y_span)`**：x 是**前向**，斜看一个目标时它随方位角涨，
  真实侧 25% 的真人框超标。**必须是垂直于视线的横向跨度。**

### 1.4 效果

- **逐框重放（同一份 1229 帧采集）**：接受 567 → **849**（覆盖真人 112 → **229 = 89%**）；
  `reject_wide` 拒掉的 397 个框里**只有 1 个**是真人。
- **正式跑、像素级核对**（`tools/check_person_markers.py`，统计地图面板里人色像素）：
  "相机标了人、地图没标" **54% → 15%**；三位真人观测数 **60/30/31 → 198/128/123**，全部确认入选。
- **真实侧**：`localised 776/963 = 80.6% → 793/963 = 82.3%`，且 `reject_wide` **一次都没有触发**
  （真实侧的框 161 px、框推高 1.73 m，"框够大"那一句把它们全兜住了）。

## 2. 灰/绿到底是怎么识别的（boss 问的）

三句话，`worldmap.add` 是唯一决定它们的地方：

```
绿 = ground          这一格被确认为"地板"：有回波落在 |h| < 容差 内（h = 离拟合地面的高度）
灰 = seen & ~ground  看过这里，但没找到地板
黑 = 其它            从没有回波落在这里
```

渲染就是 `cls[seen]=2`（灰）然后 `cls[ground]=1`（绿）。

**三个必须说清的点**：

1. **`seen` = "有回波落在这一格里"，不是"射线扫过这一格"。** 射线穿过去不留痕迹。
   ⇒ 一个真正开着的门，正常应该被画成**黑**（没回波落在门口），
   **如果门口是灰的，说明确实有回波落在那里**——问题不是"看不见"，而是"看见的是什么"。
2. **`seen` 只在回波"对地板有信息量"时置位**（`h <= OBSTACLE_HI`，即 2.0 m 以下）。
   天花板回波是天花板的测量，对下面的地板什么也没说。这条是上一轮加的，
   把真实侧"只有 >2 m 回波"的灰从 9244 格砍到 569 格。
3. **容差随距离增长**：`tol = 0.10 + 0.035 × r`。所以 7 m 以内存在一个 `tol < h <= 0.35` 的"死区"
   （回波略高于地面、又不到"障碍"），它既不是绿也不是障碍 ⇒ 灰。

## 3. 门口为什么"始终是灰的"

### 3.1 用**交付的 pcd** 回答"那一格有什么"（不用重放）

`map.pcd` 就是同一跑的点，每格一个代表点，带标签和高度。对三个"门口"格读附近 0.25 m 内的点：

| 门口（世界坐标） | 格内点数 | 离地高度 | 标签 |
|---|---|---|---|
| (−8.15, −0.25) | 64 | **0.00 → 2.53 m**，p50 2.01 | 42 背景 + 22 可通行 |
| (−5.90, −6.35) | 216 | **0.00 → 2.53 m**，p50 1.54 | 189 背景 + 21 可通行 |
| (5.40, 1.30) | 370 | **−0.03 → 2.49 m**，p50 1.09 | 311 背景 + 51 可通行 |

**0 → 2.5 m 铺满＝一个竖直面**（墙 / 门框 / 门扇），不是空穴。

### 3.2 但同一排里**既有实体格、也有透明的洞**

`tools/diagnose_door.py` 重放同一份采集，对格子逐帧统计：
被检查的那一格 **1229 帧里 0 个回波落地，却有 549 帧的射线穿过了它并继续前进**（未遮挡）。
ASCII 打印那一排的状态也看到 `############.#.###        # #  ` ——灰块与"从没看过"交错。

⇒ **一个洞口的格子是凉的（没回波），而它相邻的格子有实体回波。障碍层只要有一串"≥2 帧证据"的格子
把这条透光的线连成 4-连通，门就被缝死了。**

### 3.3 量化的结论：**不是膨胀参数问题**

`tools/diagnose_bottleneck.py`（新增）：对阈值半径 t，只保留"到最近障碍距离 ≥ t"的格子，
问客厅格与房间格是否还连通；最大的 t 就是**能通过的最大圆的直径**。

```
probe                         raw        planner      需要
客厅 → comp12(33.3 m²)      0.00 m      0.00 m      0.44 m   SEALED
客厅 → comp1 (23.7 m²)      0.00 m      0.00 m      0.44 m   SEALED
客厅 → comp21(18.2 m²)      0.00 m      0.00 m      0.44 m   SEALED
```

**连 1 cm 的圆都过不去** ⇒ 把机器人半径调小、把闭运算核调小，**一点用都没有**：
障碍层在那里的 4-连通性是拓扑问题。这与上一轮"三个方案全否、可救回 0.0 m²"是同一个结论，
但现在有了可以直接和机器人半径比大小的数。

### 3.4 ★ 而且**相机从来没看清过那里**

机器人确实贴着那面墙开过（0.6 m 距离，82 帧在其 3 m 内），但墙在它**方位 −55° ~ −140°**
——相机水平视场只有 ±57°，**几乎全程在视场外**。所以地图对那面墙的了解全部来自激光的掠射回波，
而相机从没回答过"那是门还是墙"。

⇒ **这是探索策略该改的点：不是"多走"，是"去看"。** 具体到策略：当激光报出"一条又薄又连贯的
障碍线、且两侧都是已知地板"时，应该把它当成**欠确认目标**，转过去用相机看一次
（而不是继续找"没走过的地面"）。这可以是一个独立的 frontier 类别，优先级低于
`reach_&_~visited` 但高于"绕圈"。

## 4. 真实侧灰斑：机制找到了，但针对它的改动**实测否决**

### 4.1 事实核对（同一次 1427 帧采集，重放）

| | 旧规则 | 上一轮（交付的） |
|---|---|---|
| 绿 | 395.4 m² | 429.6 m² |
| 灰 | 407.2 m² | 280.7 m² |
| **被绿包围的灰"针孔"** | 281 | **300（更差！）** |
| 绿碎块数 | 480 | 544 |

上一轮我说"灰 407 → 281，改善明显"——**面积上对，观感上不对**。灰色分解说明了为什么：

- 上一轮确实把"只有 >2 m 回波"那一类从 **9244 → 569 格（−94%）**（`seen_mask` 那条修对了）；
- 但灰里 **93.6% 是障碍层**（26283 格），而**被绿包围的 300 个针孔里 283 个是障碍格**；
- 障碍层结构：**307 个连通块，28% 只有 1 格、52% ≤5 格**——只占 1.3% 的面积。**就是这些碎点**。

⇒ **机制清楚了**：上一轮降的是"天花板灰"，而 boss 看到的是"障碍碎点"，两者不是同一批格子。

### 4.2 尝试的修法与它为什么没有交付

规则：3×3 形态学开运算，且只删满足三条的格子 —— ①开运算判定可删 ②**8 邻里没有"从没看过"的格子**
③票数 < 12。②是安全护栏（外墙的一段"1 格厚"与墙中央的碎点局部同形，删了机器人会开出房子：
同码三跑里有两次真的跑到屋外，`arrivals` 0 和 2，正常那次是 20）。

**结果在两个源上不一致：**

| 口径 | 上一版 | 开清理 |
|---|---|---|
| 仿真侧 针孔 / 绿碎块 | 24 / 28 | **10 / 13**（改善） |
| 真实侧 灰块数（中位大小） | 374（4 格） | **846（2 格）**（变差） |
| 真实侧 针孔（整图） | 300 | 1252 |
| **两图共有的已观测区域（66345 格，占上版 93%）** | **290** | **1248** |
| 同一份采集的**重放**预测 | 300 | **73**（说会变好） |

- 共有区域口径排除了"覆盖更多地面"这个解释 ⇒ **是真回归**。
- 而固定轨迹重放说它会改善。**重放与在线跑在这条规则上不一致，原因没找到。**
  第一嫌疑：`tools/diagnose_ground.py` 的障碍层**没有应用 object mask**，管线应用了
  （`obstacle_mask = ... & ~obj_mask`）⇒ 两者的 `obstacle` 不是同一个集合。

⇒ **按纪律否决**：`OBSTACLE_OPEN_PX = 0`，把上面这些数字写进 `worldmap.py` 的注释。
（与上一轮 `OBSTACLE_MIN_VOTES` 的处理方式一致：机制留着、数值关掉、理由写清楚。）

### 4.3 由此得到的一条方法论（比这个改动本身值钱）

**"固定轨迹重放"只能验证与轨迹无关的改动。** 一旦改动会改 `ground`/`obstacle`，
而这两个量又喂给探索与规划（`free_space`、前沿、`sweep`），在线跑的轨迹就变了 ——
**重放论证的是一个反事实，不是将要交付的那一跑**。（本轮真实侧可达面积 79.4 → 134.1 m²，
轨迹确实变了；但共有区域内的比较显示这次**不是**轨迹造成的，所以还有别的原因。）

### 4.4 保留的中性改动

`ground` 从"锁存"改成**重算**：`ground = ground_ever & ~obstacle`。
清理关掉后它与旧行为等价（投票单调），但它是"障碍层可以缩减"这件事的前提，
以后要再试 §4.2 必须先有它。

## 5. 本轮踩的坑（都是"看起来在跑"）

1. **同步脚本的自检变成硬失败**：它直接索引 `LABEL_MAX_BOX_RATIO[PERSON]`，而这个表本轮被**合法清空**
   ⇒ `KeyError: 2` ⇒ 脚本非零退出。已改成 `.get()` + 缺了就打印 `-`。
2. **`sync | tail` 吞掉退出码，而 `run_final.sh` 有 `set -o pipefail`** ⇒
   脚本在**打印完 `SIM_READY` 之后**中止，症状只有"输出目录的时间戳没变"。
   ⇒ **在链条里调用会失败的脚本时，不要用管道接它**（或至少 `; echo $?`）。
3. **`sim_up.sh > /dev/null 2>&1` 把 Gazebo 僵死的事实藏了**：`gzserver` 是 `<defunct>`，
   而管线照样打印"3 frames processed"（读的是陈旧缓冲），甚至跑出 124 帧才崩。
   已改成**必须自证在发布话题**（`rostopic hz` 里出现 `average rate`，否则脚本失败）。
   ⇒ **绝不要静音一个允许失败的步骤。**
4. **两次管线同时在跑，其中一个的 `rm -rf /work/cap_final` 删掉了另一个正在写的目录**
   （`FileNotFoundError: /work/cap_final/000124.npz`）。
   ⇒ 同一产物目录**同时只能有一个跑在飞**。
5. **`pkill -f online_pipeline` 匹配到了它自己那条 `docker exec` 的命令行**，把执行它的 shell 杀了。
   ⇒ 用 `docker exec -i ... bash -s` 从 stdin 传脚本（命令行里不含那个字符串），
   或把启动脚本写成容器内的文件再调用。
