## 1. ① 人标到墙上 / 视频认出但地图没标

### 1.1 虚多是什么：**房子的墙**

把交付那一跑（`out/online_sim`，1098 帧）的人实例与真值（`vendor/sim_scripts/sim_truth_model_states.json`，39 个模型）对照：

| 实例 | 位置 | 观测数 | 真值里是什么 |
|---|---|---|---|
| id 4  | (1.25, −3.26) | 163 | `person_walking` (1.09, −3.31) ✓ |
| id 8  | (−2.26, 0.04) | 118 | `citizen_extras_male_03` (−2.36, −0.08) ✓ |
| id 37 | (−1.91, −5.15) | 98  | `citizen_extras_female_02` (−2.08, −5.11) ✓ |
| id 41 | (−5.84, −3.57) | **67** | **空** —— 室内墙 |
| id 62 | (−4.53, −7.85) | 23 | **空** |
| id 2  | (0.03, −7.81)  | 17 | **空** |
| id 3  | (−3.75, −7.83) | 17 | **空** |

`y ≈ −7.8` 那一排真值里**什么都没有**（最近的模型是 4.3 m 外的 `youbot`）——
那排是房子的外墙。⇒ **"标到墙上"不是定位错，是检测器把墙面帧当成了人**。

### 1.2 为什么 v6 的门限放它们进来了

v6 把两条判据改成 `pass_width or pass_box`（各为充分条件）。这一改救回了远处的真人，
但**副作用是把 `LABEL_BOX_HEIGHT` 那个窗口架空了**：实测（1229 帧采集 + 真值投影，
`tools/diagnose_fusion.py --dump`）——

```
被融合接受的人框：  落在真人身上 192   落在空处 241     =>  精度 44%
```

而且**没有任何"框级"的量能把它们分开**：

| 候选判据 | 真人 | 虚多 | 能否分开 |
|---|---|---|---|
| 检测器置信度 `score` | p50 0.88 | p50 0.84 | ✗ 扫 conf 0.35→0.75，精度一直 44–46% |
| 横向跨度 `sel_width_lat` | p50 **0.29 m** | p50 **0.18 m** | ✗ **虚多反而更窄** |
| 点数 `n_sel` | p50 52 | p50 25 | △ 重叠 |
| **框推高 `box_height_m`** | p10 **1.74** p50 2.37 | p10 **0.87** p50 2.79 | ✓ |

**"框推高 0.87 m"= 框和距离一起说"这个东西不到 0.9 米高"** —— 一堵墙上的碎块正是如此。

### 1.3 修法：加一条**必要**条件（AND），不是再加一条充分条件

```python
# labels.py
LABEL_BOX_HEIGHT_MUST: Dict[int, Tuple[float, float]] = {PERSON: (1.40, 3.50)}
```
`fusion.object_3d` 里：原有的 `pass_width or pass_box`（充分，不变）**并且**必须落在
`[1.40, 3.50] m` 内（必要）。新拒绝计数 `reject_box_height_must`。

- `1.40` = 最矮的成年人；两个源都给足了余量（**真实侧实测 `box_height_m` p1 1.55 /
  p50 1.72 / p90 2.04 / max 2.19** —— 这条窗口在真实侧**根本不咬**）。
- `3.50` = 允许远处分辨率触底带来的虚高（仿真真人框 p90 2.97）。
- 为什么是物理量而不是"扫出来的阈值"：见 §1.4 的跨跑性。

### 1.4 A/B（**同一份 1229 帧采集、同一份代码，只把那张表清空**）

| | person 实例 | 已确认 | localised | 三位真人观测数 |
|---|---|---|---|---|
| 清空 `LABEL_BOX_HEIGHT_MUST`（= v6 行为） | 16 | 8 | 849 | 141 / 62 / 88 |
| **加上窗口 `[1.40, 3.50]`** | **7** | **4** | 709 | **132 / 52 / 82** |

确认的虚多从 5 个降到 1 个（剩下的那个在 (−0.6, −7.8)、只有 14 次观测）。
框级：真人 192 → 178（**92.7% 保留**），虚多 241 → 115，精度 **44% → 61%**。

如实说明三点：
- 这是**一次跑**的分隔度。v5→v6 的教训是"一次跑的分隔度不能当跨跑阈值"。
  但这条不是从分隔度里挑出来的，是"人至少 1.4 m 高"，属**场景陈述**。
- **两个源上都留了干净的间隔**：仿真侧被拒框 `boxh` 上限与被接受框的下限错开；
  真实侧（同采集重跑 `diagnose_fusion --dump`，32 个被拒框）**被拒最大 1.29 m、
  接受最小 1.42 m，间隔 0.13 m**，阈值 1.40 落在间隔里而不是连续体上。
- **"视频识别出来、地图上没标注"的剩余来源没有变**：仿真 `localised 709 / boxes 1762`，
  其中 `reject_short 225`（回波太少/太矮）、`reject_all_floor 83`（全落在地板上）、
  `reject_no_points 20`（框里没有激光点）。这些是**几何上真的说不清**的框，
  不是画漏了。像素级核对工具 `tools/check_person_markers.py` 仍然是这类问题的尺子。

## 2. ② 检测器能不能换 —— 实测，不换

### 2.1 先量它到底有多差

同一份采集、同一套真值投影：

```
person 框总数 1227   —— 落在真人身上只有 214 个
```

⇒ **人这个类别在本渲染上的"框级查准率"只有 17%。** boss 的直觉是对的。

### 2.2 换成更大的同类模型：**实测无收益，代价很大**

导出了 `yolo11s.onnx`（38 MB）与 `yolo11m.onnx`（80 MB），在同一份采集上跑同一套逐框诊断：

| | 人框总数 | 落在真人身上 | 到高度测试为止 真/虚 | 接受框精度 | 单帧耗时（本机 CPU） | ONNX 体积 |
|---|---|---|---|---|---|---|
| **yolo11n**（现用） | 1227 | 214 | 206 / 818 | 44% | **109 ms** | 10.7 MB |
| yolo11s | 1289 | 216 | 208 / **880** | 61%* | **269 ms** | 38 MB |
| yolo11m | —— | —— | —— | —— | **767 ms** | 80 MB |

\* yolo11s 的接受框精度 61%，与"yolo11n + 必要窗口"的 61% **完全相同**——因为它的虚多
也少（115），但那是模型自己在框阶段就少给了，**没有额外信息**。

⇒ **换更大的同类模型不解决这个问题。** 病不是容量，是**域差**：
COCO 上训的模型看 320×180 的合成渲染，本来就该乱说。而且 11s 用掉 2.5 倍时间
（本机预算 100 ms/帧，真实侧现在已经是 250–300 ms/帧），11m 直接 7 倍，
包体从 36 MB 涨到 60–105 MB。

### 2.3 真正值得做的三条（都需要重训或重导，**我没有擅自做**）

1. **用仿真自动标注微调**（最值钱）：Gazebo 真值可以把 3 个 citizen 投到图像里，
   `tools/diagnose_fusion.py` 里已有的"按方位角匹配真值"就是现成的标注器。
   代价：要跑一次带图像的采集、写训练脚本、GPU（本机 RTX 5060 的驱动当前是坏的）。
   预期：直接消灭"墙=人"，这是唯一能根治的路径。
2. **提高仿真相机渲染分辨率**：现在是 320×180，`box_h_px` 在 32 px 触底，
   远处的人框分辨不出人。渲染 640×360 是最便宜的一步（改 world 文件 + 重跑）。
3. **换架构**（RT-DETR / YOLOv10 等）：收益不确定、包体更大，优先级最低。

## 3. ③ 门口为什么"始终是灰的"（人话版）

上一轮我写的是机制，boss 没看懂。这一版按"一个格子怎么变成灰的"讲：

1. **地图上的三种颜色，只有一条规则**（`worldmap.add`）：
   - **绿**：这一格确认是能走的地板；
   - **灰**：我朝这里看过，但**没看到地板**；
   - **黑**：我的传感器**从没打到过**这里。
2. **关键**：一格变灰，必须**有一个激光回波落在这一格里**。激光"穿过去"是不留痕的。
3. 所以：**门真开着 ⇒ 激光穿过去 ⇒ 门那格什么都没打到 ⇒ 那格应该是黑的，不是灰的。**
   现在它是灰的 ⇒ **确实有回波落在那里**。
4. 查交付的点云（`map.pcd`），那三格从地面 **0 m 到 2.5 m 铺满了点** —— 那是一个**竖直的实体面**
   （墙 / 门框 / 门扇，或者一块参数上看不清的东西）。
5. 但**同一排**里还有别的格子：1229 帧里 **549 帧有激光穿过、0 个回波**（`tools/diagnose_door.py`）。
   ⇒ 那一条线是"实体格 + 透光的洞"**混着**的，几个零星的实体格就能把一条本来透光的线缝成一堵墙
   （障碍层是 4-连通，一格宽就够）。
6. **量化的结论**（`tools/diagnose_bottleneck.py`）：从客厅走到任何一个房间，
   能通过的**最大圆的直径 = 0.00 m**。0.00 m 的意思是"连 1 cm 的球都过不去" ——
   所以**调机器人半径、调闭运算核一点用都没有**（这是拓扑问题，不是参数问题）。
7. **为什么会有那些零星实体格**：机器人确实贴着那面墙开过（最近 0.6 m，82 帧在 3 m 内），
   但墙在它的方位 **−55° ~ −140°**，相机水平视场只有 **±57°** —— **相机几乎全程没看到那面墙**。
   地图对那面墙的了解全部来自激光的掠射回波，而掠射时门洞边缘容易出幽灵回波。
8. ⇒ **该改的是"去看"，不是"多走"**：把"又薄又连贯、两侧都是已知地板的障碍线"
   当成一个**待确认目标**，转过去用相机看一眼（一个独立的 frontier 类别，
   优先级低于"没走过的地板"、高于"绕圈"）。**这一条还没做。**

## 4. ④ 真实侧灰斑：**我给你的那张对比图是错的**

### 4.1 那张图错在哪（`out/ab_perception/real_grey_before_after.png`，生成脚本 `out/_grey_ab.py`）

1. 右边标着 "AFTER" 的那张**不是交付的地图**——它是**当轮被否决的**"3×3/2×2 开运算"实验的离线结果；
2. 而且它用的是 **2×2 结构元**，就是"偶数核 OpenCV 锚点偏心"那个已经查出来的坑；
3. 两边都是**重放**（`ground_real` / `ground_real_new`），而重放和真正那一跑
   在 `ground` 上差 10%（见 §4.4）。

所以 boss 从那张图上读到的"内部灰斑变多了"——**图没错，图是错的**。这个锅是我的。

### 4.2 boss 问的"你消除的那圈灰"是什么：**只看得见天花板的格子**

旧规则里**任何**回波落进一格就把它标成"看过"。天花板、墙头这些 **2 m 以上**的回波，
对**它下面的地板**什么都没说，但旧规则照样把那一格涂成灰 —— 于是走道两侧、房子外围
出现一圈灰边。新规则要求"回波 ≤ 2 m 才有资格说'我看过这里的地板'"。

真实侧实测：**"只有 >2 m 回波"的灰 92.4 m² → 5.7 m²**。
在图上就是**顶部那条橙色带**和左右两侧的橙色（`real_grey_abc.png` 的 A 图，
橙色 = `cause == ceiling-only`）。**它们从来不是地板、也不是障碍**，
把它们画成灰只是让"能走的地方"看起来被一圈障碍围起来了。

### 4.3 内部的灰斑：确实略有增加，原因是同一轮的另一处改动

用**同一把尺子**（同一份重放、同一采集，只换规则）：

| | 旧规则 | 新规则 |
|---|---|---|
| 绿 | 395.4 m² | 429.6 m² |
| 针孔（被绿包围的灰格） | 281 | **300** |
| 口袋（被绿完全包住的灰连通块） | 120 个 / 10.1 m² | **179 个 / 10.8 m²** |

原因不是 `seen_mask`，是同一轮的 `OBSTACLE_MIN_VOTES 1 → 2`：
"只有 1 帧证据"的障碍格不再算障碍 ⇒ **约 34 m² 的地板被还了回来** ⇒ 地毯变大 ⇒
里面的洞的**绝对个数**跟着变多。**是换了更大的地毯，不是地毯更破了。**

### 4.4 仪器：为什么"重放说会变好、交付却变差 4 倍"

上一轮说"重放报 300、交付产物报 1388，差 4 倍，原因未知"。这一轮查清了：

**(a) 重放少了去斜。** 管线里 `cloud = deskewer.apply(fr.cloud, fr.t_offset)`，
但 `dump_frame` 存的是 **`fr.cloud`（未去斜的原始点云）**，而 `diagnose_ground.py`
直接拿它用。真实数据集一帧扫 0.094 s 且机器人在动 ⇒ 两份点云不是一份。
已修（`--config` 传去斜参数），修完：绿 429.6 → **422.2 m²**、针孔 300 → 332。

**(b) 补上去斜仍然差 40 m² 的绿地。** 逐格比对交付栅格 vs 重放栅格：

| | 交付 | 重放（已去斜） | IoU |
|---|---|---|---|
| `seen` | 682 m² | 683 m² | **0.981** |
| `obstacle` | 241 m² | 246 m² | 0.946 |
| `ground` | **382 m²** | **422 m²** | **0.858** |

`seen` 几乎一样、`obstacle` 几乎一样，差的全在 `ground`（差 51 m²，分布在离轨迹
p50 2.2 m 的地方）。而 `ground_mask = |h| < 0.10 + 0.035r`，`h` 在**传感器系**里算，
所以差异只能来自**点云本身**——重放用 `frames.csv` 的 `(x, y, yaw)` 拼一个平面位姿去去斜，
而那一跑用的是里程计的**完整 SE(3)**（含俯仰/横滚），两者差 ≈ 0.07 m，
和地面容差 ≈ 0.20 m **同量级**。⇒ **采集里没有完整位姿，重放就不可能复刻那一跑的 `ground`。**

**（c）结论（这条比那个改动值钱）：**
- **"针孔"本身是个不稳定的统计量**——格子差 10%，它的读数就差 4 倍。所以
  "上一版 300 / 这一版 1388" 这个对比**本身没有意义**，我当时不该用它下任何结论。
  本轮给 `diagnose_ground.py` 加了一个**拓扑口径** `pockets`（被绿完全包住的灰连通块），
  它对边界抖动更稳，而且它才是人眼看到的东西（"在绿地里"而不是"在绿地的边上"）。
- **固定轨迹重放只能验证与轨迹无关的改动**（v6 已写）；现在再加一条：
  **重放也不能用来量交付地图的灰斑**（因为它复刻不出 `ground`）。
  ⇒ 以后要量"交付地图的灰斑"，用**交付产物自己的 `--dump-grids`**。

### 4.5 为此做的加固（`--dump-grids` 变成自描述）

`dump_grids` 原来只写 `ground / obstacle / seen`，而 `ground = ground_ever & ~obstacle`
是**推导量** ⇒ 拿到产物也无法问"换一条障碍层规则会怎样"，因为产生它的证据
（`_obs_votes`）和独立的地板证据（`ground_ever`）都没了。现在一并写出：

```
ground, obstacle, seen, ground_ever, obstacle_votes, obstacle_now, traj
meta: resolution/extent/n/source/pose_xy/obstacle_min_votes/obstacle_open_px/arrays
```
⇒ **交付的那一跑从此自己就是仪器。** （顺带修掉我这轮引入的一处 `NameError`：
`dump_grids` 用了 `OBSTACLE_MIN_VOTES` 但没 import。）

### 4.6 交付产物上的当前真实侧读数（`grids_real_final`）

绿 **382.16 m²**、绿块 607 个（其中 ≤5 格的 503 个）、
**口袋 701 个 / 30.95 m²**（最大的一个 216 格 = 2.16 m²）、
针孔 1388 格（**这个数不要再引用**，见 §4.4(c)）。

## 8.1 ① 定位算法：六步，以及"取框中心"这个方案**实测更差**

### 算法（每帧、每个框）

```
1. points_in_box      取所有投影落在框内的激光点（LiDAR 系），pad=2 px 先对称缩小一点
2. is_floor 剔除地面   ← 关键一步：框的下边缘常把"人脚前方更近的地板"包进来
3. to_camera_frame    转到相机系，用「到相机中心的距离」当深度
4. near_group         按深度排序，在**第一个大间隙**处切开 ⇒ 只留最近那一组（解决遮挡）
5. voxel_components   在这一组里取**最大的 3D 连通块**
6. 位置 = 该连通块各轴中位数，再转回世界系
```

### 为什么不是"取框中心附近的点"

**这个方案已经在代码里了**：`points_in_box(pad=负数)` 就是围绕框中心对称缩小。
`pad` 是像素，所以"只取中心的点"= 把 pad 调大。实测（同一采集、同一检测器、只改 pad）：

| pad | 接受框 | 真/虚 | **精度** | n_sel 中位 | 位置误差 p50 |
|---|---|---|---|---|---|
| **2（现行）** | 433 | 192 / 241 | **44%** | 30 | 1.90 m |
| 12 | 562 | 179 / **383** | **32%** | 41 | 1.88 m |
| 24 | 744 | 177 / **567** | **24%** | 41 | 1.86 m |

**缩小取点范围让精度从 44% 掉到 24%，位置精度一点没变好**，而且原因是可以讲清的：
框变小 ⇒ 选中的簇变小 ⇒ `width_lat` 变小 ⇒ **而 `width_lat` 正是尺寸门限的"充分条件"** ——
于是墙上的虚多更容易过关。**"取少一点"在这里不是更保守，是更松。**

另外两条：
- **中心先验假设"目标居中且凸"**。我们最大的失败模式是"墙被当成人"，墙**也是填满中心的**，
  所以中心先验对这种虚多没有任何鉴别力。
- **固定像素半径没有距离概念**：20 px 在 2 m 处是 10 cm，在 20 m 处是 2 m。
  要按米取中心得先知道深度，而深度正是这一步要估的东西 —— 鸡生蛋。
  现在的做法绕开了这个：**先用地板剔除 + 深度间隙把深度估出来，再选块**。

⇒ 结论：**不改**。真正该做的是 §2.3 那条（域差），以及本轮已经做的"必要框高窗口"。

## 8.4 ③b 人走过的灰迹：**确认是真 bug，已修，效果很大**

boss 的判断是对的，而且比"会不会挡路"更严重。机制：

```
_obs_votes[cell] += 1          # 每一帧有回波落在 0.35-2.0 m 带里就 +1
obstacle = votes >= 2          # 单调、只增不减 ⇒ 一旦 2 票，永久是障碍
ground   = ground_ever & ~obstacle   # ⇒ 那块地板就永久消失了
```

物体掩码只救得回"**被成功检测并融合**"的那些帧 —— 而这是少数
（仿真 1227 个人框里只有 214 个落在真人身上）。**所以一个人走过，就在地图上留下一条永久的灰带。**

### 修法：最新一次证据是地板 ⇒ 解除；但**强证据的结构永不解封**

```python
OBSTACLE_RELEASE_FRAMES = 2      # worldmap.py
# 每格记一个计数器：自从上一次"这格有障碍证据"以来，有多少帧看到过地板
# 帧内顺序：先记地板，再记障碍并清零（同一帧两者都有 ⇒ 算障碍）
released = (_ground_after >= OBSTACLE_RELEASE_FRAMES) & (_obs_votes < OBSTACLE_STRONG_VOTES)
obstacle = (votes >= OBSTACLE_MIN_VOTES) & ~released
```

- 走开的人：脚迹格拿到地板回波 ⇒ 计数器涨 ⇒ 放行；
- 墙 / 椅子 / 门框端面：**永远没有地板回波落在同一格** ⇒ 计数器恒为 0 ⇒ 永久保留；
- 强证据（≥12 帧）一律豁免 ⇒ 真结构根本进不了这条路径；
- **安全层不受影响**：`blocked() = obstacle | obstacle_now`，机器人在看的墙当场仍然挡。

# 第十三轮 —— 第一次 A/B **是回归**，已定位并修正

## 13.1 如实记：`run_v12.sh sim` 把"覆盖"做差了

| 指标 | v11（改前） | **v12（第一版）** |
|---|---|---|
| 帧 / 时长 | 1163 / 232.4 s | 1192 / 238.3 s |
| 路程 | 102.2 m | **70.4 m** |
| 轨迹 bbox | 17.4 × 13.7 m | **9.9 × 9.8 m** |
| 绿 | 246.8 m² | **186.0 m²** |
| **到过的可达格** | **86.4 m²（46%）** | **45.5 m²（32%）** |
| 内部洞 ≥0.5 m² 合计 | 4.92 m² | **2.86 m²** ← 这一项确实好了 |

**原因在目标序列里**：v12 的 **7 个目标里 6 个是 shadow**，第 26→663 帧（**53% 的跑程**）
全在右半边追洞，**从没进过左上/左下两个房间**（轨迹 x 只到 −3.8，v11 到 −11.5）。
阴影机制本身有效（内部洞 4.92 → 2.86 m²），但它把整跑劫持了。

**根因是结构性的**：地图每长大一点就产生新的"内部洞"（新看见的家具都投下新鲜阴影）
⇒ "无条件优先处理盲点" = 停下探索、绕着刚测绘完的那间房的家具转圈 ——
正是 `sweep` 当初要取代的行为。

## 13.2 三处修正

1. **`shadow_near_m = 2.0`：只有"开过去过、却还是看不见"的洞才算盲点。**
   用 `_fresh_depth`（每格到最近 visited 格的距离）判定。实测：真盲点距轨迹 **0.43 m**、
   v12 那些临时洞 **3–6 m**。★ 上线前在 v11 栅格上按轨迹长度预演：150/300 帧时洞
   被拒绝，600 帧起才够格并选出正对洞的位姿 —— **这才敢再跑**。
2. **阴影决策移到 sweep 之前**：第一版让阴影覆盖 sweep 的答案，而被丢弃的
   `_pick_sweep_target` **提交斑块是副作用** ⇒ 症状是 `sweep_targets=2` 却有
   `locks=2 / releases=1`。现在阴影赢了就根本不调用 sweep 选择器。
3. **测试夹具修正**：`WorldMap.add()` 会把传入的 pose 写进 `traj`，而夹具的 pose 是原点、
   正好在洞里 ⇒ "到 visited 的距离"恒为 0、负例形同虚设。
