## 1. 你要做的三件事

### 1.1 第一件：`robot_radius` 0.19 → 0.30

**现状**

| | |
|---|---|
| 默认值 | `r2slam/explore.py:86` → `robot_radius: float = 0.19` |
| 消费处 | `explore.py:1314` `self.planner = PathPlanner(robot_radius=float(robot_radius), ...)` |
| | `explore.py:1324` `self.fuse_planner = PathPlanner(...)`（同上） |
| 下游默认 | `r2slam/nav.py:433` `PathPlanner.__init__(robot_radius: float = 0.25, ...)`（**被上一行覆盖，实际不生效**） |

**为什么是 0.30 —— 实测，不是估计**

仿真车是 **KUKA youBot**（`/root/.gazebo/models/youbot/`），底盘碰撞体是
`meshes/base/base_convex.stl`。直接读该 STL 的顶点：

```
verts 1146   x[−0.286, 0.284]   y[−0.178, 0.179]   z[−0.068, 0.021]
half-length 0.285   half-width 0.178   max horizontal radius 0.292
```

* `0.19` ≈ **半宽**（内切圆）—— 这是"车只是一个点宽"的假设；
* 而 `PathPlanner` 的腐蚀是**圆盘**（`nav.py:443` 注释：*a cell centre is drivable iff
  a disc of `robot_radius` centred there touches no obstacle cell*），
  用圆盘就该取**外接圆 0.292**。

⇒ 参数与模型不一致，差 **0.10 m**。`0.30` = 外接圆 + 一点余量。

**⚠️ 但不要指望它治好这次的卡住 —— 这一点必须交代清楚**

在同一张最终地图上复算（起始 `(−5.94,−3.01)`、目标 `(−12.2,−4.2)`）：

```
r=0.19  path 10.02 m  free cells 17868
r=0.25  path 10.14 m  free cells 17647
r=0.30  path 10.50 m  free cells 16061   ← 路径没有改道
r=0.35  path 10.50 m  free cells 16061
```

**路径只是从 `x=−5.5` 平移到 `x=−5.4`**。再用 youBot 的真实矩形外廓
（`0.57 × 0.356 m`，沿路径按行进方向摆放）扫过整条路径，对**累计障碍层** `obstacle` 做碰撞检测：
`r = 0.19 / 0.25 / 0.30 / 0.34` **全部干净**。

⇒ **`robot_radius` 是一个真实的参数错误，值得修（真实侧尤其），但它不是本次卡住的原因。**
把它当成"顺手修正"来做，并**用它顺便验证下面 §1.2 的判据统一**。

**改哪里 —— 注意有第二份副本**

1. `explore.py:86` 默认值 `0.19 → 0.30`。
2. ★ **`tools/online_pipeline.py:1704` 有一份硬编码的副本**：
   ```python
   reach_radius = 0.19            # FrontierExplorer's default robot radius
   ```
   它被用来算 `summary["reach"]` 里的 `robot_radius_m` / `drivable_area_m2` /
   `reachable_area_m2` / `stranded_green_m2`。**只改 `explore.py` 会让
   "报告里的可达面积"与"规划器实际用的半径"描述两个不同的机器人** ——
   这违反 §6 第 2 条。两处必须一起改，且最好是**只留一处真相源**
   （把 `FrontierExplorer` 的实际半径暴露出来，让报告读它）。
3. **先别改默认值**，加一个 CLI/配置项（形如 `--robot-radius`），默认仍是 `0.19`，
   这样默认路径逐位不变（见 §5 的 Gate −1）。`FrontierExplorer` 目前是在
   `online_pipeline.py:944` 用 `v_max/w_max/sweep/**_ovr` 构造的，**不传 `robot_radius`**，
   所以要走 `_ovr` 或显式加参数。
4. A/B 通过后再翻默认。

**⚠️ 顺手要修一句过时的注释**

`tools/online_pipeline.py:1694–1701` 写着：

```
# NOTE: the *radius* is a no-op as things stand -- `free_space` quantises the
# erosion kernel with `round(2*r/res)|1`, so 0.19 and 0.22 both give 5x5, and
# the only radius that moves anything is <= 0.15 (3x3, ...)
```

**这在 `--footprint disc`（现役默认）下已不成立。** 实测（同一张最终地图，
`PathPlanner(robot_radius=r, footprint="disc")` 的 `free_space` 格数）：

```
r=0.19 → 17868     r=0.25 → 17647     r=0.30 → 16061
```

半径**确实**在改变 `free_space`。那句注释描述的是方核时代的行为，
`disc` 核按 `res·hypot(max(|a|−0.5,0), max(|b|−0.5,0)) < r` 逐格生成（见 `nav.py:443` 起），
不经过 `(2k+1)²` 的量化。**改默认值时要连这句注释一起改掉**，否则下一个人又被它误导。

**风险：这条会影响真实侧。** `explore.py` 是两源共用，真实走廊可能更窄。
**真实侧一旦无路可走，探索会整体退化。** 所以：

* Gate 必须包含**真实侧全跑**，比对 `map.pcd` md5、可通行面积、障碍格数（见 §5）；
* 若真实侧变化不可接受，退路是"只给仿真侧传 0.30"——但那会引入
  `if sim` 分支，**违反 §6 的第一条不变量**，所以更应该是"让真实侧的
  `source` 配置显式声明车体半径"。

### 1.2 第二件：把"可不可走"统一成一份实现

**现状：同一个问题，代码里有四处、两种口径。**

| 使用处 | 判据 | 未知格算 | 含本帧回波 |
|---|---|---|---|
| `nav.py:529` `PathPlanner.free_space`（A\* 用） | `wmap.ground` = `ground_ever & ~obstacle` | 不可走 | 否 |
| `explore.py:4997` `_ahead_clear`（油门判前方） | `wmap.blocked()` = `obstacle \| obstacle_now`（`worldmap.py:979`） | 可走 | **是** |
| `explore.py:4923` `_lookahead` 的 LOS | `wmap.ground`（`los_grid="floor"`） | 不可走 | 否 |
| `explore.py:4984` `_clear`（决定能否跳过 A\*） | `wmap.blocked()` | **可走** | 是 |

**已知的两个后果**

1. **`_lookahead` 与 `_ahead_clear` 会互相打架**：车朝一个"地图上可走"的点走，
   而这一帧的原始回波落在前方 ⇒ 油门立刻判死 ⇒ `backoff`。**这就是摇摆的入口。**
   `obstacle_now` 是单帧原始回波，而官方仿真器第三个坑（顶墙时 LiDAR 原点落进墙体碰撞体）
   会让它周期性变脏。
2. **`_clear` 把未知当可走** ⇒ 对远处目标"直线可达"几乎恒为真 ⇒ 车不走 A\*。
   复算证据：按记录的地图 `_clear(0.68,−0.73 → −12.2,−4.2) = False`；
   把西边的墙按"车当时还没看到"抹掉 ⇒ **`True`**。
   ⚠️ **但它不是本次卡住的原因**：`summary["explore"]["frames_routed"] = 1410 / 1436`，
   98% 的帧都处于"有路径"状态。这一条按"已确认缺陷"处理，不当作本轮修复目标。

**推荐做法（最小、单变量、可 A/B）**

**只改一处：`_ahead_clear` 去掉 `obstacle_now`，改用 `obstacle`。**

```python
# explore.py:4997 附近
def _ahead_clear(self, wmap, x, y, yaw) -> bool:
    ...
    # 现状
    return not bool(wmap.blocked()[cy[known], cx[known]].any())
    # 改为：只看确认过的障碍层，去掉本帧原始回波
    return not bool(wmap.obstacle[cy[known], cx[known]].any())
```

理由：这样"前方有没有障碍"与 A\* 的 `free_space` 出自**同一个 `obstacle` 数组**，
而"未知算可走"的约定（远方探索需要）被保留。**单变量、语义清晰。**

⚠️ **不要**把 `_ahead_clear` 改成走 `free_space` —— 那会让车在**未知区边缘**判"前方不可走"，
**很可能不敢进未知区**，直接打掉探索。这是一个真实的、很容易踩的坑。

⚠️ `_clear`（`explore.py:5563` 的 `if not self._clear(...)`）**留给下一步**，
一次只改一个变量。它改成什么取决于 A/B 结果。

**Gate**：默认关时决策列 md5 逐位不变（`robust` 见 §5）；开启后仿真**闭环**跑
（不能只 replay —— replay 无墙钟预算）。

### 1.3 第三件：卡住时"重新对准路径"，替代左右交替后退

**现状**

```python
# explore.py:5663 / 5667 / 5719
self._backoff = self.backoff_frames
self._backoff_sign = -self._backoff_sign      # ← 每次 backoff 翻转转向
self.n_backoffs += 1
```

`backoff` 期间 `v = −v_max * 0.45`、`w = ±0.49`（`explore.py:5700` 起）。
**符号每次翻转** ⇒ 在夹角几何里变成"进一步退一步、左一下右一下"，永远转不出去。

实测：`out_sim_final` 在 `(−6.0, −3.5)` **摇摆 21.7 秒**（`t=264.9 … 286.5`），
三个最大 `ahead_clear=False` 集群共 60 帧都挤在这里，`|w|` 均值 0.55–0.68。
`summary` 里 `backoffs 17`（对照跑 5）、`wedge_frames 53`（对照跑 18）。

**要改成什么**

卡住时不翻转符号，而是**朝"让 `aim` 方向变可行"的一侧**持续转。最小实现：

```python
# 卡住时：不要翻转，改成朝当前 heading error 的符号转
self._backoff = self.backoff_frames
self._backoff_sign = 1.0 if err > 0 else -1.0
```

更完整的版本（如果 A/B 支持）：后退时**把 `aim` 重设为"路径上离车最近、且在视线内的航点"**，
而不是继续指向远处目标（`self._target`）。当前 `backoff` 分支不重算 `aim`，
所以车一边后退一边还朝着撞墙的方向。

**风险**：这条改的是**所有跑**的脱困行为，方差极大（见 §8 的 `traj_xmin` 分布）。
**必须闭环、n ≥ 3 臂，比 `traj_xmin` / `arrivals` / 单次最长卡住时长。**
`stats` 里 `wedge_frames` 与 `backoffs` 是现成的观测量。

## 2. 为什么是这三件（证据速览）

完整推导见 `docs/仿真退化归因_第二轮_航向跳变与擦墙路径_20261010.md`。这里只留结论：

1. **不是代码回归。** 同一份代码当晚两跑 `traj_xmin` **−6.60 vs −12.00**；
   把坏的那跑放进 44 个留了 `frames.csv` 的归档跑里，`ahead_clear`-False 占比 **11.1%**
   （全场中位 10.7%）、spin、末段位移**全是中游** ⇒ 唯一离群量是 `xmin`。
2. **直接原因是航向跳变。** 两跑的帧间航向跳变 (>30°) **都是 28 次**，
   差别在"被打偏后恢复得快不快"：`|hdg_err|>30°` 的帧占比 **21.7% vs 12.7%**。
   `yaw_odom_deg` 全程恒为 **−0.8°**，等于没在提供信息。根因是官方仿真器第一个坑
   （LiDAR 不随车体旋转 ⇒ 航向不可观测）。
   实测片段：`t=249.6` 单帧 `hdg_err = −104.9°`，紧接着车朝 −166° 走，
   而 A\* 要它朝 −86°（正南）。
3. **两个放大它的结构缺陷**：§1.2 的判据不一致（摇摆的入口）、
   §1.3 的左右交替后退（摇摆出不来的原因）。
4. **`robot_radius` 是相关的参数错误但不是本次原因**，见 §1.1 的复算。

### 4.1 数据流 —— 三处改动分别在这条链的哪里（改前先看这张图）

```

相机图像  ──┼─→ frames.py ──→ online_pipeline.py 主循环（每帧）
```

③`backoff` 的转向符号。**改 ①会影响 A\* 的整张可走图（波及所有目标选择）**；
