### 2.1 顺带量出来的第二个量：`park_n`

`ref_band.py` 同时算 `park_n` ＝**最长的一段连续采样全部落在同一个 5 cm 方格内**（`traj.npy` 的采样间
≈0.29 s）。它直接就是"停住不动"的度量，不需要任何阈值判据：

| 群体 | `park_n` |
|---|---|
| 健康跑（`xmin` ≤ −11） | **10 – 25** |
| 退化跑（`b3profr1` `xmin −2.37`） | 497 |
| 退化跑（`b3l_ON_r3` `xmin −5.95`） | 656 |

⇒ 健康带 10–25、退化带 100–656，**中间有 4 倍空档**。这比 `backoffs`/`wedge_frames` 干净得多
（后者同码两跑就是 17 vs 5 / 53 vs 18，离散度盖过臂间差）。

⚠️ `park_n` 与 `xmin` **不是同一件事**：`b3l_OFF_r3` `park_n=154` 却 `xmin −10.37`（正常）。
这与第二轮归因的结论一致 —— **"卡住"与"探得少"无因果**。所以两个量要分开报，不能只报一个。

## 4. 对照与归因规则（这一条比判据本身重要）

故障是**间歇性**的：同一份代码两次归档跑 `xmin` 分别是 **−6.60 与 −12.00**。

⇒ 所以：

1. 本批每臂都带一个 **`r19` 对照臂**（`--robot-radius 0.19`，即改动前的行为），
   **同一容器、同一会话、背靠背** 跑。跨会话/跨归档比较是抽签。
2. **只有 `r19` 在本会话里呈现退化（A 或 B 不过），才能把 `r25`/`all` 的健康说成"修好了"。**
3. 若 `r19` 自己也健康 ⇒ **正确结论是"本会话没复现该故障"，不是"修好了"。**
   这时能说的上限是"当前默认在 3/3 跑里表现正常"。
4. 若 `r25` 与 `r19` 都健康、只有 `all` 不健康 ⇒ 说明 §1.2/§1.3 有反作用，要单独归因。

## 5. 本批配置（冻结）

| 项 | 值 |
|---|---|
| 臂 | `r19`（`--robot-radius 0.19`）、`r25`（默认，＝0.25）、`all`（0.25 + `ahead_clear_use_obstacle_now=False` + `backoff_realign=True`） |
| 每臂次数 | 3（共 9 跑，串行） |
| 预算 | **`--sim-duration 270`（传感器时间，按 `stamp` 跨度停）**，墙钟上限 900 s 仅作保险 |
| 有效性门 | `rc==0` 且 `frames.csv` 跨度 ≥ 0.97 × 270 = **261.9 s** |
| 运行器 | `_tmp_gate/run_n3.sh`；状态 `_tmp_gate/batch_n3_status.txt`；每跑一份日志 `run_<tag>.log` |
| 判读脚本 | `_tmp_gate/ref_band.py`（几何）＋ `r2slam/out/_room_cover2.py`（覆盖，唯一权威口径） |

**为什么改成 `--sim-duration`**：`--duration` 是墙钟，RTF 差的臂在同样预算里少跑房子，
会因为与改动无关的原因显得更差。这是本项目自己总结过的规矩（技能里的
"`--duration` 是墙钟秒、仿真时长不受控 / harness 应按仿真时长配平"）。
270 s 对齐归档 400 s 墙钟跑实际达到的跨度（269–272 s）。

## 6. 我会被判错的写法

如果 `r19` 对照臂在 3/3 跑里都健康（`xmin ≤ −9.80`、`park_n ≤ 60`），
那么**本批对"§1 修好了探索能力"这句话没有信息量**，我不会把它写成"修好了"。

### 7.5 对 §2 机制链的两处更正（**在归档 `final` 的 `frames.csv` 上复算**，21:35）

复算的是 `out_sim_final/frames.csv`（1436 帧 / span 287.1 s，`xmin −6.60` —— 与 §2 引的是同一次跑）。

**（1）"t=249.6 航向单帧跳变 −104.9°"不在数据里。**
三个航向列的单帧最大变化：真值 `truth_yaw_deg` **17.8°**、里程计 `yaw_deg` **10.5°**、
`yaw_odom_deg` **5.0°**；>60° 的帧 **0 个**（`final`/`seg`/`base` 都是 0）。
真正跳的是**目标方位角**：t=248.6→248.8 目标从 `(1.35, −0.85)`（方位 −13.4°）
切到 `(−12.25, −4.15)`（方位 −165.2°），**一帧变 151.8°**，状态 `drive → turn`。
随后小车**原地平滑地转了约 2.6 s**（−45° → −176°），到 t=251.2 转回 `drive`。

⇒ **"航向跳变"这个说法不成立；成立的是"目标切换导致方位角大跳、随后一次正常的原地转向"。**
一次 2.6 s 的原地转向是状态机该做的事，不是故障。
（§2 里的 −104.9° 我复现不出来，**不知道它是怎么算出来的** —— 按本项目规矩，
引用前先看它算的是什么；这次就是没看。）

**（2）`final` 的真实退化形态：`x ≈ −6.5` 处的一个极限环。**
t≈262 起，小车在 (−6.5, −3.1) 附近反复：`drive`（v=+0.55，往西）→ `backoff`（v=−0.25）
→ **偏航符号来回翻** → `arc`（v=+0.22）→ 又 `drive` → 又 `backoff`……
到 t=287 墙钟耗尽，25 s 里往西的**净推进接近零**。

⇒ 这里 `backoff` 确实在**每次翻转转向符号**（t 265.9–266.9 偏航在升，t 267.1–268.9 在降，
来回两次）—— **§1.3 冲的现象是真的、可复现的**。
⇒ 但它是"边动边打转"，不是"停住不动"，所以 `park_n`/停滞判据看不见它，只有 `xmin` 看得见。

**（3）顺带：§1.1（半径）的杠杆量级**
用规划器自己的 `PathPlanner.free_space` 在归档地图上重算（`_tmp_gate/freespace_pathcheck.py`，
零方差）：把 `robot_radius` 从 0.19 换到 0.25，"小车**自己走过的路径**仍落在可走格里的比例"
变化 **≤0.02**（健康臂 0.68–0.87 → 0.67–0.86），可走格总数变化约 **1–2%**。
⇒ **§1.1 只能挪动 1–2% 的可走面积，不可能把 `xmin` 从 −6.6 变成 −12。**
它的真实作用只是"别让规划器花掉 0.25 m 间隙里的零余量"，是个**保守化**，不是修复。
（与 `robot_radius` 在 0.19 与 0.25 下腐蚀核几乎相同这一已知事实一致。）
