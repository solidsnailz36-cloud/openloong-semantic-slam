## 1. V / P1：叠字

### 1.1 主因不是行距

`full5_cv/frames/000304.png` 放大后看得清楚：四行 HUD 之间其实没压字，**真正叠在一起的是相机面板自己的 `note`**——
`annotate()` 把 `detected 2 -> localised 2` 画在 `(8, 22)`，而 sheet 上的 HUD 底板从 `(8, 8)` 起、高 86 px：

```
实测 getTextSize(scale 0.5)：每行 h = 14，底板 4 行 = 8+86 = 94 px 高
note 在 y = 10..22   ← 完全落在底板矩形内，被底板压暗、且和第一行 HUD 重叠
```

⇒ 所以"字号相同、行距等于字高"只是次要问题；**把两块文字画在同一区域**才是主因。第二处是两个人相邻时 `person 0.72` 与 `person 0.82` 起始 x 只差 15 px、标签宽 66 px ⇒ 必然互压。

### 1.2 改了什么

| 位置 | 改动 |
|---|---|
| `r2slam/viz.py::banner_size` | **新增**：底板像素尺寸的唯一来源。此前底板用一个公式算（`8*len(lines)` 每行）、文字用另一个公式画（`字高+4`），两者只是碰巧一致；想知道"底板多高"的调用方没有入口 |
| `viz.py::banner` | 尺寸改由 `banner_size` 给；行距改成字高的 0.42 倍（原来固定 4 px，字高 14 时太挤、字高 10 时又太松） |
| `viz.py::place_labels` | **新增**标签避让：同批标签按"就近上下取位"（`0, +1, -1, +2, -2…`）错开 |
| `viz.py::label_chip` / `ink_on` | **新增**实心标签片：底色 = 类别色，字色按亮度取黑/白 |
| `annotate()` | 先收集再批量放置标签；**`note` 挪到面板底部**（自带压暗条）；新增 `top_margin` |
| `HUD_ORIGIN` / `HUD_SCALE` | HUD 的位置与字号**成为常量**，画底板和算 `top_margin` 共用 |

★ 一处**我自己引入又修掉的** 6 px 误差：`top_margin` 最初只传了底板**高度**，而底板从 `y=8` 起，
所以被"夹到 `高度+2`"的标签顶端仍然压进底板 6 px。现在传的是 `HUD_ORIGIN[1] + banner_size(...)[1]`。

### 1.3 判据（按要求：看画面无压字）

- `r2slam/out/ovl3/frames/000304.png`（最终版）：两个人 `person 0.72` / `person 0.73` 各占一片、可读；
  `detected 2 -> localised 2` 在左下角独占一条；四行 HUD 全在底板内。证据裁图 `out/_peek/ovl2_two.png`。

  现在加上限 **0.70**（`th` 上限 2、note 上限 0.80）。**真实侧 `sc`=0.42，本来就低于上限，一行没变。**
  证据 `out/_peek/sim_overlay_check.png`。

### 1.4 自测：`r2slam/tools/test_overlay.py`（新增，20 项，全过）

判据都量在**渲染出来的像素**上，不是复述实现：

| 组 | 查什么 | 抓到的真问题 |
|---|---|---|
| 1 | 底板实际覆盖的矩形 == `banner_size` | 两个公式不一致这类 bug（实测 209×74 == 209×74；6 行时无一行出框） |

## 2. M3：可达域破碎

### 2.1 方法：工具早就写好了，只是没有 dump

`r2slam/tools/diagnose_reachability.py` 的文档串开头就是这个问题，而且它**已经会把两种可能分开**：
"raw 可走网格里本来是连着的 ⇒ 是我们的侵蚀把门口封了" vs "raw 里也断开 ⇒ 墙真的挡着"。
缺的只是一份 grid。

```bash
python3 tools/online_pipeline.py --config config/real_r2.yaml --npz out/real_cap_imu \
    --frames 1427 --voxel 0.50 --no-render --dump-grids out/reach_grids --out out/grid_run
python3 tools/diagnose_reachability.py --grids out/reach_grids --robot-radius 0.19 \
    --inspect 7.62,3.17 --map-figure ../out/_peek/stranded_map.png
```

★ **为什么必须带检测**：先跑了一版 `--no-detect` 的 dump，它的 `traversable_cells 54867`、
`obstacle_released_cells 3762`，而交付跑是 `54891` / `3540` —— **检测会参与障碍释放**，所以"关掉检测跑快一点"得到的
是**另一张地图**。tf.csv 倒是逐位相同（`264a562348e966cdb845a827c9ab38e6`），
所以对**只吃 tf 的 ATE** 用 `--no-detect` 是安全的，对**地图**不是。这条以前没人写下来。

### 2.2 面积分解（`--robot-radius 0.19`，与 `FrontierExplorer` 默认一致）

```
ground（地图说可走，绿）         548.9 m2
free_space（规划器肯走）         396.5 m2   ← 关闭 + 按半径侵蚀后
ground 但 !free（绿但不敢走）    156.0 m2   (28% 的绿)
机器人所在连通分量               392.7 m2
ground 在分量之外（够不着）      159.6 m2   ← 就是规范里那个 159.6
```

★ **先证明这份 dump 就是交付跑那一份**：`seen_cells 68215 / traversable 54891 / obstacle 11860 /
obstacle_released 3540 / points 253775 / trajectory 102.54 m / seen_not_classified 1464`
**逐项与 `out/full5_cv/summary.json` 相同**，`reachability` 字典**整体相同**（含 `stranded_green_m2 159.6`）。

### 2.3 分带 + 外壳检验：**159.6 m² 几乎全是外壳**

```
=== 够不着的地面：按块大小分带（全部 616 块，共 159.6 m2）===
    0.0–0.1  m2 :  526 块    10.79 m2  ( 6.8%)
    0.1–0.5  m2 :   53 块    10.49 m2  ( 6.6%)
    0.5–2.0  m2 :   25 块    21.06 m2  (13.2%)
    2.0–10.0 m2 :    8 块    39.15 m2  (24.5%)
   10.0–∞    m2 :    4 块    78.07 m2  (48.9%)
  距障碍 <= 0.20 m 的（= 安全半径外壳）: 157.8 m2  (98.9%)
  离障碍更远的（才是「另一个区域」）      :   1.8 m2  ( 1.1%)
```

★ 这张表里**必须同时看两行**：单看分带会得出错误结论 —— "4 块 ≥10 m² 共 78 m²"看起来像
四个大房间，其实是**贴着长墙的一条 2 格宽的外壳带**（面积大，但每一点都在障碍 0.20 m 内）。
**外壳检验才是判据，分带只是解释它为什么会长成那样。**

⇒ **机器人 0.19 m 半径 ⇒ 2 格（0.20 m）= 规划器必剥的安全边**。548.9 m² 绿地里剥掉 156.0 m²，
和 548.9 m² 的边界周长同量级。**这不是"区域"，是安全边本身。**

⚠️ 别把下面两节的数对不上当成矛盾：**"离障碍 >0.20 m 的只有 1.8 m²"和"唯一一块 ≥0.5 m² 的孤岛是 3.1 m²"
是两个不同的分解**（到障碍的距离 vs 连通块的大小）。1.8 < 3.1 正因为那块 3.1 m² 的孤岛**自己就贴着**
玻璃隔断和门框，其大部分本来就在障碍 0.20 m 之内，只有内部一小块离障碍更远。

### 2.4 唯一一块不是外壳的地面

```
id=8  3.1 m2  质心(7.71, 3.21)  x[6.5,9.0] y[1.8,4.2]  可走格 314
      ⇒ **raw 可走网格里本来是连着的 ⇒ 是我们的侵蚀把门口封了**
```

`--inspect 7.62,3.17` 的解剖（`+`=机器人分量 `.`=该块 `W`=绿但被侵蚀 `#`=障碍 `o`=看过空 `?`=没看过）：

```
最近一对 free 格：房内(x=677,y=617)  机器人侧(x=675,y=616)  间隔 0.22 m
沿线：.free > W绿但被侵蚀 > .free
```

⇒ 分界处是**一条 1 格（0.10 m）宽的绿带**，`W` 被安全半径吃掉，两侧的可走格相距 **0.22 m**。
**机器人体宽 0.38 m，过不去；但那不是墙。**

### 2.5 叠回画面

新增 `--project x,y`：把世界点投影回相机帧。★ 挑帧的规矩是**看得最清**，不是**靠得最近** ——
最近的接近发生在 3.24 m 处，而那时该点在**方位角 +92.9°**（正左方），132° HFOV 够不到，投影在像平面后方，
"最近"画出来的是一张空图。改成在**视野内**的帧里取距离最小者：

```
最近一次靠到 3.24 m，那时它在方位角 +92.9 deg ⇒ 当时不在画面里（车没朝它看）
整个序列里它落在相机视野内的帧：489 / 1427 (34.3%)
取看得最清的一帧：t=91.19 s（第 170 行，距离 3.59 m）
投影：高度 0.0–1.6 m 的竖线，全部 画面内
```

图 `out/_peek/stranded_on_frame.png`：红线落在那条**玻璃隔断后的房间**地面上（画面里能看到玻璃、
里面的桌子和黄色柜子）。⇒ **那块绿是 LiDAR 透过玻璃拿到的地面回波**，与走廊的绿只通过 1 格相接。

俯视图 `out/_peek/stranded_map.png`（绿=可达 橙=外壳 红=真区域 灰=障碍/未知）：
**绿是一整片**、橙是沿每个障碍的一条薄边、**红几乎不存在**，白圈那块 3.1 m² 被橙围住。

### 2.6 结论

**M3 不失分的理由**：规范要的是"多个区域及相连结构"，而我们的地图**本来就是相连的一整片**；
`stranded_green_m2` 不是"断掉的结构"，是**我们自己安全半径的几何**（98.9%）加一块 1.8 m² 的孤立地面。
⚠️ 也不能反过来说"覆盖率 100%"：规范 M3 自己写着"**不声称真值覆盖率**"，
而且这 1.8 m² 说明**存在 LiDAR 看得见、规划器到不了的地方**（玻璃后的房间）。

## 3. M5：直接优化 ATE

### 3.1 为什么是 `voxel_size`

`runtime.voxel_size` 是 KISS-ICP 的**地图体素**，也是本仓库自己记载的"唯一能动 p50 的旋钮"，
配置注释里已经有一对 A/B：**1.0 → 0.5 让 ATE 的 p90 从 0.680 降到 0.461、max 1.116 → 0.500**。
方向是"细一点更好"，那就往细里走，同时**留一个反向对照**（0.70）防止把非单调当成单调。

新增 `--voxel`（`default=None` ⇒ 不传就是配置里的值，逐位不变；日志与 summary 的 `runtime` 块都会记下它）。

### 3.2 曲线（1427 帧，唯一变量，`--npz out/real_cap_imu`）

| voxel | ATE p50 | ATE p90 | ATE max | RPE-1s p50 | p90 | max | 路径/厂商 | >0.30 m 的帧 | 最坏窗口占平方误差 |
|---|---|---|---|---|---|---|---|---|---|
| 0.70 | 0.205 | 0.312 | 0.418 | 0.039 | 0.086 | 0.411 | 1.068 | 215（15.1%） | 3.2%（t=107.4–109.0 s） |
| **0.50（现役）** | 0.276 | 0.461 | 0.500 | 0.041 | 0.080 | 0.256 | 1.039 | **598（41.9%）** | **56.2%**（t=74.7–111.5 s） |
| 0.35 | 0.329 | 0.538 | 0.587 | 0.032 | 0.062 | 0.340 | 1.020 | **864（60.6%）** | **60.4%**（t=74.7–119.8 s，45.1 s） |
| 0.30 | 0.154 | 0.286 | 0.381 | 0.028 | 0.060 | 0.228 | 1.028 | 92（6.5%） | 4.3% |
| **0.25** | **0.140** | **0.250** | **0.323** | **0.027** | **0.056** | 0.180 | 1.018 | **8（0.6%）** | **0.9%** |
| 0.20 | 0.207 | 0.295 | 0.357 | **0.027** | **0.056** | 0.162 | 1.013 | 105（7.4%） | 4.3% |
| 0.15 | 0.303 | 0.422 | 0.467 | 0.033 | 0.061 | **0.138** | **1.005** | 724（50.8%） | 49.2% |

**两个指标的"形状"不一样，这本身就是信息：**

* **1 秒 RPE 单调变好并饱和**（p50 0.041 → 0.027，−34%），**路径长度比单调趋近 1**（1.039 → 1.005）。
  这两条有清楚的机理：地图体素越细，局部配准越稳、尺度越准。
* **ATE 是锯齿状的**：0.205 → 0.276 → 0.329 → 0.154 → **0.140** → 0.207 → 0.303。
  **在一个锯齿曲线上挑最小值，等于在噪声上做选择。**

### 3.2b 为什么锯齿：**ATE 在这条序列上主要是"几段坏段"的计数**

新增 `tools/ate_tail.py`（按帧拆开对齐后的误差，问它集中在哪）：

| voxel | 平均误差 | 最差 5% 帧占平方误差 | 超过 0.30 m 的帧 | 最坏窗口 |
|---|---|---|---|---|
| 0.70 | 0.199 | — | 215（15.1%） | t=107.4–109.0 s，1.7 s，占 3.2% |
| 0.50 | 0.275 | 12.3% | 598（41.9%） | **t=74.7–111.5 s，36.7 s，占 56.2%** |
| 0.35 | 0.279 | — | **864（60.6%）** | **t=74.7–119.8 s，45.1 s，占 60.4%**（另有两段 12.3 s / 10.6 s 各占 10.3% / 7.0%） |
| 0.30 | 0.177 | 15.1% | 92（6.5%） | t=201.0–203.0 s，1.9 s，占 4.3% |
| **0.25** | 0.154 | 14.0% | **8（0.6%）** | t=113.4–113.7 s，0.3 s，占 0.9% |
| 0.20 | 0.199 | 10.6% | 105（7.4%） | t=210.8–213.6 s，2.8 s，占 4.3% |
| **0.15** | 0.275 | 11.3% | **724（50.8%）** | **t=74.7–111.4 s，36.7 s，占 49.2%**，另有 19.8 s 一段占 19.7% |

⇒ **同一段 36.7 s（t≈74.7–111.5）在 0.15 / 0.35 / 0.50 上都是主犯**（占 49% / 60% / 56%），
在 0.20 / 0.25 / 0.30 上几乎不存在；**结尾那 20 s（t≈193–213.6）在 0.15 / 0.30 / 0.20 上冒头**。
**体素决定哪几段锁错** ⇒ 这是一张"离散的坏段表"，不是一条平滑的质量曲线。
（**0.70** 是另一种失败模式：它**没有长坏段**（最坏 1.7 s），0.205 的 ATE 来自**普遍更糙**
—— 15.1% 的帧超阈但分散在各处。同一个 ATE 数值可以由**完全不同的两种原因**产生，
这也是为什么必须把它拆开看。）

**这条结论比"ATE 腰斩"重要**：ATE 在这条序列上不是平滑的质量函数，而是"**你有几个长坏段**"。
一段 36.7 s 就能占掉一半以上的平方误差。所以：
- **"0.25 的 ATE 最好"= 这一条序列上它一段都没栽**，**不等于**换一段录像它还最好 —— **这是本轮的诚实底线。**
- **真正有机理支撑、且与序列无关的是 RPE 与路径长度比**（§3.2 第 1 条）+ §3.4 的外部几何佐证。

### 3.3 代价（这一半不能省）

`ms_odom` 随体素变细**陡增**（第一批是在有其它任务并行的链里跑的，**绝对值被污染，只能看趋势**）：
10.5（0.70）→ 16.1（0.50）→ 25.9（0.35）→ **54.5（0.25）** ms。

⇒ 按本仓库自己的规矩（`ms_*` 只能比**背靠背、同一会话**的一对），单独补了**两对干净的**
（`--no-detect --no-render`，**只隔离里程计**，机器独占，两臂交替共跑四次）：

| 干净测量 | `ms_odom` p50 | p90 | max |
|---|---|---|---|
| **voxel 0.50（现役）** 第 1 次 / 第 2 次 | **15.3 / 15.0** | **26.0 / 26.6** | 64.7 / 65.4 |
| **voxel 0.25** 第 1 次 / 第 2 次 | **53.9 / 55.5** | **131.4 / 142.8** | 483.3 / 511.5 |
| 倍数（两对） | **×3.53 / ×3.71** | **×5.06 / ×5.37** | ×7.5 / ×7.8 |

★ **同级重复只差 2.0% / 3.1%** ⇒ 这个代价是可复现的，不是负载抖动。
**只里程计一项，p50 多 38.6–40.5 ms、p90 多 105–116 ms**。
p90 131–143 ms 意味着**单这一项就吃掉 5 Hz（200 ms）预算的 66–72%**，再叠加检测（~57 ms）就超了 ——
而**边缘算力是规则要求**（`docs/改进空间评估_20261009.md` 索引 6）。
⚠️ 另外 `ms_odom` 的 max 到 **483–512 ms** ⇒ 有 0.5 s 级的单帧尖峰，实时跑会在那里丢帧。

⇒ 换 0.25 就必须**同时**把 `render`（约 58.6 ms）移出关键路径 —— 那件事本仓库已经欠了两轮
（"新默认下全帧 `ms_total` p50 222 ms ＞ 200 ms 预算；扣掉 render 才 ~163 ms ⇒ render 必须在关键路径外，
**一直没做**"）。**两件事是一套的，单独换 0.25 会把预算弄爆。**

### 3.4 佐证：**用外部意见**（不是"再跑一遍"）

拿冠军 0.25 的**带检测**地图（`out/vox025_det/map.pcd`）与现役 0.50 的（`out/full5_cv/map.pcd`）
各走一遍 `tools/check_map_vs_official.py`，**同一个官方 pcd 当参照**：

| | **0.50（现役）** | **0.25** |
|---|---|---|
| 对齐 yaw | +2.00° | **+0.00°** |
| 对齐位移 | (−0.40, −0.50) m | **(−0.10, +0.00) m** |
| IoU | 0.634 | **0.641** |
| 点到官方表面 ≤0.1 m | 96.7% | **97.8%** |
| ≤0.2 m | 98.0% | **99.1%** |
| ≤0.5 m | 99.7% | **99.9%** |
| p99 | 0.400 m | **0.200 m** |

⇒ **0.25 建出来的地图，在一个完全无关的参照下也更好**：几乎不需要旋转（+0.00° vs +2.00°）、
平移小 4–5 倍、每一个距离门槛上的占比都更高、p99 尾巴减半。
**这就把"ATE 腰斩可能只是选择噪声"这一嫌疑压下去了** —— 内部指标和外部意见指向同一个方向。

⚠️ 两点诚实边界：① 对齐本身是从两张地图算出来的，所以"转得更少"是较弱的证据，
真正硬的是**对齐之后的距离分布**；② 这条尺子**不涉及位姿**，它证明的是"建出来的楼更对"，
**不能**替代 ATE / RPE（见 §4.2 的 caveat）。

### 3.5 结论

**按规范点名的第一个量（ATE）看，0.25 在这条序列上是明确更好的**：p50 0.276→0.140、
p90 0.461→0.250、超阈帧从 598 降到 8；1 秒 RPE 全面更低；路径长度比 1.039 → 1.018。
**它在"两段长坏段"里一段都没栽**（§3.2b），而且**外部佐证同向**（§3.4）。

**但要把两件事分开说：**

| 说法 | 可靠吗 |
|---|---|
| "0.25 在这条序列上 ATE 最好" | ✅ 可复现、机理清楚（坏段消失） |
| "换成 0.25 一般会更好" | ⚠️ **不成立** —— 哪几段坏随序列变，这是**在一条锯齿曲线上挑最小值** |
| "细体素让**局部**一致性更好" | ✅ 单调、有机理：RPE p50 0.041→0.027（−34%）、路径比趋近 1 |
| "0.25 的地图更贴**外部参照**" | ✅ §3.4，独立于 ATE |
| "0.25 不花钱" | ❌ **`ms_odom` p50 ×3.5、p90 ×5.1**，且 render 必须同时移出关键路径 |

**给 boss 的三个选项**（我不替你拍）：

1. **换 0.25 + 同时把 `render` 移出关键路径**（欠了两轮的活）—— 精度收益最大，工作量最大；
2. **换 0.30**（ATE p50 0.154，接近 0.25；超阈帧 92 vs 8）—— 代价略低，但**没有干净测过**，
   且 §3.2b 显示它在结尾那段仍栽 4.3%；
3. **保持 0.50 不动**，把 ATE 记成"已知的、参数可调的"——
   **注意：保持不变的代价也是真的**，即 41.9% 的帧超 0.30 m、ATE p50 0.276。

⚠️ 无论选哪个，**默认值现在仍是 0.50**（本轮没有改配置）——这是个需要明示的决策，不是可以顺手做的调整。

## 4. 真值口径

### 4.1 官方真值：没有（条件不成立）

官方答疑第 6 条原文：**「建图 pcd 文件以及 tf，真值不提供」**
（本仓库 `docs/官方答疑解读与r2数据集适配.md` 第 27 行的解读表里已登记）。
⇒ 规范 M5 要的"**选定真实序列**的 ATE / 1 秒 RPE / 时间覆盖率"**没有官方尺子可换**，
`docs/评分规范对照_20261010.md` §2 里那三条边界**继续成立**。

### 4.2 替代尺子：与官方 pcd 的几何一致（答疑自己点名的第三条）

答疑给出三个替代口径：pcd 自洽性 / tf 连续性 / **与官方 pcd 的几何一致**。前两条已有
（`package_submission.py` 的不变量、`compare_vendor.py` 的 dt 尾部），第三条以前**从没人做过**。
新工具 `tools/check_map_vs_official.py`（自查 PCD 头、SE(2) 对齐用 FFT 互相关求平移、最近距离用
`cv2.distanceTransform` ⇒ 不需要 `scipy`，出厂运行时能跑）：

```
ours     out/full5_cv/map.pcd                    253775 pts
official map_20260923_135649.pcd                2058552 pts
grid     903x545 @ 0.10 m   (90.2 x 54.4 m)
=== 对齐（SE(2)，只用两张地图自身）===
  粗搜 yaw +3.00 deg  shift (-0.40, -0.50) m
  精修 yaw +2.00 deg  shift (-0.40, -0.50) m
=== 重叠 ===
  我们占格 64914   官方占格 89999   重合 60084   IoU 0.634
=== 我们的点到官方地图最近表面（对齐后）===
  p50 0.000  p90 0.000  p99 0.400  max 0.800 m
  <= 0.1 m :  96.7%     <= 0.2 m : 98.0%     <= 0.5 m : 99.7%     <= 1.0 m : 100.0%
```

图 `out/_peek/map_vs_official.png`（绿=两者都有 红=只有我们 灰=只有官方）：
**绿覆盖了主体**，灰是没走到的外围，红是薄薄一圈。

⚠️ **这条尺子量的是几何，不是轨迹**：官方给的是**地图**不是**位姿**，所以它**不能**得出 ATE / RPE / 覆盖率，
报告里的 `caveat` 字段就是这么写的。它回答的是"**我们建的是不是同一栋楼、对不对得上**"，
以及"有没有整块结构丢掉或错位"。

### 4.3 一旦官方给出真值：要重测什么

一句话：`compare_vendor.py` 换掉参照物即可，其余口径不变。

```bash
# 现在（参照物 = 厂商里程计 /odin1/odometry_highfreq，仅作量级核对）
python3 tools/compare_vendor.py --bag <bag> --tf out/full5_cv/tf.csv --horizons 1,5 \
        --out out/full5_cv/m5_report.json
# 将来（参照物 = 官方真值）：同样三个量，尺子换了，⇒ 数字必须重出，不能沿用
```
要重出的三个数：**ATE（p50/p90/max）· 1 秒 RPE（p50/p90/max）· 时间覆盖率（跨度/频率/dt 尾部/对参照时刻的覆盖率）**。
