### A · 定位与传感器

**A1 · GNSS 与 GPS**

**是什么**：GNSS（Global Navigation Satellite System，全球导航卫星系统）是"卫星定位"的统称，
包含美国的 GPS、中国的北斗、俄罗斯的 GLONASS、欧洲的 Galileo。日常说"GPS"其实是用一个具体系统指代全体。

**为什么**：卫星不停广播"我是谁、我在哪、现在几点"，接收机测出信号传播时间 → 距离 → 用 4 颗以上的距离交会出位置。
纯卫星的**单点定位**精度约 3–10 m —— **远远不够**给地图当尺子。

→ **本项目里**：车上的 `/qx/evk` 话题就是 GNSS 接收机的输出。地图准不准，全靠它当参考。

**A2 · 差分定位 / 基准站 / 流动站**

**是什么**：在一个**坐标已知**的点上架一台接收机（叫**基准站**），它也算自己的位置，
拿"算出来的"减"已知的真值"= 此刻的定位误差，把这个**改正数**用无线电/网络实时播发出去；
附近的接收机（叫**流动站**）收到后拿它修正自己 → 误差大幅抵消。

**为什么**：定位误差主要来自电离层、对流层延迟和卫星钟差，这些误差在**几十公里范围内高度相似**，
所以一个地方测到的误差，可以给附近用。距离越远相关性越差 —— 这就是差分定位有**作用半径**的原因。
→ 本项目的 `/qx/evk` 是"能收差分"的接收机，差分数据由赛事方的基准站或网络播发提供。

**A3 · RTK（Real-Time Kinematic，实时动态差分定位）**

**是什么**：差分定位中的**最高精度档**，靠**载波相位**测量把精度从米级压到**厘米级**。

**为什么**：普通 GNSS 用的是**伪距** —— 测的是"码片"到达的时间，而民用 C/A 码一个码片约 300 m，
实际分辨率只有几米。RTK 改测**载波相位**：L1 载波频率 1575.42 MHz，波长约 **19 cm**，
相当于换了一把细得多的尺子，能读到波长的百分之几 → 毫米级测量噪声。
代价是载波相位有个**整周模糊度**问题（下面 A4），以及必须近距离差分（通常基线 < 10–20 km）。

→ **本项目里所有"精度"结论的唯一外部真值。** 没有它，我连"车在哪"都不知道，"地图准不准"就无从谈起。

**A4 · 固定解 / 浮点解 / 单点解**

**是什么**：RTK 解算质量的三个档位，判断依据是**整周模糊度解没解出来**。
- **固定解**（Fixed / RTK Fix）：整周模糊度被正确确定为**整数** → 精度 **±2 cm** 量级。最强。
- **浮点解**（Float）：模糊度还是实数估计（没固定住）→ 精度 **±0.2–0.5 m**。能用，但是降级。
- **单点解**（Single）：压根没用差分 → 米级。基本等于废值。

**为什么**："整周模糊度"是载波相位的固有麻烦：相位测量只告诉你"在波长的第 0.37 个周期"，
但不知道"这是第几百万个周期"。把那个整数猜对，才叫"固定"。

**在数据里怎么表示**：ROS 消息里用 `NavSatStatus` 这个字段承载它（`0 = 无解 / 1 = 单点 / 2 = 差分`）。
**注意它是"压缩过"的：固定解与浮点解都被塞进了同一个 `2`** —— 所以光看这个字段分不出来（坑 1-4）。

→ **本项目里**：这是第 4 章的主角。最阴险的坑（4-2）就是
**接收机报了"固定解"，但位置其实是错的** —— 传感器在它最自信的时候骗人。

**A5 · 协方差 / σ（标准差）**

**是什么**：协方差矩阵描述"这个位置解有多不确定"。`position_covariance` 是 3×3 矩阵，
对角线依次是 east / north / up 三个方向的**方差**（单位 m²）。`σ = √方差`，就是常说的标准差。

**记号小抄**：`cov_ee` / `cov_nn` / `cov_uu` 分别指 east / north / up 三个方向的**方差**
（`ee` = east×east、`nn` = north×north、`uu` = up×up，就是 3×3 矩阵的对角线），`σ = √方差`。

**为什么**：`σ_ee = 0.02 m`（2 cm）就是固定解的典型水平；`σ = 3.0 m` 说明解基本不可用。

→ **本项目里**：这是判"这一帧 RTK 能不能信"的**第一道门**。
但要注意两件事：① 整数型的恒定值（比如整段都是 3.000 / 5.000）多半是**厂商占位值**，不是真估计（坑 4-1）；
② 它**挡不住"伪装成固定解"的坏帧**（坑 4-2）。

**A6 · IMU 与惯导（Inertial Navigation）**

**是什么**：IMU = 加速度计 + 陀螺仪。加速度积分得速度，再积分得位移；角速度积分得姿态。

**为什么**：IMU 频率高、短时间极准，但**积分会累积误差**（几秒钟就能漂出可观的量）。
所以它和 GNSS 天然互补：**GNSS 长期稳、IMU 短期稳**，两者组合（"组合导航"）才能兼顾。

→ **本项目里**：`/qx/evk` 输出的位置，其实已经是**接收机内部组合导航的结果**，
不是纯卫星解 —— 这一点在判"某一帧到底是谁在提供位置"时很关键。

**A7 · 双天线航向（Dual-Antenna Heading）**

**是什么**：车顶装**两个** GNSS 天线，刚性固定。两台接收机同时解出各自位置，
两点连成的**基线向量**直接给出车头朝向，精度可达零点几度。

**为什么**：单天线要**动起来**才能靠轨迹差分推航向，静止时不知道朝哪。双天线静止也能测 —— 这是它的价值。

→ **本项目里**：`/qx/evk/heading` 话题。它是个**坑点话题**：官方文档说它是 `std_msgs/Float64`，
实际 bag 里是**8 字节裸 double、没有 Header**（坑 1-5）。

**A8 · 激光雷达（LiDAR）与 ToF 测距**

**是什么**：LiDAR = Light Detection and Ranging。发一束激光，测它打到物体再返回的**飞行时间**，
用 `距离 = 光速 × 时间 ÷ 2` 算出距离；再结合发射时的水平/垂直角度，得到这一点的三维坐标。

**为什么**：一路扫下来就是几万到几百万个点，每帧形成一个"点云"。

→ **本项目里**：传感器是 Livox MID-360，装在车顶，是唯一的环境感知源（**没有相机** —— 所以语义只能做纯 3D）。

**A9 · 三种激光雷达扫描方式（机械 / 固态 / 非重复）**

**是什么**：
- **机械旋转式**（Velodyne、Hesai 早期）：电机带着收发模组转圈，一圈下来是固定角度的若干条"光束环"，
  **每帧的扫描路径完全相同**。
- **固态**（MEMS 微振镜 / OPA）：没有机械旋转，靠微镜偏转光束。
- **双棱镜非重复扫描**（Livox 系列）：两个棱镜以不同转速旋转，光斑走出一条**花瓣形轨迹**，
  **每帧的路径都不一样，不存在固定光束环**。

**为什么**：这个差异不是细节，它决定了"哪套算法在你的雷达上有效"。

→ **本项目里**：这是坑 5-2 的核心 —— 我们最初选的 Cylinder3D 用**柱面划分**，
那套设计是为"机械旋转、等角度光束环"量身定做的，**在非重复扫描雷达上几乎不起作用**（论文里有消融数字）。

**A10 · 点云（Point Cloud）**

**是什么**：一堆三维点的集合，每个点通常是 `(x, y, z)`，可以再带强度、颜色等属性。

**为什么**：点云有三个"反直觉"的性质，后面每个坑几乎都跟它们有关：
① **稀疏**（物体表面只被采样了有限个点）；② **无序**（没有"第几个像素"的概念）；
③ **密度随距离衰减**（远处点稀，近处点密）。

→ **本项目里**：所有交付物的几何主体。`semantic_map.pcd` 就是 938 万个点的点云。

**A11 · 量程（Range）与视场角（FOV）**

**是什么**：量程 = 最远能测多远；FOV = 视野覆盖的角度范围。

→ **本项目里**：只有 **70 m**（MID-360 @ 80% 反射率）。这个数字看起来无关紧要，
但它是**"物理不可能测试"判据的来源**（坑 3-1）：
如果地图里的点到车的轨迹超过 70 m，那这张地图**不可能**在轨迹所在的那个坐标系里 —— 不用真值、不用标定就能证伪。

**A12 · intensity（回波强度）**

**是什么**：激光回波的强弱，综合反映物体表面的反射率、距离和入射角。

**为什么**：**不同数据集对它的量纲约定完全不同**。KITTI / SemanticKITTI 用 **0–1**；Livox 原始输出是 **0–255**。

→ **本项目里**：只差 100 倍，却让模型把 **56% 的点判成"交通标志"**（坑 5-1）。
模型不会告诉你"你喂的量纲错了"，它只会给你一个错得很具体的答案。

**A13 · offset_time 与"扫描帧"（以及运动畸变 / 去斜）**

**是什么**：一帧点云**不是同一瞬间拍出来的**，而是在约 100 ms 内**逐点扫描**积累的。
每个点都带一个 `offset_time`，表示"我是这一帧开始后第几毫秒被扫到的"。

**为什么**：这 100 ms 里，如果车在动（4 m/s → 走 40 cm），那么**同一帧内的点，其实是在不同车位上测的**。
直接把整帧当成"某一瞬间的刚体点云"来配准，就会引入**运动畸变**（业内叫 skew，中文常叫"去斜"）。
消除它叫**运动补偿 / 去畸变**。**（术语小注：体育摄影里"果冻效应"就是这个道理。）**

→ **本项目里**：实测每帧跨 100.11 ms、车走 40.0 cm，确实有畸变；
但做了各向异性分析后**主动决定不修**（坑 2-7）—— 因为绝大多数可见表面平行于行驶方向，正好是剪切改不动的那一类。

**A14 · 标定与"外参"**

**是什么**：**内参**是传感器自身的固有参数（激光雷达的安装角、测距偏差；相机的焦距等）；
**外参**是传感器与传感器之间、或传感器与车体之间的**相对位姿**。

**为什么**：多传感器融合的前提是知道"它们互相在哪、互相怎么转"，否则两套数据对不上。

→ **本项目里**：KISS-ICP 解出的"世界系"带着**安装倾角**，
这一点在"要不要动姿态"的决策里反复出现（坑 3-5、2-6）。

### B · SLAM 与轨迹

**B1 · SLAM**

**是什么**：**S**imultaneous **L**ocalization **A**nd **M**apping，
**同时定位与建图** —— 一边估计"我在哪"，一边把周围环境建成地图。

**为什么**：这是个**鸡生蛋**问题：要建图得先知道自己在哪，要知道自己在哪得先有地图。
所以只能"交替迭代"：用当前地图估位姿 → 用新位姿扩地图 → 再估位姿……

**两大流派**：
- **激光 SLAM**：用点云配准（本项目属于这一类，不需要光照、精度高、但贵）。
- **视觉 SLAM**：用相机图像（便宜、信息丰富、但对光照和纹理敏感）。

→ **本项目里**：整条链路的主干。赛题名称里的"语义 SLAM"= 激光 SLAM **加上**语义标注能力。

**B2 · 位姿（Pose）**

**是什么**：一个**位姿 = 位置 + 朝向**，数学上是 4×4 矩阵，包含 3 个平移分量和 3 个旋转分量，共 **6 个自由度**。

**为什么**：整个 SLAM 的产物就是**一串位姿** —— "第 0 帧、第 1 帧……第 6521 帧，摄像机/雷达在世界里的位置和朝向"。

→ **本项目里**：`poses_fused3.npy` 是**唯一的位姿来源**。
改了它，下游的点云、三条轨迹、录屏、所有统计数字**全部要重出**（坑 3-3）。

**B3 · 里程计（Odometry）**

**是什么**：只用**相邻两帧**的关系，一帧一帧**递推**出位姿："我上一帧在这，这一帧相对走了 12 cm、转了 0.3°，所以我现在在这"。

**为什么**：递推的好处是简单、实时；代价是**误差会单调累积**——
第 1 帧的 1 cm 误差，到第 6000 帧可能长成几十米。这就叫**漂移**（B6）。

→ **本项目里**：KISS-ICP 提供里程计。实测 **2544 m 路线累积 24.7 m 漂移（0.97%）**（坑 2-2）。

**B4 · 配准（Registration）与 ICP**

**是什么**：配准 = 把两坨点云"对齐"的算法。最经典的叫 **ICP**（Iterative Closest Point，迭代最近点）：
① 给每个点找另一坨里最近的对应点 → ② 求一个位姿让这些对应点距离总和最小 → ③ 用新位姿重新找对应点 →
④ 重复直到不再改善。

**为什么**：ICP 不需要提取特征，简单可靠，是激光 SLAM 的基石。但它是**局部方法**——
初始位姿太差、或者场景里全是植被这类"糊成一团"的东西时，它会**收敛到错的地方**，而且**不会报错**。

→ **本项目里**："这类子图上 ICP 不可信" 是一个被反复引用的结论（坑 2-3）。

**B5 · KISS-ICP**

**是什么**：**K**eep **I**t **S**mall and **S**imple ICP。一个极简的纯点对点 ICP 里程计，
没有特征提取、没有复杂参数，靠自适应阈值和稳健核函数硬扛。

**为什么**：它实现干净、纯 Python 可跑（本项目为绕开 ROS 消息的坑选了它），但**它只有里程计，没有回环检测**。

→ **本项目里**：位姿的第一来源。它的短板（无回环 → 会漂移）是坑 2-2 的直接成因，
也是后来"必须引入 RTK 逐帧约束"的动机（坑 2-4）。

**B6 · 漂移（Drift）**

**是什么**：累积误差。走着走着，估计的位置和真实位置的差距越来越大。

**为什么**：任何只有递推、没有"绝对参照"的方法都必然漂移，这是原理性的，不是调参能消掉的。

→ **本项目里**：KISS-ICP 的漂移真凶**不是旋转，是竖直方向**（坑 2-6）——
两次经过同一点，地面在竖直方向差了 **58 cm**。这个归因过程很值得看。

**B7 · 闭合差（Loop Closure Error）**

**是什么**：如果车绕了一圈回到起点，那么"估计的终点位置"和"实际的起点位置"之间的差距，就叫闭合差。

**为什么**：它是**最容易算、也最干净**的精度指标之一（不需要外部真值，只要起点终点足够近）。

→ **本项目里**：闭合差从 **24.74 m** 降到 **1.90 m**（引入 RTK 后）。
但注意坑 2-9：**"闭合差 1.88 m"根本不是误差** —— 因为那辆车**压根没回到原点**，
RTK 自己说起点到终点就差 1.92 m。**指标没有参考，数值就没有意义。**

**B8 · 回环检测（Loop Closure Detection）**

**是什么**：让系统能认出"我现在走的这条路，以前走过"。

**为什么**：一旦认出来，就能加一条约束"这两处的位姿应该重合"，
从而把累积的漂移**摊回整条轨迹**。这是消除漂移的标准手段，也是 SLAM 从"里程计"升级成"SLAM"的关键标志。

→ **本项目里**：我们试过，但**回环约束太少且不独立**（51 条基线其实全来自同一次重访，等价于 **1 条独立观测**），
所以回环没救回精度（坑 2-4 失败 5 条里的第 3 条）。

**B9 · 重访（Revisit）**

**是什么**：同一辆车、**不同时刻**两次经过**同一块地方**。

**为什么**：重访处的两遍点云，如果位姿估得准，就应该严丝合缝地重叠；重叠得不好，就说明这里有误差。

→ **本项目里**：把"重访处的最近邻距离"打造成了核心指标（坑 2-5），
因为它对"同一点被观测两次"的偏差敏感，**不会被全局杂波稀释**。

**B10 · 最近邻（NN, Nearest Neighbor）**

**是什么**：给定一个点，找出另一坨点里离它最近的那个。距离就是 NN 距离。

→ **本项目里**：重访评估的基本算子。交付版把重访 NN 中位压到 **19.1 cm**（odom 是 65.0 cm）。

**B11 · ATE（绝对轨迹误差）**

**是什么**：**A**bsolute **T**rajectory **E**rror。把估计轨迹和真值轨迹**先对齐**（通常用 Umeyama 求一个最优相似变换），
然后**逐点**算位置差，报 RMSE / 中位数 / 最大值。衡量的是**全局**准不准。
（相对的还有 **RPE**，Relative Pose Error，只看局部位姿关系，衡量局部一致性。）

**为什么**：这是轨迹评估最常用的指标。但它的数值**极度依赖"跟谁比"** ——

→ **本项目里**：我早期拿"自己拟合出来的输出"当参考，ATE 看起来很好；换成原始 RTK 后**暴增到 599.5 cm**。
这是全项目最重要的一次认知修正（第 0 章观念一）。

**B12 · 内点 / 外点（Inlier / Outlier）与 RMSE**

**是什么**：配准或拟合时，被判定为"对应关系正确"的点对叫**内点**，反之是**外点**。
**RMSE**（Root Mean Square Error，均方根误差）= 各项误差平方取平均再开根号，对大误差敏感。

→ **本项目里**：判断回环质量时用过"内点 RMSE 是否 < 0.15 m"这条线，
结果**没有一条回环达标**（坑 2-4）。

**B13 · 位姿图优化（Pose Graph Optimization）**

**是什么**：把所有时刻的位姿当成图的**节点**，把"两帧之间的相对位姿"当成**边**（约束），
然后求一组位姿使所有边的约束总误差最小。是 SLAM 后端的标准做法。

**为什么**：它能把里程计的**相对约束**和回环的**绝对约束**放在一起联合求解。
常用实现有 g2o、GTSAM、Ceres、Open3D。

→ **本项目里**：这条路我**连踩四个坑全败**（坑 2-3），最后改用"只解位置、增量形式"的自写方案才成。

**B14 · 最小二乘与"残差"**

**是什么**：**残差 = 观测值 − 模型预测值**（差多少）。**最小二乘** = 调整参数，让所有残差的平方和最小。

**为什么**：绝大多数位姿优化、拟合问题，本质上都是"解一个最小二乘"。

→ **本项目里**：位姿图优化的目标函数就是残差平方和；"残差 105.97 → 0.00 cm"就是我们优化的成果。

**B15 · LM 算法（Levenberg-Marquardt）**

**是什么**：求解**非线性**最小二乘的经典迭代算法（高斯-牛顿法 + 阻尼策略）。

**为什么**：非线性问题没法一步解出来，只能迭代逼近；LM 在"走得快"和"走得稳"之间自适应权衡。

→ **本项目里**：全轨迹优化时出现"**修正量均值 340 m**、起终点误差 25 → 440 m"这种荒谬结果，
说明 **LM 发散了**（不是没收敛，是跑到错误的地方去了）（坑 2-3 失败 2）。

**B16 · 条件数与"病态"（Ill-conditioned）**

**是什么**：条件数衡量"输入的微小扰动会被放大多少倍"。条件数大 = **病态** = 答案对噪声极度敏感。

**为什么**：病态问题里，优化器会沿着某个几乎不受约束的方向乱跑。

→ **本项目里**："目标函数条件数太差，LM 走向了荒谬解"就是这个意思。
**遇到优化发散，要先怀疑"目标和条件数"，而不是"迭代次数不够"。**

**B17 · 正则化与 Tikhonov**

**是什么**：在目标函数里额外加一项 `λ·‖x‖²`，**惩罚过大的解**，把病态问题变成有唯一稳定解的问题。
这个"加 L2 惩罚"的做法就叫 **Tikhonov 正则化**。

**为什么**：位姿图有"整体平移/旋转改不了残差"的**不定性**（整体挪一下，所有约束还是满足的），
正则化就是给它一个"锚"，防止解飞出去。

→ **本项目里**：最终方案里"**极小 Tikhonov 去规范零空间**"就是我们用来定住这个不定性的手段。

**B18 · 零空间（Null Space）与稀疏直接求解**

**是什么**：**零空间** = 变换后结果为零的那些方向，也就是"改了它也不影响目标函数"的自由方向。
**稀疏矩阵** = 绝大多数元素是 0 的大矩阵（位姿图的矩阵天然如此）；对它可以**直接求解**（如 `spsolve`），比迭代法更快更稳。

→ **本项目里**：两个关键认识 ——
① 位姿图必须处理零空间（我们固定 `dx₀ = 0` 后处理归一）；
② **"直接稀疏求解比迭代解更稳"**：`AᵀA + spsolve` 一次成功（坑 2-3 教训）。

**B19 · 相似变换与 Umeyama**

**是什么**：**相似变换 = 旋转 + 平移 + 尺度**（7 个自由度：3 旋转 + 3 平移 + 1 尺度）。

**Umeyama 算法**：给定两组一一对应的点，**闭式**解出最优相似变换（不用迭代）。
（如果去掉"尺度"，就是**刚体变换**，6 个自由度。）

**为什么**：这是"把两张地图/两条轨迹对齐"的标准工具。

→ **本项目里**：用来解 `local → ENU` 的那个变换，
结果 `s = 1.01243118 / yaw +23.91124° / 拟合残差 中位 0.53 mm`（坑 3-2）。
**"Umeyama" 这个词在正文里出现很多次，记住它就是"求最优对齐变换"就够了。**

**B20 · SE(3) / SO(3) 与"自由度"**

**是什么**：**SO(3)** 是三维旋转的集合（3 自由度）；**SE(3)** 是三维刚体变换的集合（旋转 + 平移，6 自由度）。
**自由度（DoF）** = 独立参数的个数。

→ **本项目里**：解释"为什么事后配准救不了"时用的就是这个词 ——
**"6522 个点被压成 4 个自由度"**（2D 相似变换）vs 需要"逐帧弯曲"的 1.96 万个绝对观测（坑 2-4）。

**B21 · 非刚性形变（Non-rigid Deformation）**

**是什么**：形状**本身**变了。整体平移、旋转、缩放都叫**刚性/相似**变换（形状不变）；而"中段鼓起来、两端收着"这种叫非刚性形变。

**为什么**：这是关键区分 —— **6–7 个自由度的变换，无论怎么调，都吸收不了非刚性形变**。

→ **本项目里**：这就是"事后配准数学上无出路"的真正原因（坑 2-4）。
轨迹有个 **U 型残差**（两端约 11 m、中段约 1.5 m），它是**形状问题**，不是摆放问题。

### C · 坐标与几何

**C1 · 坐标系家族（世界系 / 局部系 / 传感器系 / 车体系）**

**是什么**：描述"点在哪个参照系里"的约定。同一堆点，换一个坐标系，数值就完全不同。
- **传感器系**：以雷达/相机自己为原点。点云**原始**就是这个系。
- **车体系**：以车（通常是后轴中心或质心）为原点，跟着车走。
- **局部系 / 里程计系**：SLAM 常以**第一帧的位置**为原点，之后的位姿都在这个系里。
- **世界系**：一个**固定不动**的全局参照。

**为什么**：**这是本项目最大的坑**（第 3 章整章）：地图在局部系、轨迹在 ENU 系，
两套数据**各自都自洽**，但叠一起就穿帮（坑 3-1）。
**通用规则：任何"对不上"的问题，第一步先问"这俩在同一坐标系里吗"。**

**C2 · WGS84 / 经纬度 / 海拔**

**是什么**：WGS84 是 GPS 用的**地球椭球模型**（用一个压扁的球近似地球）。
**经纬度**这个球面上的角度坐标；**海拔**（更准确叫**椭球高**）是相对这个椭球面的高度。

**为什么**：经纬度是"球面角度"，**不能直接拿来算距离** ——
1 度纬度约 111 km，但 1 度经度在赤道 111 km、在纬度 31° 只有约 95 km。

→ **本项目里**：`path.yaml` 用的是经纬度，而 `traj_enu.csv` 用的是米。
两者换算要用地表**米/度**系数（代码里是 `MLAT` / `MLON`），这是个容易出错的地方。

**C3 · ECEF（地心直角坐标）**

**是什么**：Earth-Centered, Earth-Fixed。原点在**地球质心**，Z 轴指向北极，X 轴指向本初子午线。
把"球面上的经纬度"变成"空间里的三维直角坐标"，是坐标转换的中间站。

→ **本项目里**：`WGS84 → ECEF → ENU` 是标准转换链上的两步（正文里不必每次写出）。

**C4 · ENU（东-北-天）**

**是什么**：**E**ast-**N**orth-**U**p。一个**局部切平面**坐标系：
`x` 指向东，`y` 指向北，`z` 指向天（垂直向上）。原点是**自定义的某一点**。

**为什么**：它把"球面上的角度"变成了"平面上的米"，这样点云、轨迹、地图就能用**同一套米制坐标**放在一起。

**注意**：ENU 的 `z` 是"天"，不是"海拔" —— 它相对的是某个**切平面**，不是椭球面。

→ **本项目里**：交付物的目标坐标系。**原点 = 第一个 RTK 固定解帧**
（`lat 31.121152840 / lon 121.603270630 / alt 6.2988`）。
**看到 `ENU` 这个词，脑子里应该是"一张平地上的东北网格，单位米"。**

**C5 · 原点与锚点（Origin / Anchor）**

**是什么**：坐标系里"当作 (0,0,0) 的那个点"。

→ **本项目里**：ENU 原点定的就是上面那个首帧位置；
`semantic_map.pcd` 的 `x y z`、`traj_enu.csv`、`path.yaml` 都以它为基准。
**"锚点"这个词在文里也指"用来做评估基准的参考点"，注意上下文。**

**C6 · 欧氏距离**

**是什么**：`√(Δx² + Δy² + Δz²)`，就是日常说的直线距离。

→ **本项目里**：`|v_xy| = 48.8 cm`、`|v_z| = 63.3 cm` 就是把误差向量按水平/竖直拆开算长度（坑 2-6）。

**C7 · 分位数（p50 / p90 / p99）**

**是什么**：把一堆数从小到大排，**p90 = 有 90% 的数比它小**。`p50` 就是中位数。

**为什么**：**中位数和分位数比平均值抗异常值。**
例如 100 个误差里有 5 个是 5 m、其余 0.1 m，平均值会被那 5 个拉爆，而中位数仍然是 0.1 m。

→ **本项目里**：几乎每个精度结论都用"中位 / p90 / max"三联报。
看到"中位 0.600 m，p90 1.249 m，max 1.486 m"，要理解成"**典型情况 0.6 m，最差的 10% 会到 1.2 m 以上**"。

**C8 · 弦 / 弧 / 弦切角**

**是什么**：两点之间**直线**叫**弦**；沿曲线走的**真实路径长度**叫**弧长**（arc length）；
**弦切角**是"弦的方向"和"曲线在端点处的切线方向"之间的夹角。

**为什么**：这是个几何事实 —— **一段"先直行、再转弯"的路径，其中间点距离弦可以很远，但这不代表它"鼓包"了**，
只是因为它**拐了个弯**。判断是"鼓包"还是"拐弯"，要看**航向在段内是不是恒定**。

→ **本项目里**：一段 225 m 的路径偏离两端弦 **12.18 m**，
一开始被当成"米级风险"，最后用"航向前 204 m 基本不变、末段急转 82°"证明这是**弦切角**，不是鼓包（坑 4-1）。

**C9 · 平面拟合 / 梯度 / 倾角**

**是什么**：给一堆近似共面的点，拟合出一个平面，就能知道这块地面的**倾斜程度**。
用**梯度**（或倾角，例如 0.045°）表达；`R²` 是拟合优度（越接近 1 越"贴合"，但注意它在某些比较里解释方式相反，见坑 3-2）。

→ **本项目里**：用"地面点（`label = 8`）的平面梯度"验证坐标系修正：
修正前 **1.583%（0.907°）** → 修正后 **0.079%（0.045°）** —— 地面变平了，说明坐标系统一了。

**C10 · PCA 与特征值（λ0 / λ1 / λ2）**

**是什么**：主成分分析。对一小块点云求协方差矩阵的三个特征值 `λ0 ≥ λ1 ≥ λ2`：
- `λ0` 最大 → 点在这方向上**铺得最开**；
- `λ2`（λ_min）最小 → 这个方向**最薄**。

**为什么**：`√λ_min`（代码里写作 `sqrt(λ_min)`，**`sqrt` = 开平方根**）就是这块点的**局部厚度**（面越薄越小）。
**平行于航向的面（侧墙、路面）** 在沿轨剪切下这个量不变 —— 这正是坑 2-7 决定"不去斜"的数学依据。

**C11 · 欧拉角：yaw / pitch / roll**

**是什么**：用三个角描述三维旋转：
- **yaw（偏航 / 航向）**：绕**竖直轴**转 —— 车头朝哪个方向。`0° = 正北`，`90° = 正东`（本项目用这个约定）。
- **pitch（俯仰）**：绕**横向轴**转 —— 车头上仰/下俯。
- **roll（横滚）**：绕**纵向轴**转 —— 车左右倾斜。

→ **本项目里**：到处都在用。一个反复出现的教训是**别把两个轴搞混**：
"6° 安装倾角"其实是**前向轴的俯仰**，与世界系的竖直方向无关（坑 2-6）。

**C12 · 保距与尺度（Scale）**

**是什么**：**相似变换必须保距** —— 它只允许把所有距离**统一**缩放一个倍数 `s`，不允许"有的地方放大、有的地方缩小"。

**为什么**：如果变换里混进了非刚性的东西，那么"随机取一万对点，算每对的距离比"就会**散开**；
如果变换是干净的，所有这些比值应该**全是同一个数**。

→ **本项目里**：这是验证坐标变换正确性的杀手判据 ——
"10 万随机点对距离比 `= 1.01243118`，std **1.19e-7**"（坑 3-2）。

**C13 · 断言（assert）**

**是什么**：程序里写的一句"这里必须成立，否则立刻中止"。

**为什么**：**断言的价值不在于检查，而在于"在你犯错的那一刻炸掉"**（而不是让你带着错结果往下跑三小时）。

→ **本项目里**：最著名的两条是 `rebuild3.sh` 第 0 步的
`assert a == b`（位姿文件必须是 ENU 的）和 `assert np.ptp(P[:,2,3]) < 3.0`（z 跨度小于 3 m 才像 ENU）。
**"硬断言比任何文档都可靠"** 是第 3 章的一条结论。

**C14 · OSM（OpenStreetMap，开放街图）**

**是什么**：一个人人可编辑的**开放地图数据库**，提供道路、建筑等矢量要素。

**为什么**：它是**唯一不来自我们自己管线的第三方证据** —— 拿来验证"轨迹的方向对不对"特别有用。

→ **本项目里**：A 段直行 263.1 m 的航向，我们算 **168.99°**、OSM 是 **168.94°**，差 **0.05°**（坑 4-1）。

**顺带一个重要的思维方式**：OSM 上"对不上"的 11% 区域，
最后发现是 **OSM 自己在该片区有数据空洞**（它的 note 写着"地面道路仍待添加"）——
**参考源也会错，别默认参考源是对的。**

### D · 语义与深度学习

**D1 · 语义分割（Semantic Segmentation）与点云语义分割**

**是什么**：给每个**像素**（或每个**点**）打一个类别标签，比如"这是路、这是树"。

**为什么**：2D（图像）语义分割早已成熟；**3D 点云**难得多 ——
点云是稀疏、无序、密度不均的，"相邻"这个概念不像像素网格那么天然。
常用思路是先把点云**体素化**（D4），再在体素上做卷积。

→ **本项目里**：赛题的核心要求之一"语义标注准确率"就靠它。
**注意：我们没有相机**，所以只能做**纯 3D** 语义分割。

**D2 · stuff 与 thing**

**是什么**：语义分割里把类别分两大类：
- **stuff**：**没有固定形状、连成片**的"材料"类 —— 道路、人行道、植被、建筑。
- **thing**：**有明确边界、可数的**物体类 —— 车、人、交通标志、树干。

**为什么**：这两类的处理方式不同（thing 通常还要做实例分割，"这是第几个物体"）。

→ **本项目里**：初赛场景几乎全是 stuff（road / vegetation / building / fence / pole）；
**复赛换成室内场景后，thing（家具、瓶罐、行人）会变成主角**，这是复赛计划的一个关键转折。

**D3 · SemanticKITTI（以及它为什么坑我）**

**是什么**：基于 KITTI 数据集的**点云语义标注基准**，定义了 **19 个类别**，是 3D 语义分割最常用的评价标准。
类别包括：`car, bicycle, motorcycle, truck, other-vehicle, person, bicyclist, motorcyclist,
road, parking, sidewalk, other-ground, building, fence, vegetation, trunk, terrain, pole, traffic-sign`。

**为什么它坑我**：**它的 `road` 特指"车道"（行车道路面），而 `parking` / `sidewalk` / `terrain` 是分开的**。
我们的场景是**园区铺装地**，模型把它叫 `terrain` 未必是错。

→ **本项目里**：这条语义边界没搞清，导致我立了一个错误的判据（"轮下 road 占比应 > 80%"），
**给模型判了死刑，还据此写了半页"换不了模型"的分析**（坑 5-4、第 0 章观念二）。

**D4 · 体素（Voxel）**

**是什么**：三维空间里的"像素" —— 把空间切成规则的小立方体，每个立方体叫一个体素。

**为什么**：点云无序，不好直接卷积；体素化之后就有了规则结构。
体素**边长**的选择是权衡：太小 → 大部分体素是空的（浪费算力）；太大 → 细节被抹平。

→ **本项目里**：交付点云用 **0.15 m** 体素，在线可视化地图用 **0.6 m**（不同体素**不可直接比点数**，这是 README 里专门强调的）。

**D5 · 稀疏卷积（Sparse Convolution）与 spconv**

**是什么**：点云体素化后，**99% 的体素是空的**。如果在整个立方体网格上做卷积，绝大部分计算都在乘零。
稀疏卷积只对**非空位置**计算，效率高几个数量级。
**spconv** 是实现稀疏卷积最常用的库。

→ **本项目里**：SFPNet 依赖 spconv。它的**权重布局**随编译期配置变化，是个隐蔽的坑（坑 5-3）。

**D6 · backbone（骨干网络）**

**是什么**：深度学习模型里负责"提取特征"的主体网络。后面通常再接一个"头"（head）输出结果。

**为什么**：同一个"头"配不同 backbone，性能可能差很多；选型的主战场在 backbone。

→ **本项目里**：我们对比了 Cylinder3D 和 SFPNet 两个 backbone，最终换了后者（坑 5-2）。

**D7 · 归纳偏置（Inductive Bias）**

**是什么**：模型**天生自带**的假设。比如卷积网络假设"相邻像素相关"，所以适合图像。

**为什么**：**偏置和数据的性质匹配时，效果极好；不匹配时，那部分设计就是白搭甚至有害。**

→ **本项目里**：这是坑 5-2 的核心。
Cylinder3D 的柱面划分是一种强归纳偏置，**专门为机械旋转式雷达设计**；
用在 Livox 的非重复扫描雷达上就**基本失效**。
**"选模型要看'归纳偏置 vs 你的传感器'这一对，不是看论文的 mIoU 排名。"**

**D8 · 柱面划分（Cylindrical Partitioning）**

**是什么**：Cylinder3D 的核心设计 —— 不用笛卡尔网格（x/y/z 直角切块），
而用**柱坐标** `(ρ, θ, z)` = （到传感器距离、方位角、高度）来划分空间。

**为什么**：机械旋转式雷达扫出来就是一圈圈的环，用"距离 + 方位角"切块，每一块里的点分布很均匀 —— 非常自然。
但非重复扫描雷达**没有稳定的环**，这个设计就落空了。

→ **本项目里**：论文实测数据：这套设计在 S.MID 数据集上只带来 **+1.2%**，在固态雷达 PandaSet 上只到 **55.0%**。

**D9 · SFPNet 与"焦点调制"**

**是什么**：SFPNet（ECCV 2024）是一个点云语义分割网络，本文选择的最终方案。
它的思路是"稀疏焦点调制"（sparse focal modulation），
**刻意不引入任何与雷达类型绑定的结构假设** —— 所以不会像柱面划分那样在某种雷达上失效。

→ **本项目里**：换过去之后全面胜出（F1 均值 **61.4% → 66.2%**；
在两版判断相反的 71,420 个可裁决点上，胜率 **16.8% → 83.2%**，坑 5-2）。

**D10 · 预训练 / checkpoint / state_dict / 权重布局**

**是什么**：
- **预训练**：别人先在大数据集上训好的模型，你拿来直接用或微调。
- **checkpoint**：训练过程中保存的模型文件（通常含参数 + 优化器状态）。
- **state_dict**：PyTorch 里"参数名 → 张量"的字典，加载模型就是把它塞进网络。
- **权重布局**：同一个卷积核，张量在内存里是 `[输出通道, 核, 输入通道]` 还是 `[核, 输入通道, 输出通道]` 排列。

**这两种布局的业内叫法**：**KRSC** = `[核, 输入通道, 输出通道]`；**RSCK** = `[输入通道, 输出通道, 核]`。
**这两个缩写在代码、日志和论文里会直接出现**（本项目就踩到过），遇到时不认识会被直接卡住。

**为什么**：布局不匹配的报错信息是"形状不匹配"，非常容易误判成"模型结构不对"。

→ **本项目里**：SFPNet 的一个 checkpoint 里**同时存在两种布局**（因为 spconv 按核大小自动切换算法），
最后靠一个"按目标形状自动找转置轴"的通用对齐器解决（坑 5-3）。

**修它的动作**：`permute(...)` —— 张量**维度重排**（把第 3 维挪到第 1 维之类），只改排列顺序，不改数值内容。

**D11 · 类别 id / label / 映射表**

**是什么**：类别在数据里是用**整数**存的（`label = 8`），不是字符串。

**为什么**：**同一个名字在不同体系里编号不同**！
SemanticKITTI **官方**表是 `road = 9`；但 mmdet3d 的实现用 **0 基**约定，`road = 8`。
**差 1，整体错位。**

→ **本项目里**：组委会明确"不提供类别列表"，所以我们必须在交付物里**亲手写出 id ↔ 名称的映射表**（坑 7-4）。
**"我用了某个标准" ≠ "对方知道我用的是哪个标准"。**

**D12 · 类别分布倾斜（Class Imbalance）**

**是什么**：某一类点数特别多（比如地面占了 80%），其他类很少。

**为什么**：这会让**指标作弊** —— 一个"把所有点都判成地面"的模型也能拿到很高的总体准确率。
所以评估要用对每类一视同仁的指标（D13），并且**判据本身要能抗倾斜**。

→ **本项目里**："轮下 road 占比"这条判据就容易被倾斜作弊；
而"只取两版判断相反的点来做裁决"这个判据**天然免疫倾斜**（坑 5-5）。

**D13 · precision / recall / F1 / IoU / mIoU**

**是什么**：
- **precision（精确率）**：我判为 A 的点里，有多少真的是 A。（"我说的准不准"）
- **recall（召回率）**：真的是 A 的点里，我找出来多少。（"我有没有漏"）
- **F1**：precision 和 recall 的调和平均，一个数综合两者。
- **IoU**（交并比）：预测区域和真值区域的交集 ÷ 并集。
- **mIoU**：所有类别的 IoU 求平均，是 3D 语义分割最常用的总指标。

→ **本项目里**：因为**没有语义真值**，任何 mIoU 都是编的，
所以改用"几何伪真值"下的 F1 和"分歧点胜率"（坑 5-5、D14）。

**D14 · 无真值评估与"伪真值"**

**是什么**：没有标注，怎么评质量？办法是**构造一个不依赖标注、但客观存在的物理量**当参照。

→ **本项目里**：三条判据（坑 5-5）：
① **几何伪真值** —— 每 1 m 格取 z 的低 5% 分位当"该处地面"，
`dz < 0.5 m` 判为"表面"、`dz > 2.0 m` 判为"空中结构"，算 surface / elevated 的 F1；
② **分歧点裁决** —— 只看两个模型判断相反的点，用几何来判谁对；
③ **体素纯度** —— 0.5 m 体素的主标签占比，用来区分"随机错"和"系统性错"。
**核心思想：找一个不依赖被评对象、且不能靠倾斜分布作弊的物理量。**

**D15 · 多数投票（Majority Vote）**

**是什么**：一堆点要合成一个标签时，取"出现次数最多的那个"。

**为什么**：**这是对"标签"做聚合的正确方式**（对"颜色"做平均才是错的，见 5-9）。

→ **本项目里**：体素内标签融合用投票；而且我**写了三个独立实现互相印证**，
才发现其中一个有 bug（算出的格子数差了 100 倍，坑 5-10）。

**D16 · 动态物体与"自车"（Ego Vehicle）**

**是什么**：**自车 = 传感器所在的那台车自己**。

**为什么**：激光雷达装在车顶，一圈扫下来必然扫到自己的车体。
**"数据里出现了车"和"场景里有车"是两件事。**
判断方法：**看几何稳定性** —— 自车的位置在传感器坐标系里**永远固定**，场景里的车会动。

→ **本项目里**：地图上"每隔一段出现一次"的 `car`（到本帧地面质心水平距离中位 **1.42 m**、垂直 **+1.07 m**，全程稳定）
就是自车，应剔除（坑 5-8）。

**D17 · RGB 打包 / 位重解释 / hexdump**

**是什么**：
- PCD 文件把颜色塞进**一个 float32** 里（4 字节 = R/G/B/保留 各 1 字节），叫"打包"。
- **位重解释**（`.view()`）：把这 4 个字节**当成整数读**，而不是"把浮点数值转换成整数"（`.astype()`）——
  后者会让 `3.2e-39` 变成 `0`。
- **hexdump**：把文件的原始字节按十六进制打印出来，肉眼看。

**为什么**：这是个**静默错误**重灾区 —— 我一度算出"rgb 全 0"，差点误报交付物没有颜色。

→ **本项目里**：教训是"**要下'这里有/没有某字段'的结论前，先 hexdump 两条记录看**"（坑 5-11）。

**D18 · 域外推理与量纲（Scale / Unit）**

**是什么**：拿在 A 数据集上训的模型去跑 B 数据（域外推理），**必须先核对每个输入通道的量纲**。

**为什么**：模型不会说"你的输入量纲不对"，它只会给你一个**错得很具体**的答案。

→ **本项目里**：intensity 差了 100 倍 → 56% 的点被判成交通标志（坑 5-1）。

**D19 · 伪影（Artifact）**

**是什么**：**不是真实存在、而是由测量或算法产生的**假结构。

**为什么**：伪影最危险的地方是它**"看起来很有结构"**，很容易被当成真实语义。

→ **本项目里**：地面被细分出的 `sidewalk` / `terrain`，
看起来"像斑马线"、"像声呐涟漪"，实际上**输出的是"到传感器的距离"，不是材质**（坑 5-6）。
**判别方法：换一个物理位置比较，或者找一个能把伪影参数化的物理量。**

**D20 · 混杂因素（Confounder）与"控制实验"**

**是什么**：让你误以为 A 导致 B、实际上是 C 同时在影响的那种因素。

**为什么**：**要排除混杂，就要让其他变量保持恒定，只改变你想研究的那个。**

→ **本项目里**：判断"sidewalk/terrain 差异是不是材质造成的"，
方法就是**只在同一个 0.5 m 格内比较**（同位置 = 排除材质）——
结果 sidewalk 平均距离 5.0 m、terrain 9.0 m，**距离才是真凶**（坑 5-6）。

**D21 · 边缘设备 / 量化 / 剪枝**

**是什么**：
- **边缘设备**：装在机器人/车上的低功耗计算平台（如 Jetson Orin）。
- **量化**：把模型参数从 32 位浮点压成 8 位整数，体积和算力需求大幅下降，精度略降。
- **剪枝**：删掉不重要的参数/通道。

**为什么**：FAQ 明确要求"模型大小需适合在边缘计算设备上运行"。

→ **本项目里**：我们的模型 **107.55 M 参数 / 410 MiB**，**没做量化剪枝**；
**193.7 ms/帧是 T4 服务器的数字，不是边缘平台的数字**。
这一条**如实写进了 README 的"已知限制"**（坑 7-6），初赛不评，复赛要还这笔账。

**D22 · 波束足印（Beam Footprint）**

**是什么**：激光束不是无限细的线，打到远处会变成一个**光斑**（足印），距离越远光斑越大。

**为什么**：光斑越大，一次测量覆盖的表面越杂，**测出来的几何越模糊**。
**这是个与"距离"强相关的物理效应**，很容易和真实的地形变化混淆。

→ **本项目里**：它正是让"到路线距离"变成伪影代理的元凶（相关系数 **r = +0.60**），
导致**没有任何距离无关的几何特征能切开地面**（坑 5-6）。

### E · 可视化与视频

**E1 · ROS / topic / message / node**

**是什么**：ROS（Robot Operating System）是机器人领域的事实标准中间件。
- **node（节点）**：一个在跑的程序（比如"录屏程序"是一个节点）。
- **topic（话题）**：一个**具名的数据管道**，节点往上面**发**消息，别的节点从上面**订阅**。
- **message（消息）**：管道里流动的数据，有**固定的类型和二进制格式**（如 `sensor_msgs/PointCloud2`）。

**为什么**：ROS 的强项是"解耦"（谁都不用知道谁在哪）；弱项是**消息格式一旦缓存/跨版本，就会很难受**。

→ **本项目里**：`slam_online.py` 就是一个 ROS node，往 `/map_live`、`/traj` 等话题发消息，RViz 订阅显示。

**E2 · rosbag（.bag 文件）**

**是什么**：ROS 的**记录文件格式**，像"行车记录仪"一样把某个时间段内所有话题的消息**按时间顺序**存进一个文件。

**为什么**：它是离线复盘的唯一凭据 —— 出问题时可以**回到原始数据**重算。

→ **本项目里**：`data.bag` 是赛题给的原始数据。

**一个反复踩到的点**：ROS 有**自定义消息类型**，解析时必须先知道类型定义，否则读不出来（用别的库读会报"缺类型"）。

**E3 · RViz**

**是什么**：ROS 的**三维可视化工具**（ROS Visualization）。你在它里面添加各种"Displays"（显示项），
每一项订阅一个话题，然后把它画在 3D 视口里。

**为什么**：赛题**明确要求**录屏要含"rviz 等可视化界面" —— 所以它不只是工具，是**交付要求的一部分**。

→ **本项目里**：第 6 章几乎全部在跟它打交道。它还带来两个反直觉的相机语义（E6、E7）。

**E4 · PointCloud2 / Marker / latch（latch 话题）**

**是什么**：
- **PointCloud2**：ROS 里传点云的标准消息类型（可以带颜色字段）。
- **Marker / MarkerArray**：ROS 里画简单几何图形的消息类型（箭头、文字、线、方块）。
- **latch（锁存）**：一种话题发布模式 —— **发布之后，任何新订阅者连上来，立刻能收到最后一条消息**（否则只能等下一次发布）。

**为什么**：对于"发一次就完事的静态地图"，必须用 latch，否则 RViz 连上来时什么都收不到（这就是当初"假回放"能骗过眼睛的技术原因之一）。

→ **本项目里**：探针脚本 `probe_pub.py` 就是靠一次 latch 发布整张地图，实现"秒级试机位"（坑 6-6）。

**E5 · Decay Time（衰减时间）**

**是什么**：RViz 的 PointCloud2 显示项有一个参数叫 `Decay Time`。

**它的真实语义是"显示窗口长度"，不是"淡出时间"**：
- `Decay Time = 0` → **永久累积**（所有收到过的点都留着，越堆越多）；
- `Decay Time > 0` → 只显示**最近 N 秒**收到的点。
**它没有"这一帧替换上一帧"的语义。**

→ **本项目里**：逐帧发增量小包 → 屏幕上**重影**（旧点不消失）。
解法是"每帧重发整张累积地图"+ `Decay Time: 0.35`（必须 **> 发布间隔 0.24 s**，否则大部分时间屏幕空白）（坑 6-2）。
**教训：参数的名字不代表它的语义，读文档/读源码，别猜。**

**E6 · Orbit 相机与它的四要素（Distance / Focal Point / Yaw / Pitch）**

**是什么**：RViz 默认的相机模型是"轨道相机"（Orbit）—— 相机**绕着一个焦点转**。
它的四个参数是：
- **Focal Point**：相机**看向（并绕着转）的那个点**，用世界坐标给出。
- **Distance**：相机**离焦点多远**（不是"离目标多远"）。
- **Yaw / Pitch**：相机相对焦点的方位角与俯仰角。

**为什么**：这意味着**焦点必须先放对** —— 焦点错了，你怎么转都拍不到东西。

→ **本项目里**：地图水平重心是 ENU `(39.5, 168.5)`，而旧焦点是 `(104, 128)`，
**偏了 64 m / 40 m** —— 这就是"只拍了一角"的根因（坑 6-5）。

**E7 · RViz 的 Pitch 与 Yaw（两个反直觉语义）**

**是什么**：
- **Pitch 是"从正下方量起"的**：
  `Pitch = 0` → 相机在**正上方**（俯视）；`Pitch = π/2` → 相机落在**水平面**上。
  ⇒ **`Pitch = 1.05 rad` 是约 30° 俯角，不是 60°。**
- **Yaw 的绝对值由 Focal Point 决定** —— 换句话说，在焦点放对之前，调 Yaw 没有意义。
  `Yaw = 0` 时，地图的长轴（ENU 北向）才落在**画面水平方向**。

→ **本项目里**：这两个语义是"取景重录"这一轮最大的发现，也是最费功夫的（坑 6-5）。
搞懂之后，**整幅地图只需要动 5 个数字**。

**E8 · fovy 与透视投影**

**是什么**：相机是透视投影（近大远小）。**fovy** = 垂直视场角，决定"能看多宽"。
`fovx`（水平视场角）可以由 `fovy` 和画面宽高比算出来：`fovx = 2·atan(tan(fovy/2)·W/H)`。

**为什么**：改 Distance 或 fovy 都能"让地图变小"，但两者视觉后果不同（改 Distance 会改变透视感的强弱）。

→ **本项目里**：RViz 默认 `fovy ≈ 45°`；我用距离和焦点解决了构图，没有动 fovy。

**E9 · 视口（Viewport）**

**是什么**：窗口里**真正显示三维画面**的那块矩形区域。
RViz 的 3D 视口**不是整个窗口** —— 左边有 Displays/Views 面板、底部有状态栏，这些都不算。

→ **本项目里**：1280×720 窗口里，视口是 `x[364,1263] y[62,690]` = **900×629**。
**量构图时必须先把这个矩形算准**，否则"占比 71.3%"根本无从谈起（坑 6-7）。

**E10 · 无头（headless）与 Xvfb**

**是什么**：
- **无头**：程序在跑但没有显示器（服务器、容器里常见）。
- **Xvfb**：一个**虚拟显示器**软件 —— 它假装自己有屏幕，让需要图形界面的程序（RViz）能跑起来、能被截图。

**为什么**：云端 GPU 容器里没有物理屏幕，但我们需要跑 RViz 并录屏。

→ **本项目里**：`Xvfb :99` 起一块 **固定 1280×720** 的虚拟屏幕，
然后用 `xdotool windowmove/windowsize` 把 rviz 窗口**拉满**。

**一个连带效应**：视口宽度完全由"左栏面板宽度"决定，所以探针图与实拍图的左边界会有 ±21 px 差异 —— **探针只能用来选参数，不能当验收证据**（坑 6-6）。

**E11 · 录屏、帧率与"倍率"**

**是什么**：录屏 = 把屏幕内容录成视频；帧率 = 每秒多少帧。
**倍率** = "播放速度相对真实时间的倍数"（2.43× = 真实 2 分 26 秒的内容在 1 分钟内播完）。

→ **本项目里**：赛题允许加速但有时长上限，所以要把长录屏压到规定时间内（坑 7-1）。

**一个必须区分的概念**：
**"raw 录屏时长"（整个视频文件多长，含启动与收尾）** 与 **"算法运行时长"（`RUN_COMPLETE` 报的 tick 循环耗时）**
**不是一回事**（坑 6-9）。**写文档前必须先定义清楚"原始时长"指哪个。**

**E12 · ffmpeg / PTS / setpts / drawtext**

**是什么**：
- **ffmpeg**：命令行音视频处理工具（剪辑、转码、变速、抽帧）。
- **PTS**（Presentation Timestamp）：每一帧的**显示时间戳**。
- **`setpts=PTS/F`**：把所有时间戳除以 F —— 这是最常用的**变速**手法。
- **drawtext**：把文字烧进画面（我们要在右下角标"PLAYED AT 2.43X"）。

**为什么**：`setpts` **只压缩时间戳**，输出视频**仍然停在同一个时刻**，
所以有些播放器/`ffprobe` 报的 `Duration` 看起来"没变"，需要配合 `-vsync cfr` / `-r` 才能正确报时长。

→ **本项目里**：这就是坑 6-9。

**E13 · WebGL / shader / z-buffer / Canvas 2D**

**是什么**：
- **WebGL**：浏览器里的 GPU 三维绘图接口；**shader** 是跑在 GPU 上的小程序。
- **z-buffer（深度缓冲）**：一张"每个像素当前最近深度"的表，用来判断谁挡住谁 —— 三维渲染的基础。
- **Canvas 2D**：浏览器里的普通二维绘图接口（CPU 画）。

**为什么**：WebGL 快，但**在无头/虚拟显示环境下容易出兼容问题，且报错信息不可靠**。

→ **本项目里**：本地点云查看器用 WebGL 时**画面全白**而 `getError()` 只报 1282，
最后**改用 Canvas 2D + 自建 z-buffer**：115.9 万点重投影约 25 ms，够用且没坑（坑 6-10）。
**教训：一条路线在特定环境不稳定时，换一条更笨但可靠的，是正当决策。**

**E14 · 反标定（从图像反推参数）**

**是什么**：反过来推 —— 已知画面里的像素位置，反推相机参数（位置、朝向、视场角）。

**为什么**：看起来聪明，实际上**极不可靠**，因为它有个隐藏前提："**画面里的这个东西，就是我以为的那个东西**"。

→ **本项目里**：我做过两条反标定路线（从视频里的红线推相机）**全部失败** ——
因为那条"红线"根本不是轨迹，是别的东西（坑 6-6）。

**正确的做法是"控制输入"**：改配置 → 重跑 → 拍照，一次只动一个变量。

### F · 数据格式与工程

**F1 · PCD（点云数据格式）**

**是什么**：Point Cloud Data，点云的标准文本/二进制格式。文件头声明字段：
`FIELDS x y z intensity label rgb`（有哪些字段）、`TYPE F F F F U F`（每个字段的类型，F = float、U = unsigned）、
`SIZE`（字节数）、`POINTS`（点数），然后 `DATA binary` 后面跟原始数据。

**为什么**：**它的字段定义就是"读法的合同"**，读错一个 `COUNT` 就全错位。

→ **本项目里**：坑 1-3（`COUNT 1` 陷阱）、坑 5-11（rgb 解码）都出在这里。

**F2 · .npy（numpy 数组文件）**

**是什么**：NumPy 保存数组的原生格式，前面有 **128 字节的文件头**（记录 shape、dtype 等元数据）。

**为什么**：**这 128 字节是"差 128"这类诡异差值的来源** ——
如果把它当裸数据读，长度会多出 128。**一律用 `np.load()` 读，不要自己 `frombuffer`。**

→ **本项目里**：坑 1-6 —— `9383771 + 128 = 9383899`，差点误报"交付物长度不一致"。

**F3 · NumPy 广播（Broadcasting）**

**是什么**：NumPy 在形状不匹配时**自动扩展**维度的规则。比如 `(3,3) @ (1,3,N)` 这种本不该成立的乘法，
NumPy 会**悄悄把维度对齐**算出一个结果。

**为什么**：**广播是双刃剑** —— 形状不对时，它常常**不报错，而是"帮你"算出一个错的结果**。

→ **本项目里**：坑 1-3 里，`(N,3,1)` 而不是 `(N,3)` 的形状，被静默广播后**坐标飞到了 286 m**，而程序毫无异常。
**防御手段：在关键计算后断言"物理量纲"**（"地面点云 z 跨度不可能超过 60 m"），
**物理约束比形状检查有用得多**。

**F4 · dtype 与"值转换 vs 位重解释"（astype vs view）**

**是什么**：
- **`.astype(int)`**：把**数值**换一种类型（`3.7` → `3`）。
- **`.view(int)`**：把**同一段字节**用另一种类型解读（`0x3F800000` 既是浮点 `1.0`，也是整数 `1065353216`）。

**为什么**：两者写错了**不报错，只是数字全错**。

→ **本项目里**：坑 5-11 —— 用 `astype` 解 rgb 得到"全 0"，用 `view` 才是对的。

**F5 · YAML 与 schema**

**是什么**：YAML 是一种**给人读的**配置文件格式（靠缩进表达层级）。**schema** = "这份文件应该长什么样"的结构规范（有哪些键、什么类型、什么缩进）。

**为什么**：**"看起来差不多"和"按字节对齐"是两回事**。

→ **本项目里**：`path.yaml` 的缩进（0/0/2 vs 4/4/6）和缺失的 `total_points` 键，
按 schema 逐条对齐后才能通过（坑 7-2）。**改完必须逐值回归验证，证明"只改了格式、没改数值"。**

**F6 · 时间戳与 epoch（纪元）**

**是什么**：程序里的时间常用"从某个基准时刻起过了多少秒"表示。
- **Unix 时间戳**：从 **1970-01-01 UTC** 起算的秒数（如 `1773027245.57` —— 这是个绝对时间）。
- **相对秒**：从"这段数据开始录制"起算的秒数（如 `400.23` —— 只在这段数据内有意义）。

**为什么**：两者**长得像但含义完全不同**，混用会导致"看起来不合规"的误判。
**在数据里这个字段通常就叫 `stamp`**（也写作 `timestamp` / `t_ns`）——
交付的 `traj_enu.csv` 第一列、`path.yaml` 里每条的 `stamp:` 都是它。

→ **本项目里**：坑 7-3 —— 官方样例用 1.77e9（绝对），我们用 400.2（相对）。
**回原始 bag 查证后确认：包里根本没有绝对时间**，换算成 Unix 秒只能**凭空编纪元**，所以保留相对秒。

**F7 · 二进制布局与 hexdump**

**是什么**：数据在文件里是**按字节顺序排列**的。"头部有哪些字段、各占几字节、什么字节序"就是它的**二进制布局**。
**hexdump** = 把原始字节按十六进制打印出来看。

**读法小抄**：`u8 / u16 / u32 / u64` = **无符号整数**，数字表示占**几个字节**
（`u32` = 4 字节、`u64` = 8 字节）；`f4 / f8` = **4 字节单精度 / 8 字节双精度浮点**。
**"多读或少读 4 字节"，后面整段数据就会错位** —— 这是本项目最贵的一类 bug（坑 1-1）。

**为什么**：**这是排查"数据长得不对"最快的办法** —— 比读文档、比读代码都快。

→ **本项目里**：坑 1-1（消息头部多了 4 字节 `data_type`）、坑 1-5（heading 是裸 double）、坑 5-11（rgb）都是 hexdump 一眼看出来的。
**通用规则：凡是要下"这里有/没有某字段"的结论，先 hexdump 两条记录肉眼看。**

**F8 · venv / PYTHONPATH / site-packages**

**是什么**：
- **venv**：Python 的**隔离环境**（每个项目一套自己的包版本）。
- **site-packages**：装包的地方。
- **PYTHONPATH**：一个环境变量，里面的路径会被**加到搜索路径的最前面**。

**为什么**：`PYTHONPATH` 里如果有系统 Python 的 `dist-packages`，
它会**排在 venv 前面**，把 venv 里的新版 numpy **顶掉** ——
结果编译扩展报 `numpy.ndarray size changed ... Expected 88 from C header, got 80`。

→ **本项目里的修法**：**PYTHONPATH 里不放系统路径**，
改由脚本自己 `sys.path.append()` 到**末尾**（venv 优先，同时系统里的 `rospkg` 仍能import到）。
**记忆点：`append`（加到末尾）和 `insert(0, ...)` / `PYTHONPATH`（加到最前）效果完全相反。**

**F9 · cgroup / OOM**

**是什么**：Linux 的**资源分组限制机制**。容器里 CPU、内存的上限由 cgroup 控制，**不是**宿主机物理上限。
**OOM** = Out Of Memory，内存超限被杀。

**为什么**：**`free -h` 显示的是宿主机的内存**，会让你严重高估可用资源。
被杀时**日志会静默停在上一行**，极易误判成"程序卡住"。

→ **本项目里**：容器上限 **42 GiB**（`cat /sys/fs/cgroup/memory.max` = 45097156608），
而 `free -h` 显示 **376 GB**。全轨迹位姿图优化涨到 **43.7 GB** → 被杀（坑 2-3 失败 1、坑 8-1）。
**查证手段：`dmesg | tail` 能看到 `Memory cgroup out of memory`。**

**F10 · CRLF 与 LF（行尾符）**

**是什么**：文本文件的换行，Windows 习惯 `\r\n`（CRLF），Unix 习惯 `\n`（LF）。

**为什么**：把带 `\r` 的 shell 脚本传到 Linux 上执行，
`\r` 会被当成命令名的一部分 → 报 `$'\r': command not found`。

→ **本项目里**：即使用二进制方式（SFTP）上传，如果源文件本身是 CRLF，传过去还是 CRLF。

**修法是显式转换**：读成二进制 → `.replace(b"\r\n", b"\n")` → 以二进制写回（坑 8-2）。
**教训：跨平台传文本文件，行尾是一个必须显式处理的变量。**

**F11 · SIGTERM（进程被"礼貌地杀掉"）**

**是什么**：Unix 信号之一，表示"请结束自己"。比 `SIGKILL` 温和（进程可以清理后退出）。

**为什么**：**命令跑太久、内存超限、SSH 断开**，都可能触发它。
症状是"脚本跑到一半就没了，也没报错"。

→ **本项目里**：长循环（12 万次随机搜索）、`python - <<EOF` heredoc 都可能被掐掉。
**修法：把长任务写成 `.py` 文件再跑，或者放后台。**

**相关命令 `pkill`**：按名字杀进程。用 `-f` 时它匹配的是"**完整命令行**"，
**而 `pkill` 自己的命令行也在里面** ⇒ 会把自己、连同你所在的 SSH 会话一起杀掉（坑 8-4）。

**写法是用字符类把自己"打断"**：`pkill -f "[s]fpnet_infer"` —— 这样命令行里出现的是 `[s]fpnet_infer`，
匹配不到自己。

**F12 · 正则表达式（Regular Expression）**

**是什么**：一种"描述文本模式"的小语言，用来查找/提取字符串（比如"所有 `altitude:` 后面的数字"）。

**为什么**：写起来方便，但**在不同外壳里传递时容易被吃掉反斜杠**。

→ **本项目里**：`python -c "...re.findall(r'altitude:\s*...')..."` **0 匹配**，
**同一段代码写进 `.py` 文件就正常**（坑 8-5）。
**规则：带正则的核验脚本一律写成文件再跑。**

**F13 · md5 与"指纹"**

**是什么**：md5 是一种**哈希算法** —— 把任意长度的文件压成 32 位十六进制字符串。
文件改一个字节，结果完全不同。

**为什么**：**它是"这个文件到底是不是那一份"的唯一可靠答案。**

→ **本项目里**：每个交付包、每个视频、每个点云都记录 md5。
**"指纹"这个词在文里就是"md5 / 文件大小 / 字节数"这一组标识的统称。**

**F14 · 下采样与体素滤波（Downsampling / Voxel Filter）**

**是什么**：把点云变稀疏（900 万点太多，显示/计算都吃不消）。
最常见的是**体素滤波**：每个体素格子只保留一个代表点。

**为什么**：**在哪个空间里做下采样，决定了丢失什么信息。**

→ **本项目里**：坑 5-9 —— 早期把标签**上色之后**再下采样，**颜色被平均**了，
再用"最近颜色"反推标签就落到了第三个类上，导致类别占比重排（vegetation +8.6pp、sidewalk −10.6pp）。
**正确做法：下采样时对标签做多数投票，不要对颜色求平均。**

**F15 · 帧 / tick / stride（采样间隔）**

**是什么**：
- **帧（frame）**：一帧点云 = 一次扫描。
- **tick**：算法主循环走一次 = 处理一帧。
- **stride**：采样间隔（`STRIDE=12` 表示每 12 帧取 1 帧）。

**为什么**：用 stride 可以成倍缩短实验时间，但**必须记住你测的是"抽稀后"的数字化**，
不能和"全量"数字混着报。

→ **本项目里**：录屏用 `STRIDE=12`（每 12 帧取 1 帧）来让视频在合理时长内跑完。

**F16 · SFTP / paramiko / 远端通道**

**是什么**：
- **SSH** 是安全远程登录；**SFTP** 是跑在 SSH 上的文件传输。
- **paramiko** 是 Python 的 SSH/SFTP 库（本项目用它做"远端命令 + 文件上传下载"）。

**为什么**：远端任务的一切（起进程、传脚本、拉产物）都靠这条通道。

**两个踩过的点**：① 上传脚本要转 LF（F10）；② **下载大文件要放后台**，前台会超时截断（坑 8-7）。

## 第 0 章 先建立三个观念（读后面所有章节前请先读这一章）

> **〔本章黑话〕** ATE、ENU、RTK、SemanticKITTI、NumPy 广播、PCD —— 这章在讲"怎么才知道自己没骗自己"。
>
> 看不懂先查开头的「术语总表」，或往下找同名的 `> 〔术语〕` 灰框。

这一章不是废话。本项目一半以上的时间浪费在"没想到这三件事"上。

### 观念一：**没有反馈的地方，人会无限思考；有反馈的地方，一次就够**

我在这件事上栽了最大的一个跟头：**"这条轨迹准不准"这个问题，我思考了很久，却从没做过最直接的测量**。

我早期用的是 `traj_enu.csv` 去评估 `traj_enu.csv` —— 那是自己跟自己比，任何数字都会好看。
真相是：**参考必须是原始的 RTK 记录（`run/rtk.csv`，10 Hz，6518 点）**。
换成真参考后，ATE 从"看起来对齐良好"变成 **599.5 cm**。

> **〔术语〕RTK 与 ATE**
>
> **RTK**（实时动态差分定位）是卫星定位里唯一能做到**厘米级**的技术，本项目拿它当外部真值（详见术语表 A3）。
>
> **ATE**（绝对轨迹误差）= 把估计轨迹和真值轨迹对齐后，逐点算位置差（术语表 B11）。
>
> **注意这里真正发生了什么**：系统没变，变的**只是尺子** —— 换一把独立、可信的尺子，同一个系统立刻从"良好"变成 599.5 cm。这就是观念一的分量。

> **规则**：任何"精度/质量"问题，先花 30 分钟建立**独立的可信参考**，再讨论优化。
>
> 没有独立参考的评估，是在给自己打分。

### 观念二：**判据立错，结论全错；而且错得很像对的**

我立过一条判据："车轮正下方最低 25% 的点里，road 占比应该 > 80%，现在只有 6.48% ⇒ 语义基本失效"。

> **〔术语〕SemanticKITTI**
>
> 它是 3D 点云语义分割最常用的标注体系，定义了 19 个类别（术语表 D3）。
> **它的 `road` 特指"车道"（行车道路面）**，而 `sidewalk` / `parking` / `terrain` 是**另外的类**。
>
> 记住这条语义边界 —— 第 5 章会反复用到它。

这条判据**整个是错的**。因为 SemanticKITTI 的 `road` **特指车道**，而我们的场景是**园区铺装地**，
模型把它叫 `terrain` 未必是错。用它做判据，我给模型判了死刑，还基于这个死刑结论写了半页"换不了模型"的分析。

**正确做法是先查清标签体系的语义边界，再立判据。**

> **规则**：立判据前问三个问题 ——
>
> ① 这个指标的**语义边界**在官方定义里是什么？
> ② 这个指标能不能通过**倾斜类别分布**作弊？
> ③ 有没有**第二种独立方式**能验证同一个结论？

### 观念三：**静默错误比报错可怕 100 倍**

本项目最危险的三次事故，都**没有报错**：

| 事故 | 表现 | 后果 |
|---|---|---|
| PCD 解析时 `COUNT 1` 加了子数组维度 | numpy **静默广播** | 点云 z 飞到 286 m，不抛异常 |
| 地图与轨迹不在同一坐标系 | 两套数据各自都"自洽" | 交付物内部矛盾，评委会看到轨迹穿过空白区 |
| 装箱多读/少读 4 字节 | 数字全错但仍能算出结果 | 所有探针数字作废，白跑一轮 |

> **规则**：**凡是要下"这里有/没有某字段"的结论，先 hexdump 两条记录肉眼看一眼。**
>
> **凡是要下"这个结果不对"的结论，必须用第二种独立工具复核。**

### 1-1 Livox CustomMsg 头部隐藏的 4 字节 `data_type`

**症状**
写探针脚本时，`x` 坐标恒为 **0.0**，`offset_time` 变成 2²⁰(≈1048576) 的整数倍。整轮探针数字全部作废。

**成因**
> **〔术语〕`CustomMsg` 是什么**
>
> 激光雷达在 ROS 里传数据用的是"消息"（message）—— 一种**有固定二进制格式**的数据包（术语表 E1、F7）。
> `CustomMsg` 是 **Livox 自家**的点云消息类型，**每个雷达厂商的消息格式都不一样**，
> 所以解析它本质上是在"照图纸读字节"：图纸错一个字段，后面全部错位。

Livox `CustomMsg` 的二进制头部布局是：

```
[u32 version][u32 slot_id][u64 timebase][u32 point_num]...[u8 rsvd[3]]...[u32 data_type]...[点数据]
```

在 `rsvd[3]` 之后**还有 4 字节 `data_type`**。我第一版探针少读了这 4 字节，于是整个点区起点偏移了 4 字节 ——
从此所有字段都错位，读出来的 `x` 恰好落在全零区。

**怎么发现的**
`decode_bag.py` 里其实**已经写对了**（`off += 1+3; narr=u32; off += 4`）。
是我新写的探针脚本重新实现了读取，漏了这 4 字节。发现方式是：把两个脚本的二进制读取段并排对比，
一眼就看出探针版少了一行。

**解决**
探针脚本必须**复用** `decode_bag.py` 的读取逻辑，不要重写。并在读完后加断言：
点数 == 20016（已知值）、`x` 跨度合理。

**教训**
> **同一份二进制格式，只允许存在一份解析代码。** 复制粘贴再改 = 埋雷。
>
> 这类坑的通用防御是**断言已知量**：读之前先问"这一帧应该有多少点？跨度大概多少？"，读完对不上就 abort。

### 1-2 PCD 文件名用裸时间戳 → 字典序 ≠ 数值序 → 扫描乱序

**症状**
KISS-ICP 建图结果完全不对，位姿序列混乱。

> **〔术语〕KISS-ICP / 里程计 / 漂移**
>
> **KISS-ICP** 是本项目用的里程计：只用相邻两帧点云做**配准**（对齐），一帧帧**递推**出位姿（术语表 B3、B5）。
>
> 它简单可靠，但没有回环，**误差会随距离单调累积** —— 这叫**漂移**（B6）。
> **本坑的因果很直接**：帧的顺序喂错了，它算出来的位姿当然是乱的。

**成因**
`decode_bag.py` 最初用时间戳当文件名：`1234567890.pcd`。不同帧的时间戳有时 12 位、有时 13 位。
`sorted()` 对字符串排序是**字典序**，`"999.pcd" > "1000.pcd"` —— 于是扫描顺序被打乱，
里程计把不连续的两帧当成相邻帧配准。

**怎么发现的**
建图结果诡异 → 检查 `scans/` 目录的排序 → 发现 `ls` 显示的次序和帧号次序不一致 → 意识到是字符串排序。

**解决**
两层防御：
1. `kissicp_map.py` 改为**按 int 时间戳数值排序**，而不是 `sorted(文件名)`
2. `decode_bag.py` 写文件时**补零**（定宽格式化）

**教训**
> **用文件名表达数值顺序，是必须补零的。** 或者干脆不要用排序，直接解析出数值再排。
>
> 通用规律：**任何"看起来有序"的字符串集合，都要问一句"按字符串排序真的等于按语义排序吗"**。

### 1-3 PCD 的 `COUNT 1` 陷阱 —— 静默广播出垃圾坐标

**症状**
位姿轨迹完全正常（z 只有 6.8 m 跨度），但变换后的点云 **z 飞到 286 m**。**没有任何异常抛出。**

**成因**
读 PCD 时我把 `COUNT 1` 的字段写成了"子数组维度"：

```python
# 错的
(x, '<f4', (1,))     # → 读出来是 (N, 3, 1)
# 对的
('x', '<f4')          # → (N, 3)
```

于是 `np.stack` 得到 `(N, 3, 1)` 而不是 `(N, 3)`。
接下来 `(3,3) @ (1,3,N)` 这种形状**恰好能被 numpy 静默广播**，算出垃圾坐标 —— **不报错，只是数字全错**。

**怎么发现的**
一开始怀疑位姿有 bug，但**位姿轨迹本身是正常的**（这是关键线索：位姿正常 + 点云飞了 ⇒ 问题在点云侧）。
于是加了断言：**正确建图必须落在一个薄 z 层内** → 超过阈值直接 abort。
然后再回去看解析代码，发现形状是 `(N,3,1)`。

**解决**
1. `COUNT == 1` 时**不要加子数组维度**
2. 脚本里加**量纲断言**：变换后 z 跨度 > 60 m 直接 abort
3. 交叉验证：交付的 `semantic_map.pcd` 实测 `z ∈ [−6.9, +9.8]`（**交付物本身是好的**，坏的只是我的对比脚本）

**教训**
> **Numpy 的广播是双刃剑。** 形状不对时它常常不是报错，而是"帮你"算出一个错的结果。
>
> **防御手段：在关键计算后断言物理量纲。** "地面点云 z 跨度不可能超过 60 m" 这句话，比任何形状检查都有用 ——
>
> 因为它是**物理约束**，不是语法约束。

### 1-4 `rtk.csv` 没保存 `position_covariance` → 后来不得不回炉

**症状**
无法区分 RTK 固定解 / 浮点解 —— 两者在 `NavSatStatus` 里**都是 2**。

> **〔术语〕固定解 / 浮点解 / 单点解**（术语表 A4）
>
> 这是 RTK 解算质量的三个档位，精度分别是 **厘米级 / 分米级 / 米级**。
> **固定解**是"整周模糊度被解成整数"的最高档，是唯一能当尺子用的那一档。
>
> `NavSatStatus` 是 ROS 里表示"定位状态"的字段 —— **它把 4 和 5 合并成了同一个值 2**，这就是本坑的成因。

**成因**
`decode_bag.py` 第一版只提取了 `lat/lon/alt/status/service`。而官方文档（`dataset-guide.md`）明确列出：

| KSXT `pos_qual` | NavSatStatus | 含义 |
|---|---|---|
| 0 | −1 | NO_FIX |
| 1 | 0 | 单点定位 |
| 2 | 1 | SBAS / 伪距差分 |
| **4** | **2** | **RTK 固定解（±2 cm）** |
| **5** | **2** | **RTK 浮点解（±30 cm）** |
| 6 | 0 | 惯导定位 |

**4 和 5 都映射到 2** —— 从 status 根本分不出来。**唯一途径是 `position_covariance` 的数值量级**：

| 定位质量 | east/north 方差 | up 方差 | 精度 |
|---|---|---|---|
| 固定解 (4) | 0.0004 | 0.0016 | ±0.02 / ±0.04 m |
| 浮点解 (5) | 0.09 | 0.25 | ±0.3 / ±0.5 m |
| 惯导 (6) | 0.25 | 1.0 | ±0.5 / ±1.0 m |

**怎么发现的**
做精度统计时发现"有些帧的位置明显离谱"，但 status 全是 2。回去翻官方文档才注意到 `position_covariance` 这一行。

**解决**
写 `decode_rtk_full.py` 回炉解 bag，输出 `rtk_full.csv`（**9 元 `position_covariance` + `cov_type`**）、
`heading.csv`、`velocity.csv`。

**教训**
> **官方文档里"说明字段"的那几行，要逐字读。** 我读了 `status` 的映射表，却没读下面 `position_covariance` 的近似值表 ——
>
> 而后者才是唯一能用的判据。
> 通用规则：**凡是"两种状态合并成一个枚举值"的地方，一定有另一个字段能区分它们，去找它。**

### 1-5 `/qx/evk/heading` 是 8 字节裸 float64，没有 Header

**症状**
解析 heading 话题报错 / 解出垃圾。

**成因**
> **〔术语〕`std_msgs/Float64` / Header / 反序列化 / payload**（术语表 E1、F7）
>
> `std_msgs/Float64` 是 ROS 官方定义的一个"只装一个双精度浮点数"的标准消息类型。
> **Header** 是一段标准抬头（含序号和时间戳）——**带 Header 的消息会比数据本身多 8–12 字节**。
>
> **反序列化** = 按格式把字节流还原成字段。**payload（载荷）= 这条消息实际的字节数**。
>
> **破案关键就在这里：别信"类型名"，去量"字节数"。**

官方文档说它是 `std_msgs/Float64`，直觉上应该按标准消息反序列化（先 4 字节 header.seq，再 stamp，再 data）。
但实测发现这个 bag 里它**根本没有 `std_msgs/Header`**，就是 **8 字节裸 double**。

**怎么发现的**
`dbg_topics.py`（列 bag 内 `(topic, msgtype, payload长度)`）——
发现该话题的 payload 长度就是 8，而带 Header 的 Float64 应该 >8。

**解决**
直接把 payload 当 `<f8` 解。

**教训**
> **不要相信"消息类型"这个名字，要相信 payload 长度。**
>
> 工具：写一个"列出 bag 里所有话题 + 消息类型 + payload 长度"的脚本，是排查解码问题的第一件事。

### 1-6 `.npy` 必须用 `np.load` 读

**症状**
统计 `labels.npy` 得到 `n = 9383899`，而 PCD 头部写的是 `POINTS 9383771` —— 差 **128**，差点误报"交付物长度不一致"。

**成因**
`.npy` 文件有一个 **128 字节的头部**（magic string + version + shape + dtype 等元数据）。
用 `np.frombuffer(open(f,'rb').read(), dtype=np.uint8)` 会把头部那 128 字节也算成数据。

**怎么发现的**
差恰好是 128 —— 这个数字太特征了（npy 头就是 128 B），立刻反应过来。

**解决**
一律 `np.load(path)`。它的 `dtype=uint8` + 128 B 头 ⇒ `9383771 + 128 = 9383899`，完全吻合。

**教训**
> **"差 128"、"差 64"、"差 4" 这类数字是格式头部的指纹。** 看到整数差值先想"是不是把头部算进去了"。

### 2-1 KISS-ICP v1.3.0 的 API 与旧版完全不同

**症状**
`register_frame` 报参数错误；`poses` 属性不存在；里程计结果拿不出来。

**成因**
KISS-ICP 从旧版升级到 v1.3.0 时改了公开 API：
- `register_frame` 新增 `timestamps` 参数
- 原来的 `poses` 属性被**移除**
- 必须**手动累积** `kiss.last_pose`

**怎么发现的**
报错信息直接指出来；去翻库源码确认。

**解决**

```python
from kiss_icp.pipeline import KissICP      # 不是 from kiss_icp import ...
kiss = KissICP(config)
for frame in frames:
    kiss.register_frame(frame, timestamps)
    poses.append(kiss.last_pose.copy())    # 手动累积
```

**教训**
> **第三方库升级先看 changelog / 看源码，别猜。** 尤其是 0.x → 1.x 的版本跨越。

### 2-2 纯里程计无回环 → 2544 m 累积 24.7 m 漂移

**症状**
起终点闭合差 **24.74 m**（KISS-ICP odom）。一条 2544 m 的路线，误差 0.97%。

> **〔术语〕闭合差 / odom / 漂移**（术语表 B6、B7）
>
> **闭合差** = 车绕一圈回到起点附近时，"估计的终点位置"和"真实起点位置"的差距。
>
> **odom（odometry，里程计）** = 只靠相邻帧递推、**没有任何绝对参照**的位姿估计。
>
> **漂移（drift）** = 误差随距离单调累积。**纯里程计必然漂移，这是原理性的，不是调参能修的。**

**成因**
KISS-ICP 是**纯里程计，没有回环检测**。误差从第一帧起单调累积。
在植被主导的**非结构化校园**场景下，0.97% 是这类方法的**正常水平**，不是参数问题。

**怎么发现的**
我犯了一个关键错误：**先用了错误的参考**。我用 `traj_enu.csv`（它是拟合的输出）当参考，
于是"对齐良好"。换成原始 RTK 后才看到真相：

| 指标 | KISS-ICP odom | RTK 参考 |
|---|---|---|
| 重访一致性中位 | 143.9 cm | **23.8 cm** |
| 起终点闭合差 | **2473.7 cm** | **192.3 cm** |

**铁证**：同一辆车起终点，RTK 说差 1.9 m，KISS 说差 24.7 m。RTK 自洽性好 4–6 倍。

**解决**
不是调参，是**换架构**（见 2-4）。

**教训**
> **参考的选择决定结论的对错。** 一个"拟合出来的输出"永远不能当评估参考 —— 那是自己跟自己比。
>
> 另一个副产教训：**错误结论会自我强化**。我曾记录"起终点相距 25 m 是真实的没回到原点"——
> 那是错的，那 25 m 绝大部分是 KISS 的漂移。

### 2-3 位姿图优化的四条失败路径（**都别再走**）

**背景**
发现漂移后，第一反应是"做回环 + 位姿图优化"。我连续踩了四个坑。

**失败 1：全轨迹 `global_optimization` → cgroup OOM**

- **症状**：日志**静默停在 optimization 前一行**，进程消失。极易误判为"卡住"。
  > **〔术语〕cgroup / OOM**（术语表 F9）
  >
  > 容器里的内存上限由 Linux 的 **cgroup** 控制，**不是**物理内存上限。超限被杀叫 **OOM**。
  > **"进程莫名消失、日志停住"就是它的经典症状。**
- **成因**：容器内存上限是 **42 GiB**（`cat /sys/fs/cgroup/memory.max` = 45097156608），
  而 `open3d.pipelines.registration.global_optimization` 对 **6522 节点**的全轨迹位姿图，
  内存涨到 **43.7 GB** → 被 cgroup OOM 杀掉。`dmesg | tail` 可见 `Memory cgroup out of memory`。
- ⚠️ **`free -h` 显示 376 GB 是宿主的，别信**。
- **教训**：**远端跑大内存任务前先查 `memory.max`。**

**失败 2：降到 653 关键帧 → LM 发散**

- 内存 OK 了，但修正量均值 **340 m** / max 684 m；闭环残差 98.7 → 240.8 cm；起终点 25 → 440 m。
- **成因**：目标函数条件数太差，LM 走向了荒谬解。
  > **〔术语〕LM / 条件数**（术语表 B15、B16）
  >
  > **LM**（Levenberg-Marquardt）是求解**非线性**最小二乘的经典迭代算法。
  >
  > **条件数**衡量"输入的微小扰动会被放大多少倍"；条件数大 = **病态** = 优化器会沿某个几乎不受约束的方向乱跑。
  >
  > **优化发散时，先怀疑"目标和条件数"，而不是"迭代次数不够"。**

**失败 3：自写"顺序位姿图松弛" → 发散到 NaN**

- 残差 106 → 1208 → 5416 → … → **NaN**。
- **成因（这是本项目最有价值的一条数学洞察）**：
  在世界系里施加 SE(3) 修正量 `E = T_a · D · T_a⁻¹`，它的平移项含 `(I − R_E)·t_a` ——
  **旋转分量会被"到原点的杠杆臂"放大**。轨迹离原点越远，微小的旋转修正就越被放大成巨大的平移。

  > **〔术语〕SE(3) 与"杠杆臂"**（术语表 B20）
  >
  > **SE(3)** = 三维刚体变换（旋转 + 平移，6 个自由度）的集合，**位姿用的就是它**。
  >
  > **直觉版**：你站在离原点 500 m 的地方，有人把你的**朝向**拧了 0.1°。
  >
  > 你的位置本身没动，但"绕原点转 0.1°"意味着你被推出去约 **0.87 m** ——
  > 这就是"旋转被杠杆臂放大成平移"。**修正在"世界系"里做就会被放大；改成"局部增量"就消掉了。**

**失败 4：LSQR + 1e6 权重规范位姿 → 病态、不收敛**

- 返回废解（位移 163 m）。

**最终可行方案**（`loop_lsq.py`）

只解**位置**、不碰旋转；未知量是**对里程计的修正 `dx`**（增量形式）：

```
里程计约束：dx_{i+1} − dx_i = 0        (w_o = 1   保持轨迹形状)
回环约束  ：dx_b − dx_a     = E_ab     (w_l = 100)
极小 Tikhonov 去规范零空间；dx_0 = 0 后处理归一
直接稀疏求解：A.T@A + scipy.sparse.linalg.spsolve
```

> **〔术语〕Tikhonov 正则化 / 零空间 / 稀疏直接求解**（术语表 B17、B18）
>
> 位姿图有个"不定性"：**把整条轨迹一起平移，所有约束照样满足** —— 这个方向叫**零空间**，解不唯一。
> **Tikhonov 正则化**就是加一项 `λ·‖x‖²` 惩罚过大的解，给系统一个"锚"，让答案唯一且稳定。
>
> **稀疏**指矩阵绝大多数元素是 0；对它可以"直接求解"（`spsolve`），比迭代法更快更稳。

结果：回环残差 **105.97 → 0.00 cm**；位置修正均值 118 cm / max 252 cm。

**为什么只解位置**

回环误差分解 = 平移 106 cm + 旋转 2.5–3.3°。但**面内 yaw 误差极小**（均值 0.23°）——
那 3° 是俯仰/横滚，而在这类"植被、杂波为主的小子图"上 **ICP 不可信**，硬加进去会放大误差。

**教训**
> 1. **增量形式（解"修正量"而不是"绝对量"）能消掉杠杆臂效应** —— 这是数值稳定性的关键。
> 2. 优化失败时**先怀疑目标和条件数**，不要只调迭代次数。
> 3. **直接稀疏求解比迭代解更稳**：`A.T@A` + `spsolve` 一次成功。

### 2-4 架构纠错：RTK 是"逐帧绝对约束"，不是"事后配准"

**背景**
这是本项目最重要的一次判断修正。

**旧做法（错的）**：`geo_trajectory.py` 的全局最小二乘拟合 ——
**6522 个点被压成 4 个自由度**（1 个 scale + 1 个 R + 1 个平移）。

> **〔术语〕自由度（DoF）**（术语表 B20）
>
> **独立参数的个数**。一个 2D 相似变换最多只有 4 个（1 尺度 + 1 旋转 + 2 平移）。
>
> **这里的要点是数量级对比**：**4 个参数** 对 **1.96 万个绝对观测**。
>
> 参数太少 = 无论怎么调都装不下真实的形变。
它只决定"整张地图摆在地球哪个位置"，**完全改不了地图形状**。

比喻：**建好整栋楼再整体挪一下摆正。**

> **〔术语〕非刚性形变**（术语表 B21）
>
> **整体平移 / 旋转 / 缩放都属于"刚性或相似"变换 —— 形状不变。**
>
> 而"两端翘、中段塌"这种**形状本身变了**的，叫**非刚性形变**。
> **任何有限自由度的变换都吸收不了非刚性形变** —— 这就是本坑"数学上无出路"的真正原因。

**后果**：4 个自由度要吸收 25 m 的非刚性形变 → 做不到 → 只能把误差平均摊开
→ 这就是 **U 型残差**的来源（两端约 11 m、中段约 1.5 m）。**数学上无出路。**

**新做法（对的）**：**建图时逐帧绝对约束**。
每帧 RTK 位置 + 每帧双天线航向 ≈ **1.96 万个绝对观测**，与 KISS 相对约束联合求解
→ 轨迹**逐帧弯曲**。

比喻：**每块砖按图纸砌。**

**失败 5 条（按重要性）**

1. **架构性**：KISS-ICP 纯里程计无回环，误差单调累积。
2. **后处理能力 < 误差量级**：4 自由度吸收不了 25 m 非刚性形变。
3. **回环约束少且不独立**：51 条回环基线**全在 1760–3870 帧**（同一次重访）→ **≈1 条独立观测**，中段零覆盖。
4. **回环本身不可信**：无一条内点 RMSE < 0.15 m；最优组（fitness 0.97）仍差 1.1 m。
5. **砍旋转的代价**：只解位置 ⇒ 修正上限 2.52 m，**比待修误差小一个数量级**。

**融合实测结果**

| 指标 | odom | loop（当时的提交版） | **fused3** |
|---|---|---|---|
| 闭合差 | 24.74 m | 25.07 m | **1.90 m** |
| 重访 NN 均值 | 82.3 cm | 49.9 cm | **28.4 cm** |
| 重访 NN 中位 | 65.0 cm | 27.7 cm | **19.1 cm** |
| `<50 cm` 占比 | 40.1% | 70.1% | **85.9%** |
| 轨迹贴 RTK 残差 | 604.2 cm | — | **55.6 cm** |
| 平滑度 `curv`（二阶差分中位数之比） | 1× | — | **0.05×** |

> **`curv = 0.05×` 意味着 RTK 逐帧位置比 KISS 自己的配准输出平滑 20 倍。**
>
> 所以"注入 RTK 噪声会糊地图"这个担忧**不成立** —— **KISS 的逐帧配准抖动才是噪声源**。

**教训**
> **方法学错误（我自己的）**：曾用 `traj_enu.csv`（拟合输出）当参考评估，误判"对齐良好"，
>
> 于是把优先级押在**收益边际的回环**上。
> **正确顺序应该是：先建立可信精度基线，再决定优化什么。**

### 2-5 指标选错：墙厚看不出变化，重访 NN 才看得出

**背景**
闭环做完，怎么证明它有用？

**错误的指标**：全图/区域"墙体厚度"（PCA 平面拟合 RMS）—— 中位 **103.8 → 106.0 mm**，**完全看不出变化**。
原因：被植被杂波淹没。

**正确的指标**：**重访处两遍观测的最近邻距离**（`check_revisit.py`，A 遍点云 vs B 遍点云）。
这个指标对"同一点被观测两次"的偏差敏感，不被全局杂波稀释。

**同时被排除的用法**：NN 会被**视差**污染 ——
两趟经过本来就在不同车道（横向差 0.2–4.6 m），红蓝分离有真实视差成分，**不能当墙厚用**。
12 m 密集块里三个版本的墙厚都是 2.2–2.5 cm，**完全分不出高下**（KISS 的局部一致性本来就极好）。
**只有闭合差是干净的。**

**教训**
> **选指标先问"这个指标被什么淹没了"。**
>
> 一个被环境杂波淹没的指标，无论优化多好都看不出差别 —— 那不是"没有改善"，是"尺子坏了"。

### 2-6 归因：真凶是**竖直漂移**，不是旋转（两个假设，一个被证伪）

**假设一："剩余 60 cm 是 yaw 漂移" → 证伪**

对 20 个重访对在 ±6° 内穷举最优 `dYaw`：

```
mean −0.62° ± 2.90°     corr(最优 dYaw, 航向 dYaw) = +0.034   ← 毫无相关性
```

只降 1%。**`/qx/evk/heading` 这条线彻底放弃。**

补充：分段看 `kiss_yaw + heading` 偏移，干净段（circ_std 1.27° / 1.68°）偏移是 −105.96° 与 −106.14°，
**差 0.18°** ⇒ **KISS 的 yaw 在 5000 帧跨度上根本没漂**；段间那 7° 全是噪声段贡献的。

**假设二："竖直漂移" → 确认**

NN 误差向量分解：`|v_xy| = 48.8 cm`、`|v_z| = 63.3 cm`、`signed v_z = −46.9 cm`。
最干净的一簇重访对（传感器横向只差 23–120 cm）**12 对全部同号，稳定在 −55 ~ −61 cm**。

⇒ **两次经过同一点，地面在竖直方向差 58 cm。**

**v2 版错在哪（两个错，都要记住）**

1. **只改 x、y，把 z 整个丢了** —— 对照组 `W=1 xyonly` 的 `|v_z|` 仍是 39.5 cm，**一厘米没修**。
2. **用 2D 相似拟合去定义 3D 对应关系**。

> **〔术语〕Umeyama**（术语表 B19）
>
> 给定两组一一对应的点，**闭式**解出它们之间的最优**相似变换**（旋转 + 平移 + 尺度），不用迭代。
> **看到"Umeyama"，脑子里直接翻译成"求最优对齐变换"就行。**

第 2 条展开：3D Umeyama 解出倾角只有 **0.88°**，`local up = [0.00384, 0.01493, 0.99988]`
⇒ **KISS 局部系 z 轴本来就是竖直的**。
此前"6° 安装倾角导致 z 轴倾斜"的说法**是错的** —— 那 5.83° 是**前向轴的俯仰**，与世界系 z 无关。
2D 拟合被迫用一个**虚假的 `scale = 1.0100`** 去掩盖它。而 3D 拟合的真实 `scale = 0.98772`
（**KISS 测距偏小 1.2%**）。

**尺度含义**：KISS 漂移率 0.97%，换算到 20 m 尺度就是 **19 cm**；RTK 是 2 cm。
**RTK 在每个空间尺度上都比 KISS 准 ⇒ 选 W=1（全量修正、不低通）。**

**教训**
> 1. **归因要做"假设—证伪"**，不能拍脑袋。我对 yaw 的假设错得很自然（"3° 旋转误差"看起来很像漂移），
>    但一算相关系数就倒了。
> 2. **降维是有代价的**：把 3D 问题当 2D 做，会用一个虚假参数去掩盖真实结构。
> 3. **"哪个尺度上谁更准"是选权重的依据**，不是直觉。

### 2-7 逐帧点云未做运动补偿 —— 但**不值得修**

**症状**
`decode_bag.py` 的注释自己写了 Livox 点位布局里有 `[u32 offset_time]`，但 `decode_points()` **只读了 x,y,z**，
把 `offset_time` 和 header 里的 `timebase` 全丢了。

**实测规模**（`probe_skew.py`）
每帧 **20,016 点，扫描跨度 100.11 ms**（offset_time 从 0 连续到 100 ms）。
车以 4 m/s 行驶 ⇒ **一帧内车辆位移 40.0 cm**。每帧点云被当瞬时曝光处理 = **每帧都在斜**。

**但为什么最终决定不修（这是重点）**

去斜的**几何足迹是各向异性的**。逐格 PCA 求局部厚度 `sqrt(λ_min)`，按"局部法向与航向的夹角"分桶：

> **〔术语〕PCA 与 λ_min**（术语表 C10）
>
> 对一小块点云做**主成分分析**，得到三个特征值 `λ0 ≥ λ1 ≥ λ2`。
> 最大那个方向是"点铺得最开"的方向；**最小的 `λ2`（即 λ_min）对应"最薄"的方向**，
> 而 `sqrt(λ_min)` 就是这块点的**局部厚度**。

| 类型 | 去斜前 | 去斜后 |
|---|---|---|
| **平行于航向的面**（侧墙、路面） | 0.2 / 0.5 / 0.3 / 0.3 cm | **0.2 / 0.5 / 0.3 / 0.6 cm —— 完全不变** |
| **面向航向的面**（正对立面、车头车尾、杆） | 4.5 cm | **0.9 cm**（p90 7.5 → 2.1） |

原理：**平行于航向的面在沿轨剪切下是数学不变的**（点仍然落在同一个面上）。
而这是个**街区走廊型数据集**，绝大多数可观测表面平行于行驶方向 —— 恰好是剪切改不动的那一类。

**成本**：重解码 522 MB + 重建 1700 万点 + 重录 115 s 视频 + 重打包 216 MB。**收益不抵成本。**

**教训**
> **"发现一个问题"不等于"必须修它"。** 要先算**收益的量级**，再看落在哪些面/哪些场景上。
>
> 我第一轮把这个坑写成"下一个明确的杠杆"，第二轮实测后**主动推翻了自己的结论**。
> **这种自我纠正是对的，不是反复无常。**

### 2-8 时间偏移：先测出 +0.38 s（错），后纠正为 +0.10 s（对）

**症状**
跨相关 KISS 与 RTK 的速度剖面，定 LiDAR↔RTK 时延。

> **〔术语〕跨相关 / 时延 / 沿轨**（术语表 A13）
>
> **跨相关**：把两条信号（这里都是"速度随时间变化"）相对平移，找"最像"的那个平移量 ——
>
> 它就是两个传感器之间的**时间差（时延）**。
> **沿轨** = 沿着行驶方向。`0.4 m 沿轨` 就是"车在这段时间里往前走了 0.4 m"。

**过程**
- 第一轮用"扫描 δt ∈ [−3,+3] s 全局搜索"，最优 **+0.38 s**。
- 第二轮用"速度剖面跨相关"，最优 **+0.10 s ≈ 0.4 m 沿轨**，且**相关峰极平**（±0.2 s 内只掉 0.7%，只有一格分辨率）。

**结论**
`+0.38 s` 作废。`0.4 m / 2521 m = 0.016%`，**不值得回炉**。
另外第一轮的时移假设本身也被排除：最优 +0.38 s 只把 ATE 从 599.5 降到 588.6 cm（−1.8%），scale 稳定 1.0128。

**教训**
> **峰值平坦的相关函数，其峰值位置不可信。** 要报告"分辨率"和"峰平度"，否则一个数字会被当成精确值用下去。

### 2-9 "闭合差 1.88 m" 根本不是误差

**症状**
README 里把"闭合差 1.88 m"当误差报。评委会问：141 m 的误差怎么来的？

**实测（`probe_floor.py`）**

```
frame    0  t=400.21 s  E=+0.00 N=+0.00 U=+6.30  sigma=0.020  status=2  GOOD
frame 6521  t=1052.30 s E=+1.81 N=+0.65 U=+6.29  sigma=0.020  status=2  GOOD
RTK-only start->end:  |d| = 1.92 m
|pos − pos[0]| 在最后 300 帧的最小值 = 0.17 m（第 6272 帧）
```

- 车辆**起点静止、终点静止**，两端都是 **RTK 固定解（σ = 2 cm）**
- **RTK 自己说起点到终点差 1.92 m —— 这是真实位移，不是误差**
- 第 6272 帧（结束前 7 s）车离起点只有 **0.17 m** ⇒ 轨迹确实回到了起点附近，然后又移动 1.9 m 停下

**解决**
表格加"RTK 参考"列：

| | 水平位移 | 相对 RTK 残差 |
|---|---|---|
| KISS-ICP odom | 25.019 m | 23.096 m |
| **本提交** | **1.923 m** | **0.000 m** |
| RTK 参考 | 1.923 m | — |

另加一行**端点绝对定位误差：首帧 0.008 m / 末帧 0.009 m** —— 比"1.92 m 闭合差"有说服力得多，
它直接说明轨迹已落在 RTK 固定解自身的绝对精度量级上。

**教训**
> **一个指标如果没有明确参考，它的数值毫无意义。** "闭合差"这个词预设了"应该闭合"，
>
> 但**车本来就没回到原点**。加一列参考值，同一张表就从"自曝其短"变成"自证其准"。

### 3-1 交付物内部坐标不一致（地图在局部系、轨迹在 ENU）

**症状**
把交付轨迹叠到交付点云上 —— **穿帮**。轨迹穿过空白区，完全不贴道路。

**定量**
`semantic_map.pcd` 在 **KISS 局部里程计系**；`traj_enu.csv` 与 `path.yaml` 在 **ENU 系**。

> **〔术语〕坐标系 / 局部系 / ENU**（术语表 C1、C4）
>
> **坐标系** = "以谁为原点、轴朝哪"的约定。同一堆点换个坐标系，数值全变。
>
> **局部系**：以**第一帧位置**为原点，跟着算法走（KISS 输出的就是这个）。
>
> **ENU**（东-北-天）：一个**固定在地面上的切平面**坐标系，`x` 东 / `y` 北 / `z` 天，单位是米。
>
> **两套数据各自都自洽，不代表它们互相自洽** —— 这就是本坑。
两者差：**yaw +23.9°、尺度 1.25%、倾角 0.883°**。

**怎么发现的（三条独立证据，缺一不可）**

1. **位姿↔轨迹刚体拟合**
   `run_night.sh:34` 跑 `semantic_label_v3.py` 时**未传 `--poses`**，走了默认路径 `run2/poses_fused3.npy`。
   该数组的平移列与 `traj_local.csv` 拟合残差 **0.000 m / 0.00°**；与 `traj_enu.csv` 差 **23.91°**。
   ⇒ 地图用的是局部系位姿。

2. **物理不可能测试**（不依赖任何自定标）
   地图点到 ENU 轨迹的距离：中位 33.9 / p90 88.5 / **max 152.2 m** / **>70 m 占 15.6%**。
   **MID-360 量程 70 m ⇒ 该地图不可能属于 ENU 系。**
   施加局部→ENU 相似变换后：中位 6.9 / p90 15.4 / **max 64.3 m** / **>70 m 占 0.000%**。

3. **叠加图渲染**
   原样那条（浅红）穿过空白区；旋转后（深红）**精准骑在道路环带上**。

**交叉验证（这一条让人睡踏实）**
`s⁻¹ = 0.98764`，与管线自述的 Umeyama `scale = 0.98772` 吻合到 **0.008%**
⇒ **尺度和航向本来就算出来过，只是没施加到建图位姿上。**

**顺带确认**：地图几何本身**没问题**（变换后所有点都在量程内、外边界干净地卡在 70 m）
⇒ 这是**纯坐标系问题**，不是重建质量问题。

**教训**
> 1. **"两条数据各自都自洽"不代表它们互相自洽。** 必须做**跨交付物的交叉检查**。
> 2. **"物理不可能测试"是最好用的一类判据**：不需要真值、不需要标定，只用传感器的物理量程就能证伪。
> 3. **看到一个"差一个旋转"的巧合，先怀疑是不是同一个变换的两面。**
>    `1/s ≈ 管线自述的 scale` 就是信号。

### 3-2 修法的演进：2D 解不够，必须做 3D

**我第一轮的判断（错）**
"修法很轻：Umeyama 2D，施于 PCD 的 xyz 即可，两条轨迹 CSV 与 path.yaml 保持原样。"

**为什么错**

- 局部系相对真竖直有 **0.883° 合成倾角**（yaw +23.911° / pitch +0.548° / roll −0.693°）。
- `geo_trajectory.py` 第 109–113 行写着 `# 2D fit already rejected do not drag the altitude either`
  → 它只做了**竖直中值平移** `up_off = median(enu_z − poses_z)`，**没有做 3D 旋转**。
- 后果：**水平走 262 m，海拔假涨 3.45 m（1.32%）**。
- 关键推论：**`traj_enu.csv` 的 `up` 与 `path.yaml` 的 `altitude` 也带着这个倾角** ⇒
  它们**也必须一起改**，不能"保持原样"。
- 若只做 2D：地图被搬到 ENU 但竖直仍带倾角 → **仍然叠加不上**。

**最终变换**（鲁棒 3D Umeyama，15 轮剔最差 25%）

> **〔术语〕相似变换 / 保距 / 尺度**（术语表 B19、C12）
>
> **相似变换 = 旋转 + 平移 + 统一缩放。** 它的定义性质是**保距**：
>
> 变换前后，任意两点之间的距离只会被**同一个倍数**缩放。
> **所以只要验证"随机取一万对点，距离比是否全等于同一个数"，就能证明这个变换是干净的** ——
>
> 没有混进任何非刚性的东西。

```
s = 1.01243118    yaw +23.91124°  pitch +0.54793°  roll −0.69278°（合成 0.88327°）
t = (−6.78463, +6.69089, +1.42540) m
ENU 原点 lat 31.121152840 / lon 121.603270630 / alt 6.2988
拟合残差 中位 0.53 mm / max 3.36 mm
```

**改了什么 / 不动什么**（改动的**最小化**是纪律）

| 文件 | 改的字段 | **不动的字段** |
|---|---|---|
| `semantic_map.pcd` | `x y z` | `intensity` / `label` / `rgb` **逐字节相同** |
| `traj_enu.csv` | `up` | `stamp` / `east` / `north` |
| `path.yaml` | `altitude`（6520/6522 行） | `latitude` / `longitude` / `stamp` 逐帧相同 |

字节数与原文件完全相同（227,665,294 B）。

**验收（`fx_accept.py`）**

| 判据 | 修正前 | 修正后 |
|---|---|---|
| 地面点(label=8)平面梯度 | 1.583%（0.907°） | **0.079%（0.045°）** |
| 地面点平面 R² | 0.8233 | **0.0086** |
| 地图→轨迹距离 >70 m 占比 | 15.621% | **0.000%** |
| 同上 >40 m / max | 40.64% / 153.67 m | **1.03% / 67.17 m** |
| 同帧 位姿↔traj_enu | — | east 中位 4.3 mm、north 4.5 mm、**up 恒 0** |
| 10 万随机点对距离比 | — | **1.01243118**，std 1.19e-7（**零扭曲**） |
| `path.yaml` vs 原始 `/qx/evk`（5729 固定解帧） | — | 水平 中位 0.8 cm / max 5.3 cm；竖直 **0.00000 m** |

> **"10 万随机点对距离比 std = 1.19e-7" 是什么意思**：相似变换必须**保距**（只允许整体缩放）。
>
> 如果变换里混进了非刚性的东西，随机点对的距离比就会散开。这个判据直接证明**变换是干净的**。

**教训**
> **"轻量修法"这四个字要警惕。** 当你发现一个系统性的坐标系错误时，
>
> 先问："这个错误在**每一个**分量上都出现了吗？" 2D 解只处理了水平分量，而倾角同时污染了竖直分量。
> **改动最小化 ≠ 改动最少的分量。** 正确的最小化是：**改必须改的，一个字节都不多改** ——
>
> 所以 `label`、`rgb`、`stamp`、经纬度都要**逐字节保留**。

## 第 4 章 RTK 数据质量（被真值背叛的那种坑）

> **〔本章黑话〕** RTK 固定解/浮点解、协方差 σ、厂商占位值、NO_FIX、弧长/弦切角、OSM、"假固定解"。

### 4-1 "RTK 中断"其实是接收机在报无解

**症状**
有三段"RTK 中断"：`3521-4071`（551 帧 / 227 m）、`2061-2259`（199 帧 / 79 m）、`5911-5946`（36 帧 / 15 m）。

**实测（`probe_rtk_gap.py`）**

- 段内 **RTK 消息照常发布，10.2–12.9 Hz，最近样本 |dt| 中位 42–48 ms** —— **数据没有丢**。
- 丢的是**解算质量**：`status` 直方图 `{0: 550, 2: 10}`，即 **status = 0（NO_FIX）**。
  > **〔术语〕status / NO_FIX**（术语表 A4）
  >
  > `status` 是接收机上报的"定位质量档位"：`0 = 无解`、`1 = 单点`、`2 = 差分/RTK`。
  > **`NO_FIX` = 接收机自己承认"我算不出来"。**
  >
  > **关键区分**：消息还在发（**数据没丢**），但内容不可信（**解算质量丢了**）。
- 而 `sqrt(cov_ee) = sqrt(cov_nn) = 3.000 m`、`sqrt(cov_uu) = 5.000 m` 是**厂商占位值**（全段恒定，**不是真实方差估计**）。

**解决**
`rtk_fuse3.py` / `rtk_fuse4.py` 用 `SIG_MAX = 0.5 m` 拒掉这些帧 —— 正确。

**但重要的补充**：段内位置逐样本地面步长中位 0.41 m（@10 Hz = 4.1 m/s），**平滑合理**，
可是**无解状态的输出不可信**。现有处理（把改正量按**累计弧长**插值，再 `T = P0 + e`）
**保留了 KISS 的局部路径形状**，只叠加一个平滑斜坡 —— **不是**被拉直成弦。
在 227 m 上，KISS 弧长 227.28 m vs 该段弦长 219.01 m，**KISS 路径离弦最大 12.0 m**。

**一个 12 m 的悬念，最后是怎么收掉的**

- 起初我把它记为"米级风险"。
- 「逐点偏离 A→B 弦」剖面是决定性的图：A 段最大偏离 **12.18 m**，出现在**第 91%**（帧 4019），
  **不是中点**；剖面形状 = **线性爬升到 91%，再在最后 21 m 掉回 0**。
- 段内航向前 204 m **恒定**（−102° → −104°，净变约 2°）；末段急转 82°。
- **反证**：若它真是半径 543 m 的圆弧，前 204 m 航向该变 **21.5°**，实测只变 ~2° ⇒ **圆弧假设证伪**。
- 结论：**12.18 m 是「弦切角」不是鼓包。**
  > **〔术语〕弦 / 弧 / 弦切角**（术语表 C8）
  >
  > **弦**是两点之间的直线；**弧长**是沿曲线走的真实长度。
  >
  > **弦切角**是"弦的方向"与"曲线在端点处切线方向"之间的夹角。
  >
  > **直觉**：一段"先直行、再急转弯"的路，其中间点离两端连线可以很远 —— 但那是**拐弯**，不是**鼓包**。
  >
  > 判据是**航向在段内是否恒定**（前 204 m 只变约 2° ⇒ 是拐弯）。

**反解模型（关键时刻的杀手锏）**
用 RTK 两端切向 + 两端点钉死，直接解形状。入口切向 −102.5°、出口 −9.6°（各 60 帧窗口），差 **93.3°**。
解「直行 s + 圆弧 R 转 93.3° + 直行 t = B」两方程两未知量：

| R (m) | s | t | 总长 | 最大弦偏离 |
|---|---|---|---|---|
| 2 | 214.6 | 8.9 | 226.8 | 10.87 |
| **6** | **210.4** | **4.7** | **224.8** | **10.66** |
| 8 | 208.3 | 2.6 | 223.9 | 10.56 |
| ≥12 | **无解**（t<0） | | | |
| ∞（硬折角） | 216.7 | 11.0 | 227.7 | 10.97 |

**R = 6 m 时总长 224.8 m 与实测吻合到 0.1 m**；且 **R > 10 m 几何上放不下**。
⇒ **形状不是自由参数，是被 RTK 两端切向唯一确定的。**

残余风险从「225 m 内米级未知」收窄到「约 20 m 转角区的曲率细节（亚米级）」。

**外证（OSM 路网交叉验证）**

> **〔术语〕OSM**（术语表 C14）**OpenStreetMap**，人人可编辑的开放地图数据库。
>
> 它是**唯一不来自我们自己管线的第三方证据** —— 用来验证轨迹方向对不对，特别有价值。
> 但记住本坑后面那个反转：**OSM 自己也有数据空洞，参考源也会错。**

| | 提交轨迹 | OSM | 差 |
|---|---|---|---|
| A 段直行 263.1 m 航向 | 168.99° | 168.94° | **0.05°** |
| A 段末段转角 | −94.05° | −94.91° | **0.86°** |
| 两条拟合直线交点 vs OSM 路口节点 | — | — | 4.26 m |

全量：**87.3%** 的帧落在某条 OSM 道路 5 m 内；9 段直行中位偏差 **0.20°**；7 个转角中位 **0.60°**。
唯一"对不上"的 11%（帧 2436–3158，距最近道路 55–62 m）——
该处是 `张江集成创新园` 内部，而 **OSM 自己在该片区有一条 note：「临时性连接至秀浦路；地面道路仍待添加」**
⇒ **参考源的空洞，不是轨迹误差。**

**教训**
> 1. **"数据没丢"和"数据不可用"是两件事。** 消息还在发 ≠ 内容可信。
> 2. **厂商占位值要认出来**：σ 恒定不变（3.000 / 5.000 这种整数值）就是占位，不是估计。
> 3. **形状常常是被约束唯一确定的，不是自由参数。** 当你能用两端的信息反解出中间的形状，
>    不确定性就从"整段"收缩到"局部细节"。
> 4. **外部参考（OSM）能救命** —— 它是唯一不来自我们自己管线的第三方证据。

### 4-2 RTK 的 7 段「假固定解」—— 本项目最阴险的坑

> **〔术语〕"假固定解"是什么**
>
> 接收机**报**"我解到了固定解"（`status = 2`，协方差也是好值），但**那个位置其实是错的**。
> 它比"无解"阴险得多 —— **所有常规质量门限都会放它过去**。
> 唯一的破案方式是：拿它和"邻域高度中值"对照，或者用**单帧激光扫描**（不依赖位姿、不依赖 RTK）
> 反证"车在那个位置根本没有上下坡"。

**症状**
`/qx/evk` 在全程有 **7 段高度异常**，但 `status = 2`（固定解）、`position_covariance` 正常。

**定量**（`fx2_seg.py` 从交付数据重建）

| 段（行号） | 帧数 | t (s) | alt 范围 | 偏离邻域中值 | `σ_ee` 构成 |
|---|---|---|---|---|---|
| 1889–1938 | 50 | 589.13–594.03 | 3.232–4.980 | **−3.201 m** | 0.30 ×50 |
| 2034–2085 | 52 | 603.63–608.75 | 5.576–6.605 | +1.710 m | 0.30 ×27 + 3.00 ×25 |
| 2091–2258 | 168 | 609.35–626.07 | 0.663–4.288 | **−5.624 m** | 3.00 ×168 |
| 2798–2869 | 72 | 680.03–687.13 | 6.980–9.511 | +3.040 m | **0.02 ×2** + 0.30 ×70 |
| 3671–3690 | 20 | 767.35–769.25 | 1.090–1.235 | −0.666 m | 3.00 ×20 |
| 4021–4070 | 50 | 802.37–807.27 | 0.338–1.106 | −1.458 m | 3.00 ×50 |
| 5927–5945 | 19 | 992.95–994.75 | 4.255–5.799 | −2.056 m | 3.00 ×19 |

**合计 7 段 / 431 帧 / 6521 = 6.61%**（另有 3 帧 `alt = 0.000` 占位 → 434 帧 / 6.66%）。

σ 分级：`σ_ee = 3.00 m` **282 帧**；`σ_ee = 0.30 m` **147 帧**；**`σ_ee = 0.02 m` 2 帧**。
⇒ **149 帧（2.28%）"伪装成固定解"**，**协方差门限完全看不见它**。

**最刺眼的一条**：段 2798–2869 里有 **2 帧 `σ_ee = 0.02 m`**
（比固定解判据严格 **25 倍**）而海拔偏离 **+3.040 m**。

**为什么要修（而不是"如实保留组委会数据"）**

- 这 7 段在点云上留下**帧间 2.36 m 的地面断崖**。
- 而**单帧激光扫描**（不含位姿、不含 RTK）证明车辆在那些位置**根本没有上下坡**。
- ⇒ 保留它们不是"忠于真值"，是**把已知的坏观测灌进地图**。

**四条判据的重新校准（**重要，别再用错**）**

| 判据 | 结论 |
|---|---|
| ① 协方差门限 `cov_ee` | 只拦得住 282 帧，**149 帧漏网** ⇒ **不充分** |
| ② 高度变化率 | 辅助 |
| ③ **帧间地面步进** | **对断崖级异常是决定性的**：旧位姿 max **2358.8 mm**（4 对 >1 m）→ 新位姿 **520.2 mm**（0 对 >1 m） |
| ④ 单帧地面平面拟合 | **分辨不出小坡度**，只能给大坡度设上界 |

**判据 ④ 的正确用法（`fx_slope.py` 最终版）**
- 航向**取自里程计**（`odom[k,:3,:3].T @ d`），**不拟合** ——
  从 0–180° 里挑与 RTK 相关最大的方向**等于拿答案造指标（循环论证）**。
- 窗口用**紧邻 ±70 帧**并排除所有异常段。
- 结果：要求俯仰 **7.6°–25.6°** vs 实测 **≤0.038°**，噪声底 **0.012°**。
- **诚实边界**：干净路段逐帧相关仅 **−0.022** ⇒ 判据 ④ 对**小**异常无分辨力，只能说
  "若有断崖级坡度必被看到，而没看到"。

**两条被我自己否掉的判据（写进 AUDIT §8，避免后人重复）**

- `fx_odom_z.py`（里程计 z 与 RTK 对比）：噪声底 155 个干净窗口中位 **1467 mm**、p99 **8463 mm**
  ⇒ 完全被里程计漂移淹没，**证伪**。
- 6×6 分块平面拟合：上一版 1.382°/44.65° vs 本版 0.985°/42.67° ⇒ **无分辨力，已撤下**，
  未在任何结论中引用。

**处置口径**
**只丢高度、不丢水平** —— 异常帧只插值**竖直改正量**，`lat/lon` **原样保留**；
插值沿**累计弧长**（非时间）。判据：40 s 中值窗 + 0.5 m 容差 + 5 帧最小段长。

**教训**
> 1. **"status = 固定解"不等于"这个解是对的"。** 传感器会骗你，而且是在它最自信的时候骗。
> 2. **一个门限拦不住所有异常，要有"独立的第二道门"。** 协方差门限看不见伪装帧，高度中值一致性门限能看见。
> 3. **"只丢坏的那个分量"比"整帧丢弃"更聪明。** 一个把高度打偏 5 m 的解，它的平面位置并没有跟着坏。
> 4. **判据要标注适用边界。** "判据 ④ 只能设上界、不能分辨小坡度" 这句话如果不写，
>    下一个人就会拿它去证一个它证不了的东西。
> 5. **循环论证要主动防范**：从 0–180° 里挑一个和答案最相关的方向，是在拿答案造指标。

### 4-3 统计 RTK 精度必须只取固定解帧

**症状**
对 RTK 做逐帧精度统计，p90 得到 **9.6 m** —— 看起来 RTK 很差。

**成因**
混入了**降级帧**。降级报文的 lat/lon/alt **本身就是废值**（`alt` 会报 0.000 或 0.510）。

### 5-1 intensity 必须 ÷255（否则 56% 点变 traffic-sign）

**症状**
Cylinder3D 推理结果里 **56% 的点被判成 traffic-sign**。

> **〔术语〕intensity（回波强度）与"量纲"**（术语表 A12、D18）
>
> **intensity** 是激光回波的强弱，反映物体表面反射率。
>
> 问题在于**不同数据集对它的取值范围约定不同**：SemanticKITTI 用 **0–1**，Livox 原始输出是 **0–255** ——
> **差 100 倍**。而模型不会说"你量纲错了"，它只会给你一个**错得很具体**的答案。

**成因**
SemanticKITTI 训练时 intensity 用 **0–1** 量纲；我们的原始 Livox 数据是 **0–255**，**差 100 倍**。
模型完全被这个异常输入带偏。

**怎么发现的**
看类别分布异常（traffic-sign 不该是大类）→ 逐字段检查输入 → 发现 intensity 量纲问题。

**解决**
`--norm-inten`，除 255。之后分布正常（sidewalk / terrain / road / vegetation / building 主导）。

**教训**
> **域外推理时，逐个输入通道核对量纲。** 模型不会告诉你"你的输入量纲不对"，它只会给你一个错得很具体的答案。

### 5-2 选错 backbone：柱面划分对我们的传感器是惰性的

> **〔术语〕backbone / 归纳偏置 / 柱面划分**（术语表 D6、D7、D8）
>
> **backbone** = 模型里负责"提特征"的主体网络。
>
> **归纳偏置** = 模型**天生自带**的假设（比如卷积网络假设"相邻像素相关"）。
>
> **柱面划分** = Cylinder3D 用"到传感器的距离 ρ + 方位角 θ + 高度 z"来切空间，而不是用直角坐标切 ——
>
> 这套假设**专门为机械旋转式激光雷达设计**（那种雷达扫出来就是一圈圈的稳定环）。
> **我们的雷达不是那一种。** 偏置和数据不匹配时，那部分设计就是白搭。

**症状（最初被误读成"模型不行"）**
Cylinder3D 输出看起来"系统性错位"（体素纯度 p25–p90 全是 1.000 ⇒ **不是噪声，是成片的稳定错判**）。

**真正的成因**
SFPNet（ECCV 2024）论文里对 Cylinder3D 做了直接消融：

> **Cylinder3D 的柱面划分（cylindrical partitioning）在非机械旋转激光雷达上几乎不起作用
>
> —— 在 S.MID 上只带来 +1.2%，在 PandaSet 固态上只到 55.0%。**

Cylinder3D = `(ρ, θ, z)` 柱面划分 + 固定网格，这套归纳偏置是为**机械旋转、等角度光束环**设计的。
Livox MID-360 是**双棱镜非重复扫描**，每帧点云路径不固定、**没有稳定光束环**。

⇒ **我们选的 backbone，它最核心的设计在我们的传感器上是惰性的。** 这不是推测，是作者量出来的。

**解决**：换 SFPNet（稀疏焦点调制，**不引入任何雷达类型的归纳偏置**）。

**换完之后的对照实验（152 帧，跨全程 stride 43，两模型跑同一批帧、同一组位姿、同一份几何）**

| 判据 | Cylinder3D | SFPNet |
|---|---|---|
| F1 surface | .772 | **.809** |
| F1 elevated | .456 | **.515** |
| **F1 均值** | 61.4% | **66.2%** |
| 几何不可能桶占比（越低越好） | 24.4% | **19.3%** |
| 把真·平坦点标成垂直类（越低越好） | 20.6% | **11.6%** |
| 两版判断相反的 98,531 点中可裁决的 71,420 点的胜率 | 16.8% | **83.2%** |

**教训**
> **选模型要看"归纳偏置 vs 你的传感器"这一对，不是看论文的 mIoU 排名。**
>
> 一个在 KITTI 上 68.8 的模型，在一个它**天生不适配**的传感器上可能还不如 71.9 的那个。
> **并且：论文里的消融数字，要能在自己的数据上复现一遍才算数。**

### 5-3 SFPNet checkpoint 加载：spconv 的两种权重布局

**症状**
> **〔术语〕state_dict / 权重布局**（术语表 D10）
>
> `state_dict` = "参数名 → 张量"的字典，加载模型就是把这些张量塞进网络。
> **权重布局** = 同一个卷积核在内存里的排列顺序（`[输出通道, 核, 输入通道]` 还是 `[核, 输入通道, 输出通道]`）。
>
> **"形状不匹配"的报错，十有八九会被误判成"模型结构不对"，其实可能只是排列顺序不同。**

`load_state_dict` 报形状不匹配。同一个模块里：`focal_layers.0` 是 `(32,3,3,3,32)`，
而 `focal_layers.1` 却是 `(5,5,5,32,32)` —— **两种布局混在一个 checkpoint 里**。

**成因**
spconv 的权重布局**取决于 algo 与编译期宏**（`spconv/pytorch/conv.py` ~line 128）：

```python
if self.algo == ConvAlgo.Native and not ALL_WEIGHT_IS_KRSC:
    weight_shape = [*kernel_size, in_channels, out_channels]   # RSCK
else:
    weight_shape = [out_channels, *kernel_size, in_channels]   # KRSC
```

algo 按核体积 `kv` 自动选，**阈值 32**：
- `k=1`（kv=1）/ `k=3`（kv=27）→ 走 MaskImplicitGemm → **KRSC**
- `k=5`（kv=125）/ `k=7`（kv=343）→ 掉到 Native → **RSCK**

**SFPNet 的 focal 调制核长恰好是 3 / 5 / 7 ⇒ 一个 checkpoint 里同时存在两种布局。**

我们的 wheel `ALL_WEIGHT_IS_KRSC = True`，所以只需把 RSCK 张量 `permute(4,0,1,2,3)`。

**解决**
写 `sfpnet_ckpt.py::load_aligned()`（**按模型期望的形状自动找轴**，通用）。
结果：`OK=388 / layout-repaired=18 / unfixable=0 / strict=True 通过`。
18 个里还包括 stride=2 的 `unet.conv` 降采样核 `(2,2,2,64,32)`。

**教训**
> **"形状不匹配"有很多种原因，编译期配置是常被忽略的一种。**
>
> 一个"通用对齐器"（按目标形状自动找转置轴）比一串硬编码 `permute` 更耐用。

### 5-4 判据立错："轮下 road 占比应 >80%"

**症状**
我立了判据"车轮正下方最低 25% 的点里 road 占比应 >80%，现在只有 6.48% ⇒ 语义基本失效"，
并据此写了"两个模型都差不多、换模型不治本"的结论。

**成因**
**SemanticKITTI 的 `road` 特指车道**。我们的场景是**园区铺装地**，模型把它叫 `terrain` 未必是错。

**后果链条（值得警惕）**
判据错 → 结论错 → 优先级排错（我把时间花在别处）→ 直到另一个独立判据组（几何审计）给出相反结论，才推翻。

**解决**
改成**两层判据**：
1. **是不是地面类？**（轮下任一 ground 类占比：Cylinder3D 81.8% / SFPNet **89.1%**）
2. **ground 内部切分是否与几何一致？**（road/sidewalk/terrain 中位高度差只有 1–8 cm ⇒ **不一致**）

并在 README §1.5.1 里**明确承认了这次判据设计错误**。

**教训**
> **立判据前先查清标签体系的语义边界。**
>
> 这个错误的代价是：我基于一个错判据写了半页分析，还差点据此决定"不换模型"。
> **判据错了，后面的推理越严密，错得越远。**

### 5-5 无真值怎么评数据质量：三个不依赖标注的判据

**问题**
数据库没给语义真值。任何 mIoU 都是编的。

> **〔术语〕mIoU / 伪真值**（术语表 D13、D14）
>
> **mIoU** = 所有类别的 IoU（交并比）求平均，是点云语义分割最常用的总指标 ——
>
> **但它必须有"真值标注"才成立**。没有真值，算出来的 mIoU 只是在跟自己的假设比。
>
> **"伪真值"** 的思路是：构造一个**不依赖标注、又客观存在的物理量**当参照
>
> （本章用的是"每 1 m 格的地面高度"）。

**判据一：几何伪真值**（不依赖标注）
每 1 m 格内取 z 的**低 5% 分位**当"该处局部地面"；
- `dz < 0.5 m` ⇒ 判为**表面**
- `dz > 2.0 m` ⇒ 判为**空中结构**

算 surface / elevated 的 recall、precision，取 F1 均值。

**判据二：分歧点上的几何裁决**
两版标注**判断相反**的点（98,531 个），其中 71,420 个可由几何裁决
⇒ **Cylinder3D 对 16.8%，SFPNet 对 83.2%（差 66.4 个百分点）**。

> 这个判据的威力在于：**它只使用"两版不一致"的点，天然免疫类别分布倾斜**。

**判据三：体素纯度**
0.4 m 体素的主标签占比 p25–p90 全 = **1.000**，≥0.9 占 80.5%，随机基线 0.385。
⇒ **标签不是噪声，是成片的系统性错位**（稳定地判错）。
这条判据的作用是**区分"随机错误"和"系统性错误"** —— 修复策略完全不同。

**外加外部仲裁**：OSM 路网（初赛用过）；复赛可换 Gazebo GT。

**教训**
> **没有真值不等于不能评估。** 构造"伪真值"的关键是：
>
> **找一个不依赖被评对象、且不能靠倾斜分布作弊的物理量。**
>
> "每 1 m 格的 z 低 5% 分位"就是一个 —— 它是几何事实，不是标注。

### 5-6 地面三级细分输出的是「距离」不是「材质」（不可恢复）

**症状（boss 肉眼观察，全部命中）**

> **〔术语〕伪影（artifact）**（术语表 D19）
>
> **不是真实存在、而是由测量或算法产生的假结构。**
>
> 伪影最危险的地方是它**"看起来很有结构"**，很容易被当成真实语义。
> 本坑就是典型：地面被细分出的 `sidewalk` / `terrain` 看起来"像斑马线"、"像涟漪"，
> 实际上模型输出的是**"到传感器的距离"**，跟材质一点关系都没有。
- Cylinder3D 的 sidewalk / terrain 交替出现，"**像斑马线**"
- **car 每隔一段出现一次；附近地面呈"以 car 为中心、近处 sidewalk、远处 terrain"的同心圆，像潜艇声呐的涟漪**
- SFPNet 的"圆"更大、色块更规整

**决定性检验（同一 0.5 m 格内，排除材质混淆）**

| | sidewalk 点均值距离 | terrain 点均值距离 | 差 | sidewalk 更近的格子占比 |
|---|---|---|---|---|
| Cylinder3D | 5.0 m | 9.0 m | **−3.80 m** | **95.3%** |
| SFPNet | 5.8 m | 9.1 m | −2.81 m | 87.7% |

全局 sidewalk 占比随距离：
- Cy3D：0–1 m **87.0%** → 4–6 m 57.5% → 6–8 m 30.8% → 12–16 m **0.4%**（分界 ~6 m）
- SFPNet：0–1 m **74.7%** → 4–6 m 48.5% → 8–12 m 27.9% → 12–16 m **17.4%**（分界 ~7.5 m）

**⇒ 分界半径差 = boss 肉眼看到的"SFPNet 圆更大"，精确吻合。**
**涟漪成因 = 每帧以自身传感器为中心的距离偏差 × 多帧叠加。**

**结论**：ground 细分层**不可信**。用世界系粗糙度与"到路线距离"做相关，r = +0.36 ——
但**单程采集下"到路线距离"就是距离的代理**，波束足印效应（r = +0.60）没被除掉。

> **〔术语〕波束足印（beam footprint）**（术语表 D22）
>
> 激光束不是无限细的线，打到远处会散成一个**光斑**；距离越远，光斑越大、测量越模糊。
> 这是一个**与距离强相关的物理效应**，很容易和真实地形变化混淆 ——
> 所以"用距离相关的特征做分析"时，必须警惕它。
**没有任何距离无关的几何特征能切分地面。**

**解决**：**地面五类归并到 `road`**。这与"fence/building 不合并"形成对比（见 5-7）。

**教训**
> 1. **一个模型输出"看起来有结构"，不等于那个结构是语义。** 要做**混杂因素控制实验**：
>    在同一个物理位置（同一 0.5 m 格）里比较，才能排除材质差异。
> 2. **"分界半径"这种参数化的伪影，往往对应一个物理量**（这里是到传感器的距离）。
>    找到那个物理量，就能一眼看穿。
> 3. **归并是一种"承认不知道"的诚实做法。** 它不是偷懒，是纠错。

### 5-7 fence 与 building 不要合并（与 5-6 的分界在哪）

**核查**
- 离地高度（相对 1 m 格内 z 的 5% 分位地面）：`building` p50 **3.03 m**（65.4% >2 m）；
  `fence` p50 **1.52 m**（34.6% >2 m）⇒ **模型确实按高度把两者分开了**，这是正确的物理线索。
- 两者都薄（2 m 格 PCA 的 λ2/λ0 ≈ 0.28）；0.5 m 邻域内互相出现率 81–89%（墙边就是栅栏，**正常**）。

**不合并的理由**
与"地面三级细分"情况**不同**：
- 那个是模型**伪影**（输出的是到传感器的距离）⇒ 归并 = **纠错**
- 这个是**真实存在的两类几何**，只是边界模糊 ⇒ 合并 = **自创标签体系**

⇒ 按类打分时直接让其中一类归零、另一类被不同高度的点污染，**净亏**。

**教训**
> **"要不要合并类别"不能用同一把尺子。**
>
> 判据是：**这个区分在物理世界里存在吗？**
> 存在但模糊 → 保留；不存在（是模型伪影）→ 归并。
> 这条区分能力，是我在这一轮里学到的最有用的判断。

### 5-8 car 就是自车

**症状**
地图上有一类"car"，**每隔一段距离出现一次**。

**实测（boss 判断正确）**
- 152/152 帧都有 car，中位 692 点/帧（Cy3D）、928（SFPNet）
- 到本帧地面质心的**水平距离中位 1.42 m**（p90 2.55 m）
- **垂直偏移 +1.07 m**（p10 +0.90 / p90 +1.46），**全程稳定**
- car 点覆盖全程 `x[−4,219] y[−29,316]`

⇒ 车顶 Livox MID-360 **扫到自身车体**。官方要"场景"点云，**自车不是场景，应剔除**。

**解决**
`semantic_label_v3.py` 中 `keep = ~np.isin(lab, DYNAMIC_SKIP)`（DYNAMIC_SKIP = 0..7）。
实测交付 `semantic_map.pcd`：动态类**只剩 2 个点**（0.00%）。

> 注：boss 在对比查看器里还看到 car，那是因为**对比数据是刻意保留的**（`build_cmp` 不过滤）。

**教训**
> **"数据里出现了车"和"场景里有车"是两件事。**
>
> 判断依据是**几何稳定性**：自车的位置在传感器坐标系里**永远固定**（1.42 m / +1.07 m 全程稳定），
> 而场景里的车会移动。

### 5-9 颜色链路有损（下采样对颜色求平均）

**症状**
提交 PCD 反推的类别分布 ≠ 模型原始输出：
vegetation 29.9% → 38.55%（**+8.6pp**）、sidewalk 18.8% → 8.22%（**−10.6pp**）、fence 5.7% → 1.97%。

**成因**
`semantic_label_ml.py` 的融合链：
```
按标签上色 → voxel_down_sample(0.15) 颜色被平均 → colors_to_labels 用颜色最近邻反推标签
```
体素内混类 → 平均色 → **最近邻可能落到第三个类**。

**解决**
**下采样时对标签做多数投票，不要对颜色求平均。**

**教训**
> **凡是"编码 → 变换 → 解码"的链，都要问"这个变换在这条链的哪个空间里做的"。**
>
> 在颜色空间做下采样，等于把标签信息降维丢失。

**症状**
`zebra.py` 算出 Cy3D 的 sidewalk 只有 **182 格**，而另外两个实现算出 **17415 格** —— 差 100 倍。

**怎么发现的**

### 5-11 交付 PCD 缺 `label` 字段（第一版）

**症状**
"pcd 点云与语义标注信息"这一项 —— 我们的 `semantic_map.pcd` **只有 rgb，没有 label 字段**。
评委要量化评估只能自己拿调色板反解。

**成因**
早期设计只想着"给人看"，用正则 `rgb` 存颜色。但赛题要求的是**语义标注**，评审要按类算准确率。

**解决**
PCD 加 `label` 字段：`FIELDS x y z intensity label rgb` / `TYPE F F F F U F` / `POINTS 9383771`，
另存同序的 `labels.npy`。

**另一个相关的坑（差点误报交付物缺颜色）**
我做 rgb 统计时，把 `rgb` 从 float32 **值转换**成 uint32（而不是 `.view()` 位重解释）：

```python
# 错的：值转换
rgb_u = arr[:, 3].astype(np.uint32)      # float 值 3.2e-39 → uint32 → 0
# 对的：位重解释
rgb_u = arr[:, 3].view(np.uint32)        # 把 32 位浮点当 32 位整数读
```

于是算出"**rgb 全 0，100%**"，差点误报交付物没有颜色。

**怎么发现的**
**hexdump 了两条记录肉眼看**：

```
rec0 00000000 00 00 80 3f | ...
as f4: [...]
as u4: [...]
```

一看 rgb 那 4 字节其实是有值的。

**解决**
用 `.view()`；PCL 约定的解码是 `r = (rgb_u >> 16) & 255; g = (rgb_u >> 8) & 255; b = rgb_u & 255`（**r 在高字节**）。

**教训**
> **"值转换"和"位重解释"是两回事，写 numpy 时最容易混。**
>
> 凡是把一种类型"当成"另一种类型读，必须用 `.view()`，并且**先 hexdump 两条记录确认**。

### 6-1 从"假回放"升级为"真·在线"

**症状（被 boss 目视发现）**
录屏看起来是"彩点云 + 红线延伸 + 白点被照亮又消失"。
检查 `rviz_replay.py` 头部自述：**`replays the full 652 s run`**。
`/map` 一次性 latched 发完静态成品，`/traj` 逐帧 append 已存位姿，`/current_scan` 逐帧发已解码扫描。

> **〔术语〕latched（锁存）话题**（术语表 E4）
>
> 普通话题只在"发布的那一刻"把消息送出去，晚连上来的订阅者什么都收不到。
> **latched 话题会把最后一条消息留在内存里，任何新订阅者一连上就立刻收到** ——
>
> 适合发"一劳永逸"的静态数据（比如整张成品地图）。
> **⚠️ 顺带一个判断技巧**：如果一份"运行录屏"里的东西**全部来自 latched 的成品**，
>
> 那它就**不是"运行过程"**。
**零在线计算**（无配准、无优化、无增量建图、无在线推理）。

**而赛题要的是「SLAM 算法运行**全过程**录屏」。**

**解决**
写 `slam_online.py`（约 460 行），每帧现场跑：
① KISS-ICP 逐帧配准 → ② SFPNet 逐帧推理 → ③ 用融合位姿把该帧搬进世界系做增量建图

### 6-2 RViz 的 PointCloud2 `Decay Time` 没有"替换"语义

**症状**
逐帧发增量小包，屏幕上**重影**（重复点越堆越多），最后"一点地图都没有"。

**成因**
`Decay Time` 的语义是：
- `0` = **永久累积**（重复点越堆越多）
- `>0` = 显示**最近 N 秒收到的所有点**

**没有"替换"语义** —— 它不是"覆盖上一帧"。

**解决**
**每帧重发整张累积地图**（`PUB_EVERY=1`）+ `Decay Time: 0.35`
（**必须 > 发布间隔 0.24 s**，否则大部分时间屏幕空白）。

改完之后：从"一点地图都没有"变成**连续铺开**。

**教训**
> **一个参数的名字不代表它的语义。** "Decay Time" 听起来像"淡出时间"，
>
> 实际是"显示窗口长度"。**读文档/读源码，别猜。**

### 6-5 视频"只拍了一角"：RViz 相机的两个反直觉语义

**症状（boss 发现）**
`视频没有拍全整图，只拍了一角。`

**定量确认（不是目视，是量出来的）**
抽旧 `slam_run.mp4` 的 t=165 s 帧，量**彩色像素**（`sat > 40`，即语义地图 + 轨迹）的包围盒：

| | 视口 | 彩色内容 bbox | 横向占比 | 留白 L/R/T/B |
|---|---|---|---|---|
| 旧 | `x[364,1263] y[62,690]` = 900×629 | `x[364,1263] y[234,690]` | **100.0%（溢出）** | **0 / 0 / 172 / 0** |
| 新 | 同上 | `x[508,1149] y[202,601]` | **71.3% × 63.6%** | **144 / 114 / 140 / 89** |

旧机位：`Distance 330 / Focal Point (104,128) / Yaw 3.14 / Pitch 1.05`。
焦点比地图水平重心 `(39.5, 168.5)` **偏了 64 m / 40 m**，距离也太近
⇒ **左、右、下三边同时被裁**。

> **〔术语〕Orbit 相机（轨道相机）**（术语表 E6）
>
> RViz 的默认相机模型：**相机绕着一个"焦点"转**。四个参数是
> **Focal Point**（看向哪个点）/ **Distance**（离焦点多远）/ **Yaw**、**Pitch**（方位与俯仰）。
>
> **关键推论：焦点必须先放对** —— 焦点错了，你怎么转都拍不到东西。
>
> 我们的旧焦点离地图重心偏了 **64 m / 40 m**，这就是"只拍了一角"的根因。

**两个 RViz 反直觉语义（本轮最大的发现，也是最费的功夫）**

1. **`Pitch` 从正下方量起**：
   `0` = 相机在**正上方俯视**，`π/2` = 相机落在**水平面**上。
   ⇒ **`Pitch: 1.05 rad` 是约 30° 俯角，不是 60°。** （我一直按"从水平面量"理解，所以怎么调都不对。）

2. **`Yaw` 的绝对值由 `Focal Point` 决定**：
   `Yaw = 0` 时相机自身 −Z 才对准 `−Y_world`，地图长轴（ENU 北向，跨度 452.8 m）
   才落在画面水平方向。
   ⇒ **焦点没放对之前，怎么调 `Yaw` 都不对。** 之前把 `Yaw: 3.14` 当"转 180°"是错的，正确值是 `0`。

**修法：只动 5 个数**（`mk_rviz_framefix.py` 从 `slam_online.rviz` 生成修正版，5,966 B）

| 项 | 旧 | 新 |
|---|---|---|
| `Focal Point` X/Y | 104 / 128 | **39.5 / 168.5**（= 地图水平重心） |
| `Grid.Offset` X/Y | 104 / 128 | **39.5 / 168.5** |
| `Distance` | 330 | **520** |
| `Yaw` | 3.14 | **0.0** |
| `Stats3D` MarkerArray | Enabled **true** | Enabled **false** |

`Pitch: 1.05` **不动**。

脚本纪律：逐条 `assert count == 1` 后替换，末尾再断言旧值不残留。

**教训**
> 1. **"调不对"往往是因为语义理解错了，不是因为参数空间太大。**
>    一旦搞懂 `Pitch` 从哪量、`Yaw` 由什么决定，5 个数字就解决了。
> 2. **`Stats3D` 是 3D TEXT Marker，在相机构图里本来就读不清** —— 遥测一律交给独立的 Tk 屏幕叠加层。
>    这解释了为什么"地图上的文字看不清"这件事根本不该修，该换方案。

### 6-6 两条失败的反标定路线（**别再试**）

**背景**
想让"选机位"这件事自动化，于是尝试从视频像素反推相机参数。

**路线一：`camfit.py`**
用视频里的红色轨迹像素反标定相机（固定 `D`/`fovy`，只拟合方向与焦点）。
- **失败**：红色像素只有 **1100 个 2× 格**；而且拟合完后发现 **那条红线与地图不是同一个东西**
  （红色像素横跨 `x 364..1183`、有断续与锯齿，是**一条很长的红色线状物**；
  真正的 `TrajectoryFused` 是贴在紫色地面带上的细线）。
- cost 26 px，属于**噪声**。

**路线二：`fovfit.py`**
用探针截图反标定 `fovy`。
- **失败**：各候选的最优点**全部顶到搜索边界**（`fovy` 39–74° 都出现），F1 最高仅 **0.28** ⇒ 不可靠。

**有效的做法：远端探针实测**

- `probe_pub.py` —— 把交付地图抽稀（`NTH=8`）+ `traj_enu.csv` 一次性 **latch** 发布
- `probe_sweep.sh` —— 一次起 Xvfb / roscore / 发布节点，然后**逐个候选重启 rviz 拍照**
- 候选格式：`TAG DIST FOCAL_X FOCAL_Y YAW PITCH`，**秒级出图**

**教训**
> **从"结果图像"反推"参数"看起来聪明，实际上极不可靠** —— 因为你先要假设"图像里的这个东西就是我以为的那个东西"。
>
> 而这个假设一旦错（红线不是轨迹），整套拟合就变成在拟噪声。
> **正确做法：直接控制输入（改配置 → 重跑 → 拍照），一次一变量。**

### 6-7 量构图的正确做法

**规则**
**不要目视估，要量。**

> **〔术语〕视口（viewport）**（术语表 E9）
>
> **窗口里真正显示三维画面的那块矩形。** RViz 的视口**不是整个窗口** ——
>
> 左边有 Displays/Views 面板、底部有状态栏，都不算。
> 本项目 1280×720 窗口里，视口实际是 `x[364,1263] y[62,690]` = **900×629**。
> **量构图之前必须先把这块矩形算准**，否则"占比 71.3%"从根上就是错的。

1. 抽一帧，取**强彩色像素**（`sat > 40`）—— 即语义地图 + 轨迹，天然排除灰色 UI
   > **〔小注〕`sat`** = **saturation（饱和度）**，就是"颜色有多浓"。
   >
   > 最常见的近似算法是"RGB 三通道最大值减最小值"：**灰色 UI 的 sat ≈ 0，彩色地图的 sat 很高**，
   > 所以拿它当"彩色掩膜"最省事 —— 不用去认"这块是面板还是地图"。
2. 视口边界靠**自动探测**："第一段连续亮列"（左栏面板）+ 亮行段（顶部菜单带 / 底部状态栏）
3. 算彩色像素包围盒的**四边留白**，要求**四边均不触界**

**这里有个坑**：自动探测视口边界时，`cols.max()` 会撞上**窗口右侧亮边框**
（x = 1264–1279 也是亮列）⇒ 视口宽度算成**负数**、彩色像素统计为空。
**必须取第一段连续亮列的末尾。**

**验收标准**（本交付）：视口 `x[364,1263] y[62,690]`（900×629），
地图 `x[508,1149] y[202,601]`，占比 **71.3% × 63.6%**，四边留白 **144 / 114 / 140 / 89 px**，**最小 89 px**。

**教训**
> **"看起来居中"和"量出来居中"是两件事。**
>
> 而且量的时候要**只量你关心的东西**（彩色像素），不要让背景/UI 混进来。

### 6-9 `setpts` 变速不改时长（以及 raw 时长 ≠ tick 时长）

**症状一**
用 `setpts=PTS/F` 压缩 PTS，但 `ffprobe` 报的 `Duration` 看起来没变。

> **〔术语〕PTS / setpts / ffprobe**（术语表 E12）
>
> **PTS**（Presentation Timestamp）= 每一帧的"显示时间戳"。
>
> **`setpts=PTS/F`** 就是把所有时间戳除以 F —— 这是最常用的**变速**手法。
>
> **ffprobe** 是 ffmpeg 套件里"读取媒体文件信息"的工具。
>
> **注意**：`setpts` 只压缩时间戳，输出**仍停在同一时刻**，
>
> 要正确报时长需配合 `-vsync cfr` / `-r`。

**成因**
`setpts` 只压缩时间戳，**输出停在同一 t**。要正确报时长需要配合 `-vsync cfr` / `-r` 等。
⚠️ 另一个更基础的概念区分：

| 概念 | 值 |
|---|---|
| **raw 录屏时长**（`slam_run_online_full.mp4`，含启动 + 收尾全图发布） | **恒为 4′32.16″** |
| **tick 循环时长**（`RUN_COMPLETE` 报的） | **258.3 s** |

**这两个不是一回事。** README 里的"原始时长"指的是前者。

**解决**
写 `speed_calc.py` 统一算倍率（目标 112 s → `F = 2.43`），再用 `setpts=PTS/$F` +
`drawtext`（右下角烧入 `PLAYED AT 2.43X`）+ libx264。

**教训**
> **"原始时长"这个词要定义清楚** —— 是"文件时长"还是"算法运行时长"？
>
> 不问清楚，同一个数字会有两种含义，然后写进文档就再也分不清了。

### 6-10 无头 WebGL POINTS 管线静默失败

**症状**
本地做语义对比查看器，用 WebGL 渲染点云：**画面全白**。

> **〔术语〕WebGL / shader / z-buffer**（术语表 E13）
>
> **WebGL** 是浏览器里的 GPU 三维绘图接口；**shader** 是跑在 GPU 上的小程序。
>
> **z-buffer（深度缓冲）** 是"每个像素当前最近深度"的表，用来判断谁挡住谁 —— 三维渲染的基础。
>
> **为什么值得记**：WebGL 快，但在无头/虚拟显示环境下**容易出兼容问题，且报错信息不可靠**
>
> （`getError` 只说"我检测到一次非法操作"，不说"这是根本原因"）。
`getError()` 返回 **1282 (INVALID_OPERATION)**。
但 shader 编译、link、attribute 位置、uniform 位置、VBO 大小**全部自检正常**。

**排查方式**
把 shader / attribute / uniform 状态**直接渲染到 HUD 上用截图读** —— 全绿，但画面还是白的。

**解决**
**不继续深挖，改用 Canvas 2D + 自建 z-buffer。**
115.9 万点重投影 ~25 ms，够用且无兼容性坑。

**教训**
> 1. **`getError` 会骗人。** 它报的是"我检测到的那次操作非法"，不等于"这是根本原因"。
> 2. **当一条技术路线在无头环境里表现不稳定时，换一条更笨但更可靠的** ——
>    25 ms 的 Canvas 2D 和 5 ms 的 WebGL，在"生成本地 HTML 给 boss 看"这个需求下完全等价。
> 3. **不继续深挖也是一种决策**，前提是记录清楚（本项目把这条写进了记忆）。

### 7-3 `stamp` 用绝对秒还是相对秒 —— 必须回原始 bag 才能定

**症状**
官方样例是 `1.77e9`（绝对 Unix 秒），我们是 `400.2 ~ 1052.3`（相对秒），**看起来像不合规**。

> **〔术语〕Unix 秒 / 纪元（epoch）**（术语表 F6）
>
> **Unix 时间戳** = 从 **1970-01-01 UTC** 起算的秒数，是**绝对时间**（`1.77e9` ≈ 2026 年 3 月）。
>
> **相对秒** = 从"这段数据开始录制"起算（`400.2` 只在这段数据内有意义）。
>
> 两者**长得像但含义完全不同**。本坑的结论是：**包里根本没有绝对时间，换算成 Unix 秒只能凭空编一个纪元。**

**查证（直接读原始 bag）**

```
bag start_time = 399889542176 ns (399.889 s)
/qx/evk msg#0   bag ts = 400.234315 s   header.stamp = sec 400, nsec 234002144 = 400.234002 s
```

⇒ **bag 自身和消息 `header.stamp` 都是相对秒**，两者只差 0.3 ms
⇒ **包里根本没有绝对时间**，换算 Unix 秒只能**凭空编纪元**。

样例那份 `1.77e9` 是**另一个采集会话** —— 经纬度差 12 km，组委会只拿它当**格式样板**。

**解决**

## 第 8 章 工程环境类（从简，只收会改变方法论的那几条）

> **〔本章黑话〕** cgroup/OOM、CRLF、PYTHONPATH/venv、SIGTERM、正则、SFTP。
>
> 看不懂先查开头的「术语总表」，或往下找同名的 `> 〔术语〕` 灰框。

> 纯"装什么包、配什么源"的过程略去。以下是**思路层面有收获**的。

### 8-1 容器内存上限 42 GiB，而 `free` 显示 376 GB

`free -h` 显示的是**宿主的**内存。容器 cgroup v2 上限要查 `cat /sys/fs/cgroup/memory.max` = 45097156608 = **42 GiB**。
超限被杀时**日志静默停在上一行**，极易误判为"卡住"。
`dmesg | tail` 可见 `Memory cgroup out of memory: Killed process ... (python)`。

> **教训：任务开始前先问"我的真实资源上限是多少"，不要信第一个看到的数字。**

### 8-2 上传 `.sh` 带 CRLF → `$'\r': command not found`

paramiko 的 `sf.put()` 上传的 shell 脚本带 `\r`，远端 bash 报
`$'\r': command not found` / `cd: $'/root/...\r': No such file or directory`。

**修法**：自建 `put_lf.py` —— 二进制读取 + `.replace(b"\r\n", b"\n")` + `sf.open(dst,"wb")`。
**一律以 LF 上传。**

> **教训：跨平台传文本文件，行尾是一个必须显式处理的变量。**

### 8-3 PYTHONPATH 顶掉 venv 的 numpy

`/usr/lib/python3/dist-packages` 里有系统 numpy 1.17.4，而 PYTHONPATH **排在 site-packages 之前**
⇒ venv 的 1.24.4 被顶掉 ⇒ skimage/mmdet3d 的编译扩展报
`numpy.ndarray size changed ... Expected 88 from C header, got 80`。

**修法**：**PYTHONPATH 里不要放 `/usr/lib/python3/dist-packages`**，
改由脚本自己 `sys.path.append()` 到**末尾**（venv 的 numpy 优先，`rospkg` 仍找得到）。

> **教训：`append`（加到末尾）和 `insert(0, ...)` / PYTHONPATH（加到前面）效果完全不同。**
>
> 想让 venv 优先，就只能 append。

### 8-4 `pkill -f` 会杀掉自己

`pkill -9 -f "sfpnet_infer"` —— pattern 会匹配到 `pkill` 自己所在的命令行
⇒ **SSH channel 直接挂**（`remote_exit=-1`）。

**修法**：用 `pkill -f "[s]fpnet_infer"`（`[x]` 形式）。
并且**不要把待匹配的字符串同时写进同一条命令的别处**（例如后面跟一句 `pgrep -fa "sfpnet_infer"`）。

> **教训：`-f` 是"匹配完整命令行"，而 `pkill` 自己的命令行也在里面。**

### 8-5 `python -c` 里带正则会被 bash 吃掉反斜杠

```bash
python -c "import re; re.findall(r'altitude:\s*([-\d.]+)', s)"    # → 0 匹配
```

同一段代码写进 `.py` 文件就正常。

> **教训：带正则的核验脚本一律写成文件再跑，别塞 `-c`。**
>
> 同类：`python - <<'EOF'` heredoc 里的长循环会被 SIGTERM 掐掉（本项目的相机拟合跑了 120000 次随机搜索），
> 也必须写成文件。

### 8-6 中文路径的假阴性（Git Bash）

**症状**：`ls` / `cd` / `find` 对中文路径报 `No such file or directory`，但目录明明存在。
`ffmpeg -i E:/SLAM-大师赛/...` 也报 `No such file or directory`。

**修法**：
1. 判断存在性一律用 Python `os.path.exists`（UTF-8）
2. ffmpeg 等外部程序：先 `shutil.copyfile` 到**纯 ASCII 路径**再跑
3. **向别人报告"文件丢失"之前，必须用第二种独立工具复核**（本项目差点因此误报"2.4 万字产物全部丢失"）

### 8-7 sftp 下载大文件在前台会超时

下载 228 MB 前台超时被 SIGTERM 截断（只落了 100 MB）。
**修法**：后台执行（`run_in_background`）。
**同类**：下载大包用 `.part` 中转再 `mv -f` —— `os.replace` 会因句柄占用报 `WinError 5`。

### 8-8 文档生成器的 `%` 格式化会炸

`update_readme.py` 用 `u"""...""" % {...}` 生成 README，
被正文里的 `61.4% |` 触发 `ValueError: unsupported format character '|'`。
⇒ README 静默回落到旧版（17M 点、1′55″、Cylinder3D）—— **交付物与数据不一致**。

**修法**：改成 **`@@NAME@@` 哨兵 + `str.replace`**；章节替换改为**锚点切割**（heading → next heading）；
**锚点缺失直接 `SystemExit`**，不再静默产出半成品。

> 附带坑：docstring 里写 `"""` 会把字符串提前终止 → `SyntaxError`。

> **教训：模板生成文档时，绝不能用 `%` 或 `.format()`（正文里任何 `%` 或 `{}` 都可能炸）。**
>
> 用不可冲突的哨兵串。

### 8-9 scipy / numpy 版本不兼容 → 自写替代

numpy 2.4.2 与 scipy 版本不匹配：`A module that was compiled using NumPy 1.x cannot be run in NumPy 2.4.2`。

**修法**：**完全不用 scipy** —— 自己写 4 邻域 `binary_dilation`；
距离变换用分块暴力 `((q[:,None,:]-blk[None,:,:])**2).sum(2).min(1)`。

> **教训：一个 5 行的替代实现，比修复一个版本冲突更快。** 前提是你能确定自己实现得对（要交叉验证）。

### 8-10 numpy 2.x 移除 `ndarray.ptp()`

`a.ptp()` → `AttributeError`。改成 `np.ptp(a)`。（本项目**踩了两次**。）

### 8-11 大点云的邻域统计不要用广播

9.49 M 点 × 1300 个轨迹站点 = **1.2e10 次运算** ⇒ 必被 SIGTERM。

**修法**：**先把地图点栅格化（0.5–2 m），对占用格算距离再回填**，快 **3 个数量级**。

**另一个相关坑**：
- float64 + `np.hypot` 跑 9.4M × 2.1k 会被 SIGTERM ⇒ 改 **float32 原地运算**（~40 s 跑完）
- **"粗→精"两段式完全无效** —— `coarse=75` 时 slack = **38.20 m**，9,145,136 / 9,383,771 点仍需精算。
  **别做两段式。**
- **栅格键编码负坐标**：`key = cx*100000 + cy` 在 `cy < 0` 时 `//` 与 `%` 分解会错，
  解出的坐标飞到 20 万米。**必须加偏移**：`(cx+10000)*100000 + (cy+10000)`，解完再减。

### 9.2 关于"怎么避免自己骗自己"

| # | 规则 | 来源坑 |
|---|---|---|
| 6 | **判据立错，结论全错，而且错得很像对的。** 立判据前先查清语义边界 + 能不能靠倾斜分布作弊。 | 0-2、5-4 |

| # | 规则 | 来源坑 |
|---|---|---|
| 10 | **"发现一个问题"≠"必须修它"。** 先算收益量级、算影响面、算成本。 | 2-7 |

- **13. 先建精度基线，再决定优化什么。** 顺序反了，时间就全花在边际收益上。（来源：2-4）
