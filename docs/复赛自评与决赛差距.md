## 0. 一句话结论

**交付物已经齐了，可以交；但"能进决赛"不取决于我们做完了什么，取决于评审怎么读"泛化性"。**
我们最薄的三处按危险程度排：**① 仿真侧没探索完（覆盖率）② 实时性卡在预算线上且无余量 ③ 语义只有 2 类、且赛题标题里的"目标关联"根本没做**。

## 1. 复赛以来做了什么（四步流水，全部有验收判据）

| 步 | 内容 | 完成日 | 判据 |
|---|---|---|---|
| 0 | 一台能跑 Gazebo Classic + ROS 1 Noetic 的 Linux 机器 | 09-22 | 官方栈四条验收全 PASS（栈能起 / LiDAR 5.000 Hz / 相机有画面 / `/cmd_vel` 能驱动） |
| 1 | **统一数据接口**：一套代码、两个数据源 | 09-22 | 同一份代码只换 `--config`，两源各出帧统计；投影与图像结构吻合 |
| 2 | **人物 + 可通行区域**（复赛最关键的一次"是/否"） | 09-22 | 320×180 仿真相机**能**检出 person（3–6 m）⇒ 走检测路线 |
| 3 | **在线管线**：去斜→里程计→检测→融合→可通行→建图→探索→渲染，一条循环出三项交付物 | 09-29 | 两源各跑一次完整数据集，指标与视频/qcd 全部落地 |
| 4 | 探索 + 录屏 + pcd 导出 | 09-29 | 两个视频 ≤2 min、画面含过程；pcd 自洽 |
| 5 | **按赛题逐条终审 + 打包** | **未做** | — |

技术路径上真正换掉的是**三件事**（都是复赛相对初赛的换轨）：

1. **离线批处理 → 在线单循环**。`tools/online_pipeline.py` 是唯一主程序，
   `ingest→deskew→odom→detect→fuse→traversable→worldmap→explore→render` 九阶段一条循环，
   两个视频 + 建图 pcd 在同一次运行里产出。
2. **RTK → 无 RTK 室内**。里程计换成 KISS-ICP，并加**逐点去斜**（用 `offset_time` + 自家里程计，不依赖 IMU）。
3. **SFPNet 19 类 → 人物 + 可通行区域**。这是**主动放弃**初赛资产：19 类 SemanticKITTI 与"人物 / 可通行"不是一回事。
   可通行走**几何法（零训练）**，人物走 **2D 检测 + 标定投影到 3D**。这条正是评审要看的"泛化性"。

**外加一件方案外的事：自己写探索。** 官方 `src.zip` 里**没有规划器**（只有 `/cmd_vel`），
所以"场景探索"必须自建 —— 实现了 frontier 探索器（按角度分扇区选候选 + 卡住倒车自救）。

## 3. 自评：按复赛评审口径（泛化性 / 部署与迁移能力）

### 3.1 正面证据（这三条是硬货，应该主动展示）

| 证据 | 说明 |
|---|---|
| **一套代码两个数据源，差异只在配置** | `r2slam/config.py` + `sources/` 是全项目**唯一**允许知道"仿真/真实"的地方；下游只认 `Frame`，**下游出现 `if sim` 即视为设计失败**。仿真 5.6k 点 @5 Hz 与真实 49k 点 @10.3 Hz 走同一条循环 |
| **两源阈值完全相同、没调参** | 可通行区域的地面容差、障碍高度带、聚类阈值**没有为任何一源单独调过**。这是"泛化"最直接的证据 |
| **相机模型 / 外参 / 去斜方向全部配置化** | 真实是鱼眼等距 `r=f·θ`，仿真无畸变针孔；外参真实 3 cm 平移、仿真 0；去斜方向（从帧首正推 vs 从帧尾倒推）是**传感器属性**、写在 yaml 里 |

外加上一条**方案层**的：**没有搬 SFPNet**。复赛评的是"换环境还能用"，而初赛那套是 SemanticKITTI 19 类预训练的，
硬套"人物/可通行"两头不讨好。**放弃它本身就是泛化能力的论证**。

### 3.2 弱点（按危险程度）

| # | 弱点 | 量化 | 为什么危险 |
|---|---|---|---|
| 1 | **仿真覆盖率不足** | 观测 174.6 / ~280 m² ≈ **62%**；只跑 92 s 就收工 | "探索 + 覆盖"是我们自己第 4 步的验收判据；评审看到地图缺一角，会怀疑探索策略的完备性 |
| 2 | **实时性无余量** | 真实侧在线栈 p50 **95 ms** 对 **100 ms** 预算（95%）；p90 179 ms total | 赛题要"适配嵌入式平台"，而这是 Xeon + 8 核额度的数字。**p50 卡线 = 换个平台就崩** |
| 3 | **语义只有 2 类** | `person` + `traversable`（+background） | 赛题原话是"**语义分析与标注**"。初赛是 19 类，复赛掉到 2 类，容易被读成"语义能力退化" |
| 4 | **"目标关联"没做** | 赛题标题含"语义地图构建与**目标关联**"，实现里零 | 只有人物被投到 3D，**没有实例化、没有跨帧关联、没有物体级标签**。若评审按标题逐条核，这是空项 |
| 5 | **真实侧无真值** | 轨迹 114.85 m 只有**内部**三条判据（步长 p50 0.085 m / 帧间隔 ±1 ms / 隐含速度 0.87 m/s） | 无法回答"你的轨迹精度是多少"。**初赛就是在这条上吃的意见**（RTK 置信度偏高） |
| 6 | **无闭环 / 没用先验图** | 方案里的 M5 是空的 | 130 s 长走廊的累积漂移**完全没量化**；`LiDAR Map.pcd`（纯墙体先验图）没用上 |
| 7 | **画面无 Gazebo GUI** | 自组面板 | 若评审要求"仿真环境画面"字面合规，需要重录（成本：一次跑 + 一次编码） |
| 8 | **只验证了一个仿真场景** | `house.world` 一个 | 赛题强调"**不同环境**下的部署与迁移"；配置化设计能扛第二个场景，但**没有实证** |

## 4. 距离决赛还差什么

**决赛任务（官网）：人形机器人真机，语音指令 → 导航到目标物。**
评分：**准确率 50% / 效率 30% / 鲁棒性 20%**。

把决赛的四个要件对着我们现有的栈摆一遍：

| 决赛要件 | 我们有什么 | 差什么 | 工作量级 |
|---|---|---|---|
| **语音指令理解** | 无 | 语音→文本→目标类别的解析；这一步**基本是独立的**，可以后置 | 中 |
| **目标物语义** | 只有 person / traversable | **可指名的物体类别**（沙发/冰箱/电视/床/柜…）。这是最大的一块：决赛的"目标物"必须有名字 | **大** |
| **目标关联 / 实例化** | 无 | 跨帧把同一个物体聚成一个实例、并维持 id。赛题标题里的"目标关联"就是指这个 | 中大 |
| **导航到指定目标** | frontier 探索（只求"往未知走"） | **语义导航**：给定目标实例 → 代价地图 → 路径规划 → `/cmd_vel` 跟踪。我们的探索器只能"选最近的未知边界"，**不能"去某个沙发"** | 中大 |
| **效率**（30%） | 仿真 92 s 走 14.04 m | 探索效率、路径效率。**目前完全没做优化** | 中 |
| **鲁棒性**（20%） | 卡住自救（固定阈值）、检测 3–6 m 有效 | 未知环境、动态人、光照变化的鲁棒性 | 中 |
| **真机适配** | 无 | 人形机器人（不是轮式底盘）；传感器型号/话题/标定全不同；ROS 版本可能不同 | **大** |
| **定位** | KISS-ICP，无闭环 | 真机长时运行的累积漂移必须处理（回环 / 先验图配准） | 中大 |

**一句话**：复赛交付的是"**能跑通的在线感知 + 建图**"；决赛要的是"**能听懂话、认识东西、走过去**"。
中间隔着的不是工程量，是**两个新能力**：物体级语义、语义导航。

## 5. 如果这版进不了决赛，最可能是哪条原因

按"概率 × 危害"排序（我的判断，不是事实）：

| 排序 | 最可能的原因 | 概率判断 | 提交前能否补救 |
|---|---|---|---|
| 1 | **仿真覆盖率不足 + 没探索完就收工** | 高 | ✅ **能**：把仿真跑满（4–5 min 仿真时间 → 覆盖全屋），重新出一版视频。成本半天 |
| 2 | **语义太薄（只有 2 类）+ "目标关联"空项** | 高 | ⚠️ **部分能**：至少把**物体级检测**（COCO 已有 80 类，模型不用换）加进来，把"目标关联"从空项变成有物 |
| 3 | **实时性无余量**（95 / 100 ms） | 中 | ✅ **能**：把 render 移出在线回路（已经是了）；再给一版"里程计 5 Hz + 位姿插值"的降级实测，把"嵌入式可行"论证完整 |
| 4 | **真实侧无法自证精度** | 中 | ⚠️ 部分：用 `LiDAR Map.pcd` 做 scan-to-map，给出**与先验图的配准残差**作为外部判据 |
| 5 | **画面不含 Gazebo GUI** | 低–中 | ✅ 能：重录一版带 GUI 的（或做画中画） |
| 6 | **只有一个仿真场景** | 低 | ✅ 能：在 `house.world` 里换个出生点跑第二趟，作为"同场景不同起点"的弱证据 |

**注意第 1、2 条的性质差别**：第 1 条是**没做完**，第 2 条是**做浅了**。
没做完可以补；做浅了要看评审是否按标题逐条核 —— 如果是，那"目标关联"这一项是零分项，靠别的项补不回来。

## 6. 改进计划（三档）

### A 档 · 提交前必做（都是"不做就等于没做完"）

1. **第 5 步：按赛题逐条终审 + 打包**。
   含：两个视频 + 两个 pcd + **类别表（id↔名称↔颜色，独立文件）** + 对外说明（复赛版 README）。
2. **统一 pcd 字段口径**：补 `intensity` / `rgb`，或改 §3 的口径并写明理由。二者不能悬着。
3. **把仿真跑满**：延长时间直到覆盖全屋，重出视频 + pcd。**这是性价比最高的一条**。
4. **修掉文档里的数字错误**（已做：`41.8 MB` → `92.4 MB`）。
5. **发一次答疑邮件**，问 §8 的第 1、2、5 条（视频是否要 Gazebo GUI / 真实侧是否要 pcd / 是否有第二批场景）。
   **离截止还有 9 天，还来得及。**

### B 档 · 提交前应做（若时间允许，直接对应"进决赛"）

6. **加物体级语义**：tiny-yolov3 本来就是 COCO 80 类，我们只取了 `person`。
   把家具类（`chair`/`couch`/`tv`/`bed`/`refrigerator`/`dining table`）一并投到 3D ——
   **模型和投影代码都不用改，只是不再过滤**。这一步直接把"语义只有 2 类"和"目标关联空项"两条弱点一起消掉。
7. **补一版"里程计 5 Hz + 位姿插值"的降级实测**，把"嵌入式可行"从"算法侧不构成障碍"升级成"有降级预案"。
8. **真实侧加 scan-to-map**：用格式公开的 `LiDAR Map.pcd`（纯墙体，正适合匹配）做配准，
   给出配准残差作为**外部**精度判据 —— 这是对初赛"RTK 置信度偏高"那条意见的正面回答。

### C 档 · 决赛准备（10/13 之后，如果晋级）

9. **物体级语义 → 目标关联 → 语义导航**这一条链，是决赛的主体。
   顺序：① 物体实例化（跨帧聚类 + id 维持）→ ② 语音→目标类别 → ③ 代价地图 + 路径规划 → ④ `/cmd_vel` 跟踪。
   其中 ③④ 可以从 frontier 探索器扩展（它已经有"选目标 + 转 + 走 + 卡住自救"的骨架）。
10. **真机适配**：人形机器人的传感器、话题、标定、ROS 版本全未知 ⇒
    **现在的配置化设计正是为这一步准备的**，但要尽早拿到真机接口说明。
11. **回环检测**：真机跑得比复赛长得多，累积漂移必须有兜底。

## 7. 这段工作里最值得留下的三条（方法论）

1. **不要在饱和的机器上做优化决策。** 我照一个 150 ms 的读数把地面 RANSAC 向量化了 ——
   空闲机上**零提速**还把平面挪了 1.2 cm，已回退。那 150 ms 是机器争抢。
   现在有一条跨机可比的定标脚本（`probe_cpu.py`），怀疑机器变慢先跑它。
2. **配额受限的容器里，任何库自己按 `nproc` 开的线程池都要显式限制。**
   同一个机制栽了三次（KISS-ICP 的 TBB / onnxruntime 的 intra-op / OpenCV 的全局池），
   而且它**拖慢的是进程里完全无关的单线程代码**（地面拟合从 20 → 138 ms）。
3. **bag 的"记录时刻"不是传感器时间。** 这条代价最大：记录器一缓冲冲刷，
   写入时刻就塌成簇（241 帧间隔 <5 ms），喂给里程计后 **130 s 的行程从 114.85 m 变成 9,573 m**。
   必须用 `header.stamp`，且**回落次数要打出来** —— 静默使用坏时钟正是它藏这么久的原因。

航向误差（死推 vs 真值）p50 **1.85°**。真值只用于评分，从不进入产物。

### 8.3 ★ 查出一个官方仿真器的缺陷，代价是覆盖率

`vehicleSimulator.cpp` 在移动 LiDAR 模型前把四元数的 yaw 写死为 0 ⇒
**LiDAR 不随车体旋转**（相机则正常随转）。直接后果：

- 航向从扫描里**不可观测**。任何按航向控制的策略永远转不完 —— 这就是"仿真没探索完"的真正原因，
  不是策略差，是**控制量本身是错的**。修好后（`heading.py` 指令死推）机器人真的跑起来了。
- 但覆盖率**没有变好**（146.7 / ~280 m² ≈ 52%）：这份仿真器的 LiDAR 世界对齐 + 量程 40 m，
  一分钟就把能看见的都看见了；剩下的是**被墙挡住的房间**，而前沿在连通环上退化，
  当前的 frontier 策略不会"穿门而过"。

⇒ **这是本版最大的已知不足**，而且性质变了：从"没做完"变成"策略不会穿门"。
两者都可以补，但后者要动探索策略（房间级拓扑 / 门检测），不是加时间能解决的。
