# 开放词汇（路②）第一轮实测 —— 2026-10-09

> 目的：把 YOLO-World 的**在线成本**与**实际收益**量出来，决定它能不能进配置。
> 三条结论：**① 算力问题有解（降分辨率）；② INT8 量化在 CPU 上走不通；③ 发现一个会让整条路"看起来无效"的接线缺陷。**

---

## 0. 一句话

**我们之前判断"开放词汇收益很小、算力不划算"——算力那半是对的，收益那半可能是被一个接线缺陷掩盖的。**
`online_pipeline.py` 构造检测器时**从未加载类映射 sidecar**，而 YOLO-World 的类索引与 COCO 完全不同：
**除 `person` 外的 35 个类会被静默丢弃**，画面看起来"正常"（person 框还在），只是**永远不会多出任何新类别**。

## 1. 方法与复现

## 2. 结果 A：分辨率是唯一有效杠杆

| arm | 输入 | p50 | p90 | boxes/帧 | vs 640 保留 | 标签分布 |
|---|---|---|---|---|---|---|
| **w640**（基线） | 640 | **289.4 ms** | 314.3 | 1.32 | — | 2:80 4:12 8:8 9:6 |
| **w416** | 416 | **107.0 ms** | 119.8 | 1.02 | 86.2% | 2:80 4:2 |
| **w320** | 320 | **68.2 ms** | 76.5 | 1.02 | 84.6% | 2:78 4:4 |
| yolo26n（现役） | 640 | 64.7 ms | 72.8 | 1.00 | 86.2% | 2:80 |

**读法**：
- 640 → 416 是 **2.70×**，640 → 320 是 **4.25×**（FLOPs 按面积，实测与理论吻合）。
- **w320 的 68.2 ms 与现役 yolo26n 的 64.7 ms 基本相等** —— 也就是说，**换用词表更宽的模型可以做到"零算力代价"**。
- ⚠️ **但降分辨率会吃掉 YOLO-World 相对 yolo26n 的额外检出**：w640 是 1.32 框/帧，w416/w320 掉到 1.02，与 yolo26n 的 1.00 持平。
  ⇒ **降分辨率后的收益是"词表宽度"，不是"检出更多"。** 这两件事必须分开说。

**相对 yolo26n 的覆盖（另一轮，ref=y26n）**：w640 kept **100%**、new **+0.33 框/帧**；w320 kept **97.5%**、new +0.05。
⇒ **w320 几乎没有丢掉 yolo26n 已有的东西，而 w640 证明"多出来的那部分确实存在"。**

## 3. 结果 B：INT8 静态量化在 CPU 上走不通

| arm | 格式 | p50 | 相对 FP32 | boxes/帧 |
|---|---|---|---|---|
| w640 FP32 | — | 289.4 ms | 1.00× | 1.32 |
| w640 QOperator INT8 | QOperator | 211.2 ms | **1.37×** | **0.00** ❌ |
| w640 QDQ INT8 | QDQ (per-channel) | 192.2 ms | **1.51×** | **0.00** ❌ |

**两个独立的失败**：

1. **模型被打坏**：两种量化格式都是**零检出**（40 帧全空）。`OnnxYoloDetector` 能加载、`kind` 仍是 `v8`、输出形状正常 —— **是一次静默失效**（没有异常，只有空结果）。
   最可能的原因：ORT 的 `quantize_static` 默认量化**所有可量化算子，包括 YOLO 的回归头**；
   检测头输出的是**连续坐标**，压到整数格点后框全废。救援方向是 `nodes_to_exclude` 排除输出头，但要先接受下面第 2 点。

2. **即便修好也不够**：加速只有 **1.37–1.51×**，远低于社区常引用的 2.3×。
   ORT CPU EP 的 INT8 卷积内核在这个图/这个线程数下拿不到更高倍数。
   ⇒ **289 ms × 1.5 = 192 ms，仍远高于 100 ms 的目标。**

**结论：`onnxruntime.quantization` 这条量化路线，投入产出比不成立。** 模型体积倒是从 50.37 MB → 13.09 MB（3.85×），
如果"模型大小"本身是评分项，体积收益仍是真的；但**速度收益不成立**。

## 4. 结果 C：接线缺陷（★ 最重要）

`grep class_map` 全库结果：`load_class_map` 只在 `r2slam/detect.py` 里定义、在我新写的 `bench_detector.py` 里被使用。
**`tools/online_pipeline.py:505` 构造检测器时没有传它**：

```python
det = OnnxYoloDetector(det_model, conf=rt.person_conf,
                       num_threads=rt.detector_threads)      # ← 没有 class_map=
```

而 `detect_mapped()` 的逻辑是：

```python
lab = (self.class_map.get(coco) if self.class_map is not None
       else L.COCO_TO_LABEL.get(coco))
if lab is None:
    self.n_unmapped += 1
    continue                                                   # ← 整个框被丢弃
```

**YOLO-World 的索引是我们的 prompt 顺序，不是 COCO 索引。实测对照**：

| 烘焙 idx | 我们的 label / prompt | `COCO_TO_LABEL[idx]` | 后果 |
|---|---|---|---|
| **0** | 2 `person` | **2** | 巧合一致 ⇒ person 正常 |
| 1 | 3 `couch` | **None** | **丢弃** |
| 2 | 4 `chair` | **None** | **丢弃** |
| 3 | 5 `bed` | **None** | **丢弃** |
| 4 | 6 `dining table` | **None** | **丢弃** |
| … | … | **None** | **丢弃** |
| 35 | — | **None** | **丢弃** |

⇒ **换用 YOLO-World 而不修这行，结果是"只有 person 能出来，其余 35 个类全被静默扔掉"。**

**这解释了 §11 里"开放词汇收益预计很小"的结论从哪来 —— 那是推理，不是实测；而实测（带 sidecar）显示
w640 确实多检出了 label 4 / 8 / 9（chair / refrigerator / potted plant），比 yolo26n 多 32% 的框。**

⚠️ 注意后果的**隐蔽性**：`n_unmapped` 会记录"有把握但叫不出名字的框数"，所以**日志里能看见**，
但**画面看起来完全正常** —— 又是一次"自检通过 ≠ 正确"。

**修复**（一行）：

```python
from r2slam.detect import OnnxYoloDetector, load_names, load_class_map   # + load_class_map
...
    det = OnnxYoloDetector(det_model, conf=rt.person_conf,
                           num_threads=rt.detector_threads,
                           class_map=load_class_map(det_model))          # + 这一行
```

**Gate −1 可验**：现役 `yolo26n.onnx` 旁边**没有** sidecar ⇒ `load_class_map` 返回 `None`
⇒ 行为与改动前**逐位相同** ⇒ 决策列 md5 必须不变（r3 基线 `94df03cd8a087fc9b15d2ff4086a5d7f`）。

## 5. 判读与已知弱点（诚实声明）

1. **样本量小**：40 帧、1600×1296、来自**单个房间**（`real_r2.yaml`）。
   `person`（label 2）占了 80/106 个框 ⇒ **kept% 被 person 主导**，小类别（label 4/8/9）的保留率统计功效很弱。
   ⚠️ 例：label 4 在 w640 是 12 次、w416 是 2 次、w320 是 4 次 —— **三个数字都不稳定**，不能当作"416 比 320 差"。
2. **只测了 CPU**。参考平台是 Jetson Orin 级；**Orin 上走 TensorRT/FP16 的排序可能与这里完全不同**。
   本轮的结论只对"CPU onnxruntime"这一条路径成立。
3. **INT8 的"零检出"是一次静默失效**，与 §2 的结论一样，都被记录为"机制跑了但没起作用"。
   量化能不能救，取决于是否值得为 1.5× 的上限去调 `nodes_to_exclude`。
4. 所有 arm 的**类别分歧都是 0.00** —— 这不是"标签很准"，而是**只有 person 一个类占了绝大多数样本**，
   分歧根本没有机会出现。**不要把它读成标签质量的证据。**

## 8. 顺带修掉第二个缺陷：`detect.py` 硬编码 640

接上 w320 后立刻报错：日志打 `size 640` 而模型是 320 图 ⇒ 喂 640 blob 给 320 图。
根因是 `OnnxYoloDetector` 在 `size=None` 时写死 `640 if kind=="v8" else 416`，**从不读图的输入形状**。

修法遵循本文件已有的原则（`kind` 从**输出签名**读、不从文件名猜）：
新增 `_declared_side()`，从 `sess.get_inputs()[0].shape` 读方阵边长；读不到（cv2 后端、动态形状）才回落旧默认。

**验证**：`yolo26n → 640`、`yoloworld_s → 640`、`_320 → 320`、`_416 → 416` 全部正确。
**Gate −1 复验**：改 `detect.py` 前后各跑 150 帧，**55 列中只有 10 个 `ms_*` 不同**。

## 9. INT8 零检出：根因找到并修好

**第一轮的猜测（"回归头被压坏"）是错的。** 真因是**输出端 `Concat` 共用了一个量化尺度**：

```
output0 = /model.22/Concat_5
   ├── /model.22/Mul_2       框分支   值域 0 ~ 680 px
   └── /model.22/Sigmoid     类别分支 sigmoid ⇒ 0 ~ 1
```

两条分支拼进同一个 `Concat` ⇒ 一个 scale 同时管 0~680 与 0~1 ⇒ **小值那条被压成精确的 0**。

**逐通道实测（同一帧）**：

| | 框通道 max | **类别通道 max** |
|---|---|---|
| FP32 | 680.29 | **0.8445** |
| INT8（全量化） | 687.75 | **0.0000** ← 全零 |
| INT8（排除尾部 3 节点） | 752.86 | **0.8819** ✓ |

**修法**：`quantize_onnx.py` 新增 `--exclude-tail N`，从输出反向 BFS 取 N 层节点名交给 `nodes_to_exclude`
（默认 2 ⇒ 排除 `Concat_5` / `Mul_2` / `Sigmoid`）。

**修好后的完整账**：

| arm | p50 | p90 | 体积 | 保留 |
|---|---|---|---|---|
| w640 FP32 | 251.6 ms | 264.3 | 50.37 MB | — |
| **q640 INT8** | **177.2 ms** | 192.0 | **13.39 MB** | **91.2%**（vs w640） |
| w320 FP32 | 60.5 ms | 67.9 | 50.24 MB | 84.6%（vs w640） |
| **q320 INT8** | **45.3 ms** | **48.5** | **13.31 MB** | **97.5%**（vs w320） |

⚠️ **量化只值 1.35–1.42×，且修与不修几乎一样**（1.45 → 1.42）—— 因为只排除了 3 个节点。
⇒ **分辨率是主杠杆；INT8 是锦上添花，不是救命稻草。**

## 10. 结论：q320 是当前最优候选（但不是终点）

**真实 bag，150 帧闭环**（同一条命令，只换 `--model`）：

| arm | 实例数 | 观测 | 新增类别 |
|---|---|---|---|
| yolo26n（现役） | 1 | person ×150 | — |
| w320 | 2 | person ×144 + clock ×3 | **clock** |
| **q320** | **4** | person ×144 + clock ×2 + chair ×2 | **clock + chair** |

**q320 的账：45.3 ms（比现役 yolo26n 的 64.7 ms 还快 30%）＋ 13.31 MB ＋ 36 类词表。**

⚠️ **必须一起报的信号**：q320 的**融合拒收率 9.8%**（16/164）远高于 w320 的 1.3%（2/149）
⇒ **量化确实引入约 8% 的低质量框**。它们被 `labels.py` 的高度门挡住了（`reject_box_height_must` 15 个）
—— 门在起作用，但这说明"多检出"里有一部分是**得而复失**的，不能直接当净收益讲。
