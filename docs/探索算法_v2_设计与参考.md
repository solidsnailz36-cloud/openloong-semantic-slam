# 探索算法 v2 —— 现状、实测失败模式、参考实现与修改方案

> 2026-10-04 晚。触发：boss 说"这次仿真小车进了一个房间，在里面绕来绕去一直出不来"，
> 并问"现在寻路用的什么算法？给一串点能不能依次到达？"以及"小车特别喜欢钻墙角"。
>
> **本文所有数字都是从 `out/y26_sim`（yolo26n 那版实跑，617 帧 / 123 s）和
> `out/ab_perception/grids_y26_sim`（同一跑自己导出的栅格）上量出来的，不是估的。**

## 1. 现在用的是什么（回答"什么算法"）

### 1.1 规划：A\*，8 连通，按机器人半径膨胀

`r2slam/nav.py :: PathPlanner`（`nav.py:420-648`）

| 项 | 现在 |
|---|---|
| 搜索 | **A\***，8 连通，直走代价 1.0 / 斜走 √2 |
| 启发 | 欧氏距离 |
| 可行格 | **只走"已知可通行"**（`ground` 去掉确认障碍），不穿未知 |
| 安全余量 | 按 `robot_radius`（0.22 m）腐蚀；障碍再 3×3 膨胀 |
| 起点 | 允许 snap（机器人可以贴着墙站） |
| 目标 | **最多 snap 4 格**（历史事故：目标落在墙里被 snap 到脚边，于是绕 0.24 m 的圈跑了 674 s） |
| 上限 | `max_expand=300000`，超了返回 None（＝不可达） |

### 1.2 跟随：三档油门 + 1.2 m 前视点

`explore.py :: _lookahead` / `command`（`explore.py:950-967`、`996+`）

- **取路径上距机器人 ≤1.2 m 的最远点**当瞄准点（直接瞄 0.1 m 的下一格会让车来回摆）；
- 航向差分三档：**原地转 / ≤25° 直行 / 中间走弧**（"航向差不是停车理由——该画弧"）；
- 前视安全检查读 `blocked() = obstacle | obstacle_now`（**含当帧回波**），所以当帧看见的墙立刻能停。

### 1.3 探索：前沿（frontier）簇 + 角扇区代表 + 距离衰减

`explore.py :: FrontierExplorer`。打分是

```
score = 前沿簇大小 / (1 + 距离)
```
外加：按**角扇区**每个扇区先留一个代表（防止一个方向被挡就看不到别的方向）、
`min_target_range`（太近的目标不值得那一次转身）、可达性用**连通分量**而不是直线。

### 1.4 ★ 目标是什么：**前沿格子本身**，不是"看它的位置"

`_pick_target` 返回的是 `wx[i], wy[i]` —— **一个 free 与 unknown 交界的格子**。
机器人于是把"开到那一格"当成目标。**这就是钻墙角的直接原因**：
那一格就在墙角，所以它当然会开到墙角、脸贴脸。

## 2. "给一串点能不能依次到达？"

**核心能力有，驱动没有。** 拆开说：

| 需要的东西 | 现状 |
|---|---|
| 规划到任意地图点 | ✅ `PathPlanner.plan(wmap, start_xy, goal_xy)`，就是 A\* |
| 规划失败要说出来 | ✅ 返回 `None`（不是静默绕圈） |
| 单目标驱动 | ✅ `SemanticNavigator`（`--goto 沙发`）：规划→跟随→重规划→超时放弃 |
| **多目标队列** | ❌ **没有**。一次只有一个目标 |
| 到点判据 | ✅ `arrive_dist`（默认 0.9 m）+ 逐目标超时/放弃 |

⇒ **"依次到达一串点"是一个约 60 行的新增**：一个目标队列 + 到点弹出 + 超时跳过。
可复用的东西都已经在了：`plan()`、跟随器、`arrive_dist`、以及 `SemanticNavigator` 里
"必须有 deadline，不然就会绕圈 674 s"那条教训。

我建议的接口（决赛大概率会用到"先去 A 再看 B"这类指令）：

```python
class WaypointMission:
    def __init__(self, goals, arrive_dist=0.9, per_goal_timeout=90.0,
                 give_up_after=3): ...
    def command(self, wmap, pose_xy, yaw):   # 与 explorer / navigator 同签名
        # 队列头为目标；到点 ⇒ 弹出；超时/规划失败 ⇒ 记一次放弃并弹出；
        # 单目标连续放弃 3 次 ⇒ 整个任务放弃并如实上报
```

## 3. 实测失败模式一：钻墙角（**程序自己记录在案**）

同一跑 `out/y26_sim/summary.json` 的 `explore`：

```
targets_committed 603   target_switches 12   plans 70   plan_failures 0
arrivals 11             barren_targets 8   ← 到了目标点、什么都没观察到，连续 8 次
done_reason: "reached 8 frontier targets in a row without observing anything
              new, and nothing but small clusters left (214.0 m2 known)"
```

- **11 次到达里 8 次是白跑**，然后它自己判定"没什么可看的了"收工。
- 总路程 54.1 m / 123 s，后 400 帧全在 `x≈-8~-12, y≈-2~5` 那一小块里来回（3~4 m 的短程跳来跳去）。

**机制**（代码层面）：
1. 目标是**前沿格子**（§1.4）⇒ 天然指着墙角；
2. `barren_targets` **只被计数，不产生任何后果** —— 白跑过的目标**不会被排除**，
   下一轮同样的格子还能被再选一次（`_target_still_frontier` 只在"整窗都被观察过"时才判它过期）；
3. 前沿的"角扇区代表"会让**同一个墙角在别的扇区里再被选中一次**。

> ⚠️ **上面第 2、3 条已被实测推翻，见 §8.2。** 黑名单实现并实跑之后，
> **一次都没有真的剔除过候选**（`blacklisted_candidates = 0`），
> 也就是说那 8 次白跑**去的是 8 个不同的地方**，不存在"反复瞄同一个墙角"。
> 结论：**钻墙角的原因是"目标是格子"（第 1 条，成立），不是"目标被重复选"（第 2、3 条，不成立）。**

**参考实现怎么做的（这是标准做法，不是我们的发明）**：
- `explore_lite` / `m-explore`：**目标黑名单** `frontier_blacklist_`，
  触发条件是 (a) 导航 ABORTED，(b) **`progress_timeout_` 内没有进展**；
  查询容差 = 5 × 栅格分辨率；**所有前沿都被拉黑 ⇒ 停止探索**。
  （`explore/src/explore.cpp`、`explore/include/explore/explore.h`）
- 同一个包里的 **"目标外推"**：如果目标质心在 x 和 y 上都离机器人太近（`target_prox_lim`），
  就把目标沿"机器人→目标"方向**推到 `recovery_delta` 以外**。
  **这条正好治"脸贴脸看墙角"。**
- `CS137A/frontier_explorer.py`：**`min_goal_distance`（默认 0.35 m）以内的前沿直接拉黑**，
  注释写的就是 "prevents unnecessary navigation to frontiers already within sensor range"。
- 同一个文件的 costmap 目标校验：如果目标处 cost > 80，就在 16×16 邻域里找替代点。

**给我们的改法**（按性价比排序）：
1. **把 `barren_targets` 变成真黑名单**：目标连续两轮"到达但 `seen` 没增加"⇒
   把该点周围半径 R（建议 0.6 m，≈6 格）标黑，**选目标时跳过**。
   验收：`barren_targets` 从 8 降到 ≤2，且 `done_reason` 不再是"连续 8 次白跑"。
2. **目标外推**：把目标从"前沿格子"改成"前沿簇质心"，并且**至少离前沿 `standoff`（建议 0.8 m）**。
   验收：轨迹到最近障碍的最小距离中位数上升；视频里不再贴墙。
3. （可选）**前沿按"可视角"过滤**：从候选视点对未知区做一次射线投射，
   看不见的未知格不算前沿。这条最贵，但能一次性干掉"墙后面的未知"。

## 4. 实测失败模式二：进去出不来（**地图把门堵了，不是探索策略的错**）

### 4.1 机器人被困在哪

在**它自己导出的栅格**上算（`PathPlanner.free_space` + 连通分量）：

```
绿（有地板证据）        214.0 m2
规划器可走              166.1 m2
★ 机器人真正够得到      32.5 m2   ← 只占 20%
可走域连通块            4 个：129.9 / 32.5 / 2.2 / 1.6 m2
机器人所在块            32.5 m2（一个房间）
```

⇒ **它不是"绕圈出不来"，是被**关**住了：129.9 m² 在它够不到的另一侧。**

### 4.2 门是怎么堵的（关键证据）

两块之间最近的一对格子：**`(-8.9, +0.2)` 与 `(-8.9, -0.7)`，相距 0.90 m**。
而这两格在**原始地图**上：

```
ground = True / True      障碍 = False / False      seen = True / True
```

**地图说"这里就是地板、也不是障碍"，可规划器的可走域在这条线上 clearance 全是 0.00 m。**

逐格追下去（`x = -8.9` 那一列）：

| 步骤 | 结果 |
|---|---|
| `ground` | 整段都是 1（地板证据在） |
| `obstacle` | **只有 2 格是 1**（y = −0.2, −0.3），合计 **0.2 m** |
| `solid = dilate(obstacle, 3×3)` | 变成 4 格（0.4 m） |
| 再按机器人半径 5×5 腐蚀 | **变成 7 格（0.7 m）不可通行** |

⇒ **2 格（0.2 m）障碍被放大成 0.7 m 的墙，3.5 倍。**
而 `free_space` 里这两个量是**各自独立**加的：
3×3 障碍膨胀假装"机器人更大一点"，5×5 腐蚀**又**为同一个机器人半径留一次余量。

**这是真的重复计算，但它不是全部原因 —— 必须说清楚：**
我把 6 种形态学组合都离线试了一遍（去掉膨胀 / 去掉腐蚀 / 两者都缩 / 不闭运算），
**没有任何一种能把门重新连通**（机器人块仍然只有 35.8–39.4 m²，最大块另有 140–154 m²）。
⇒ 就算把那 2 格障碍直接删掉，门也未必通；**剩下的部分我没有解释清楚，所以不据它改代码。**

### 4.3 还有一条独立的矛盾（值得单独修）

轨迹 617 格里有 **4 格在最终地图上被标成障碍**（位置 `(-9.3, -0.4)`，**23 票、100% 属强证据**），
而**机器人就是从那里开过去的**。

⇒ **地图与自己走过的路径相矛盾。** 不管那 2~4 格是掠射回波、门框端面还是别的什么，
一条"能开过去"的路径上的格子不该成为"强证据障碍"。
这条可以做成一个**自检指标**并写进运行报告：
`轨迹上被标成障碍的格子数` **应当为 0**；不为 0 就是地图的错。

### 4.4 为什么这属于探索问题（而不是纯建图问题）

探索的停止条件是 `reach & ~visited`，而 `reach` 来自规划器的可走域。
**一旦门被堵住，那 129.9 m² 就从 `reach` 里消失**，机器人永远不会去，也不会认为那是"未完成"——
它会带着"只剩小簇了"的结论收工。**所以"门被堵"和"探索提前收工"是同一个故障的两面。**

参考实现的对应教训：nav2 的探索节点（`explore_lite`）**规划与探索共用同一张 costmap**，
不存在"探索认为能去、规划认为不能去"这种分裂。我们现在
`explore._usable_frontier` 用一个**膨胀过的 reach** 判可达，
`PathPlanner.free_space` 又自己算一套**更强的**可走掩码 —— 两套不一致。

## 6. 修改方案（按性价比，每条都带验收判据）

| # | 改动 | 为什么 | 验收 |
|---|---|---|---|
| **P0** | 把 `barren_targets` 变成**真黑名单**（到达但 `seen` 未增 ⇒ 该点半径 0.6 m 标黑，选目标时跳过） | 原以为是治 §3 的 8 次白跑 | ⚠️ **已实现并实跑：是 no-op**（剔除候选数 0，见 §9）—— 保留但不算解法 |
| **P0** | **目标外推**：目标 = 前沿簇质心，且离前沿 ≥`standoff`（0.8 m） | **这才是治"脸贴脸看墙角"的那一刀**（目标现在是前沿格子本身） | 轨迹到最近障碍的最小距离中位数上升；视频里不再贴墙 |
| **P1** | **统一可走图**：探索与规划用**同一个** `free_space()`，删掉 `explore` 里那套"膨胀 reach" | 治 §4.4 的分裂 | 两条路径对同一张图给出同一个可达面积；`reach` 的算法只有一处 |
| **P1** | **`free_space` 去掉重复计算**：障碍膨胀与半径腐蚀只保留一个（建议保留腐蚀、去掉 3×3 膨胀，并在注释里写清两者为什么不能叠加） | §4.2 量到 3.5 倍放大 | 门洞处 clearance > 0；机器人可达面积上升（**注意：离线 6 种组合都没连回门 ⇒ 先用 P2 的自检确认，再谈收益**） |
| **P1** | **新自检指标：`轨迹上被标成障碍的格子数`，正常运行必须为 0** | §4.3 那个硬矛盾 | 加进 `summary.json` + 终审；不为 0 就 FAIL |
| **P2** | 门洞那 2~4 格为什么进障碍带：**在那几格上打印每帧的 h 与来源**（掠射/门框/门楣） | 根治堵门 | 能说出那几格的回波长什么样，而不是"大概是掠射" |
| **P2** | **多目标队列**（§2） | 决赛"先去 A 再看 B" | 给 5 个点，依次到达并在每个点停住；规划失败要如实上报 |
| **P3** | WFD（波前前沿检测）替换现有关联分量法；增量前沿更新 | 少算、且天然只给可达前沿 | 每帧耗时下降；前沿集合与现法一致率 >95% |

**先做 P0 两条**：它们互相独立、都不碰安全层、且都能在**同一份采集上离线验证**
（用 `out/y26_sim/frames.csv` + `grids_y26_sim` 重放目标选择即可）。

> ⚠️ 上面最后半句是错的，已更正：`--npz` 复算里 **`explore.enabled = False`**（没有驱动器就不跑探索），
> 所以目标选择**只能实机验证**。P0-1 已实现（见 §8），正在实机跑 A/B。

## 8. 已实现的改动：前沿黑名单（P0-1）

`explore.FrontierExplorer`：

| 位置 | 改动 |
|---|---|
| `__init__` | 新增参数 `barren_blacklist_m=0.60`；新增 `_barren_spots: List[(x,y)]`、`n_blacklisted` |
| 到达结算 | "到了但 `seen` 没长"那一步（原来只 `n_barren_targets += 1`）**同时把该点记进黑名单** |
| `_pick_target` | 在角扇区/距离筛选**之后**再剔除"离任何黑名单点 ≤0.6 m"的候选；被剔除的数记进 `n_blacklisted` |
| `summary.json` | 新增 `blacklist_places`（黑名单条数）与 `blacklisted_candidates` |

**为什么是 0.6 m 而不是一格**：前沿簇的质心会随地图生长而轻微移动，
一格范围的黑名单下一帧就漏掉了同一个墙角。

**为什么放最后剔**：前面的计数器（`big`/`far`/`frontier_used`）仍然反映"拉黑之前有多少候选"，
这样才能看出黑名单到底咬掉了多少。

验证方式与结果见 §9（实机跑，`--npz` 复算里不跑探索，见上）。

## 9. P0-1 实机验证结果：**它是 no-op**

同一台机、同一世界、`--duration 400 --explore`，各跑一次：

| | 改前 `out/y26_sim` | 改后 `out/y26_black` |
|---|---|---|
| 帧 | 617 | 1255 |
| 可走面积 | 214.0 m² | 220.3 m² |
| arrivals | 11 | 16 |
| **barren_targets** | **8** | **3** |
| 黑名单条数 | — | 7 |
| **被黑名单剔除的候选数** | — | **0** ← |
| 路程 | 54.19 m | 104.54 m |
| done_reason | "连续 8 次白跑…" | 空（被 `--duration 400` 截断） |

**看只看那一栏：`blacklisted_candidates = 0`。**
黑名单里有 7 个点，但**一次都没有真的剔除掉任何候选** ——
说明机器人**从来没有再次瞄准同一个地点**。

**所以必须如实说三件事：**
1. §3 里"同一个墙角被反复选中"的机制**是错的**（我原来的第 2、3 条推断不成立）。
   钻墙角的真原因只剩第 1 条：**目标是前沿格子本身**。
2. 表面上的"改善"（路程 54 → 105 m、barren 8 → 3）**落在本项目已知的单跑方差区间内**
   （同码不同跑的路程 44–112 m），**不能归因于这次改动**。
3. 这次改动**保留**（它无害、且在"真的会重复瞄同一点"的情况下有用），
   但**不要把它当成解决问题的那一刀**。真正的 P0 是 **§6 的 P0-2：目标要外推成观测位姿**，
   那条本轮**没有实现**。

> 这一条的价值不在代码，在于**它推翻了我自己的诊断**：

原因不是"退得不对"，是**退完之后没路可走了**：机器人站在离前沿 0.8 m 处，而它到

改完：**79% moving、净推进 4.0 m、终点 x=4.01（到了未知区）**。

而 `_masks` 里写的是：

```python

```

`lab_raw != rseed` 把"**和机器人同一个 ground 连通块**"的部分排除掉了。于是这块房间
**既不在 `reach` 里、也不在 `other` 里** —— 扫掠看不见（扫掠在 `reach` 内），

### 12.3 ★ 顺带查出来：门口的探针机制**从来没有真正生效过**

修完 12.2 之后 `probe` 里有 5.6 m²（两块房间的门口都在），但 `_pick_island_probe` 仍返回 `None`。
逐层追下去，三个独立的 bug：

1. 它的 docstring 一直写着"瞄紧挨可走域的格"，**代码做的是"瞄离机器人最近的格"**。
   最近 6 个候选全在 `x = +5.85..+6.25`（**东墙外**），`plan()` 全部失败 ⇒ 返回 None。
2. 改成按"离可走域最近"排序后**仍然全失败**：`probe` 到 `reach` 的距离是 **5–20 格**
   （腐蚀壳 + 那条障碍线），而 `plan()` 的**目标吸附上限只有 4 格** ⇒ 瞄在洞里永远失败。
3. 面积门限加在**并集**上（`probe.sum()`），而并集永远够大 ⇒ **门限从没生效**，
   于是一个 0.41 m² 的小坑（21.3 m 远）排在 2.11 m² 的房间前面。

最终：按**块**过滤面积 → 按块面积从大到小选 → 块内取"离可走域最近"的格 →
**对准该块最近的 `reach` 格**（机器人合法能为的最靠门口的位置）。
现在探针指向 `(-5.45, -6.05)`、路径 14.3 m —— **正是块2 的门口** ✓。

触发器也改了。旧规则：

```
stranded > max(island_trigger_m2, fresh_in)      # 够不到的地板 > 没走过的可达地板
```

40 m 雷达下这个永远不成立（实测 **15.9 vs 92.0 m²**）⇒ **841 帧里探针 0 次**。
改成"有实质斑块（≥ `island_trigger_m2 = 4 m²`）就值得去一趟"，理由是这两类动作**性质不同**：

* 去扫掠目标：把**已经看见过**的地板变成**走过**的地板 —— 覆盖率；
* 去门口：可能**改变"地图认为哪里能去"** —— 信息。门后面每一平米在有人去看之前
  都从 `reach` 里消失，所以**扫掠连"那间房是待办工作"都看不见**；
* 而且旧规则是**循环**的：扫掠自己那套"我能去哪"的定义，正是被这些门堵着的。

`_pick_island_probe` 本来就拒绝瞄准"已经到过的地方"，所以每道门最多一趟；
`island_probe_limit = 12` 兜底（万一那条带子真的是墙、永远解不开）。

### 13.1 ★ 门是 **1.0 m 宽** —— 是我查漏了

### 13.2 ⚠️ `robot_radius` 0.22 → 0.19：**按 boss 指示改了，但它是空操作**

```python
k = max(1, int(round(2 * robot_radius / resolution)) | 1)
```
`round(2×0.19/0.1) = round(3.8) = 4`，`4|1 = 5`；`round(2×0.22/0.1) = 4`，同样 5。
**0.19 与 0.22 产生完全相同的 5×5 腐蚀核。** 真正能动的杠杆是 **≤ 0.15**（→ 3×3），

### 13.3 ★ 左上房间：**可达，但从没被选为目标** —— 是 sweep 的排序

| 跑次 | 左上房间（约 20 m²）可达 | 轨迹覆盖率 |
|---|---|---|
| r8 `y26_sim` | 20.2 m² | **79%** |
| r9 `v9_sim` | 20.8 m² | **60%** |
| r10 `v10_sim` | 19.3 m² | **0%** |

**一直是"同块"**，所以不是"进不去"，是**没去**。原因在排序：

```python
cands.sort(key=lambda c: c[0])      # c[0] = 离起点最近  ← 旧
```

**"离起点最近优先"** —— 这正是本项目硬规则①写的"候选只按距离排 ⇒ 极限环，
要用 簇大小/(1+距离)"，当年只改到了**前沿**选择，**sweep 一直是纯最近优先**。
一跑结束时在 `reach` 内、未走过、≥3 m² 的斑块有 6 个：

| 面积 | 离起点 | 最近优先的排名 | `面积/(1+距离)` |
|---|---|---|---|
| 6.6 m² | 2.2 m | **1** | 2.05 |
| 7.2 m² | 2.8 m | 2 | 1.91 |
| **28.7 m²（就是那间房）** | 5.4 m | 3 | **4.45 ← 取它** |
| 21.0 m² | 5.6 m | 4 | 3.17 |

最近优先取 6.6 m² 那块；`size/(1+d)` 取 **28.7 m² 的左上房间**。
改法：`cands.sort(key=lambda c: -size/(1+d_start))`。
**距离仍用"离起点"而不是离机器人** —— 排序在行驶中稳定，这是防
"在两个等距斑块之间乒乓"（当年那 214 帧、0.61 m 净位移）的那条老教训。

### 13.4 一条正在变清楚的模式

本项目"走到过哪儿"这件事，**三次**都是同一个形状的错：
**用两套东西描述同一件事实，然后只改其中一套。**

| 第几次 | 两套东西 | 症状 |
|---|---|---|
| r9 §4 | `reach`（腐蚀后）与 `ground`（原始地板） | 门两端都"是地板"，规划器却过不去 |
| r10 §12.2 | ``reach`` 与 `other`（够不到的地板） | 房间掉进差集，既不走也不探 |
| r11 §13.3 | sweep 的"最近优先"与 frontier 的"大小/距离" | 同一类目标，两种排序，一个已经修过一个没有 |

⇒ **凡是"选哪个目标去"的逻辑，全项目应该只有一种打分形状。**

### 14.4 改的两处

**A. 斑块承诺**（`sweep_patch_keep_m2=1.20`，`sweep_patch_max_targets=4`）

选斑块仍用全局 `size/(1+d_start)`（所以**进入房间的顺序不变**），选中后留在里面：
按**重叠**跟随斑块（连通域 label 跨帧不稳定，斑块本身也会被机器人自己开出的走廊切开 ——
跟最大的那一半），直到剩余 < 1.2 m² 或没有 `depth ≥ 0.5 m` 的格；最多连续 4 个目标，
然后重新全局排序。

`max_targets=4` 的理由是取舍，不是推导：有墙钟预算时，"这间做更好"是用"那间没去"换来的。
4 站 = 房间内 4 倍停留（现状是 1），而房间之间每 4 站还能重新排序一次。**设 0 是不限，**
**那是"彻底"的极限，也是固定预算下的错默认。**

**B. 遮挡阴影的观察位姿**（`shadow=True`，`shadow_min_m2=1.00`）

```
pocket = ~seen & ~exterior          # 内部洞（_exterior 早已存在）
闸门：≥1 m² 且 邻接 ground_ever ≥4 格   # 否则是柜子内部，没有位姿看得进去
位姿：在洞的"岸边"格上找可达格，用 _clear 逐条射线验证视线，
      取"看得最多、再取最近"；得分 面积/(1+离起点距离)，与 sweep/frontier 同形
一趟制：shadow_blacklist_m=1.0 + shadow_probe_limit=10
```

★ **优先级在 sweep 之前**，理由与 `island_trigger_m2` 同一套：两者的性质不同 ——
去 sweep 目标是把"已看见的地板"变成"走过的地板"（**覆盖**），去阴影位姿是唯一能
**对那块地学到任何东西**的动作（**信息**）。这也是 FUEL / TARE 的 viewpoint generation，
缩到一张 2-D 占据栅格能支持的程度（不做未来射线投射，只问"从这里到它这条线通不通"）。

**离线验证**（v11 栅格，机器人放 4 个不同位置：终点/右上门口/右上房内/客厅）：
四次都选出观察位姿 `(+4.45, +2.05)` —— 正对那个 1.64 m² 的洞 ✓。

⚠️ **一次我自己的假阴性**：第一版离线验证忘了给 `WorldMap.ground_ever` 赋值
（它是 `add()` 维护的派生层，手工造 `WorldMap` 时不会自动有），于是 `near_floor` 全 False、
每个洞都被闸门挡掉，而**当时没有任何计数说明这件事**（返回 None、`skipped` 是 0）。
现在"过闸门但找不到位姿"单独记 `shadow_skipped`，闸门拒绝也在离线脚本里逐条打印。

`run_v12.sh sim`（duration 400，与 v11 同时长 A/B）与 `run_v12b.sh sim`（duration 900）
的结果见 §15。

> 这一节必须原样保留。**它证明"给一个新目标类别最高优先级"是错的**，
> 而且错误的量级足以把整跑带偏。

目标序列给出了全部原因：

```
v12 的 7 个目标里 6 个是 shadow：
  帧0   frontier
  帧26  (-0.35,-3.15) shadow
  帧56  (+6.55,+0.45) shadow
```

第 26 → 663 帧（**637 帧 = 53% 的跑程**）全在右半边追洞，**从没进过左上/左下两个房间**
（轨迹 x 只到 −3.8，而 v11 到 −11.5）。尾段 106 s 还耗在 `turn`/`backoff` 里
（帧 800–1000：净位移 0.66 m / 路程 6.18 m）。

### 15.1 根因是结构性的，不是调参错误

**地图每长大一点就会产生新的"内部洞"**：新看见的家具都会投下一个新鲜的阴影。
于是"无条件优先处理盲点"= 让机器人停下探索、开始绕着它刚测绘完的那间房的家具转圈 ——
**正是 `sweep` 当初被发明出来取代的行为，从侧门回来了。**

### 15.2 改法：只有"开过去过、却还是看不见"的洞才算盲点（`shadow_near_m=2.0`）

判据用现成的 `_fresh_depth`（每格到最近 visited 格的距离，单位格）：洞的任一部分必须在
机器人走过的地方 2 m 之内。

| | 到轨迹最近距离 | 判定 |
|---|---|---|
| v11 那个 1.64 m² 真盲点 | **0.43 m** | 够格 ✓ |
| v12 劫持跑程的那些临时洞 | **3–6 m** | 不够格 ✗ |

★ **上线前的离线预演**（v11 栅格，按轨迹长度截断）：

| 轨迹长度 | 被"太远"拒绝 | 选出的位姿 |
|---|---|---|
| 150 帧 | 2 | None |
| 300 帧 | 2 | None |
| 600 帧 | 1 | **(4.45, 2.05)** ← 正对 1.64 m² 的洞 ✓ |
| 1163 帧 | 0 | (3.35, 3.45) |

**轨迹还很短时洞被拒绝、等机器人开过去之后才够格** —— 这正是想要的行为，
也是这次敢再跑的依据。这不是调出来的数，是关于世界的一句话：**走过去了，还是看不见。**

### 15.3 第二个缺陷：被丢弃的候选**不能有副作用**

第一版先调 `_pick_sweep_target`、再让阴影覆盖它的答案 —— 而 sweep 选择器
**提交斑块是副作用**，于是那些被丢弃的 sweep 照样推进了斑块承诺的计数。
症状就在计数里：`sweep_targets=2` 却有 `locks=2 / releases=1`。
现在阴影先问，它赢了就**根本不调用** sweep 选择器。

### 15.4 第三个缺陷：测试夹具把负例变成了空操作

`WorldMap.add()` 会把传给它的 pose 写进 `traj`，而 `world_with_pocket()` 的 pose 是原点 ——
而原点就在洞里。于是"洞到 visited 的距离"**恒为 0**，"距轨迹 2.9 m 的洞必须被拒绝"
这条负例形同虚设（第一次跑就是它 FAIL，才发现）。夹具现在先清空 `traj`。

⇒ **做离线复现前先问一句：哪些状态是 `add()` 才有的？**（同一轮还踩过 `ground_ever`：
手工造 `WorldMap` 时它是空数组，依赖它的闸门全 False 而且**不报错**。）

### 15.5 测试（全套 105 项）

用例 16 扩成三条：正例（开过去的洞必须给位姿 + 用 `_clear` 独立验证视线）、一趟制、
`shadow=False` 必须完全关掉；**加一条负例把 v12 这次回归本身钉死**：
距轨迹 2.9 m 的洞必须被拒绝，且 `n_shadow_far > 0`（否则"是闸门在起作用"这句话不成立）。

## 16. 第十二轮真正的发现：**房间级分配是抽签**

把五次仿真实跑（五个不同构建，同一世界、同一检测器）的**逐房间**轨迹覆盖摆在一起 ——
同一套房间框、同一个 0.6 m visited 半径：

| 跑次 | 路程 m | 仿真 s | 可达% | 右上 | 左下 | 左上 | 帘子一带 |
|---|---|---|---|---|---|---|---|
| r8 `y26_sim` | 54.1 | 123.0 | 76 | 0 | 0 | **79** | 0 |
| r10 `v10_sim` | 100.5 | 217.7 | 46 | 3 | 47 | 0 | 13 |
| r11 `v11_sim` | 102.2 | 232.4 | 46 | 17 | **71** | 44 | 11 |
| r12 `v12_sim` | 70.4 | 238.3 | 32 | **78** | 0 | 0 | 0 |
| r13 `v13_sim` | 107.8 | 227.5 | 46 | 51 | 23 | 5 | 0 |
| r14 `v14_sim` | 122.3 | 254.4 | 53 | 58 | 47 | 16 | 0 |
| r15 `v15_sim` | 112.8 | 268.2 | 44 | 74 | 32 | 0 | 0 |
| r16 `v16_sim` | 102.2 | 275.4 | 40 | 50 | 0 | 44 | 0 |

| 房间 | min | 中位 | max | **跨度** |
|---|---|---|---|---|
| 右上 | 0% | 34% | 78% | **78 个百分点** |
| 左下 | 0% | 35% | 71% | **71** |
| 左上 | 0% | 11% | 79% | **79** |
| 帘子 | 0% | 0% | 13% | 13 |

**每间房都在 0%–78% 之间跳**，跨度比这一轮任何改动都大。
⇒ 单跑数字（含 r13 的"右上 51%"、r14 的"58/47/16"）**都不能当战果**。

⇒ 三件必须承认的事：

1. **"这次哪间房做得好"基本由早期那次全局打分的运气决定，然后一路沿用。**
   r12 那版把右上做到 78% 却把另外两间做成 0% —— 它并不是"更聪明"。
2. **单跑的逐房间数字不能作为战果**，包括我自己 r13 的"右上 17%→51%"。
   同一个机制换成 r12 会得到 78%，换成 r10 会得到 3%。
3. 这也回头解释了 r8/r9/r10/r11 的左上覆盖为什么是 79/60/0/44 —— 那不是"能力退了"。

### 16.1 改法：两段式扫掠（`sweep_first_pass`，`sweep_stop_spread_m=2.0`）

人不会那样探索：**先把每间房都进去一次，再回头抠角落。**

1. **第一遍（勘察）**：只要还存在"最深处离**已停靠点**都 >2 m"的候选斑块，就取它，
   并且**忽略斑块承诺**（`locked=0`）—— 一遍下来每间房各一站，不集中在任何一处。
2. **第二遍（细做）**：没有"别处"可去了 ⇒ **闩掉**（`sweep_first_pass=False`，
   不每帧重算），此时斑块承诺生效（"这间做到 1.2 m² 或最多 4 站"）。
3. 边界：第一遍若候选全部无法规划，退回全部候选 ——
   **散布是"顺序偏好"，不是停工的理由。**

新增计数 `first_pass_stops` / `deep_stops` / `first_pass`：
`deep_stops=0` 说明整跑只做了勘察、`first_pass_stops=0` 说明根本没勘察过 ——
**两个数必须都能报出来**，否则"机制存在"和"机制生效"又会混成一件事。

### 16.2 测试 17 → 18 项（全套 106 项）

* 用例 17 加 `sweep_first_pass=False`：它测的是**斑块承诺**，而"每间房先来一站"会
  **正确地**把第二站送去别处 ⇒ 不显式关掉勘察，这个用例就是在测别的东西。
  （这条改动本身就是一条教训：**加了一层新机制时，旧用例的隐含前提要重新审一遍。**）
* **新增用例 18**：连做 4 站，断言**没有任何两站相距 ≤ `sweep_stop_spread_m`** ——
  把"集中"这件事本身钉死。实测 4 站分居走廊四角
  `(5.75,−1.15) / (−1.55,−1.15) / (5.75,1.15) / (−1.55,1.15)`，`deep_stops=0`。
* 用例 17 的期望值不变（第二个目标仍必须在同一斑块内、走完才换块、`locks==1`）。

### 16.3 一句必须写下来的话

**这一轮的结论不是"探索变好了"，而是"原来的评价方式本身不可靠"。**
在改动任何东西之前，先把**逐房间覆盖在多次跑次上的分布**量出来 ——
否则就会把一次运气当成功劳，或者把一次坏运气当成回归（我在 r12 上差点反过来做）。

### 16.4 勘察这条机制我改了三次，前两次都是同一个错误的两种衣服

| 版本 | 跑次读数 | 结论 |
|---|---|---|
| v14 | `勘察 0 / 细做 13` | **第一帧地图是空的** ⇒ `new_c` 为空 ⇒ 判定"没有别处可去" ⇒ **当场闩死**，整跑没勘察过 |
| v15 | `勘察 2 / 细做 16` | 一次性 latch：那一刻只有客厅，两站就覆盖完 ⇒ 闩死 ⇒ **后面才发现的房间一次都没被勘察** |
| v16 | `勘察 6 / 细做 0` | **去掉 latch 后勘察正常了，但它把整跑吃光了** —— 275 s 全在做勘察，`deep_stops = 0` |

★ **v16 给出了本轮最有价值的一条结构性结论**：
**在固定预算下，"把每间房都进一次"和"把任何一间房做深"是零和的。**
勘察 6 站 = 6 次跨房间车程，275 s 用完；细做 0 站。
所以"更充分的探索"在固定墙钟下不是一个排序问题，是一个**配额问题** ——
要么给更多时间（`--duration`，容器里 Gazebo 跑不到实时，232–275 s 仿真 ≈ 400 s 墙钟），
要么显式给每个区域留预算（本轮没做）。**继续加排序规则解决不了它。**

**两次都是把"暂时没有活"当成了"没有活"。工作集在跑的过程中会长大，
所以这个判断必须每帧重问，不能一次定死。**

台账 `_survey_stops` **只记勘察停靠点**：细做的停靠点若记进去，每个细做目标都会显得
"是新地方"，勘察就永远不会交棒给斑块承诺。

⚠️ 还修了一处**自己造成的自相矛盾**：`sweep_first_pass` 既是"勘察开关"又是
"上次是不是勘察"，而选择器会把自己的答案写回去 ⇒ `sweep_first_pass=False` 形同虚设
（用例 17 因此失败才暴露）。**配置与上报必须是两个变量。**

### 16.5 测试 18 → 19 项（全套 107 项）

* 用例 18 的空地图断言改成"计数器必须都是 0"（不再有 latch 可断言）；
* **新增用例 19**：短走廊上先做 4 站勘察，**然后揭示更多地板**，断言勘察
  **重新开火**并落在新区域（实测目标 `(5.75, 0.85)`、勘察站 4 → 5）。
  **这条用例就是把 v15 的 bug 本身钉死** —— 这也是本轮的一个模式：
  每修一个"机制没生效"的 bug，就把那个失效模式写成一条断言。

### 16.6 诚实的结论（写给下一个接手的人）

**七次跑次之后，我不能声称房间级分配变可靠了。** 各版本的单跑逐房间数字：

```
r8   0/0/79     r10  3/47/0     r11 17/71/44   r12 78/0/0
r13  51/23/5    r14  58/47/16   r15 74/32/0
```

跨房间的极差在**每一版**上都到 0%，也就是说"某间房这次几乎没进"在**任何版本**上都发生。
**下一步不该再改策略，而该改"验收方式"**：同一构建跑 N≥3 次，看
**"三个房间的最小覆盖"**（或"每间房都 ≥X% 的跑次比例"）这个统计量 ——
它才是 boss 那句"有间房从没进去过"的直接对应物，而且**抗运气**。
单跑对比只能用来抓"明显故障"（比如 v12 的劫持、v14/v15 的勘察失效），
那几次它确实抓到了，这部分结论是可靠的。

### 17.1 蹲墙角：控制器里有一个"什么都不做"的状态

不要猜，看 v16 自己的帧表。`out/_stuck_scan.py` 扫出来的九个片段里，
最长的一段在 `t=211.7–254.9 s`（**43 秒，占整跑 275 s 的 16%**），小车钉在 `(-7.6, 0.2)`：

```
      t      x      y state    kind         tx     ty     d      v      w     yaw    tyaw    herr
  213.7  -7.62   0.15 turn     sweep     -2.85   6.35  7.82   0.00   0.03   -67.9   -48.0     1.1
  214.1  -7.62   0.15 turn     sweep     -2.85   6.35  7.82   0.00   0.01   -67.3   -47.3     0.3
  214.3  -7.62   0.15 turn     sweep     -2.85   6.35  7.82   0.00  -0.12   -67.2   -47.1    -4.2
  ...（每 3.6 秒 backoff 一次，转约 60 度，再回到同一个位姿，再来一遍）
```

`heading_err_deg` 约等于 0、`v = 0`、`w` 约等于 0 —— **小车被要求既不前进也不转向。**

机理（`explore.py` 的 `command()`，改动前的四行）：

```python
if not ahead:                       # 前方受阻
    mode, v = "turn", 0.0
elif err_deg <= turn_only_deg:      # 航向已对 -> 本该 drive
    mode, v = "drive", ...
...
w = clip(1.6 * err, +-w_max)        # <- err 约等于 0 时 w 也约等于 0
```

`ahead` 为假时无条件进 `turn`，而 `turn` 的角速度正比于航向误差 ——
**航向已经对准、前方却受阻**这种组合落进 `turn`，输出就是 `(0, 0)`。
★ 这是一个**没有出口的状态**：`(0,0)` 不产生任何新信息，下一帧推出同一个 `(0,0)`。
**`(0,0)` 不是"慢"，是"停"。** v16 在这上面花了 161 帧（11.7% 的跑程），而**程序从头到尾没有报任何错**。

**前方为什么会受阻、而航向又是准的？** 因为 `_lookahead` 的错：

```python
# 改动前
best = path[0]
for p in path[1:]:
    if hypot(p - pose) > 1.2: break
    best = p
return best        # <- 路径上 1.2 m 处的点，不管直线能不能过去
```

路径在**急弯**处，1.2 m 处的点在**弯的另一侧**。小车站在架子边、路径要绕过去时，
这个"前视点"就在架子里面。于是 `aim` 指向架子里、`err` 因此变成 0（因为小车正对准自己那个错的 aim），
`_ahead_clear` 说"前面是架子"，输出 `(0,0)`。**两条 bug 相乘。**

**修法两条（都要）：**

1. **`_lookahead` 改成视线可达**：在路径窗口内，从最远往回找**直线走得通**的点，
   找不到就退回最近的那个（`n_los_shortened` 报出来）。
   这就是纯追踪里的 line-of-sight lookahead（nav2 `RegulatedPurePursuit` 的碰撞检查是同一个想法）。
2. **`wedge` 成为一个有名字的状态**：`aligned` 且 `ahead` 为假 ⇒ 不是 `turn`，是 `wedge`；
   `wedge` **立刻触发 backoff**（转不出去就往后退，至少不是雕像）。

### 17.2 `los_grid`：视线检测用哪张栅格，我量了两种

| 用哪张 | 结果 | 结论 |
|---|---|---|
| 规划器的可走栅格 `free_space()`（已按 0.19 m 腐蚀） | 663 个位姿里"朴素前视点不可达" 89 个，修好 39，**剩下 50 个无解**；实跑重放里 `turn` 585 帧（比不修的 536 还多） | **过严**：腐蚀壳有 0.19 m 厚，小车贴着墙站时**任何方向**的第一步采样都在壳里 ⇒ 前视点永远退回最近点 ⇒ 航向误差被放大成"0.1 m 处的角度"，转得更凶。**药和病一样贵。** |
| 已知地板 `wmap.ground`（已扣掉确认障碍） | 不可达 18，修好 10，无解 8，`turn` 422 帧 | **取它。** 它修的正是"aim 穿墙"这个病，且与近场护栏（一直用未腐蚀的 `blocked()`）口径一致 |

> 没做的事，记一笔：更"正确"的做法是**视线采样跳过机器人自身半径**（0.19 m 以内的采样点不参与判断），
> 这样就能用严的 `walk` 栅格而不踩腐蚀壳的坑。这一轮没做，因为已经有一条量过的路。

### 17.3 「抽签」的机理：**1e-7 米**

这一条是本轮最有价值的发现。做法：把一次实跑的每一帧 npz 重新喂回同一条流水线
（新增 `tools/replay_explore.py`）。KISS-ICP 对同一份点云是确定性的、`control_yaw` 也存了，
所以**位姿可以逐帧复现**。实测复现精度：

```
max |dpose| over 40 frames = 4.988e-07 m
```

**只有 5e-7 米。** 不是 bit 相同（KISS 的最近邻搜索受线程顺序影响），但小到可以忽略。

然后：**这 5e-7 米，让第一次阴影观察位姿从 `(-3.05,-0.45)` 变成了 `(2.35,-1.25)` —— 差了 3 米。**
再往后两跑只有 **49% 的帧状态一致**：42 次 backoff vs 13 次，6 个 sweep 目标 vs 12 个。
一次性采集、同一份代码、5e-7 米的输入差 ⇒ **整跑走向完全不同**。

**这就是 boss 说的"抽签"**，而且它不是玄学，有确切机制：
目标排序用的是连续分数 `size/(1+d)`，
**前两名只差几个百分点时，谁赢取决于哪个斑块多算进/少算进了一个格子**，
而"多一个格子"正是那 5e-7 米能干的事。

**修法：把分数和次序都量化。** `_rank_key(score, d, x, y)` 返回
`(-round(score/0.25 m2), round(d/0.25 m), round(x/0.25 m), round(y/0.25 m))`：

* 分数差在 `score_quantum_m2 = 0.25 m2` 以内 ⇒ **判定为平手**，比距离；
* 距离也平手 ⇒ 比位置；
* 三者都是**结构量**，不受最后一个十进制位影响。**任意但是稳定** —— 缺的就是"稳定"。

⚠️ 量化不能吃掉真差别：用例 22 同时钉住"差 0.03% 不许改序"和"差 13% 必须赢"。

### 17.4 第二个蹲墙角：`turn` 的计数器数的是"连续"，不是"同一个目标"

v17（修了 `(0,0)`）实跑之后，卡顿扫描仍然找出 30 s / 262 s（11.5%）的片段。
v18 的逐帧表把形状摊开了：

```
  91.3  -10.23  -2.51  drive  sweep  (-11.95,-1.95)  d=1.81  v=0.55  w=0.56  herr=20.1
  91.5  -10.19  -2.50  turn   sweep  (-11.95,-1.95)  d=1.84  v=0.00  w=0.90  herr=172.5   <- aim 翻到背后
  ...7 帧 turn -> 8 帧 arc -> 2 帧 drive -> 再 7 帧 turn...
```

周期约 20 帧（4 秒），**`d` 从头到尾没下降过**，而整段跑了 40 秒、转了 **5.5 圈**。
逃逸机制（`max_turn_frames=18` ⇒ backoff）**整跑只触发 7 次**，因为
`_n_turn` 在"这一帧没被挡住"时就清零 —— 周期里的 `arc`/`drive` 帧一直在清零它。
**计数器数的是"连续被挡的帧数"，而这里需要的是"这个目标一共被挡了多少帧"。**

**修法（把两个计数器合成一个 —— 机制更少，不是更多）：**
`goal_blocked_frames = 30`（6 秒）：

* 计入 `turn` 和 `wedge` 两种被挡帧；
* **只要对目标的距离创了新低（`progress_eps_m = 2 cm`）就把预算补满**；
* 预算花完 ⇒ 目标作废、拉黑（`wedge_deny_m = 0.9 m`）、换目标。

★ `progress_eps_m` 必须**远小于** `sweep_stuck_improve_m`（0.5 m）：那个量问的是"这趟路还值不值得走"，
这个量问的是"车是不是卡住了"。用 0.5 m 会让一个 5 mm/帧慢慢靠近的车在赚到补满之前就花光预算 ——
**那正是上一轮实测"按距离弃目标更差"（33.5% → 27.5%）的病**。用例 21d 钉死这一条。

| 第 4 次 | (−1.77, −2.53) | (−1.77, −2.53) | 40/40 |

⇒ **策略是输入的确定函数**（给同一份输入，它每次都给同一个答案），
所以四次跑的不一样**不是代码随机**，而是**输入在第 0 帧就不一样**（那 7.6 mm），
而**第 0 帧的决策把 7.6 mm 放大成了"往哪边开 6 米"**。

★ 这和 §17.3 是同一个现象的两种尺度：那里是 5e-7 m 的输入差改掉阴影观察位姿；
这里是 7.6 mm 的输入差改掉第一段旅程。**共同点不是"噪声大"，而是"决策在信息最少的那一刻做，并且被长期执行"。**

### 19.4 两个候选修法，分别治不同的东西（要 boss 选）

| 修法 | 治什么 | 对验收指标（三房最小值）的作用 |
|---|---|---|
| **① 开头不要用"一帧地图"下长期决定**（或前 10 s 用一个与排名无关的固定行为：转向未知最多的方向） | 治**方差**：让四次跑不再各奔东西 | **不直接改善**。它让结果可复现，但如果那个唯一的结局仍然是某间房 0%，指标不动 |
| **② 欠覆盖债务（coverage debt）**：一个区域"已知、未完成、且长期没有推进"时，它的效用随时间增长 | 治**覆盖**：那 7 例早停正是它要对的东西 | **直接对应** |

★ **两者不是一回事，不要混着上。** 而且 ② 不是硬配额：没有"每间房必须 50%"，
只有"欠得越久、优先级越高"，最终仍然压不过一个真正新发现的大区域 —— 这保住了
boss 说的"仍然是探索策略，而不是人为路线"。

**建议顺序**：先做 ②（它直接对着验收指标），做完跑 N≥3 看「三房最小值」的分布，
再决定 ① 值不值得做。**两次都不要再比单跑**（§18）。

## 20. 第十四轮：boss 说「做 ②，不做 ①」—— 欠覆盖债务做出来了，**结果是**否定的

boss 的设计约束（2026-10-05）：

> 「**先做 ②，不做 ①**」「第一版**只加欠覆盖债务**，不碰启动策略、不碰控制器、不碰 safety、不碰配额」
> 「不要让它无限累积然后强迫车穿越很远距离」「债务项最终必须和**旅行成本**耦合」
> 「第一轮最有价值的成功标准是：**那些『某房间 t=0 以后 150–250 秒完全没再推进』的情况消失**。
> 即使最终三房最小值只有 25–35%，我也会认为**机制验证成功**。反过来，如果三房最小值提高了，
> 但出现大量 target switch、大量横穿地图、m²/m 明显下降，那就是一个失败的修法。」

这一轮把 ② 按他给的形状做了、测了、**并按他的判据判为没通过**。下面按他列的量逐条报。

### 20.1 实现（一行一个决定）

| 决定 | 值 | 为什么是这个 |
|---|---|---|
| 区域粒度 | 1 m 粗格 | 比"房间"小、比栅格大；房间要手写，那就成配额了 |
| 每块债务 | `gain × min(idle / recall, 1)`，gain=1 m²、recall=40 s | **上限是 boss 要求的**（见 20.6，问题正出在这里） |
| 三个条件 | 已知（≥0.5 m² 见过地板）**且** 仍有可达未覆盖（≥0.25 m²）**且** 没在被推进（本次新增覆盖 <0.10 m²） | boss 原话的三条，逐条落地 |
| 被覆盖时 | **直接清零**，不是衰减 | 残值会把车拉回一间已经做完的房间 |
| 加在哪 | 现有打分的**分子**，与 patch size 共用同一个 `1/(1+d)` 分母 | 这就是"和旅行成本耦合"：排的还是 m²/m，债务只是另一种 m² |

| 时钟 | `command(..., stamp=None)`；没有时钟就**完全不累积** | 否则 recall 在 5 Hz 上意味着 8 s、在 10 Hz 上意味着 4 s |

### 20.6 下一步（要 boss 拍板，因为上限是他定的）

boss 当初要上限的理由是对的（"不许无限累积然后强迫车横穿地图"），但测量说上限放错了地方。
保留他的顾虑的正确形状是：

```
每块的债   = gain × idle / recall            （不设上限，随被忽略的时间线性长）
每个候选的拉力 = min(Σ 半径内各块的债, debt_pull_cap)   （上限放在这里）
```

* 次序来自**求和**：被忽略 80 s 的区域严格排在 40 s 的前面，"哪片最该回去"有了答案；
* 强度仍然有界：一个候选最多拿到 `debt_pull_cap`；
* 这正好是 boss 自己写的 `U = 信息/代价 + λ·债务/代价` 里 **λ 该管的事**，
  而不是给每块加一个截断。

顺序建议：**先在重放上确认新形状在这份采集上会给出不同的决策**（≈10 分钟），
再跑 N=4（≈35 分钟）。**不建议再调 `debt_gain_m2`** —— cap 从 1 加到 9 决策一字不差。

## 21. 第十五轮：boss 要的「零成本 replay 剂量响应」跑了 —— **八臂全平，因为桌上往往只有一个候选**

boss 的指令（2026-10-05，第二轮）：

> 「我会接受这个『② 第一版失败』，但**不同意现在就把无上限线性债务作为下一步默认方案**。」
> 债务要改成 **区域状态**：`debt ≈ 未覆盖可达面积 × 自上次有效推进以来的时间`；`f(t)=min(t,T)`，
> **cap 的是时间的有效区间而不是每个区域只有 9 分**（0–20 s 几乎没有债 / 20–120 s 持续增长 / >120 s 不再增长）；
> **不要把房间拓扑硬编码进探索器**。
> 「不过在写代码之前，我会先做一个零成本 replay」：扫 `T = 20/40/60/90/120/180`，看
> **第一次真正发生 debt-induced target switch 在什么时候、把哪个目标换成了哪个**；
> 「如果 replay 里发现任何合理 λ 要么完全不影响、要么一上来就疯狂抢目标，那就说明 utility 结构还需要调整，
> **根本不值得上仿真**。」

这一轮照做了，而且答案是**比"没改善"更彻底的一种**：**它连一次决策都没改** —— 而原因不在债务身上。

### 21.1 按 boss 的形状重写的实现

| 决定 | 值 | 依据 |
|---|---|---|
| 区域是什么 | **新鲜斑块**（`reach & ~visited` 的 8 连通分量）—— 不写房间 | boss：「不要硬编码房间」 |
| 未完成量 | **斑块面积**（已经在 `base = area/(1+d)` 里） | 这就是他那个 `未覆盖面积` 因子 |
| 时间 | `f(idle) = clip((idle - grace)/(cap - grace), 0, 1)`，`grace=20 s`、`cap=120 s` | 他给的"0–20 几乎没债 / 线性 / >120 不再涨" |
| idle 怎么算 | 1 m 粗格上"自上次被覆盖以来的秒数"，取**斑块内各格平均** | 均值而不是 min/max：max 会被一个陈旧角落拖住整块，min 会被刚瞥见的一小条清零 |
| 合成 | `score = base × (1 + λ f)` ≡ `U = base + λ·(base×f)` | 就是 boss 写的加法式，`λ=debt_lambda` |
| 加在哪 | **只在 sweep**（区域候选） | v21 把同一项加到 shadow/frontier 上过，那两类是点状候选，只会把它变成一个常数 |
| 默认 | **`debt_lambda = 0`（关）** | 见 21.4，这是测量结论不是口味 |
| 覆盖时 | 该块 idle **清零**（不是衰减） | 承接 v21 的教训 |

测试 **24 → 25 项**（全套 112 项全绿）：

* **用例 24（新）**：`f` 的语义 —— 0/10/20 s → 0.00、70 s → 0.50、120 s → 1.00、360 s → 1.00，
  并且**钉死"45 s 和 200 s 必须不同"**（差 <0.2 就 FAIL）—— 这一条正是 v21 失败的定义。
* **用例 25（新）**：**忽视相同不许改序**（两块同样老 → 选原来的）、**忽视不同必须改序**
  （东边老 → 翻到东边；西边老 → 不动），并检查 `debt_swaps` 记 1 / 0。
* 用例 23 保留并改名：idle 以**秒**增长（90 s 站住 → 90 s）、覆盖清零的是**那一个块**而不是附近。

### 21.4 为什么？三个独立测量，指向同一件事

**① 桌上通常只有**一个**候选。** 在 `_plan_first` 真正的决策点上数候选个数（43 次）：

| 路径 | 次数 | 其中 ≥2 个候选 |
|---|---|---|
| `global`（回退到全部新鲜斑块） | 21 | **0** |
| `locked`（跟着当前房间做深） | 11 | **0** |
| `survey`（"去一个离之前停靠点都远的地方"） | 9 | 2 |
| `lock-failed` | 2 | 0 |

**41/43 次只有 1 个候选。** 排序器没有东西可排 —— 此时任何权重、任何效用、任何滞回都无处施力。

**② 有得选的时候，被忽略最久的恰好就是 plain 已经选中的那个。**
`f_gap = f_max − f_plain = 0` 在**每一次**多候选的决策上成立（重放里 2 次、离线末帧状态 5×6 次）。
结构性原因：**候选按定义是 `reach & ~visited`，是由"从没走近过的地板"组成的**
⇒ 组成所有候选的那些块，恰恰就是"很久没人管"的那些块 ⇒ 权重在候选之间**天然是平的**。
★ 这个项问的是"这块最近有没有被照顾过"，而它被问的对象**按定义就是没被照顾过的**。

**③ 就算权重完全相反，也推不翻首名。** 债务最多能把候选的分数乘 `1+λ = 2`。
在**真实的末帧地图**上（那里确实有 3–9 个候选），首名 / 次名的 plain 分差是：

| 跑次 | 首名 | 次名 | 分差比 | 推翻它需要的 λ |

所以"加大力度"这条路两头都堵死了。

> 顺带修正 §20 的归因：那里我把根因写成"**每块的上限抹平了忽略时长的次序**"。
> 那件事是真的（cap 40 s = 忽略 45 s 与 200 s 等价），但**它不是约束**：
> 这一轮把上限换成"时间区间"、把 λ 开到 2，依然一次决策都没改。
> **真正的约束是候选集**，而这是这一轮才有仪器去测的东西（`pick_sizes` / `debt_margin` / `last_sweep_cands`）。

### 21.5 结论：**「改打分」这一整族修法在这里是空的**

上一轮之后的讨论（债务、效用、滞回、量化）都在改**排序**。这一轮量出来的是：

* 95% 的决策桌上只有 1 个候选 ⇒ **排序不参与决策**；
* 剩下 5% 里权重是平的 ⇒ **排序也无从参与**；
* 而"哪间房被做完"这个 boss 真正关心的问题，在这套策略里是由
  **"机器人此刻的可达集里有什么"**决定的 —— 也就是**什么时候某间房通过门口被连通起来**
  （`island` 探针 / 门口解析），而不是由任何跨房间的比较决定的。

所以真正的两个杠杆是：

1. **候选生成**：把一个新鲜斑块拆成**多个**"值得去的地方"（自然做法：`_fresh_depth` 场上的**局部极大**，
   也就是一个斑块里离已走过区域最远的几个方向）—— 这是让"排序"第一次有对象；
2. **房间何时进入候选集**：`island`/门口解析的时机（Discover），而不是室内的覆盖排序（Cover）。

**验收门槛（写在这里，免得下次又越级）**：**在重放里多数 pick 出现 ≥2 个候选之前，不再跑任何仿真。**
`pick_sizes` / `cand_med` 已经进了 summary 和 frames.csv 的同一套仪器里，下一轮直接读。

## 22. 第十六轮：① 候选生成 —— **排序第一次通电**

boss 的指令（2026-10-05 第三轮）：

> **不要把"大斑块机械地拆成多个点"本身当成目标，目标是让候选集从"只有一个方向"变成"具有竞争关系的多个方向"**。」
> 第一版建议：用 `_fresh_depth` 做**局部极大 + 空间抑制（NMS）**，`K=3`、`min_separation=0.8–1.2 m`。
> 「第一轮甚至不要接 debt」—— `v22 = v19 + candidate subdivision`，只做 replay。
> 验收三条：①`median(pick_size)` 能不能从 ≈1 上升到 ≥2（+ `P(N≥2)`、`P(N≥3)`）；
> ②候选**必须真的分开**（"如果三个候选全部集中在 ±5° 内，还是没用"）；
> ③排序**终于有没有"通电"**。
> 「我甚至建议把这写成项目里的硬门槛：**任何探索策略改动，在固定输入 replay 中必须至少改变
> 一定比例的有效候选排序/目标选择，否则不得进入长时间仿真**。」

### 22.1 实现：一个斑块 → 最多 K 个"值得去的地方"

| 参数 | 含义 | 默认 |
|---|---|---|
| `sweep_cands_per_patch` | 一个新鲜斑块最多出几个候选 | **1**（＝现状，A/B 才是一个变量） |
| `sweep_cand_sep_m` | 候选之间的最小间距（米） | 1.0 |
| `sweep_cand_sectors` | >1 时候选必须落在**不同的方位扇区**（见 22.4） | 1（关） |

* 生成：在 `_fresh_depth` 场上**贪心 NMS** —— 先取最深的格，再取离已取点 ≥`sep` 的最深格，
  依次到 K 个。`np.argsort(-dep, kind="stable")`：距离场上沿墙有大量并列值，不稳定排序会让
  **内存顺序**决定选点，正是 `_rank_key` 想挡掉的那类 bug。
* 排序键：原来的 `_rank_key` 后面**加一个后缀**（该候选的距离 → 位置）。同斑块的候选共享
  size / anchor / 忽视，所以**新问题只有一个**："这几个地方先去哪个" —— 收益相同 ⇒ 取最近的。
* **可证的最小改动**：K=1 时后缀是那个唯一候选的函数 ⇒ 前四项完全相同 ⇒ **排序与改动前逐帧一致**。
  25 项既有测试在默认 K=1 下全部原样通过，这就是证据；用例 26 把它钉住。

测试 **25 → 26 项**：用例 26 在同一份夹具上钉四件事 —— K=1 恰好 1 个候选（否则 A/B 不是一个变量）、
K=4/sep1.0 **≥3 个候选且最近一对 ≥1.00 m 且方位张角 >0**、K=4/sep6.0 在 3 m 宽的走廊里**只剩 2 个**
（抑制真的在起作用）、K=4/扇区8 的**张角 ≥45°**。

### 22.3 结果二：③ 的第二问暴露了第二个缺陷 —— 1 m 之隔，但只有 7.4°

原因是 NMS 只在**欧氏距离**上抑制。修法是同一个斑块里**按方位扇区**也要互斥

## 23. 第十七轮：候选级局部效用项（2026-10-05；**只做 replay，没跑仿真**）

boss 的原话（2026-10-05）：

> 「我赞成下一步做『逐候选局部效用项』，但我会给这个方案加一个非常重要的约束：
> **不要把上一轮 debt 原样搬过来，只是把它从 patch-level 改成 candidate-level。先明确
> 『局部效用』究竟要解决什么，再做 replay。**」
> 「第一版我建议只做一个局部量：**candidate 周围的局部未覆盖面积** … 不要同时加时间 /
> debt / hysteresis / 路程 / turning cost。」
> 「**Gate 1**：如果绝大多数时候 `max - min ≈ 0`，那么这个指标又会变成『大家加一样的东西』，
> **直接毙掉，不跑 8-arm**。**Gate 2**：`λ_required = plain_margin / local_difference`，
> 如果绝大多数需要 λ=20、50、100 才能翻转，那说明形状又有问题。」
> 「如果局部未覆盖量本身在候选之间没有足够方差，**直接停止，不要为了让实验继续而硬调 λ**。」
> 「这一次最重要的不是『让它变』，而是证明：**它为什么应该变，以及变了以后是否朝正确方向变。**」

### 23.1 这一项是什么（一句话）

```
local_u(候选点) = 该点周围 cand_local_radius_m(1.0 m) 内、(可达 ∧ 从未走近) 的地板面积 m²
score           = base + cand_local_lambda · local_u / (1 + d0)
```

`base = patch面积 / (1 + d_起点)` 是**同一 patch 里每个候选共享的同一个数** —— 它只能回答
「哪个 patch 值得跑一趟」。§22 把一个 patch 拆成了几个方向之后，真正缺的是
「**这几个方向里，哪个门前还剩着最多没走过的地板**」，所以这一项是**候选级**的。

三条刻意的限制：

* **不含时间、不含历史**（与 debt 的本质区别）：如果决策变了，原因只能是它；
* **走同一个 `1/(1+d)` 分母**（与 debt 学到的教训一致）：不与旅行成本耦合的加项 =
  「去还最大的债」变成「横穿地图」；
* **`cand_local_lambda = 0` 时按位等于旧 key**（乘 0 相加）⇒ A/B 是一个变量，用例 27 钉住。

### 23.2 三道门，都在**冻结重放**上量（`cap_v16`，一次感知）

|---|---|---|---|

| **Gate 1** | 候选之间这一项**有没有差别** | u 中位 **1.25 m²**；极差 p10 0.48 / **中位 0.55** / p90 1.52 / max 2.30；**只有 1/19 次是平的** | **过** |
| **Gate 2** | 翻榜首**要多大 λ** | 19 次里：**14 次不需要任何 λ**（榜首本来就是 u 最大）、**4 次 λ=0**（同一 patch，base 相同 ⇒ 任何 u 差都算数）、**1 次 λ≈11.98**（跨 patch，base 差太大） | **过，但边界要写明** |

对照 §20–§21 的债务：同一位置的读数是**恒为 0**（41/43 次只有 1 个候选；多候选时

1. `u_gap_flat_frac = 0.63`：**63% 的决策里，现行规则（同 patch 取最近）挑中的那个点，本来
   就是 u 最大的那个**。也就是说这一项**大部分时候与现行规则一致**，它只在「最近的点并不是
   门前剩得最多的点」时说话。这不是缺陷，但它决定了这一项的上限 —— 它不是新策略，是一个
   很小的修正。
2. Gate 2 的 λ≈12 那一次说明：**跨 patch 的取舍不是这一项该干的活**，也**不要靠加大 λ 去够**
   —— 那正是 boss 警告的「硬调 λ 让实验继续」。

### 23.4 这一轮**不能**说明什么

* **覆盖率**：重放跟的是**记录轨迹**，它不会走到新目标去，所以 `m²/m`、房间覆盖在重放里
  没有意义（§17.5 的边界）。这一轮能证明的只有「**决策变了，且方向正确**」。
* **过 10% 线 ≠ 变好**：那条线是「**允许上仿真**」的许可证，不是成绩。真正的验收仍是
  §19/§20 那两条：**「三房最小覆盖率」的 N≥3 分布**、**「某房间 ≥100 s 没推进且还剩 ≥40%」
  的条数**。λ=1 与 λ=2 都过线，所以**没有理由据此挑 λ**；建议取 **λ=1**，因为它的物理
  含义最干净（「候选点周围 1 m² 没走过的地板」记作「1 m² 的 patch」），λ=2 需要额外理由。
* **跨房间**：这一项只在 patch 内部竞争（见 23.2 第 2 条），**对 Discover 层没用**，这与
  §22.6 的层级判断一致，不要指望它顺带解决。

### 23.5 仪器：这一轮抓到并修掉的三个坑（都是"看着在工作"那类）

1. **`local_margin` 的 t 全是 0**：它写的是 `self._debt_t`，而那个时钟只在
   `debt_lambda > 0` 时推进 ⇒ 债务关掉时每条记录的时间戳都是 0，
   「第一次分歧在何时」这个问题在记录里**无法回答**。改成本帧自己的 `stamp`。
2. **swap 计数把"路由落选"当成了"排序改写"**：原写法是「实际选中的点 ≠ 关掉这一项后的
   榜首」，但榜首可能**不可规划**，于是实际选中的点是从更低名次顶上来的 ——
   这种"改写"两项下都会发生，属于虚报。现在只在「这一项自己的第一选择**真的被采纳**」时
   才计一次改写，落选单独记 `n_local_fallthrough`。
3. **逐次决策的 CSV 对齐是错的**：第一次分歧之后两条链各自换过目标，下标就错位了，
   `diff = 12/15` 会被误读成「改了 12 次决策」（实际是 1 次）。**决策级判据只有
   `swaps / decisions` 那一个数**，它是同一候选表、同一帧上算的。报告脚本里已经写明。

### 24.5 ★★ 根因：这一项让目标为了 +0.4 m² 搬了 18 米

`local_switches` 记录了实跑里全部 10 次改写。把「位移」和「买到的 Δu」放在一起看：

| 跑次 | 时刻 | 位移 | Δu |
|---|---|---|---|
| v23r2 | t=64.6 | **18.12 m** | **+0.40 m²** |
| v23r3 | t=136.1 | **13.82 m** | +1.14 m² |
| v23r1 | t=90.3 | 8.26 m | **+0.07 m²** |
| v23r1 | t=163.1 | 7.69 m | +0.98 m² |
| v23r2 | t=112.6 | 7.01 m | +0.94 m² |
| v23r3 | t=167.1 | 6.55 m | **+0.03 m²** |
| v23r3 | t=252.5 | 6.40 m | +0.54 m² |
| v23r1 | t=325.0 | 4.33 m | +1.57 m² |
| v23r2 | t=320.0 | 3.05 m | +1.72 m² |
| v23r1 | t=191.9 | 1.00 m | +0.56 m² |

**10 次里有 8 次把目标搬到 3 m 以外，2 次搬到 14–18 m 以外 —— 而买到的只有 0.03–1.7 m²。**

机理，一句话：**`base` 是 patch 级、分母 `1/(1+d0)` 也是 patch 级**，所以**同一个 patch 里
旅行成本对候选之间的比较完全不可见**——而在这个房子里，**一个「新鲜斑块」是穿过没探过的门口
的一整片连通未访问区域，可以横跨两三个房间**。于是"patch 内 base 相同 ⇒ 任何 Δu 都算数"
（§23 里被我当成"排序第一次通电"的那条）在实跑里变成：**为了 0.07 m² 的局部未覆盖面积，
把目标从房子这一头换到那一头。**

★ **必须承认：这个现象在 §23 自己的表里就已经印出来了** ——
`t=78.1 (-11.85,4.75) u=0.77 → (6.55,-2.55) u=1.62`，**位移 14.2 m、Δu +0.85**。
我当时把它读成"这一项偏好更宽敞的方向"，还写进文档说"每一次都改向门前剩得更多的点"。
**方向是对的，位移是错的**——而我的仪器只记了方向（`u_to > u_from`），没记位移，
所以 14 m 和 1.4 m 在记录里长得一模一样。**这是本轮真正的教训：改写类仪器的判据必须同时
包含"改了多远"，否则"朝对的方向去"可以把目标送到地图另一头而你还在为方向正确鼓掌。**

### 24.6 结论与下一步（要 boss 拍板）

* **默认保持 `cand_local_lambda = 0`**，**不再扫 λ**（λ=1 与 λ=2 在 replay 上都过 10% 线，
  实跑证明过线不等于有用，加 λ 只会放大同一个错误）；
* **不要**因为这一轮是负结果就回退 §22 的候选生成：对照臂（K=4/扇区12）本身的
  三房最小中位 9%，好于 v19 那四次的 0/0/0/18（中位 0%），但那也是 N=3，只能算"不像倒退"；
* 要修的话，修的是**形状**，而且有两条都在**冻结重放**上可先验证的路：
  1. **局部项用自己的距离**：分母从 patch 级 `d0` 换成候选自己的 `cd` ⇒ 18 m 外的点必须
     用多得多的 Δu 才买得起；
  2. **把比较限制在空间局部**：同一个 patch 内的候选，还要互相在半径 R 内才算同一组竞争者。
  验收方式现成：**那两次 18.1 / 13.8 m 的改写点，`need λ` 必须从 0 涨到 >1**；
  若涨不上去，说明形状还是错的，**不许上仿真**。
* 另一条路是**转去 Discover**（`帘子` 两臂 6/6 全 0%、右上 3/3 全 0%——「房间何时进入候选集」）。
  **这是方向选择，请 boss 定。**
