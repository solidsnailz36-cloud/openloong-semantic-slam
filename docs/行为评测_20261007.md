## 1. 设计与事前判据

| 项 | 值 |
|---|---|
| 臂 | `A0`（无覆盖）｜`S1`（`fresh_split_m=3.0`）｜`SV4`（+`sweep_value_mode=view`、`sweep_cands_per_patch=4`、`sweep_cand_sectors=4`） |
| 次数 | **每臂 4 次**，**轮流**（A0→S1→SV4→A0→…） |
| 单次 | 实时 Gazebo，`--duration 400`（墙钟），`--explore`，`--dump`/`--dump-grids` 与历史跑一致 |
| 并发 | **串行**。`--duration` 是墙钟秒 ⇒ 并行会改变每次拿到的帧数，把"帧数"变成自变量 |
| 耗时 | 单次 **7 分 16 秒**（12 次共 87 分钟，07:44:25→09:12:04 UTC） |

**为什么轮流**：中途被打断时拿到的是**平衡的部分样本**，而不是"某个臂跑得多"的偏样本。

**主指标（探索进展）—— 用时间对齐窗**
* `Tauc2` = `∫₀²⁰⁰ T dt / 200`（窗内平均覆盖，m²）
* `T@200` = `t=200 s` 时的覆盖（m²）
* `t80` = 达到**自身** 80% 覆盖的时刻（秒）—— 这是"速度"，与"总量"是两个轴

**⚠️ `t80` 自带分母**：它除的是**该次跑自己的**最终覆盖 ⇒ 一次"总共没看到多少"的跑，
到 80% 会很快。**所以 `t80` 永远不能单独读，必须和覆盖水平一起读**（boss 规则①的同族）。
本数据里 A0 既**覆盖更高**又**t80 更快** ⇒ 方向不是分母造成的。

**次指标（跑到哪算哪）**：`T_final`、`T_auc`（÷ 该次自己的时长）。

**效率**：`eff_m = T_final / 轨迹长度`、`eff_s = T_final / 时长`。

**稳定性**：每个量报 **中位 / IQR / 最差**（boss：中位数漂亮不代表最差没问题）。

## 3. ★ 一个必须先处理的口径问题：`--duration` 是**墙钟**秒

`t_end`（每次跑实际推进的**仿真时长**）：

```
min 214.9   中位 288.3   max 303.1      极差/中位 = 30.6%
⚠️ t_end < 0.9×中位 的跑：S1 r4 (215 s)、SV4 r4 (236 s)
```

**这不是"策略被提前停掉"，是"这台机器在那两次跑里推进得少"**：`--duration` 是墙钟秒，
而仿真的实时倍率受机器负载影响（Gazebo + llvmpipe 渲染是纯 CPU）。
同一个 400 s 墙钟里，有的跑推进 303 s 仿真时间，有的只推进 215 s。

⇒ **直接比 `T_final` 会把"仿真推进少"读成"走得差"**（项目既有规则：
"少走了 N m² 先问是走得差还是被提前停掉"）。
**处置**：主指标一律改成**固定窗口 0–200 s**（12 次跑全都覆盖了这个窗口），
`t_end` 逐次报出，并另给"剔除短跑"的一份重算。

**这也是这一轮暴露的 harness 缺陷**：行为对比应该按**仿真时长**跑，而不是按墙钟秒。
下次要么 `--duration` 换成样本数上限，要么在 `summary.json` 里记 `t_end` 并在验收时按它配平。

## 8. ★ 指标有效性：`traversable_m2` 会被**地图膨胀**骗到

`SV4 r4` 是全场最离谱的一次：`T_final = 342.1 m²`，但只走了 **51.5 m**（全场最短）、
`t_end = 235.8 s`（全场第二短）。查它的 `summary.json`：

| run | `seen_cells` | `drivable_area_m2` | `reachable_area_m2` | `trajectory_len_m` | `traversable_m2` |
|---|---|---|---|---|---|
| `A0 r4` | 29,920 | 171.6 | 152.8 | 118.7 | 252.7 |
| `SV4 r4` | **44,199** | **228.7** | 139.8 | **51.5** | **342.0** |

`drivable_area_m2` 说只有 228.7 m² 是可驾驶的，但 `traversable_m2` 报了 342 m²
——**"可通行面积"超过了"可驾驶面积"**，而房子本身的 drivable 只有 ~170 m²。
⇒ **`traversable_m2` 不是"能走的地板"，是"被判成可通行的格"**，会被一次地图膨胀整体抬高。

**处置**：把它当**主指标的上界代理**使用，另报两套更硬的量：
`reachability.reachable_area_m2`（§7）与**走到过的房间覆盖**（同 §7）。
**而结论对这次膨胀是稳健的**：`SV4 r4` 那次膨胀**帮了** SV4（把它从 217 抬到 230 的中位），
排除它之后 SV4 更差；主指标用的是**窗内**量，且 `SV4 r4` 的窗内 AUC（232.6）是四臂里最高的那次。

## 9. 局限（必须一起读）

1. **N=4**。臂内离散很大（`t_end` 极差 30.6%、房间覆盖 0–32%）。
   主指标的两条分离（窗内AUC 与 `T@200`）在**剔除短跑后 IQR 仍不相交**，这是能说"更好/更差"的
   最弱证据级别；房间级指标则**分不开**，只能按"最差"读。
2. **`--duration` 是墙钟秒**（§3）⇒ 每次跑的仿真时长不受控。这是 harness 缺陷，不是策略差异。
3. **一次跑只有 ~215–303 秒仿真时间、~120 m 行程**。房子需要多久才该走完，本数据回答不了。
4. **`t80` 自带分母**（§1）；`switches` 自带分母（§6，已按 boss 规则②处理）。
5. **`traversable_m2` 会被地图膨胀抬高**（§8）。
6. **本轮没有改任何探索代码**：`A0/S1/SV4` 都是 §51 之前的已装开关，默认关。

## 10. 按 boss 的三种情况归属 & 下一步

```
情况 A：S1/SV4 明显改善        → 回来做 link_m / d0 精调
情况 B：没改善                 → 找第二个瓶颈
情况 C：中位改善、worst 恶化   → 研究鲁棒性
```

**实测归属：情况 B，而且比 B 更硬** —— 基线在**时间对齐窗**的主指标上是 IQR 不相交地更好。

> **结论：对象尺度问题（§50）确实存在且已被构造性解决，
> 但"把大对象切小 + 换局部价值"并没有改善真实探索；真实探索在时间对齐口径下比基线更差。**

**下一步（建议，未实施）**：
1. **先修 harness**：让行为对比按**仿真时长**配平（§3），否则任何一次跨臂比较都可能被调度差异污染。
   这一条的优先级高于任何策略改动——它影响**所有**后续行为评测。
2. **找第二个瓶颈，而不是回来调参数**。本轮两臂共同的方向是：
   * `switches` 与覆盖**反向**（§6）：`SV4` 早停、`S1` 抖动；
   * **房间级"一次都没走到"三臂都有 ≥3/4 次**（§7）——这与 §46 那条旧账（进不去的房间）同族，
     说明**真正卡住覆盖的是"某些房间进不去"，而不是"选哪个 patch"**。
   ⇒ 建议把下一轮的对象从"patch 选择"换成**"进不去的门"**（`island` 探针 / 门口那一族），
     并复用 §46 的 `reach` 塌陷工具链。
3. **不要在 `link_m` / `d0` 上继续**（boss 已压住，本轮的 B 结论正是压住的依据）。
