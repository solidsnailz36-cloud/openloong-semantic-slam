## 一、左右反：`render()` 把世界 +y 画成了屏幕向下

### 1.1 排除掉的三条路

| 嫌疑 | 怎么排掉的 |
|---|---|
| 相机面板被翻转 | 拼接是 `np.hstack([left, right])`，`left` 是**原始图像 + 框**；全仓 `grep cv2.flip` —— 除本次新增外**一处都没有**，`viz.imwrite` 只做编码 |
| KISS-ICP 里程计"镜像" | 刚性配准**不可能产生镜像**（最多转 180°），所以一致性只能由渲染约定决定 |
| 某个补偿性翻转 | 无。`render()` 里 `py = (cy − y0) * k`，而 `win = img_world[y0:y1, x0:x1]` ⇒ **图像行号直接等于格行号，而图像行号向下增长** |

### 1.2 机理一句话

**世界 +y 被画成屏幕向下 ⇒ 面板是标准俯视图的上下镜像 ⇒ 对读地图的人，机器人的左右被互换 ⇒ 右转画成左转。**

### 1.3 实测（不是推理）

`tools/test_worldmap.py` 新增 §12：铺一条沿 **+x（航向）** 的地面条带、一条沿 **+y（机器人左侧）** 的地面条带，
渲染，然后**从渲染出的像素里把两条带读回来**。不变式按"人怎么读地图"陈述：

> **朝面板右侧的机器人，它的左手边必须在面板上方。**（面朝东时左手边是北。）

| | 机器人所在行 | +y（左侧）条带所在行 | 判读 |
|---|---|---|---|
| 修前 | row 270 | **row 280–434** | 画在了**下方** ⇒ 镜像 |
| 修后 | row 270 | 上方 | ✅ |

### 1.4 ⚠️ 为什么 §11 抓不到它（这一条比 bug 本身值钱）

§11 早就有"叠加层落在它下面的地图上"的断言，**而且在镜像的图上照样全绿**。
原因：§11 的 `pixel_of` 辅助函数是**手写的、模仿渲染器口径的**，它写着
`"+y downwards"` —— **和坏掉的渲染器编码了同一个错约定，于是互相印证**。

**⇒ 一个把实现复述一遍的测试，抓不到实现里的约定错误。**
§11 的辅助函数已改成按**文档口径**写（+x 向右、+y 向上），改后仍全绿。

### 1.5 修法

```python
img = cv2.resize(win, (size, size), interpolation=cv2.INTER_NEAREST)
img = cv2.flip(img, 0)                       # 世界 +y 向上
def to_px(x, y):
    c = self.cell_of(x, y)
    return ((c[0] - x0) * k, ((y1 - y0 - 1) - (c[1] - y0)) * k)
```

**翻转只作用于栅格本身**：图例、5 m 比例尺、机器人圆点都在其后绘制，必须保持正立。
**行为影响：零。** 同一份 bag 重跑，**决策列 md5 逐位相同（`dcc8fd551e32`）**，
`traversable 439.1 m² / seen 68215 / obstacle 178.4 m²` 全部一致。

## 二、绿区灰斑：**画面在说谎，地图是对的**

### 2.1 先量清楚"灰"是什么

`灰 = seen & ~ground`，而 `ground = ground_ever & ~obstacle`。真实侧（`out/_diag_real/grids`）：

```
灰                    243.1 m2
  ├─ 障碍层**拥有**它          178.4 m2   （墙/家具，涂灰是对的）
  └─ 障碍层**没有**拥有它       64.7 m2   <── 却被涂成和墙一模一样的灰
绿区里的灰斑            17.70 m2
  ├─ 真的被晋升为障碍            1.42 m2
  └─ **从未晋升**              16.28 m2   = 92%
```

并且：**绿区里的灰斑是 1006 个连通块，面积中位数 0.01 m²（就是单格），最大 0.15 m²** —— 盐噪声。

### 2.2 逐条排除（每条都用测量，不靠推理）

| 假设 | 测量 | 结论 |
|---|---|---|
| 记账 bug：`ground_ever=False` 却存着地面点 | 与 `map.pcd` 逐格对照，**0 格矛盾** | 否 |
| 死带（`ground_mask` 的 `|h|<tol` 与 `obstacle_mask` 的 `h>0.35` 之间） | 上窗 3/1770 格、下窗 17/1770 格 | 否 |
| 是行人挡出的影子 | 9% 在 person 观测 0.5 m 内，34% 在 2 m 内 | 是**部分**原因，不是主因 |
| 是真实物体 | **回相机看**：机器人当时看向那些位置，画面里是**普通地面**（地面黄色标线、木地板、瓷砖），**没有 0.35–2 m 高的东西** | 否 |

剩下的事实：每个斑格只有 **2–3 个点**，且同一格里还常有**低于地面平面约 1.4 m 的点**（物理上不存在）——
**⇒ 稀疏多径 / 假回波**。而项目此前已经判过：**观测层判别器 AUC 0.638，分不开**
（"观测层信息不足，不是特征不够，别再堆特征"）。

### 2.3 修法（两条，都只动画面）

**（a）四分类着色**：原来 `seen & ~ground` 一律涂成墙灰。现在：

```
绿   = ground
灰   = seen & obstacle        （障碍层拥有它 —— 真的挡住）
暗   = seen & ~ground & ~obstacle（看过，但从未判为障碍）
```

**（b）单格斑点填充**：`seen & ~ground & ~obstacle` 且**八个邻居全是可通行**的格，按可通行绘制。
依据不是我编的：**这些格地图自己就没判它是障碍**（`~obstacle`），而一个有体积的实物不可能 8 个邻居全通。

**⚠️ 这是画面规则，不是地图规则**：`seen / ground / obstacle` 三个数组与 `map.pcd` **一个字节都没改**
⇒ 规划器、覆盖口径、replay、反事实全部不受影响。
（`seen` 不能动：`explore.py` 的前沿逻辑 `~wmap.seen` 在读它。）
开关 `worldmap.RENDER_FILL_LONE_SEEN`（默认开，可关）。

### 2.4 验收

`tools/test_worldmap.py` §13/§14：晋升格与未晋升格**必须不同色**；单格且八邻可通行**必须被填**；
成簇的未晋升格**不许填**；单个被晋升的障碍格**一律不许填**。**59 checks / 0 failed。**

**★ 落在真实画面上的效果**（同一份 bag、同一帧 `001400`，只数地图面板的像素）：

| 面板 | 绿色像素 | 灰（墙色）像素 | 其中**落在绿区里**的 | 新的“看得到但未判障碍”类 |
|---|---|---|---|---|
| BEFORE | 37,473 | 20,317 | **2,982** | 0（原来与墙同色，分不出来） |
| AFTER | 37,600 | 15,089 | **663** | 5,270 |

**⇒ 绿区里的灰色像素 2982 → 663（−78%），而绿色面积只涨 0.3%** ——
改善来自“不再把非障碍画成障碍”，不是靠把可通行区灌水。

## 三、顺带抓到第三个缺陷：视频里有帧尺寸不一致

排查面板裁剪位置时发现：真实 bag 的 **1427 帧里有 2 帧（第 1200、1201）拼图宽度是 1080，其余是 1206**，
编码器把那两帧**压进了固定尺寸** ⇒ 视频里会看到一闪的形变。

根因：`camera_panel` 按**该帧图像自身的长宽比**缩放，而 bag 里有 2 帧图像尺寸不同。
修：`online_pipeline.py` 用**第一帧渲染出的面板宽度钉死**后续所有帧（不一致时 resize）。
代价是那 2 帧被重采样；收益是每一张拼图同形——本来就是视频文件的前提。
（自检：重跑后应 1427/1427 同宽。）

### 5.2 ★ 形态：为什么上一轮的单格填充没抓住它

`seen & ~ground & ~obstacle` 这类灰在绿区里的形态是**薄长条**（2–3 格宽、断续），不是孤立单格 ——
`_gray_v2.py` 的「闸门」扫描（灰带两侧都是绿）找到 12 处，其中 **8 处真障碍 0 格**：

gate#8  (12.7, 26.1)  0.30 x 1.40 m   20 格   真障碍 0/20

**「0.2–0.4 m 厚、1.4–2.4 m 长的薄带，一格真障碍都没有」** ——
这就是「形状不规则」＋「把入口几乎拦起来」的实体。物理上也不成立：一面墙不会只有 20 cm 厚还断续。

### 5.3 修法：**渲染相信障碍层的判决**

`obstacle` 是地图对「这里是否被挡住」的**唯一判决** ——
`blocked()` 就是 `obstacle | obstacle_now`，规划器的 `ground` 也已经是 `ground_ever & ~obstacle`。
一个「收到过回波但从未被晋升」的格，按地图自己的定义**不是障碍**；把它画成障碍色是在**发明一面墙**。

```python
# worldmap.RENDER_TRUST_OBSTACLE_LAYER（默认 True）
cls[self.seen & ~self.obstacle] = 1        # 只有 obstacle 才画灰
```

**仍然是画面规则**：`seen` / `ground` / `obstacle` / pcd **一个字节没动**
⇒ 规划器、覆盖口径、replay、反事实全不受影响（`seen` 也不能动：`explore.py` 的前沿逻辑在读 `~wmap.seen`）。

## 六、★ 渲染与规划必须一致（boss 指出：「这个问题很严重，要认真对待」）

### 6.1 上一轮我修错了地方

上一轮我在**渲染层**打了个补丁：`cls[seen & ~obstacle] = 1`，让画面好看。
那在工程上是错的 —— **画面和规划各算一套判据**。画面说能走、规划器说不走，
或者反过来，**两条判据迟早漂移**，而且漂移的方向没人能保证。boss 一句「很严重」是对的。

### 6.2 工程根因：同一个问题有五六处各自重算

```
nav.free_space          free = wmap.ground.copy()          <- 规划器读的
explore.py:1357         free = wmap.ground & ~wmap.obstacle
explore.py:1498         raw  = wmap.ground
explore.py:1522         passable = ~wmap.obstacle          <- 有意不同（判"是否已知挡路"）
explore.py:4950         grid = wmap.ground
worldmap.render         cls[seen & ~obstacle] = 1          <- 上一轮我加的补丁
```

**没有一个"官方答案"。** 只要渲染能自己算，它就一定会和规划不一致。

### 6.3 真正的问题：那些格为什么既不是地面也不是障碍

在线管线的判据（`tools/online_pipeline.py`）：

```
ground_ever  <-  |h| < tol                 tol = 0.10 + 0.035 * range
obstacle     <-  h in (0.35, 2.00]
seen         <-  h in [-0.60, 2.00]
```

⇒ 两条**死带**：上侧 `tol <= h <= 0.35`、下侧 `-0.60 <= h <= -tol`。
落在里面的回波让格 `seen`，却**不给地面、也不给障碍票**。

**先测死带（`out/_deadband.py`，把 `map.pcd` 的每个回波按高度分档）—— 假设被否：**

```
该格收到的 17445 个回波里：
  tol <= h <= 0.35     （上侧死带）        8  ( 0.0%)
  -0.60 <= h <= -tol   （下侧死带）      211  ( 1.2%)
  |h| < tol                                1654  ( 9.5%)
  h > 0.35             （障碍高度带）     11328  (64.9%)   <- 主体
  h < -0.60            （非"有信息"）     4691  (26.9%)
```

**真实原因**：这些格确实收到了障碍高度带的回波，但每格只有 2–3 个点、
**落在的帧数不够 `OBSTACLE_MIN_VOTES = 2`**，所以障碍层不晋升它们；
而它们的回波又不在 `|h| < tol` 里，所以 `ground_ever` 也不成立。

**回相机（`out/_deadband_look.py`，按位姿+bearing 找"当时正看着那里"的帧）：
五处最密的格，画面里全部是空旷走廊地面** —— 没有桌腿、没有柱子。

⇒ 这是地图的一个**空的第三类**：看到了、没有障碍证据、也没测到地面。

### 6.4 修法：让分类**完备**，渲染不再有自己的一套

`worldmap.GROUND_COVER_INFORMATIVE`（新，A/B 开关）：在 `add()` 里

```python
ground_ever |= seen & ~obstacle & ~object
```

语义一句话：**有信息、没有障碍证据、不是检测到的物体 ⇒ 它是地面。**
物体点必须排除 —— 障碍层对检测到的物体**故意不投票**，若从这道门放进来，
**每一个被检测器命名的椅子都会把自己的格子变成可通行**。

渲染侧同时**删掉两个画面补丁**（`RENDER_FILL_LONE_SEEN`、`RENDER_TRUST_OBSTACLE_LAYER`）：

```python
cls = zeros; cls[seen]=3; cls[seen & obstacle]=2; cls[ground]=1
```

**画面现在画的就是 `ground` —— 规划器读的同一个数组。没有任何中间层可以漂移。**

### 7.1 ★ (a)(b) 是同一个机制：**`ground` 不是单调的**

```python
ground = ground_ever & ~obstacle        # ground_ever 只增；obstacle 任何时候都能增
```

`ground_ever` 单调，`obstacle` 不单调 ⇒ **`ground` 会被"夺走"**。实测（`out/cover_on/grids`）：

```
grey & obstacle                        178.4 m2
  ├─ 其中 ground_ever = True           120.9 m2   <- 曾是地面，后来被障碍夺走 = 「绿变灰」
  └─ 其中 ground_ever = False           57.6 m2
ground_after_obstacle == 0             165.5 m2   <- 晋升之后再没看到地面
```

**`ground_after_obstacle = 0` 是 (b) 的关键**：`OBSTACLE_RELEASE` 规则要求
"晋升之后又看到 ≥2 帧地面"才释放。车从旁边开过去就不再回看 ⇒ **这个计数永远是 0 ⇒ 永不释放**。
而 `OBSTACLE_STRONG_VOTES` 对强证据豁免释放，所以**一个格一旦攒到 2 票就基本永久是墙**。

**(a) 的形态（`out/_wallband.py`，"到最近的强障碍（`votes >= 20`）的距离"）：**

|---|---|---|---|
| 0.0–0.1 m | 0.0 m² | 78.1 m² | 52 |
| **0.1–0.2 m** | 29.1 m² | **50.4 m²** | **9** |
| **0.2–0.3 m** | 33.0 m² | **20.5 m²** | **6** |
| 0.3–0.5 m | 66.7 m² | 19.6 m² | 4 |
| 0.5–1.0 m | 158.5 m² | 11.1 m² | 5 |

* **77% 的灰在墙的 0.3 m 以内**；而 0.0–0.1 m 那一档（78.1 m²）**就是强障碍本身**（距离 0）。

### 7.2 ⚠️ 这一条**不能**用 `GROUND_COVER_INFORMATIVE` 治

§6 那个开关治的是"**没有**障碍证据"的格。墙边这些格**恰恰是有障碍证据的**（6–9 票），
它们被排除在"无证据类"之外是**对的**。用同一个开关放它们过去等于**抹掉墙的证据**。

**现成的、更精准的杠杆是 `worldmap.OBSTACLE_GROUND_RATIO`**（默认 `0.0` = 关）：

## 九、感知侧：真实侧的识别率正常吗？再结合 3D 点云有用吗？

boss 问：「**目前真实侧这个物体识别率是正常的吗？还有办法继续提升吗？比如进一步结合 3d 点云？
我不太懂，你要客观中正地评价这个方法。**」

### 9.1 先说最重要的一句：**现在没法回答"识别率是否正常"**

因为**真实侧没有真值**。要算 precision/recall，需要每帧人工标出"这里有没有人、有没有椅子"——
我们只有这段 bag，没有标注。**任何"识别率 85%"之类的说法都会是编的。**

能给的只有**内部一致性**：

```
851 个检测框 -> 630 定位（74%），202 拒（24%）
instance: 22 个（14 person / 3 chair / 2 tv / 2 bottle / 1 suitcase）
其中 person 的 n_obs 分布：183, 123, 73, 71, 45, 36, 33, 15 | 3, 3, 1, 1, 1, 1
```

最后那 6 个 `n_obs <= 3` 的 person **不会被标**（实例确认要 12 次观测）。
**这不是漏检，这是"看见一次不算数"**——但它确实会让"短暂出现的人"不上图。

### 9.2 ★ 3D 点云**已经在用了**，而且用了三层

`r2slam/fusion.py::object_3d()` 对每个 2D 框做：

1. **框内 LiDAR 点的聚类**（按深度间隔切簇，取最靠前的簇）
2. **竖直范围的物理门**：`min_height` / `max_height` ——
   这是图像给不了的。注释里写得很清楚："**地面挡住'椅子被当成'人'，天花板挡住'墙被当成冰箱'**"。
   实测过：真实走廊里有 3,876 个点被标成 `refrigerator`，竖直跨 **4.42 m**（从地板到天花板）。
3. **地面平面**：`reject_all_floor`（51 次）就是"框里的点全在地面" ⇒ 空地上的假框。

**⇒ 所以"再结合 3D"不是从零开始；问题变成"现有 3D 用法还能加什么"。**

### 9.3 拒检的 202 个框，原因分布（`summary["fusion_rejects"]`）

```
reject_short            73   点云的竖直范围达不到该类别的高度下限
reject_box_height_must  57   框自身高度与其量程不符
reject_all_floor        51   框内点全在地面（应该拒）
reject_no_points        16   框内没有点
reject_tall              4
reject_box_height        1
```

**⇒ 分类讨论：**
* **`reject_all_floor` + `reject_no_points`（67）= 真·假框**，拒得对。
* **`reject_short` + `reject_box_height_must`（130）= "太远 / 点太稀"**。
  这一类**用漏检换精度**：`person` 的 `min_height` 从 1.00 m 降到 **0.40 m**，
  是在 **905 帧仿真**上对着 `/gazebo/model_states` 扫出来的（1.00 m 时精度只有 59%）。
  **⇒ 想让远处的人也上图，就是把 0.40 再降 ⇒ 精度必然掉。这是一个可调的旋钮，不是 bug。**

### 9.4 还可以做什么（按"性价比"排，不按"听起来高级"排）

| 手段 | 治什么 | 代价 / 风险 |
|---|---|---|
| **时序规则：静止 N 秒的 `person` 降级为静态物体** | 人形机器人、海报、衣架 | **低**。但需要一条判据（比如 10 s 内质心位移 < 0.2 m），且"站着不动的人"会被误降 |
| **跨帧一致性：只在连续 K 帧出现才上图** | 闪光假框 | **低**。已经部分有了（12 次观测） |
| **形状 / 体积特征**（宽高比、点云体积、竖直点密度剖面） | 人 vs 椅子 vs 机器人 | **中**。远处点云只有几个点，特征不稳定；**且需要标注才能验证** |
| **运动模式（步态）** | 真人 vs 刚性物体 | **中**。要连续多帧点云配准，单帧 LiDAR 不够 |
| **换更大的检测器**（YOLO26n → s/m） | 全面降误检 | **中**。模型要过 `check_onnx_parity.py`，且实时性预算要重测 |
| **RGB-D / 双目** | 稠密几何 | **高**。现在是单目鱼眼 + LiDAR，硬件不变 |

### 9.5 客观结论（不留情面版）

1. **"机器人被识别成人"这件事，3D 点云基本治不了。** 那台是人形机器人，高度 1.5 m 左右、
   宽度也够、还站在支架旁——**它满足"人"的所有几何条件**。要分开它和真人，得靠
   **运动模式**（它不动）或**更强的语义模型**，不是靠"更多的 3D"。
   **最便宜的一招反而是时序规则**：一个"人"在 200 s 里一步没动，就不是人。
2. **"识别率正常吗"这个问题的正确答案是"不知道"**，因为没真值。
   **任何一层新融合，如果没有真值，就只能靠仿真验证——而仿真的"人"是一个圆柱模型，
   恰好是最容易分辨的那种。用仿真数据调出来的门，在真实场景的收益会打折。**
   这条必须说在前面，否则加的东西只是"看起来更严谨"。
3. **从任务角度：不值得为人物分类投大工程。** 这次的交付要的是
   **建图 + 导航到指定物体**（"navigate to the sofa"）。多标一个人**不影响**这件事；
   把沙发漏掉才影响。**投入应该按"任务受影响的程度"排，不按"看起来不完美"排。**
4. **值得做的是两件便宜事**：
   （a）**静止物体降级**（治人形机器人、治海报）；
   （b）**把 `reject_*` 的分布报在视频上**（已经报在 summary 里，让看视频的人知道
   "框没上图是因为点云不够"，而不是"系统漏了"）。
5. **`OBSTACLE_GROUND_RATIO` 比上面所有的都更值得先做** ——
   它治的是 boss 这次报的**主要视觉问题（靠墙灰带）**，是现成开关，而且**有明确的判据**
   （墙边 0.1–0.3 m 的灰能不能掉下来 + 走廊宽度有没有恢复），可以在同一份 bag 上确定性地量。

**⇒ 两件事同时成立：**
* **只做减法，不做加法**（`新晋升 = 0`）—— 它只否决，从不新增障碍。
* 全图有 **13.57 m²** 的"**从未见过地面 且 votes ≥ 20**"的格（真正坚固的墙），
  **RATIO=1.0 一格都没碰**。被放掉的 60 m² 里，"纯墙"只有 **0.24 m²**。

**⇒ 也就是说：这个旋钮精确地只吃"地面证据与障碍证据矛盾"的那一类，正是 §7 查到的那一类。**

### 10.2 取值

**`RATIO = 1.0`**，理由不是"放得更多"，是**语义对称**：
"**地面可见的帧数不少于障碍可见的帧数时，信地面**"。
0.5 的效果方向相同、量小一半，留作保守备选。

### 10.3 但真实侧测不出行为影响

## 十一、⑤ 再结合 3D 目标检测 —— 调研与客观评估

boss 问：「现在有很多东西没有标出来，我想的是搭配 3D 目标检测（就是我们初赛用的类似的东西）
结合起来做，效果会不会好？有没有类似的室内 3D 目标检测的模型？」

### 11.1 ★ 先纠正一个前提：**类别表是我们自己定的**

交接文档 §5.2 记录着一句关键的话：

> **组委会 FAQ 明确「不提供类别列表」→ 交付物必须自带 id↔名称↔色表**

**⇒ 我们没有"被限制在 COCO 23 类"。** 现在的 23 类（`labels.py::_SPECS`）是**我们自己的选择**。
而画面里那些"没被标出来"的东西 —— **灭火器箱、栏杆、地毯垫子、健身器材、人形机器人** ——
**一个都不在 COCO 的 80 类里。**

### 11.2 "很多没标出来"其实是**四个不同的原因**

| # | 原因 | 证据 | 换 3D 检测能治吗 |
|---|---|---|---|
| 1 | **词表里没有这个类** | 灭火器箱/栏杆/垫子/健身器材/机器人 都不在 COCO 80 | **不能**（除非是"开放词汇"那一路） |
| 2 | **远处 / 点云太稀，被 LiDAR 门拒** | 202 拒里 130 是 `reject_short`+`box_height_must` | **不能**（它的输入也是点云） |
| 3 | **没有"实例"这一层** | 同类多物体混在一起；实例确认要 12 次观测 | **能** |
| 4 | YOLO 对小目标/罕见类本来就漏 | `detector_unmapped_boxes = 252` | 部分（3D 检测不依赖 2D 词表） |

**⇒ 把四条分开，是因为改的东西完全不同。** 换检测器只治 3 和 4。

### 11.3 项目已有的基础（不是从零开始）

* **初赛跑的就是 3D 深度学习**：`SFPNet`（ECCV 2024）+ spconv 逐帧推理，权重 430 MB。

* `.workbuddy/out/model_options.md`（初赛时代的调研）把可选路线列全了：

* 交接文档 §482-483 自己写了复赛的差距：
  **"语义从 stuff 转向 thing" ⇒ "19 类 SK 体系不再适配" ⇒ "开放词汇从备选变成刚需"。**
* **W2-③ 已经写下要做的事**：**"目标关联（thing 聚类 + 实例 id）"**。

**⇒ 项目自己给出的下一步就是"实例关联"，不是"再换一个检测网络"。**

### 11.4 候选（按"能落地"分档，不按先进程度）

| 档 | 方案 | 新增依赖 | 需要标注 | 实时 | 对我们 |
|---|---|---|---|---|---|
| **零** | **全场景欧式聚类 + 语义投票 ⇒ 实例 id** | **无**（numpy+cv2） | 否 | ✓ | **1–2 天，马上能做** |
| 中 | **IGLOSS**（开放词汇语义，**只用点云**，类别用文本 prompt） | torch + WaffleIron | 零样本 | 待测 | 项目已评为"复赛首选" |
| 中 | SFPNet（初赛在用；S.MID 是同款传感器数据） | spconv + GPU | 可换权重 | 慢 | 已跑通 |
| 重 | **FCAF3D / TR3D**（室内 3D 检测 SOTA：ScanNet mAP@0.5 57.3） | mmdetection3d + **MinkowskiEngine** | **需要** | **8 fps**(1080Ti) | 见 11.5 |
| 重 | VoteNet / SPFormer / TD3D | pointnet2 CUDA 核 / spconv | 需要 | 慢 | 见 11.5 |
| 重 | **Open3DIS**（开放词汇 3D 实例，CVPR 2024） | SAM + CLIP + ISBNet/Mask3D | 零样本 | 慢 | **需要 RGB-D 稠密重建** |

### 11.5 为什么监督式 3D 检测（FCAF3D 一类）**我不建议先做**

1. **训练数据不存在。** ScanNet / S3DIS / SUN RGB-D 是 **RGB-D 稠密扫描（单场景几十万点）**；
   我们是 **Livox 稀疏扫描（单帧 49,152 点）**。同一间屋子采出来的点数差一个量级，
   直接迁移的域差距**没有任何人量过**（`model_options.md` §4 已经强调过这条）。
2. **要标注。** 真实侧**没有真值**。仿真能生成，但要自己标，而且**仿真的物体是简单几何体**
   ⇒ 训出来的模型对真实场景会打折。**这正是初赛踩过的坑**：`person` 的 `min_height`
   在 905 帧仿真上扫到 0.40 m，真实侧还得重新量。
3. **部署。** FCAF3D 依赖 **MinkowskiEngine（CUDA 自定义算子）⇒ ONNX 导出困难**；
   而交付要求**实时运行**（那个 8 fps 还是 1080Ti 上的**场景**吞吐）。
4. **收益无法验证。** 没有真值就说不清"新检测器比现在好多少"，只能回到"看起来更全"。

### 11.6 建议的顺序

1. **先做实例层（零依赖）**：整帧欧式聚类 → 逐簇语义投票 → 实例 id。
   复用 `fusion.object_3d` 已有的"按深度间隔切簇"逻辑，把它从"框内"扩到"全帧"。
   **判据现成且可复算**：实例数、每实例观测数、**同类多物体是否真的分开**（视频里直接可看）。
2. **同时扩词表**：COCO 80 里还有可用的（`door` / `sink` / `book` / `clock` / `vase` /
   `potted plant` / `dining table` …），再加几条**几何规则类**
   （栏杆 = 细长水平结构、地毯/垫子 = 贴地薄层）。**这一步的模型成本是零。**
3. **若要覆盖"任意类别"**：**IGLOSS**（类别用自然语言定义、只用点云、单帧即可）。
   代价是需要 GPU 环境，且要**先在我们这种稀疏点云上量一次**再决定。
4. **不建议**先上 FCAF3D / VoteNet / Open3DIS。

### 11.7 一句总结

**方向是对的** —— 缺的确实是"实例"和"类别覆盖"。
**但"3D 目标检测模型"不是第一步**：第一步是把**已有的点云聚类能力从"框内"扩到"全场景"**，
零新增依赖、1–2 天，而且判据好定。
**真正的瓶颈很可能不在检测器，而在"我们只用了 COCO 的 23 类"** ——
而组委会**不给类别表**，这块完全可以自己补。

（诚实起见：README 已如实披露未做，没有虚假声称。）

### 12.2 ★ 现状：**在加任何感知之前，预算已经不富裕了**

真实侧同一份 bag，各阶段 p50（本机 i5-14400F，主机，**不是边缘设备**）：

| 跑 | deskew | **detect** | fuse | **map** | odom | **render** | total | **compute*** |
|---|---|---|---|---|---|---|---|---|
| `cover_off`（默认配置） | 7.1 | 55.6 | 23.2 | 64.3 | 15.5 | 59.2 | 229.2 | **170.0** |
| `cover_on`（+`GROUND_COVER_INFORMATIVE`） | 10.5 | 87.3 | 42.7 | 93.7 | 23.8 | 90.8 | 354.5 | **263.7** |
| `ratio_0.5` | 7.3 | 58.9 | 25.4 | 71.8 | 16.8 | 62.5 | 246.6 | **184.1** |
| `ratio_1.0` | 7.6 | 59.5 | 24.8 | 75.4 | 16.2 | 62.4 | 249.8 | **187.5** |

*** `compute = total − render − dump`，即真正的算法代价**（视频不是算法，见 12.4）。
**5 Hz 的帧预算是 200 ms。**

三条读数：

1. **`ratio_0.5`/`ratio_1.0` 与 `cover_off` 在 170–188 ms 同一档，而 `cover_on` 是 263.7 ms。**
   ⚠️ 前三者在**两个不同批次的作业**里跑的，`detect` 这一列（同样代码同样数据）在批间差了
   55.6 → 59.5（+7%），而 `cover_on` 的 87.3 是异常高的。**跨批次的绝对 ms 不可比。**
   可比的是**同批次内**的 `cover_off`(170.0) → `cover_on`(263.7)：** +55%**。
   ⇒ 由此**不能**断言 RATIO 把开销降回来了；**要下这个结论必须做一次同批次的 2 跑对照**（已列入手头待办）。
2. **`GROUND_COVER_INFORMATIVE` 是这一轮唯一的成本回退项**，而它是我们为"渲染/规划一致"付的价。
   所以"一致性"与"边缘预算"这两件事是**互相拉扯**的。
3. **detect 已经是轻的那一端**：`yolo26n.onnx = 9.43 MB`（fp32）。往上还有 `yolo11s = 36.25 MB`、
   `yolo11m = 76.89 MB` —— **一档就是 4× 和 8×。** 所以"换更大的检测器"这个念头在边缘上没有多少空间。

### 12.3 ★★ 地图层是**平方律**，这是边缘上最该动的地方

```
真实侧: map_resolution 0.10 m, map_extent 60.0 -> n = 1200   -> 1.44 M 格
仿真侧: map_extent 30.0                      -> n =  600   -> 0.36 M 格
```

`nav.free_space()` 里：

* 缓存键是 `int(wmap.ground.sum())` 和 `int(wmap.seen.sum())`
  ⇒ **即使缓存命中，每次调用也要对 144 万格做两次全量归约**；
* 未命中时还要 `wmap.ground.copy()`（1.44 MB）+ 一次全图腐蚀；
* 而**每帧被调用 4 处以上**（`explore.py:1389/1439/4864/4951`，`nav.py:579/639`）。

`ms_map` p50 **64–94 ms**、`ms_fuse` 23–43 ms 就是在付这笔钱。
**⇒ 而 `ground` 一变大 11%，`ms_map` p50 就从 64.3 涨到 93.7（+46%）—— 这就是"平方律"的直接证据。**

**边缘化的方向（按收益/风险）**：把 O(格数) 的每帧全图操作换成 O(障碍边界) 或 O(局部 ROI)：

| 手法 | 说明 |
|---|---|
| 缓存键别用 `.sum()` | 改成维护一个**增量计数器**（`add()` 里顺手加/减），或直接用 `n_frames` 之类的单调量做键 |
| 只在机器人附近 ROI 腐蚀 | 规划只用机器人周围几十米；不需要每帧处理整张 AMR 图 |
| 用距离变换代替腐蚀 | `cv2.distanceTransform` 一次可拿到所有半径的安全区，避免多个半径各腐蚀一遍 |
| 分辨率/范围分级 | 0.10 m / ±30 m 是当前设定；边缘上"近处细、远处粗"的两级栅格是标准做法 |

⚠️ **这一条会改行为**（`free_space` 是规划器的输入）⇒ 必须走 A/B，不能凭"更快"就上。

### 12.4 `render` 占了 24–35% 的帧时间，而它**不是算法**

`render` p50 **59–91 ms**。它做的是**拼图 + 画字 + 存 PNG**，即**交付视频**，不是感知/建图/规划。

交付物要求"实时运行 + 整个数据集的视频"。**"跑的时候要实时"和"视频是这么录出来的"可以解耦**：
渲染降频 / 降到离线 / 只在关键帧出图，都是合规的（`--no-render` 已存在）。

**⇒ 这是唯一一块"不碰算法、不动判据、直接回血 25–35%"的预算。** 边缘化时它应当是第一刀。

### 12.5 ★★★ 建议的变化：从"按工作量排序"改成"按**每瓦覆盖率**排序"

| 原建议（§11） | 边缘约束下 | 为什么变 |
|---|---|---|
| ① **全场景欧式聚类 + 语义投票 ⇒ 实例 id**（零依赖） | **不变，仍是第一优先** | 边际算力 ≈ 0：numpy/cv2，O(点数)，**不引入任何新模型**。边缘上"免费"的东西排第一 |
| ② **扩词表**（COCO 剩余 + 几何规则类） | **不变，同样升级** | 词表扩展的**模型成本为 0**（多映射几个已有输出）；几何规则（"细长水平结构=栏杆"）是几次 numpy 运算。**每瓦覆盖率最高** |
| ③ **IGLOSS**（3D 开放词汇） | ⚠️ **降级：很可能不能上边缘** | 需要 **torch + WaffleIron + GPU**，**代价比现在整条栈加起来还大**。项目把它列为"复赛首选"是在**没有边缘约束**的前提下 |
| ④ FCAF3D / TR3D / VoteNet / Open3DIS | **从"不建议先做"变成"边缘上判死"** | **MinkowskiEngine 是 CUDA 自定义算子 ⇒ 导不出 ONNX ⇒ 边缘端没有 CUDA 编译链就跑不了**；410 MB 级权重；1080Ti 上 8 fps。Open3DIS 还要 RGB-D 稠密重建 + SAM + CLIP |

**⑤（新，替代原 ③ 的位置）开放词汇应该走 2D，不走 3D。**

`YOLO-World` 的推理机制正好解决这个问题：**"prompt-then-detect" —— 文本编码器被重参数化
"烤"进 1×1 卷积权重，推理阶段可以整个丢掉**，所以**任意词表的在线成本是零**。

已发表的边缘实测（不是我的推算）：

| 项 | 数字 |
|---|---|
| 模型 | 轻量化 YOLOv8l-worldv2 + INT8/FP16 混合精度 TensorRT |
| **量化后体积** | **115 MB → 32 MB** |
| **平台** | **Jetson Orin Nano Super** |
| **速度** | **32.6 FPS** |
| 精度代价 | mAP@0.5 **64.9%**（比原版低 1.6 个百分点）；GFLOPs 204.5 → 67.2 |

而且它是**替换**现在的 `yolo26n`，不是**叠加** ⇒ 不会让延迟翻倍。
**⇒ 这一条同时治了"词表里没有这个类"（§11.2 的第 1 条原因）和"边缘预算"两件事，
比我上一轮推荐的 IGLOSS 好得多。**

**⑥（新）先量预算，再加东西。** 现在**没有任何一个数字是边缘设备上量的**。
HANDOFF §4.5 已经写明做法：量化检测器（ONNX → INT8）+ 逐阶段量 `ms_*` 预算。
在那之前，"这个模块在边缘上能不能跑"全部是猜。
**可继承的两条既有实测结论**：`max_num_threads: 1` 必须（不要超订核）；`voxel_size: 0.50` 是精度下限。

### 12.6 ⚠️ 一个必须说清的推算（不是实测）

本机是 **i5-14400F 桌面 CPU**（单核性能远高于边缘 SoC 的 Arm A78AE）。
**现在实测算术代价 170–264 ms，而 5 Hz 的预算是 200 ms。**
⇒ 换到 Jetson Orin Nano 一类的平台，**单线程 Python+numpy 的算子很可能慢 2–4×**，
即 **400–700 ms 量级**，**已经超预算 2–3 倍**。

**这是推算，不是测量。** 但它足以说明一件事：
**"再加一个 3D 检测网络"在当前架构下不是"重一点"，而是"直接跑不动"。**
要么改架构（12.3/12.4），要么换推理栈（ONNX Runtime / TensorRT / NPU），否则加什么都白搭。

### 12.7 一句话总结

**方向不变，顺序全变。**

* 原来按"工作量"排：先把实例层做出来 → 再扩词表 → 不行就上开放词汇模型。
* 边缘约束下按"**每瓦覆盖率**"排：
  **① 先把预算拿回来**（render 下关键路径 + 地图层的平方律）→
  **② 免费的覆盖**（全场景聚类出实例 + 扩词表 + 几何规则类，**零新模型**）→
  **③ 若真需要任意类别，用 2D YOLO-World 替换现在的检测器**（已在 Jetson Orin Nano 上验证 32 MB / 32.6 FPS）→
  **④ 3D 大模型路线在这个交付形态下应判死。**

**且，以上全部建立在"我们还没有一个边缘平台上的实测数字"之上 —— 这是要先补的第一块。**

1. **INT8 量化** —— 文献里那个 115 MB→32 MB / Jetson Orin Nano Super 32.6 FPS 的实测，

2. **换更小的 backbone** —— YOLO-World v2 只有 s/m/l/x，**没有 nano**，所以 s 已是最小；
   要更小就得走第 3 条。
3. **换推理栈**（TensorRT / NPU）。

### 19.3 ★ 更正一条记录：那条"地图层 +46% 代价"是假的

MEMORY 与本文档都记过「`ground` 大 11% ⇒ `ms_map` p50 **+46%**」，来源是 `out/cover_off` vs `out/cover_on` 那一对。
**那一对不是背靠背跑的**：

| `out/cover_off` → `out/cover_on`（历史对） | 变化 |
|---|---|
| `ms_deskew` | **+48.2%** |
| `ms_odom` | **+53.8%** |
| `ms_detect` | **+56.8%** |
| `ms_fuse` | **+83.7%** |
| `ms_map` | +45.8% |

**deskew / odom / detect 不可能因为一条地面规则变慢 50%** ⇒ 那一对整跑被机器负载污染，
`ms_map` 的 +46% **不能归因给这个开关**。

**今天背靠背重测**（同 bag、同模型、同会话、相邻两次）：

| | OFF | **ON** | |
|---|---|---|---|
| `ms_map` p50 / p90 | 65.17 / 78.15 | **61.20 / 65.71** | **−6.1%** |
| `ms_total` p50 / p90 | 230.01 / 266.46 | **222.01 / 241.72** | **−3.5%** |

⇒ 在这对里 ON 臂**并没有更贵**：−6.1% 与同一对的 `ms_deskew` −5.3% / `ms_detect` −2.1% 同量级，是抖动。
**正确说法是"代价测不出来"，不是"代价 +46%"。**
⚠️ 仍然只有 **1 对**；方向至少证明原来那个数字不能当依据。
