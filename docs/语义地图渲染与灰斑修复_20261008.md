# 语义地图："轨迹与圆圈飘移"和"灰斑"两个观感问题的定位与修复（2026-10-08 第二轮）

> boss 报的三件事里的前两件：
> 1. **仿真和真实侧的语义地图里，轨迹和各种物体的圆圈会飘移**；
> 2. **真实侧语义地图里灰斑很多很显眼，而且"人走过的路面"是灰色的**。
>
> 结论：**两件都是真的，而且都不是策略问题。**
> 第 1 件是 `WorldMap.render()` 的一个**纯渲染 bug**（裁剪窗口非正方形 + 单一缩放系数），
> 影响**交付包里的仿真视频**（叠加层比地图**高 15.0%**）。
> 第 2 件是**交付包里的真实侧视频比代码旧**：它录于 10-04 18:13，而修这个问题的
> `_on_path`（"机器人走过的格子不许被判成墙"）是当晚 21:14 才进的代码。
> **同一份采集、同一条 102.54 m 轨迹重跑**：灰色 300.0 → **243.1 m²**，
> 机器人自己走过的路面 8.07 → **1.21 m²**，可通行 382.2 → **439.1 m²**。
>
> 改动：`r2slam/r2slam/worldmap.py`（render 裁剪）+ 回归测试 `tools/test_worldmap.py` §11。
> commit `a86f85f`。**没有改任何策略参数。**

## 0. 一屏结论

| 问题 | 是什么 | 证据 |
|---|---|---|
| 轨迹/圆圈"飘移" | **渲染 bug**：`render()` 的裁剪窗口在贴到网格边界时变成非正方形，而叠加层（轨迹 + 圆圈）只用了**横向**的一个 `px/cell` | 仿真交付跑复现出 **15.0%** 的纵向拉伸（`out/_render_probe.py`） |
| 为什么看着像"飘"而不是"整体偏一点" | 裁剪比例随机器人位置**每帧变**，所以偏移量一直在动 | 复现图与交付视频**逐像素同形** |
| 真实侧"灰斑" | **交付视频比代码旧**：`online_real/` 产于 10-04 18:13 | 目录时间戳 + `_on_path` 的 commit 时间 10-04 21:14 |
| "人走过的路面是灰的" | 同一个原因：旧代码把**机器人自己走过**的 998 格里 **807 格**判成了障碍 | `worldmap.py` 里 `_on_path` 的注释记着这个 807/998 |
| 重跑后还剩多少灰 | 243.1 m² 灰里：真正贴地的"斑点"13.8 m²、与人观测相关的 10.5 m²、其余是墙与家具 | 见 §2.3 |

## 1. 轨迹与圆圈"飘移"：是渲染，不是位姿

### 1.1 先看现象长什么样

交付包里 `online_sim/run.mp4` 最后一帧的地图面板：**轨迹（浅蓝）明显跑到绿色房子外面**，
物体圆圈在房子下方排成一把**扇形**。真实侧同一现象弱一些（因为它的窗口只是轻微被裁）。

### 1.2 反证：轨迹与地图在**世界坐标**里是一致的

把 `out/ab_perception/grids_subr2_sim/` 的栅格按世界坐标画出来（`out/_grid_plot.py`）：

```
traj points 1632   off-grid 0
traj points on UNSEEN cells: 1 (0.1%)          <-- 1632 个轨迹点里只有 1 个落在"没观测过"的格
```

**轨迹 99.9% 落在图里**。所以"轨迹跑出房子"不可能发生在数据侧。

### 1.3 根因：裁剪窗口非正方形，叠加层只有一个缩放系数

`WorldMap.render()`（修之前）：

```python
half = max(int(round(span / (2.0 * self.resolution))), 8)
x0, x1 = max(cx - half, 0), min(cx + half, n)     # <-- 贴边就变窄
y0, y1 = max(cy - half, 0), min(cy + half, n)     # <-- 贴边就变矮，且幅度不同
win = img_world[y0:y1, x0:x1]
img = cv2.resize(win, (size, size))               # 地图按 (size/(x1-x0), size/(y1-y0)) 缩放
k = size / float(max(x1 - x0, 1))                 # <-- 叠加层却用这一个 k 同时算 px 与 py
```

`span` 会被**自动放宽以容纳所有物体实例**（原意是"面板必须装得下地图知道的一切"）。
仿真那次：机器人离网格原点很远 + 最远的实例 18.21 m ⇒ `span` 长到 50 m，
窗口被裁成 **427 × 491** 格：

```
centre cell (177,241)
half=250   window x[0,427) w=427   y[0,491) h=491
px/cell  horizontal 1.2646   vertical 1.0998
*** ASPECT MISMATCH: overlay drawn 15.0% taller than the map ***
```

**叠加层被画高了 15.0%。** 而且比例随机器人位置每帧变 ——
所以它读起来是"**飘**"，不是一个固定的偏移。真实侧同理，只是它的 `span` 顶到
`2*extent` 上限，窗口 571 × 597，偏差 4.5%（约 100 px 里的 4 px，不容易一眼看出）。

### 1.4 修复

窗口**恒为 `2*half` 格的正方形**，落在网格外的部分用 `unknown` **补齐**（不再裁剪）：

```python
half = max(int(round(span / (2.0 * self.resolution))), 8)
x0, x1 = cx - half, cx + half
y0, y1 = cy - half, cy + half
sx0, sx1 = max(x0, 0), min(x1, n)
sy0, sy1 = max(y0, 0), min(y1, n)
win = np.zeros((y1 - y0, x1 - x0, 3), np.uint8)
win[:] = lut[0]
if sx1 > sx0 and sy1 > sy0:
    win[sy0 - y0:sy1 - y0, sx0 - x0:sx1 - x0] = img_world[sy0:sy1, sx0:sx1]
```

补齐同时修掉一个没人提过的问题：**原来贴边时机器人并不在面板中央**（差多少就是被裁掉多少）。

### 1.5 验收

* `tools/test_worldmap.py` §11 用**世界坐标**陈述不变式，不复用渲染器自己的算法：
  机器人 ±5 m 处三个点，地图说是 `ground` 就必须落在绿像素上。
  **先把裁剪改回旧的，测试变红**（两个 y 方向的采样落到 `unknown`）；改回来，**45 checks / 0 failed**。
* 复现脚本 `out/_render_probe.py`（只读）：修前打印 `ASPECT MISMATCH 15.0%`，修后打印
  `OK: square window -> one px-per-cell factor is correct`，且机器人恰好落在 `(270,270)`。
* 修完重跑仿真一次（`subr4r1`，见 §3），最后一帧轨迹**完整落在绿色房子内**。

## 2. 真实侧的"灰斑"与"人走过的路面"，以及它还剩多少

### 2.1 交付的真实侧视频比代码旧

`online_real/` 全部文件的时间戳是 **2026-10-04 18:13**。而 `worldmap.py` 里为解决
"灰色轨迹"而加的 `_on_path`（机器人自己占过的格，永远不会被障碍层判成墙）在
**同一天 21:14 / 21:35** 才提交（`ecf2524` / `d29093e`）。**旧的视频里没有这条规则。**

代码注释里留着当时的实测：

> 实测（真实采集，1427 帧）：机器人轨迹跨过的 998 个格里有 **807 个被标成障碍**，
> 票数中位数只有 2（恰好等于 `OBSTACLE_MIN_VOTES`），**沿路线散落而不是聚在某处**。
> 那正是视频里走廊中间那条灰色带，释放规则够不到它。

### 2.2 同一份采集、同一条轨迹，重跑

真实侧输入是本地 bag（`D:/E-Downd/openloong_r2_ex/bag/rosbag2_2026_09_23-14_09_45`），
所以**不需要云机、不需要仿真**，直接本机重跑：


|---|---|---|
| 帧数 / 仿真时长 / 里程 | 1427 / 139.0 s / 102.54 m | 1427 / 139.0 s / **102.54 m** |
| `seen_cells` | 68215 | **68215** |
| `traversable_cells`（绿） | 38216 (382.2 m²) | **43907 (439.1 m²)** |
| `obstacle_cells`（灰的一部分） | 24112 (241.1 m²) | **17842 (178.4 m²)** |

**同一条 102.54 m 的轨迹、同一个 `seen_cells`** ⇒ 这不是"跑得好一点"，是**同一个输入换了代码**。

### 2.3 重跑后剩下的 243.1 m² 灰是什么

| 来源 | 面积 |
|---|---|
| 障碍层（墙 / 家具 / 柱子） | 178.4 m² |
| 有回波但从未成为地板的格（含墙、家具、行人躯干） | 149.0 m² |
| 其中"曾经是地板、后来被判成障碍" | 94.1 m² |
| **落在机器人轨迹上的灰** | **1.21 m²** |
| **"地板中间的孤立斑点"**（8 邻域里 ≥6 个是绿） | 13.8 m² |
| **离任一次 person 观测 0.35 m 以内的灰** | 10.5 m² |

⇒ **剩下的灰绝大部分是墙和家具**，那是语义地图该有的东西。
"很显眼"的那部分（走廊中间那条带 + 地板上的斑点）已经收掉。
**其中只有 10.5 m² 能追到"人"，而且它只占 4.3%** —— 见 §4。

### 2.4 ★ 一个必须先排除的混淆：检测器也换了 —— **实测排除，改善 100% 来自地图层**

两次跑的 `summary.json` 的 `detector.model` 不同：

```
online_real      yolo11n.onnx     person 699 / chair 18 / refrigerator 14 / tv 4 / bottle 22 / suitcase 35
online_real_v2   yolo26n.onnx     person 589 / chair  5 / tv 3 / bottle 6 / suitcase 27
```

`默认检测器换成 yolo26n` 是 10-04 的提交（`e1ed683`，同样在那次真跑之后）。
所以 §2.2 那张表**表面上**是"检测器 + 地图层"两项之和，不能直接归因。

**用一个臂把它拆开**：同一份采集、**同一个检测器（yolo11n）**、只换地图层代码：

```bash
python tools/online_pipeline.py --config config/real_r2.yaml --npz out/real_cap \
    --out out/_real_y11 --dump-grids out/_real_y11/grids --no-tf --no-render \
    --model vendor/detector/yolo11n.onnx
```

| 臂（同一采集、同一 102.54 m 轨迹） | 绿（可通行） | 障碍 | **灰** | 轨迹上的障碍 |
|---|---|---|---|---|
| **交付版**：yolo11n + 旧地图层 | 382.2 m² | 241.1 m² | **300.0 m²** | **8.07 m²** |
| yolo11n + **新**地图层 | **439.2 m²** | **178.3 m²** | **243.0 m²** | **0.00 m²** |
| yolo26n + 新地图层 | 439.1 m² | 178.4 m² | 243.1 m² | 0.00 m² |

⇒ **8.07 → 0.00 与 300.0 → 243.0 全部由地图层贡献；yolo11n 与 yolo26n 在灰上只差 0.1 m²（不可分辨）。**
§2.2 的归因成立，不必打折。

**顺带暴露一个交付包的问题**：包里的**仿真侧用 yolo26n、真实侧用 yolo11n**，
两侧检测器不一致（`online_sim/summary.json` vs `online_real/summary.json`）。
重跑之后两侧统一在 yolo26n。

## 3. 仿真侧：用修好的渲染重跑

```bash
DURATION=560 bash vendor/sim_scripts/run_repeat.sh subr4 2
```

`--duration` 是**墙钟秒**，必须按 RTF 折算（设计文档 §73 的教训）：
560 s 墙钟在 RTF≈0.79 下换到 **~330 s 仿真时间**，与 `subr2`（327.2 s）可比。

| 跑 | 帧数 | 仿真时长（`sim_span`） | 墙钟 | 里程 | 可通行 | 已观测格 | **权威三房最小** |
|---|---|---|---|---|---|---|---|
| `subr2`（包内） | 1632 | 327.2 s | — | 141.42 m | 248.1 m² | 29300 | **32%** |
| `subr4r1` | 1519 | 308.8 s | 560 s | 134.70 m | 276.0 m² | 32486 | **31%** |
| `subr4r2` | — | 406.0 s | 560 s | 145.70 m | — | — | **18%** |

（权威口径 = `out/_room_cover2.py`，单调分母；**`wall_s` 与 `sim_span` 必须同时报**，
`--duration` 只是墙钟。两次重跑用同一条命令、同一次会话，RTF 差别很大 —— 这正是"必须报 RTF"的现场。）

**⇒ 三次跑的"三房最小"是 32% / 31% / 18%，`subr4r1` 与包内的 `subr2` 统计上分不开。**
所以：**渲染缺陷是真的（15.0%，逐帧可见），重跑也确实修掉了它；
但"要不要把包里的仿真产物换成 `subr4r1`"是"一个观感缺陷"对"一次不同分布的跑"的权衡，要 boss 拍。**
（本轮**没有动 `提交包/`**。）

## 4. 没做什么，以及为什么

**没有**去改"人"的回波不许升格成障碍。理由：

1. 量出来的上界只有 **10.5 m²**（占灰的 4.3%），而 §2.2 的 8.07 m² 那条带
   （boss 真正指着的东西）是**机器人自己的轨迹**，已经由 `_on_path` 收掉；
2. 它动的是**障碍层**，属于项目里明确划出的危险区（"改阈值前先读已证伪清单"），
   而收益 / 风险比在这种量级上不成立；
3. 真正该做的版本不是"排除 person 回波"，而是**动态物体不该进累积层**——
   那是一个需要闭环 A/B 的机制改动，不该顺手做。

**另外一个已知但未处理的**：`render()` 的自动放宽会选择"装得下所有物体实例"的跨度。
一次误定位的实例（仿真里 36 个真值物体、p50 0.90 m）会把 `span` 顶到 60 m 上限，
面板于是缩得很小。**这不是 bug**（原来的动机是"面板必须装得下地图知道的一切"），
但**它的代价现在看得见了**：修好几何之后，面板小就成了下一个观感问题。
要不要给 `span` 加一个上界（或改成按实例的**置信度**过滤），是 boss 要拍的。

**一个可复用的判据**（这次靠它把两件"看着像算法"的事拆成两个非算法问题）：

> **叠加层与它下面的图层必须用同一个坐标变换。**
> 只要两者用了不同的缩放、不同的裁剪或不同的中心，观感上一定会读成"漂移"，
> 而且偏移量会随画面移动而变——**"会动"是渲染 bug 的特征，"不动"才是位姿 bug 的特征。**
